# 9-2. Singleton이 하나의 객체를 생성한다는 것을 어떻게 보장할 수 있을까요?

<details>
<summary>**질문:** Singleton이 하나의 객체를 생성한다는 것을 어떻게 보장할 수 있을까요?</summary>

기본적으로 **생성자를 private으로 막고**, 클래스 내부의 **static 필드에 인스턴스를 하나만 저장**한 뒤, **정적 메서드(getInstance)로만 꺼내 쓰게** 해서 보장합니다. 다만 이것만으로는 부족한데, **멀티스레드 환경**에서는 동시에 생성될 수 있으므로 이른 초기화, Holder 방식, `volatile` + Double-Checked Locking 같은 스레드 안전한 방법을 써야 합니다. 또 **리플렉션, 직렬화, clone**으로도 새 객체가 만들어질 수 있어 각각 방어 코드가 필요합니다. 이 모든 경우를 가장 간단하게 막는 방법은 **enum 싱글톤**입니다.
</details>

---

## 1. 큰 그림: "새 객체가 생기는 문"을 모두 막기

Java에서 새 객체가 만들어지는 경로는 여러 가지입니다. 싱글톤을 보장한다는 건 **이 문들을 하나씩 다 잠그는 것**이라고 생각하면 쉽습니다.

| 새 객체가 생기는 경로 | 막는 방법 |
| --- | --- |
| ① 외부에서 `new` 호출 | `private` 생성자 |
| ② 여러 스레드가 동시에 생성 | 스레드 안전한 초기화 (Eager, Holder, DCL) |
| ③ 리플렉션으로 private 생성자 호출 | 생성자 안에서 두 번째 생성 시 예외 발생 |
| ④ 직렬화 → 역직렬화 | `readResolve()` 구현 |
| ⑤ `clone()` 복제 | `Cloneable` 구현하지 않기 / `clone()`에서 예외 |
| ①~⑤ 한 번에 | **enum 싱글톤** |

## 2. 기본 보장 장치 3가지

```java
public class Settings {
    // ② 인스턴스를 담아둘 static 필드 (클래스당 하나만 존재)
    private static final Settings INSTANCE = new Settings();

    // ① 외부에서 new Settings() 금지
    private Settings() {}

    // ③ 인스턴스를 얻는 유일한 통로
    public static Settings getInstance() {
        return INSTANCE;
    }
}
```

- **① private 생성자**: 클래스 밖에서 `new Settings()`를 쓰면 **컴파일 에러**가 납니다.

- **② static 필드**: static 필드는 객체마다가 아니라 **클래스에 딱 하나** 존재하므로, 인스턴스를 하나만 담아둘 수 있습니다.

- **③ 정적 팩토리 메서드**: 객체를 얻는 방법을 `getInstance()` 하나로 통일하고, 항상 같은 객체를 돌려줍니다.

> 💡 `final`을 붙이면 한 번 대입된 인스턴스를 **다른 객체로 바꿔치기할 수 없습니다.**

## 3. 멀티스레드 환경에서의 보장

### 문제: 지연 초기화를 단순하게 구현하면 깨진다

"처음 쓸 때 만들자(지연 초기화, Lazy Initialization)"를 단순하게 구현하면 문제가 생깁니다.

```java
public class Settings {
    private static Settings instance;
    private Settings() {}

    public static Settings getInstance() {
        if (instance == null) {         // 스레드 A, B가 동시에 통과
            instance = new Settings();  // 둘 다 생성 → 객체 2개!
        }
        return instance;
    }
}
```

**시나리오**

1. 스레드 A가 `instance == null` 확인 → true

1. A가 객체를 만들기 전에, 스레드 B도 `instance == null` 확인 → 역시 true

1. A와 B가 각각 `new Settings()` 실행 → **객체 2개 생성**

### 해결 ① 이른 초기화 (Eager Initialization)

```java
public class Settings {
    private static final Settings INSTANCE = new Settings();
    private Settings() {}
    public static Settings getInstance() { return INSTANCE; }
}
```

- **원리**: static 필드는 **클래스가 로딩될 때 JVM이 딱 한 번** 초기화하며, 이 과정은 JVM이 스레드 안전하게 처리합니다.

- **장점**: 가장 단순하고 안전합니다.

- **단점**: 한 번도 쓰지 않아도 객체가 미리 만들어집니다.

### 해결 ② synchronized 메서드

```java
public static synchronized Settings getInstance() {
    if (instance == null) {
        instance = new Settings();
    }
    return instance;
}
```

- **원리**: 한 번에 **한 스레드만** 메서드에 들어갈 수 있게 잠급니다.

- **단점**: 객체가 이미 만들어진 뒤에도 **호출할 때마다 락**을 걸어 성능이 떨어집니다.

### 해결 ③ Double-Checked Locking (DCL)

```java
public class Settings {
    private static volatile Settings instance; // volatile 필수!
    private Settings() {}

    public static Settings getInstance() {
        if (instance == null) {                  // 1차 확인: 락 없이 빠르게
            synchronized (Settings.class) {
                if (instance == null) {          // 2차 확인: 락 안에서 다시
                    instance = new Settings();
                }
            }
        }
        return instance;
    }
}
```

- **원리**: 객체가 **없을 때만** 락을 걸어서 성능 문제를 줄입니다.

- **왜 두 번 확인할까?** 락을 기다리던 스레드가 들어왔을 때, 그 사이에 다른 스레드가 이미 만들었을 수 있기 때문입니다.

- **왜 ****`volatile`****이 필요할까?** `new Settings()`는 내부적으로 `메모리 할당 → 생성자 실행 → 참조 대입` 순서인데, CPU가 순서를 바꿔 **참조 대입을 먼저** 할 수 있습니다. 그러면 다른 스레드가 **초기화가 덜 된 객체**를 가져가게 되므로 `volatile`로 이를 막습니다.

- **단점**: 구현이 복잡하고 실수하기 쉽습니다.

### 해결 ④ Holder 방식 (Bill Pugh Singleton) ⭐ 권장

```java
public class Settings {
    private Settings() {}

    // getInstance()가 처음 호출될 때 비로소 Holder 클래스가 로딩됨
    private static class Holder {
        private static final Settings INSTANCE = new Settings();
    }

    public static Settings getInstance() {
        return Holder.INSTANCE;
    }
}
```

- **원리**: 내부 클래스 `Holder`는 **처음 사용될 때 로딩**되고, 클래스 로딩은 JVM이 **스레드 안전하게 한 번만** 처리합니다.

- **장점**: 지연 초기화 + 스레드 안전 + 락 없음 → 성능과 안전성을 모두 챙깁니다.

### 스레드 안전 방식 비교

| 방식 | 스레드 안전 | 지연 초기화 | 성능 | 구현 난이도 |
| --- | --- | --- | --- | --- |
| 단순 지연 초기화 | ❌ | ✅ | 좋음 | 쉬움 |
| 이른 초기화 | ✅ | ❌ | 좋음 | 쉬움 |
| synchronized 메서드 | ✅ | ✅ | 나쁨 | 쉬움 |
| Double-Checked Locking | ✅ | ✅ | 좋음 | 어려움 |
| **Holder 방식** | ✅ | ✅ | 좋음 | 쉬움 |
| **enum** | ✅ | ❌ | 좋음 | 가장 쉬움 |

## 4. 그래도 싱글톤을 깨는 방법들과 방어법

스레드 문제를 해결해도, Java에는 `new` 없이 객체를 만드는 **우회로**가 있습니다.

### ① 리플렉션 (Reflection)

리플렉션은 실행 중에 클래스 내부를 들여다보고 조작하는 기능으로, **private 생성자도 강제로 호출**할 수 있습니다.

```java
Constructor<Settings> constructor = Settings.class.getDeclaredConstructor();
constructor.setAccessible(true);           // private 무시!
Settings fake = constructor.newInstance(); // 새 객체 생성

System.out.println(fake == Settings.getInstance()); // false → 싱글톤 깨짐
```

**방어법**: 생성자 안에서 이미 인스턴스가 있으면 예외를 던집니다.

```java
public class Settings {
    private static final Settings INSTANCE = new Settings();

    private Settings() {
        if (INSTANCE != null) {
            throw new IllegalStateException("이미 인스턴스가 존재합니다.");
        }
    }

    public static Settings getInstance() { return INSTANCE; }
}
```

### ② 직렬화 / 역직렬화 (Serialization)

객체를 파일이나 네트워크로 보내기 위해 바이트로 바꾸는 것이 직렬화, 다시 객체로 되돌리는 것이 역직렬화입니다. 역직렬화할 때는 **생성자를 거치지 않고 새 객체**가 만들어집니다.

```java
// 직렬화 후 다시 역직렬화하면
Settings copy = (Settings) in.readObject();
System.out.println(copy == Settings.getInstance()); // false → 싱글톤 깨짐
```

**방어법**: `readResolve()` 메서드를 구현해, 역직렬화로 만들어진 객체 대신 **기존 인스턴스를 돌려주게** 합니다.

```java
public class Settings implements Serializable {
    private static final Settings INSTANCE = new Settings();
    private Settings() {}
    public static Settings getInstance() { return INSTANCE; }

    // 역직렬화 시 JVM이 자동 호출 → 새 객체는 버려지고 기존 객체가 반환됨
    private Object readResolve() {
        return INSTANCE;
    }
}
```

> 인스턴스 필드가 있다면 `transient`로 선언해야 완벽하게 방어할 수 있습니다.

### ③ clone()

`Cloneable`을 구현하면 `clone()`으로 객체를 복제할 수 있습니다.

**방어법**: 싱글톤 클래스는 `Cloneable`을 **구현하지 않는 것**이 원칙입니다. 부모 클래스가 구현했다면 `clone()`을 오버라이드해서 예외를 던집니다.

```java
@Override
protected Object clone() throws CloneNotSupportedException {
    throw new CloneNotSupportedException("싱글톤은 복제할 수 없습니다.");
}
```

### ④ 여러 개의 클래스 로더

static 필드는 정확히는 **"클래스 로더마다"** 하나씩 존재합니다. 웹 서버(Tomcat 등)처럼 클래스 로더가 여러 개인 환경에서는 같은 클래스라도 **로더마다 인스턴스가 따로** 생길 수 있습니다. 즉 GoF 싱글톤은 "JVM 전체에서 하나"가 아니라 "클래스 로더 하나당 하나"를 보장합니다.

## 5. 가장 확실한 방법: enum 싱글톤

```java
public enum Settings {
    INSTANCE;

    private String mode = "dev";

    public String getMode() { return mode; }
}

// 사용
Settings.INSTANCE.getMode();
```

**왜 가장 확실할까?**

- **멀티스레드**: enum 상수는 클래스 로딩 시 JVM이 한 번만 생성 → 스레드 안전

- **리플렉션**: enum 생성자를 리플렉션으로 호출하면 JVM이 **예외를 던져** 막아 줌

- **직렬화**: enum은 JVM이 직렬화를 특별 처리해서, 역직렬화해도 **항상 같은 상수**를 반환 (`readResolve` 불필요)

- **clone**: enum은 복제가 불가능

> 『이펙티브 자바』에서도 "대부분의 상황에서 원소가 하나뿐인 열거 타입이 싱글턴을 만드는 가장 좋은 방법"이라고 소개합니다.

**단점**

- 다른 클래스를 **상속할 수 없습니다** (인터페이스 구현은 가능).

- 지연 초기화가 되지 않습니다.

## 6. 정리

| 단계 | 방법 | 막아 주는 것 |
| --- | --- | --- |
| 기본 | private 생성자 + static 필드 + getInstance() | 외부의 `new` |
| 동시성 | 이른 초기화 / Holder / DCL + volatile | 멀티스레드 중복 생성 |
| 우회로 방어 | 생성자 체크, `readResolve()`, clone 금지 | 리플렉션, 직렬화, 복제 |
| 한 번에 해결 | **enum 싱글톤** | 위 모든 경우 |

실무에서는 직접 구현해야 한다면 **Holder 방식** 또는 **enum 방식**을 쓰고, Spring을 쓴다면 **Spring 컨테이너가 Bean을 하나만 만들어 관리**하므로 직접 구현할 일은 거의 없습니다.

## 7. 꼬리 질문 대비

**Q. static 필드를 쓰면 왜 인스턴스가 하나로 유지되나요?**

static 필드는 객체가 아닌 **클래스에 소속**되어 메모리(메서드 영역)에 클래스당 하나만 존재합니다. 따라서 거기에 담아 둔 인스턴스도 하나로 유지됩니다.

**Q. 이른 초기화는 왜 스레드 안전한가요?**

static 필드 초기화는 **클래스 초기화 단계**에서 일어나는데, JVM 명세상 클래스 초기화는 내부적으로 락을 걸어 **한 스레드만, 한 번만** 실행하도록 보장되기 때문입니다.

**Q. Holder 방식은 어떻게 지연 초기화가 되나요?**

내부 클래스는 바깥 클래스가 로딩될 때 함께 로딩되지 않고, **실제로 처음 참조될 때** 로딩됩니다. `getInstance()`에서 `Holder.INSTANCE`를 처음 참조하는 순간 Holder가 초기화되면서 객체가 생성됩니다.

**Q. DCL에서 volatile을 빼면 어떤 일이 생기나요?**

명령어 재정렬로 인해 **생성자 실행이 끝나기 전에 참조가 먼저 대입**될 수 있습니다. 그러면 다른 스레드가 1차 확인에서 `instance != null`을 보고 **초기화가 덜 된 객체**를 그대로 사용할 수 있습니다.

**Q. 리플렉션 방어 코드는 지연 초기화 방식에서도 완벽한가요?**

아닙니다. 지연 초기화 방식에서는 `getInstance()`가 호출되기 전 인스턴스가 null이므로, 리플렉션으로 **먼저** 생성하면 방어 코드를 통과할 수 있습니다. 그래서 완벽한 방어가 필요하면 enum을 권장합니다.

**Q. Spring은 어떻게 Bean을 하나로 보장하나요?**

Spring 컨테이너는 Bean을 생성한 뒤 내부 **저장소(Map)에 이름별로 보관**하고, 같은 Bean을 요청하면 새로 만들지 않고 저장된 객체를 돌려줍니다. 클래스 자체가 아니라 **컨테이너가 관리**하므로, 컨테이너당 하나를 보장합니다.
