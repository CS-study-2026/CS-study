# 9-1. Singleton의 장단점에 대해 설명해 주세요.

<details>
<summary>**질문:** Singleton의 장단점에 대해 설명해 주세요.</summary>

싱글톤은 클래스의 인스턴스를 **단 하나만 만들고, 어디서든 그 하나를 공유**하도록 하는 패턴입니다. 장점은 객체를 한 번만 만들기 때문에 **메모리와 생성 비용을 아낄 수 있고**, 여러 곳에서 **같은 데이터를 공유**하기 쉽다는 점입니다. 단점은 사실상 **전역 상태**가 되어 클래스 간 **결합도가 높아지고**, **테스트가 어려우며**, 멀티스레드 환경에서는 **동시성 문제**를 신경 써야 한다는 점입니다. 그래서 실무에서는 직접 구현하기보다 Spring 컨테이너처럼 싱글톤을 대신 관리해 주는 방식을 주로 사용합니다.
</details>

---

## 1. 싱글톤

### 한 문장 정의

- "인스턴스를 딱 하나만 만들고, 모두가 그 하나를 같이 쓰는 패턴"입니다.

### 비유로 이해하기

회사에 **공용 프린터가 한 대** 있다고 생각해 보세요.

- 직원마다 프린터를 한 대씩 사면 돈(메모리)이 낭비됩니다.

- 모두가 같은 프린터를 쓰니 관리가 편합니다.

- 하지만 여러 명이 **동시에** 인쇄를 누르면 순서가 꼬일 수 있고, 프린터가 고장 나면 **모두가 영향**을 받습니다.

이 비유 속 장점과 단점이 그대로 싱글톤의 장단점입니다.

### 기본 구현

```java
public class Settings {
    // 1. 단 하나의 인스턴스를 미리 만들어 둔다
    private static final Settings INSTANCE = new Settings();

    // 2. 외부에서 new를 못 하도록 생성자를 막는다
    private Settings() {}

    // 3. 항상 같은 인스턴스를 돌려준다
    public static Settings getInstance() {
        return INSTANCE;
    }
}

Settings a = Settings.getInstance();
Settings b = Settings.getInstance();
System.out.println(a == b); // true
```

## 2. 장점

### ① 메모리 절약과 생성 비용 감소

객체를 **한 번만** 만들고 재사용합니다. DB 커넥션 풀, 스레드 풀처럼 **만드는 데 비용이 큰 객체**일수록 효과가 큽니다.

```java
// 싱글톤이 아니라면: 요청마다 무거운 객체가 새로 생성됨
for (int i = 0; i < 10000; i++) {
    ConnectionPool pool = new ConnectionPool(); // 매번 생성 → 낭비
}

// 싱글톤이라면: 같은 객체 하나를 계속 재사용
for (int i = 0; i < 10000; i++) {
    ConnectionPool pool = ConnectionPool.getInstance();
}
```

### ② 데이터 공유가 쉬움

모두가 같은 인스턴스를 쓰므로, 설정 정보나 캐시처럼 **프로그램 전체에서 같은 값을 봐야 하는 데이터**를 공유하기 쉽습니다.

### ③ 인스턴스가 하나임을 보장

생성자를 `private`으로 막기 때문에, 실수로 객체가 여러 개 생기는 것을 **문법적으로 방지**합니다. 로그 기록기처럼 "반드시 하나여야 하는" 객체에 적합합니다.

### ④ 어디서든 접근 가능

`getInstance()`만 호출하면 되므로, 객체를 여기저기 전달하지 않아도 됩니다.

> ⚠️ ②와 ④는 장점이지만, 동시에 아래 단점의 원인이 되기도 합니다.

---

## 3. 단점

### ① 전역 상태가 되어 결합도가 높아짐

어디서든 `Settings.getInstance()`를 호출할 수 있다는 건, 그만큼 많은 클래스가 **싱글톤 클래스에 직접 의존**한다는 뜻입니다.

```java
public class OrderService {
    public void order() {
        // 구체 클래스에 직접 의존 → 다른 구현으로 바꾸기 어려움
        PaymentClient client = PaymentClient.getInstance();
        client.pay();
    }
}
```

- 구체 클래스에 의존하므로 **의존 역전 원칙(DIP)** 위반

- 구현을 바꾸려면 사용하는 코드를 수정해야 하므로 **개방-폐쇄 원칙(OCP)** 위반

- 어떤 클래스가 어디서 상태를 바꿨는지 추적하기 어렵습니다.

### ② 테스트가 어려움

- 테스트에서 진짜 객체 대신 **가짜 객체(Mock)로 바꿔 끼우기 어렵습니다.** (생성자가 막혀 있고, 코드 안에서 직접 `getInstance()`를 호출하므로)

- 인스턴스가 프로그램 내내 살아 있어서, **앞 테스트가 바꾼 상태가 다음 테스트에 남아** 테스트끼리 영향을 줍니다.

```java
@Test
void test1() {
    Counter.getInstance().increase(); // count = 1
}

@Test
void test2() {
    // test1이 먼저 실행됐다면 count가 0이 아니라 1에서 시작 → 실행 순서에 따라 결과가 달라짐
    assertEquals(0, Counter.getInstance().getCount());
}
```

### ③ 멀티스레드 환경의 동시성 문제

**(a) 인스턴스가 2개 생길 수 있음**

처음 사용할 때 생성하는 방식(지연 초기화)을 단순하게 구현하면, 두 스레드가 동시에 들어와 인스턴스가 2개 만들어질 수 있습니다.

```java
public static Settings getInstance() {
    if (instance == null) {         // 스레드 A, B가 동시에 null 확인
        instance = new Settings();  // 둘 다 생성 → 싱글톤 깨짐
    }
    return instance;
}
```

**(b) 공유 상태가 꼬일 수 있음**

하나의 객체를 여러 스레드가 함께 쓰므로, 객체 안에 **변경 가능한 필드**가 있으면 값이 꼬입니다.

```java
public class Counter {
    private int count = 0;          // 여러 스레드가 공유하는 상태
    public void increase() {
        count++;                    // 동시에 실행되면 값이 유실될 수 있음
    }
}
```

👉 그래서 싱글톤 객체는 **상태를 갖지 않게(무상태, Stateless)** 설계하는 것이 원칙입니다.

### ④ 유연성 부족

- 생성자가 `private`이라 **상속(자식 클래스 생성)이 어렵습니다.**

- 나중에 "인스턴스가 2개 필요하다"는 요구가 생기면 구조를 크게 바꿔야 합니다.

### ⑤ 단일 책임 원칙(SRP) 위반 논란

싱글톤 클래스는 **원래 맡은 일**과 "인스턴스를 하나로 관리하는 일"까지 두 가지 책임을 갖게 됩니다.

## 5. 단점을 보완하는 방법

### 스레드 안전한 구현 방법

| 방식 | 설명 | 특징 |
| --- | --- | --- |
| 이른 초기화 (Eager) | 클래스 로딩 시점에 미리 생성 | 안전하지만, 안 써도 메모리를 차지함 |
| `synchronized` 메서드 | `getInstance()`에 락을 걺 | 안전하지만, 호출할 때마다 느려짐 |
| Double-Checked Locking | `volatile` + 처음 생성할 때만 락 | 빠르지만 구현이 복잡함 |
| **Holder 방식** | 정적 내부 클래스로 지연 생성 | 안전 + 지연 로딩, **많이 권장** |
| **enum 방식** | `enum`으로 선언 | 가장 간단하고 직렬화·리플렉션 공격에도 안전 |

**Holder 방식 (Bill Pugh Singleton)**

```java
public class Settings {
    private Settings() {}

    // getInstance()가 처음 호출될 때 Holder 클래스가 로딩되면서 인스턴스 생성
    // 클래스 로딩은 JVM이 스레드 안전하게 처리해 줌
    private static class Holder {
        private static final Settings INSTANCE = new Settings();
    }

    public static Settings getInstance() {
        return Holder.INSTANCE;
    }
}
```

**enum 방식**

```java
public enum Settings {
    INSTANCE;

    public void doSomething() {
        System.out.println("작업 수행");
    }
}

// 사용
Settings.INSTANCE.doSomething();
```

### Spring의 해결 방법: 싱글톤 컨테이너

Spring은 Bean을 **기본적으로 싱글톤으로 관리**하면서도, 위의 단점을 대부분 해결합니다.

- 클래스에 `private` 생성자나 `getInstance()`를 **직접 작성하지 않아도** Spring이 하나만 만들어 관리합니다.

- 의존성 주입(DI)으로 객체를 받기 때문에, 구체 클래스가 아닌 **인터페이스에 의존**할 수 있습니다. → 결합도 감소, 테스트 시 Mock 교체 쉬움

```java
@Service
public class OrderService {
    private final PaymentClient client; // 인터페이스에 의존

    // Spring이 싱글톤 Bean을 주입해 줌
    public OrderService(PaymentClient client) {
        this.client = client;
    }
}
```

> 단, Spring Bean도 하나의 객체를 여러 스레드가 공유하므로 **무상태(Stateless)로 설계**해야 합니다.

## 6. 꼬리 질문 대비

**Q. 싱글톤 객체를 무상태로 설계해야 하는 이유는?**

하나의 인스턴스를 여러 스레드가 동시에 사용하기 때문에, 변경 가능한 필드가 있으면 한 요청이 바꾼 값을 다른 요청이 보게 되는 문제가 생깁니다. 필요한 값은 필드 대신 **지역 변수, 파라미터, ThreadLocal** 등을 사용해야 합니다.

**Q. Double-Checked Locking에서 ****`volatile`****이 필요한 이유는?**

`instance = new Settings()`는 내부적으로 ① 메모리 할당 ② 생성자 실행 ③ 참조 대입 순서로 진행되는데, CPU나 컴파일러가 순서를 바꿔 ③을 ②보다 먼저 할 수 있습니다. 그러면 다른 스레드가 **초기화가 덜 된 객체**를 가져갈 수 있어, `volatile`로 재정렬을 막아야 합니다.

**Q. enum 싱글톤이 가장 안전하다고 하는 이유는?**

JVM이 enum 인스턴스가 하나임을 보장하고, **직렬화/역직렬화**나 **리플렉션**으로 새 인스턴스를 만드는 것을 막아 주기 때문입니다. 다만 다른 클래스를 상속할 수 없다는 제약이 있습니다.

**Q. Spring Bean의 싱글톤과 GoF 싱글톤 패턴의 차이는?**

GoF 싱글톤은 **클래스 스스로** 인스턴스를 하나로 제한합니다(JVM 전체에서 하나). Spring의 싱글톤은 **컨테이너가** Bean을 하나만 만들어 관리하는 것이며(컨테이너당 하나), 클래스 자체는 평범한 클래스라 `new`로 생성할 수도 있습니다.

**Q. 싱글톤과 static 클래스(유틸 클래스)의 차이는?**

static 클래스는 객체가 아니라서 **인터페이스 구현, 상속, 다형성, DI**를 활용할 수 없습니다. 싱글톤은 객체이므로 인터페이스를 구현하고 주입받을 수 있습니다. 상태 없이 기능만 모아둔 경우(`Math`)는 static, 상태나 다형성이 필요하면 싱글톤이 적합합니다.
