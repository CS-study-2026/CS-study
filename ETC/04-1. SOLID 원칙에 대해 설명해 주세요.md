# 4-1. SOLID 원칙에 대해 설명해 주세요.

**SOLID**는 객체지향 설계에서 **유지보수성과 확장성을 높이고, 변경의 영향을 줄이기 위한 5가지 설계 원칙**입니다.

핵심은 클래스를 무조건 작게 나누는 것이 아니라, **객체의 책임과 의존 관계를 적절히 설계하여 변경에 유연한 구조를 만드는 것**입니다.

| 원칙 | 핵심 질문 |
| --- | --- |
| **SRP** 단일 책임 원칙 | 이 클래스가 변경되는 이유가 여러 개인가? |
| **OCP** 개방·폐쇄 원칙 | 새 기능을 추가할 때 기존 코드를 계속 수정해야 하는가? |
| **LSP** 리스코프 치환 원칙 | 하위 타입으로 바꿔도 기존 동작이 유지되는가? |
| **ISP** 인터페이스 분리 원칙 | 사용하지 않는 기능까지 의존하고 있는가? |
| **DIP** 의존성 역전 원칙 | 핵심 로직이 구체적인 구현체에 직접 의존하는가? |

## 1. 단일 책임 원칙(SRP)

> **클래스는 하나의 변경 이유만 가져야 한다.**

단순히 클래스가 하나의 기능만 수행해야 한다는 의미보다는, **하나의 책임을 가져야 한다**는 의미입니다.

예를 들어 `OrderService`가 주문 처리뿐 아니라 영수증 생성과 이메일 발송까지 담당한다면 주문 정책, 영수증 형식, 이메일 발송 방식 중 하나만 변경되어도 `OrderService`를 수정해야 합니다.

이를 각각 `OrderService`, `ReceiptService`, `EmailService` 등으로 분리하면 **각 책임의 변경이 다른 코드에 미치는 영향을 줄일 수 있습니다.**

## 2. 개방·폐쇄 원칙(OCP)

> **확장에는 열려 있고, 변경에는 닫혀 있어야 한다.**

새로운 기능을 추가할 때 기존 핵심 코드를 계속 수정하기보다 **새로운 구현을 추가하는 방식으로 확장할 수 있어야 한다**는 의미입니다.

예를 들어 결제 방식에 따라 `if`문을 계속 추가하는 구조보다 `Payment` 인터페이스를 만들고 카드 결제, 계좌이체 등의 구현체를 각각 만드는 방식입니다.

```java
interface Payment {
    void pay();
}

class CardPayment implements Payment {
    public void pay() {
        // 카드 결제
    }
}
```

새로운 결제 방식이 추가되면 새로운 `Payment` 구현체를 추가할 수 있습니다.

단, 기존 코드를 **절대 수정하면 안 된다는 의미는 아니며**, 변경 가능성이 높은 부분에 적절한 확장 지점을 만드는 것이 핵심입니다.

## 3. 리스코프 치환 원칙(LSP)

> **하위 타입은 상위 타입을 사용하는 위치에 대체되어도 기존 프로그램의 동작을 깨뜨리지 않아야 한다.**

즉, 단순히 문법적으로 상속이 가능하다는 것뿐 아니라 **상위 타입이 보장하던 동작과 규칙도 하위 타입이 지켜야 합니다.**

예를 들어 모든 `Bird`가 `fly()`할 수 있도록 설계한 뒤 `Penguin`이 이를 상속받아 `fly()`를 호출할 때 예외를 발생시킨다면 `Bird`를 기대하는 코드에서 `Penguin`을 안전하게 사용할 수 없습니다.

이 경우에는 모든 새가 가지는 특성과 날 수 있는 특성을 분리하여 `Flyable`과 같은 별도의 인터페이스로 설계하는 것이 적절합니다.

## 4. 인터페이스 분리 원칙(ISP)

> **클라이언트가 사용하지 않는 메서드에 의존하도록 강요하지 않아야 한다.**

하나의 거대한 인터페이스를 제공하기보다 **역할에 따라 작은 인터페이스로 분리해야 한다**는 원칙입니다.

예를 들어 다음과 같은 인터페이스가 있다면,

```java
interface Machine {
    void print();
    void scan();
    void fax();
}
```

인쇄만 가능한 기계도 `scan()`과 `fax()`를 구현해야 하는 문제가 발생합니다.

따라서 `Printable`, `Scannable`, `Faxable` 등으로 인터페이스를 분리하면 각 객체는 **자신에게 필요한 기능에만 의존**할 수 있습니다.

## 5. 의존성 역전 원칙(DIP)

> **고수준 모듈과 저수준 모듈 모두 구체적인 구현이 아닌 추상화에 의존해야 한다.**

- **고수준 모듈**: 핵심 비즈니스 로직을 담당하는 부분

- **저수준 모듈**: DB, 파일, 외부 API 등 구체적인 기술을 담당하는 부분

예를 들어 `OrderService`가 `MySqlOrderRepository`를 직접 사용하면 저장 기술이 변경될 때 `OrderService`도 수정해야 합니다.

대신 `OrderRepository`라는 인터페이스에 의존하도록 만들 수 있습니다.

```java
class OrderService {

    private final OrderRepository orderRepository;

    OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

이렇게 하면 실제 저장 방식이 MySQL에서 다른 DB로 변경되더라도 `OrderService`는 `OrderRepository`라는 추상화에만 의존하기 때문에 변경의 영향을 줄일 수 있습니다.

여기서 생성자를 통해 외부에서 구현 객체를 전달하는 것은 의존성 주입(DI)입니다.

**DIP는 ****`무엇에 의존할 것인가`****에 대한 설계 원칙이고, DI는 ****`의존 객체를 어떻게 전달할 것인가`****에 대한 구현 방법**이므로 둘은 같은 개념이 아닙니다.

## SOLID 원칙의 관계

SOLID 원칙은 각각 독립적이지만 결국 **변경의 영향을 줄인다**는 공통된 목적을 가지고 있습니다.

```plain text
SRP → 책임을 분리한다.
OCP → 기존 코드 변경 없이 확장할 수 있도록 한다.
LSP → 상속·다형성을 안전하게 사용한다.
ISP → 필요한 인터페이스에만 의존하게 한다.
DIP → 구체적인 구현보다 추상화에 의존한다.
```

특히 **OCP를 구현하기 위해 추상화를 사용하다 보면 DIP와 다형성이 함께 활용되는 경우가 많습니다.**

### 한 줄 정리

> SOLID는 객체의 책임을 명확히 나누고 추상화와 다형성을 적절히 활용하여, 기능 추가나 변경이 다른 코드에 미치는 영향을 줄이기 위한 객체지향 설계 원칙입니다.
