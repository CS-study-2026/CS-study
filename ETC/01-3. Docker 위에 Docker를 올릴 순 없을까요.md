# 1-3. Docker 위에 Docker를 올릴 순 없을까요?

# 1-3. Docker 위에 Docker를 올릴 수 있을까?

네. **가능합니다.**

다만 "Docker 위에 Docker를 올린다"는 표현에는 대표적으로 두 가지 방식이 있으며, 구조와 용도가 다릅니다.

## 1. Docker in Docker (DinD)

가장 직관적인 방법입니다.

**Docker 컨테이너 내부에서 또 다른 ****Docker Engine****을 실행**하는 방식입니다.

```plain text
Host
│
└── Docker Engine
     │
     └── Container A
          │
          └── Docker Engine
               │
               ├── Container B
               └── Container C
```

즉,

```plain text
Docker
└── Container
     └── Docker
          └── Container
```

처럼 중첩해서 사용하는 것입니다.

이를 흔히 **Docker in Docker, DinD**라고 부릅니다.

Docker에서는 공식 `docker:dind` 이미지도 제공합니다.

```plain text
docker run --privileged --name dind docker:dind
```

여기서 `--privileged`는 컨테이너에 매우 강한 시스템 권한을 부여하는 옵션입니다.

### 내부 컨테이너는 Kernel을 어떻게 사용할까?

여기서 중요한 점이 있습니다.

DinD라고 해서 Kernel이 계속 중첩해서 만들어지는 것은 아닙니다.

```plain text
Host
│
│ Kernel
│   ▲
│   │
│ Container A
│   │
│   └── Docker Engine
│        │
│        ├── Container B
│        └── Container C
│
└──────────────────
```

컨테이너는 독립적인 Kernel을 가지고 있지 않기 때문에 결국 **같은 기반 Kernel을 사용하면서 격리된 환경이 중첩되는 것**에 가깝습니다.

---

## 2. Docker outside of Docker (DooD)

또 다른 방법은 컨테이너 안에 새로운 Docker Engine을 띄우지 않고 **Host의 Docker Engine을 컨테이너에서 사용하는 것**입니다.

보통 Host의 Docker socket을 컨테이너에 연결합니다.

```plain text
                Host
                  │
           Docker Engine
          ↙      ↓       ↘
Container X  Container A  Container B
     │
     │ Docker CLI
     │
     │ Docker Socket
     └───────────────────┐
                         │
                         ▼
                  Docker Engine
                  (위와 동일)
```

Container X 안에서:

```plain text
docker run nginx
```

를 실행하더라도 Container X 내부에 Docker Engine이 하나 더 있는 것이 아닙니다.

실제로는:

```plain text
Container X의 Docker CLI
          ↓
Host의 Docker Engine
          ↓
새로운 Container 생성
```

이 됩니다.

따라서 새로 생성된 컨테이너는 Container X의 **자식 컨테이너가 아니라 Host Docker Engine이 관리하는 컨테이너**입니다.

---

## 3. DinD와 DooD 비교

|   | DinD | DooD |
| --- | --- | --- |
| 의미 | 컨테이너 내부에 Docker Engine 실행 | Host의 Docker Engine 사용 |
| Docker Engine | 내부에 별도로 존재 | Host의 것을 공유 |
| 구조 | 실제 중첩 구조 | Host Docker를 원격 제어하는 것에 가까움 |
| 격리 | 별도의 Docker 환경 구성 가능 | Host Docker 환경을 그대로 사용 |
| 주의점 | `privileged` 등 강한 권한이 필요한 구성이 흔함 | Docker socket 접근 권한이 매우 강력함 |

---

## 4. 왜 이런 방식을 사용할까?

대표적인 용도 중 하나가 **CI/CD 환경에서 Docker 이미지를 빌드하거나 컨테이너를 실행해야 할 때**입니다.

예를 들어 CI 작업 자체가 컨테이너에서 실행되고 있다고 해보겠습니다.

```plain text
CI Container
│
├── Source Code
├── Test
│
└── Docker Image Build
```

여기서 CI 작업이 `docker build` 같은 명령을 실행해야 한다면 Docker 기능에 접근해야 합니다.

이때 DinD 같은 구조를 사용할 수 있습니다.

---

## 5. 보안상 주의할 점

가능하다고 해서 아무 상황에서나 사용하는 것은 좋지 않습니다.

특히 DinD에서 흔히 사용하는:

```plain text
--privileged
```

옵션은 컨테이너에 매우 강한 권한을 부여하므로 **컨테이너 격리를 크게 약화시킬 수 있습니다.**

DooD에서 사용하는 Docker socket:

```plain text
/var/run/docker.sock
```

역시 Docker Engine을 강력하게 제어할 수 있는 통로이기 때문에, 신뢰할 수 없는 컨테이너에 노출하면 Host까지 영향을 받을 수 있습니다.

---

## 핵심 정리

> **Docker 위에 Docker를 실행하는 것은 가능하다.**

대표적으로 두 가지 방식이 있습니다.

```plain text
① Docker in Docker (DinD)

Host Docker
└── Container
     └── Docker Engine
          └── Container


② Docker outside of Docker (DooD)

Container
   │
   │ Docker 명령
   ▼
Host Docker Engine
   │
   └── Container
```

**DinD는 실제로 컨테이너 내부에 별도의 Docker Engine을 실행하는 방식**이고, **DooD는 컨테이너에서 Host의 Docker Engine을 사용하는 방식**입니다.

둘 다 강력한 권한이 필요한 구성이 될 수 있으므로 **보안상의 주의가 필요합니다.**
