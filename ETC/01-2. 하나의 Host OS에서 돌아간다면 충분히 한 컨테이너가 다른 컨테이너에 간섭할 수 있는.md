# 1-2. 하나의 Host OS에서 돌아간다면 충분히 한 컨테이너가 다른 컨테이너에 간섭할 수 있는 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?

# 1-2. 하나의 Host OS에서 돌아간다면 한 컨테이너가 다른 컨테이너에 간섭할 위험이 있지 않을까요? 이를 어떻게 방어할 수 있을까요?

네. **컨테이너는 커널을 공유하기 때문에 한 컨테이너의 문제가 다른 컨테이너나 Host에 영향을 줄 가능성이 있습니다.**

그래서 컨테이너 환경에서는 여러 격리 및 보안 기술을 함께 사용합니다.

## 1. 왜 간섭할 위험이 있을까?

가상머신(VM)은 각각 독립적인 OS와 Kernel을 가지지만, 컨테이너는 그렇지 않습니다.

```plain text
Virtual Machine

VM A                 VM B
┌──────────┐        ┌──────────┐
│ App A    │        │ App B    │
├──────────┤        ├──────────┤
│ OS       │        │ OS       │
│ Kernel A │        │ Kernel B │
└──────────┘        └──────────┘


Container

Container A         Container B
┌──────────┐        ┌──────────┐
│ App A    │        │ App B    │
└────┬─────┘        └────┬─────┘
     │                   │
     └─────────┬─────────┘
               ▼
          Shared Kernel
```

따라서 컨테이너의 격리가 제대로 이루어지지 않는다면 다음과 같은 문제가 발생할 수 있습니다.

> 📍 

  - 다른 컨테이너의 프로세스나 파일에 접근

  - CPU나 메모리를 과도하게 사용하여 다른 컨테이너에 영향

  - 과도한 권한을 이용해 Host 시스템에 접근

  - 커널 취약점을 악용하여 컨테이너 밖으로 탈출하는 **Container Escape**

이를 방지하기 위해 여러 기술을 사용합니다.

---

## 2. Namespace — 컨테이너가 볼 수 있는 범위를 격리

**Namespace**는 각각의 컨테이너가 볼 수 있는 시스템 자원을 분리합니다.

예를 들어 실제 Host에는 여러 프로세스가 존재하더라도:

```plain text
실제 시스템

Process A
Process B
Process C
Process D
```

각 컨테이너에서는 자신에게 속한 프로세스만 보이도록 만들 수 있습니다.

```plain text
Container A       Container B

Process A         Process C
Process B         Process D

    서로의 프로세스를 볼 수 없도록 격리
```

프로세스뿐만 아니라 네트워크, 파일 시스템의 마운트 영역, 사용자 등의 환경도 격리할 수 있습니다.

쉽게 말하면:

> **Namespace = "각 컨테이너에게 서로 다른 시스템 환경을 보여준다."**

Docker가 컨테이너를 생성할 때 필요한 Namespace를 자동으로 구성.

---

## 3. cgroup — 자원 사용량을 제한

격리되어 있더라도 한 컨테이너가 CPU나 메모리를 모두 사용해버리면 다른 컨테이너가 영향을 받을 수 있습니다.

이를 방지하기 위해 **cgroup(Control Groups)**을 이용하여 컨테이너가 사용할 수 있는 자원의 양을 제한할 수 있습니다.

```plain text
Host
CPU 8 Core
Memory 16GB

        │
        ├── Container A
        │    CPU 제한
        │    Memory 2GB
        │
        └── Container B
             CPU 제한
             Memory 4GB
```

Docker에서도 다음처럼 제한을 설정할 수 있습니다.

```plain text
docker run --memory="2g" --cpus="1" my-app
```

아래와 같은 의미이다.

```json
docker run
│
│  → 새로운 컨테이너를 생성하고 실행
│
├── --memory="2g"
│     → 컨테이너의 메모리 사용량을 2GB로 제한
│
├── --cpus="1"
│     → 컨테이너가 사용할 수 있는 CPU 처리 능력을
│        CPU 1개 분량으로 제한
│
└── my-app
      → 실행할 Docker 이미지의 이름
```

따라서:

> **cgroup = "각 컨테이너가 자원을 얼마나 사용할 수 있는지 제한한다."**

라고 이해하면 됩니다.

---

## 4. 권한 제한 — 컨테이너가 할 수 있는 작업을 제한

컨테이너 내부의 프로세스에 너무 많은 권한을 주면 Host나 다른 컨테이너에 영향을 줄 위험이 커집니다.

그래서 다음과 같은 방법으로 권한을 최소화합니다.

```plain text
Container
│
├── 필요한 작업          → 허용
├── 불필요한 시스템 권한 → 제한
└── 위험한 시스템 작업   → 제한
```

대표적으로 **Linux Capabilities, seccomp, SELinux, AppArmor** 등의 보안 기능을 활용할 수 있습니다.

또한 컨테이너를 불필요하게 `root`로 실행하거나 Docker의 `--privileged` 옵션으로 과도한 권한을 주는 것을 피하는 것도 중요합니다.

네 가지 모두 **컨테이너가 시스템에 할 수 있는 행동을 제한해서 보안을 강화하는 기술**입니다. 다만 제한하는 대상과 방식이 조금씩 다릅니다.

## 각각 무엇을 제한할까?

| 기술 | 간단한 역할 | 쉽게 말하면 |
| --- | --- | --- |
| **Linux Capabilities** | root 권한을 세분화 | "이 권한만 줄게" |
| **seccomp** | System Call 제한 | "이 시스템 요청은 하지 마" |
| **SELinux** | 자원 접근 정책 적용 | "너는 이 파일/자원에 접근하면 안 돼" |
| **AppArmor** | 프로그램별 접근 정책 적용 | "이 프로그램은 여기까지만 접근 가능해" |

### 1. Linux Capabilities

원래 Linux의 `root`는 거의 모든 시스템 관리 권한을 가지고 있습니다.

Capabilities는 이 강력한 권한을 **여러 개의 작은 권한으로 쪼개서 필요한 것만 부여할 수 있게 하는 기능**입니다.

```plain text
기존

root
└── 거의 모든 권한


Capabilities 적용

프로세스
├── 네트워크 관련 특정 권한  ✅
├── 시스템 시간 변경         ❌
├── 커널 모듈 관리           ❌
└── 기타 관리자 권한         ❌
```

즉,

> **Capabilities = "root의 권한을 잘게 나눠 필요한 권한만 허용"**

Docker도 기본적으로 모든 capability를 컨테이너에 주지 않습니다.

---

### 2. seccomp

프로그램은 Kernel의 기능이 필요할 때 **System Call(시스템 콜)**을 사용합니다.

예를 들어:

```plain text
Application
     │
     │ System Call
     ▼
   Kernel
     │
     ├── 파일 열기
     ├── 프로세스 생성
     ├── 메모리 관리
     └── 기타 시스템 기능
```

**seccomp**는 프로세스가 사용할 수 있는 System Call을 제한합니다.

```plain text
Container
    │
    ├── 허용된 System Call → ✅
    │
    └── 위험한 System Call → ❌
```

컨테이너가 애초에 불필요하거나 위험한 Kernel 기능을 호출하지 못하게 만들어 **공격 가능한 범위를 줄이는 것**입니다.

> **seccomp = "사용할 수 있는 System Call 제한"**

---

### 3. SELinux

**SELinux(Security-Enhanced Linux)**는 프로세스가 파일, 디렉터리, 포트 등의 시스템 자원에 접근할 수 있는지를 **보안 정책에 따라 통제하는 기술**입니다.

예를 들어:

```plain text
Container A
    │
    ├── 자신의 데이터 → ✅
    │
    ├── 허용된 파일   → ✅
    │
    └── 보호된 파일   → ❌
```

단순히 Linux의 `rwx` 파일 권한만 확인하는 것이 아니라 **추가적인 보안 정책을 적용**할 수 있습니다.

> **SELinux = "정해진 보안 정책에 따라 시스템 자원 접근 통제"**

---

### 4. AppArmor

AppArmor도 SELinux와 비슷하게 **프로그램이 어떤 시스템 자원에 접근하고 어떤 행동을 할 수 있는지 제한하는 보안 기술**입니다.

예를 들어 Nginx에 다음과 같은 정책을 적용한다고 생각할 수 있습니다.

```plain text
Nginx
│
├── /var/www 읽기       → ✅
├── 필요한 네트워크 사용 → ✅
│
└── 민감한 시스템 파일   → ❌
```

> **AppArmor = "프로그램별 보안 프로필을 통해 행동과 자원 접근을 제한"**

SELinux와 AppArmor는 둘 다 Linux의 L**SM(Linux Security Modules)**이라는 보안 프레임워크를 기반으로 하며, 접근 통제 방식과 정책 모델에는 차이가 있습니다.

---

## 어떻게 구분하면 될까?

예를 들어 컨테이너 안의 프로그램이 뭔가 위험한 행동을 하려고 한다고 생각해보겠습니다.

```plain text
               Container
                   │
                   ▼
        "이 권한을 가지고 있어?"
          Linux Capabilities
                   │
                   ▼
        "이 System Call 해도 돼?"
               seccomp
                   │
                   ▼
        "이 자원에 접근해도 돼?"
          SELinux / AppArmor
                   │
                   ▼
                 Kernel
```

실제 내부 처리 순서가 항상 위와 같이 단순하게 직렬로 이루어진다는 뜻은 아니고, **각 기술의 역할을 이해하기 위한 개념도**입니다.

### 핵심 정리

> **Capabilities** → 어떤 **권한**을 가질 수 있는가?

**seccomp** → 어떤 **System Call**을 사용할 수 있는가?

**SELinux / AppArmor** → 어떤 **시스템 자원과 행동**에 접근할 수 있는가?

이 기술들은 서로 대체 관계라기보다는 **여러 계층에서 컨테이너의 권한과 행동을 제한하여 보안을 강화하는 수단**이라고 이해하면 됩니다.

**참고:** [Docker Engine Security](https://docs.docker.com/engine/security/?utm_source=chatgpt.com) · [Docker seccomp 공식 문서](https://docs.docker.com/engine/security/seccomp/?utm_source=chatgpt.com) · [Linux Kernel LSM 문서](https://docs.kernel.org/admin-guide/LSM/index.html?utm_source=chatgpt.com)

## 5. 파일 시스템과 네트워크도 분리

컨테이너마다 기본적으로 독립적인 파일 시스템 환경과 네트워크 환경을 제공할 수 있습니다.

```plain text
              Host
               │
        ┌──────┴──────┐
        │             │
 Container A     Container B
 ├─ Files A      ├─ Files B
 └─ Network A    └─ Network B
```

따라서 다른 컨테이너의 파일이나 네트워크에 무조건 접근할 수 있는 것은 아닙니다.

다만 Volume, bind mount, 컨테이너 네트워크 등을 통해 **의도적으로 자원을 공유하도록 설정할 수도 있으므로 설정을 잘못하면 격리가 약해질 수 있습니다.**

셋 다 Docker 컨테이너가 **외부와 데이터를 공유하거나 다른 컨테이너와 통신하도록 만드는 기능**입니다. 다만 `Volume`, `bind mount`는 **파일/데이터**, 컨테이너 네트워크는 **통신**에 관한 기능입니다.

## 1. Volume

**Docker가 관리하는 별도의 저장 공간을 컨테이너에 연결하는 기능**입니다.

컨테이너 내부에만 데이터를 저장하면 컨테이너를 삭제했을 때 데이터도 함께 사라질 수 있습니다. Volume을 사용하면 중요한 데이터를 컨테이너와 분리해서 보관할 수 있습니다.

```plain text
Docker Host

┌─────────────────────┐
│ Volume              │
│ ┌─────────────────┐ │
│ │ DB 데이터       │ │
│ └────────┬────────┘ │
└──────────┼──────────┘
           │ 연결
           ▼
┌─────────────────────┐
│ MySQL Container     │
│                     │
│ /var/lib/mysql ─────┘
└─────────────────────┘
```

예를 들어:

```plain text
docker run -v mysql-data:/var/lib/mysql mysql
```

`mysql-data`라는 Volume을 컨테이너의 `/var/lib/mysql`에 연결합니다.

컨테이너를 삭제하고 새 MySQL 컨테이너를 만들어도 **같은 Volume을 다시 연결하면 기존 데이터를 사용할 수 있습니다.**

> **Volume = Docker가 관리하는 영구 저장공간**

---

## 2. Bind Mount

Bind mount도 Host의 파일을 컨테이너와 연결한다는 점에서는 Volume과 비슷합니다.

차이는 **Host에 이미 존재하는 특정 파일이나 디렉터리를 직접 연결한다는 것**입니다.

예를 들어 내 컴퓨터에 다음 소스 코드가 있다고 해보겠습니다.

```plain text
Host

/Users/me/project
├── index.html
├── app.js
└── ...
       │
       │ Bind Mount
       ▼
Container

/app
├── index.html
├── app.js
└── ...
```

다음처럼 연결할 수 있습니다.

```plain text
docker run --mount type=bind,source=/Users/me/project,target=/app my-app
```

그러면 Host의 `/Users/me/project`와 컨테이너의 `/app`이 연결됩니다.

Host에서 `app.js`를 수정하면 컨테이너에서도 변경된 파일을 볼 수 있습니다.

그래서 **개발 중인 소스 코드를 컨테이너에 연결하는 용도** 등에 많이 사용합니다.

### Volume과 Bind Mount 비교

|   | Volume | Bind Mount |
| --- | --- | --- |
| 저장 위치 | Docker가 관리 | 사용자가 Host 경로 지정 |
| 목적 | 데이터 영구 저장에 적합 | Host 파일을 직접 공유할 때 유용 |
| 대표 예 | DB 데이터 | 개발 소스 코드 |

둘 다 설정에 따라 Host의 데이터를 컨테이너에 노출하므로, **민감한 Host 디렉터리를 잘못 연결하면 보안 문제가 될 수 있습니다.**

## 3. 컨테이너 네트워크

이번에는 저장공간이 아니라 **컨테이너끼리 통신하기 위한 기능**입니다.

예를 들어 웹 애플리케이션과 DB를 각각 다른 컨테이너에서 실행한다고 해보겠습니다.

```plain text
┌──────────────────┐
│ Web Container    │
│ Spring           │
└────────┬─────────┘
         │
         │ Docker Network
         │
┌────────▼─────────┐
│ DB Container     │
│ MySQL            │
└──────────────────┘
```

둘을 같은 Docker Network에 연결하면 서로 통신할 수 있습니다.

예를 들어:

```plain text
docker network create my-network
```

네트워크를 만들고,

```plain text
docker run --network=my-network --name=db mysql
docker run --network=my-network --name=web my-app
```

두 컨테이너를 같은 네트워크에 연결할 수 있습니다.

그러면 `web` 컨테이너에서 `db`라는 이름을 이용해 DB 컨테이너에 접근하는 식으로 구성할 수 있습니다.

---

## 왜 앞에서 이 개념들이 나왔을까?

앞에서 "컨테이너는 서로 격리되어 있다"고 했지만, 실제 애플리케이션에서는 완전히 단절되어 있으면 사용할 수 없습니다.

그래서 필요한 부분만 의도적으로 연결합니다.

```plain text
기본 상태
────────────────────────────

Container A    Container B
     ↕ 격리 ↕


필요한 것은 선택적으로 공유
────────────────────────────

파일/데이터 공유
→ Volume / Bind Mount

네트워크 통신
→ Docker Network
```

즉, **컨테이너는 기본적으로 격리하되 필요한 데이터와 통신 경로만 명시적으로 연결한다**고 이해하면 됩니다.

> **Volume** → Docker가 관리하는 저장공간을 컨테이너에 연결

**Bind Mount** → Host의 특정 파일/디렉터리를 컨테이너에 직접 연결

**Container Network** → 컨테이너끼리 네트워크 통신이 가능하도록 연결

참고: [Docker Storage 공식 문서](https://docs.docker.com/engine/storage/?utm_source=chatgpt.com) · [Docker Networking 공식 문서](https://docs.docker.com/engine/network/?utm_source=chatgpt.com)

## 6. 그래도 VM보다 격리 측면에서 주의가 필요하다

컨테이너에는 여러 격리 기술이 있지만 **Kernel 자체까지 분리되는 것은 아닙니다.**

```plain text
VM
→ Kernel까지 분리

Container
→ 실행 환경은 격리
→ Kernel은 공유
```

따라서 커널 취약점이나 잘못된 권한 설정 등이 존재하면 컨테이너의 격리가 깨질 가능성이 있습니다.

실제 환경에서는 하나의 기술만 믿기보다는 **여러 보안 계층을 함께 적용하는 Defense in Depth(심층 방어)** 방식이 중요합니다.

## 핵심 정리

컨테이너는 Kernel을 공유하기 때문에 **컨테이너끼리 서로 영향을 줄 위험이 완전히 없는 것은 아닙니다.**

이를 방어하기 위해 대표적으로 다음과 같은 방법을 사용합니다.

| 방법 | 역할 |
| --- | --- |
| **Namespace** | 프로세스, 네트워크, 파일 시스템 등 컨테이너가 볼 수 있는 환경을 격리 |
| **cgroup** | CPU, 메모리 등의 자원 사용량 제한 |
| **권한 제한** | 컨테이너가 수행할 수 있는 시스템 작업 최소화 |
| **파일/네트워크 격리** | 다른 컨테이너의 파일 및 네트워크에 대한 접근 제한 |
| **보안 정책** | seccomp, SELinux, AppArmor 등을 통한 추가 제한 |

가장 핵심적인 두 가지를 기억하면:

> **Namespace → "무엇을 볼 수 있는가?"를 격리**

**cgroup → "얼마나 사용할 수 있는가?"를 제한**

즉, 컨테이너는 같은 Kernel을 공유하지만 **격리 + 자원 제한 + 권한 제한**을 여러 계층으로 적용하여 컨테이너 간 간섭 위험을 줄입니다.
