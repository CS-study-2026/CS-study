# 2-0. CI/CD 를 사용해 본 경험이 있나요? 있다면 간단하게 설명해 주세요.

## 0️⃣ CI/CD란?

- **CI(Continuous Integration)**: 코드 변경사항을 지속적으로 통합하고 빌드·테스트하여 코드의 문제를 빠르게 확인하는 과정

- **CD(Continuous Delivery / Deployment)**: 검증된 애플리케이션을 배포 환경에 자동으로 전달하거나 배포하는 과정

유망주 프로젝트에서는 **GitLab → Jenkins → Docker Hub → AWS EC2**를 연결하여 코드 변경부터 서버 배포까지 자동화

```plain text
GitLab
   ↓
Webhook
   ↓
Jenkins
   ├── 변경사항 확인
   ├── Docker Image Build
   ├── Docker Hub Push
   └── EC2 배포
          ↓
     Docker Compose
          ↓
   Backend / Frontend / AI
```

## 1️⃣ 유망주의 CI/CD 전체 구조

### 1.1. 배포 환경

- **GitLab**: 소스 코드 관리

- **Jenkins**: CI/CD Pipeline 실행

- **Docker**: 애플리케이션 컨테이너화

- **Docker Hub**: 빌드된 Image 저장

- **AWS EC2**: 운영 서버

- **Docker Compose**: 여러 컨테이너 실행 및 관리

- **Nginx**: Frontend 제공 및 Backend / AI Reverse Proxy

```plain text
                    GitLab
                       │
                    Webhook
                       ↓
                   Jenkins
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
      Docker Build             환경 변수 주입
          │
          ↓
      Docker Hub
          │
          ↓
        EC2
          │
     Docker Compose
          │
     ┌────┼──────────────┐
     ↓    ↓              ↓
   Nginx Backend       AI Server
          │              │
          └──────┬───────┘
                 ↓
          MySQL / Redis /
             MongoDB
```

## 2️⃣ Jenkins Pipeline 구성

유망주의 Jenkins Pipeline은 대략 다음 단계로 구성

```plain text
Checkout
   ↓
Check Changes
   ↓
환경 변수 주입
   ↓
Docker Image Build
   ↓
Docker Hub Push
   ↓
EC2 Deploy
   ↓
Health Check
   ↓
실패 시 Rollback
```

### 2.1. Git Diff를 이용한 변경사항 확인

모든 Git Push마다 모든 서비스를 다시 빌드하지 않도록 변경된 파일을 확인

```bash
git diff --name-only
```

주요 확인 대상

Jenkinsfile : `be/`  `fe/`  `docker-compose.yaml`

Jenkinsfile.ai : `ai/`  `docker-compose.ai.yaml`

- 애플리케이션과 관련된 변경이 있는지 확인

- 관련 변경이 없으면 불필요한 Build / Deploy 과정 생략

---

### 2.2. Docker Image Build & Push

변경된 애플리케이션을 Docker Image로 빌드한 후 Docker Hub에 Push

```plain text
Source Code
    ↓
Docker Build
    ↓
Docker Image
    ↓
Docker Hub Push
```

Image Tag는 다음 형식으로 관리

```plain text
BUILD_NUMBER-GIT_COMMIT_SHORT
```

예시

```plain text
100-321c162
```

이를 통해 배포된 Image가 어떤 Jenkins Build와 Git Commit에서 만들어졌는지 확인 가능

---

### 2.3. EC2 배포

Jenkins에서 SSH를 이용해 EC2 서버에 접속

```plain text
Jenkins
   ↓ SSH
AWS EC2
   ↓
Docker Hub Image Pull
   ↓
Docker Compose
   ↓
Container 재생성
```

운영 환경에서는 Docker Compose를 이용해 여러 서비스를 함께 관리

```bash
docker compose -f docker-compose.yaml --profile prod up -d
```

AI 서버는 별도의 Compose 파일을 사용

```bash
docker compose -f docker-compose.ai.yml --profile ai up -d
```

---

### 2.4. Health Check

배포가 완료된 후 서비스가 정상적으로 동작하는지 확인

```bash
curl https://yoomangju.kr/api/health
curl https://yoomangju.kr/ai/health
```

정상적으로 응답하지 않으면 배포 실패로 판단하고 후속 처리 수행

---

### 2.5. Rollback

Docker Image에 Build Number와 Git Commit 정보를 포함한 Tag를 사용하여 이전 버전 식별 가능

```plain text
현재
100-321c162

이전
99-8a72f31
```

새로운 버전 배포 후 Health Check가 실패하면 이전 Image Tag를 사용하여 Rollback

```plain text
New Image Deploy
       ↓
Health Check
       ↓
   ┌───┴───┐
   ↓       ↓
 성공     실패
   ↓       ↓
 완료    이전 Image
          ↓
       Rollback
```

## 3️⃣ Docker Compose를 이용한 환경 구성 (내 방식 추천x)

Docker Compose를 사용하여 애플리케이션과 인프라를 컨테이너 단위로 관리

### 3.1. 주요 Compose 파일

| 파일 | 용도 |
| --- | --- |
| `docker-compose.yaml` | 기본 서비스 및 운영 환경 |
| `docker-compose.ai.yml` | AI 서버 운영 환경 |
| `docker-compose.override.yml` | 로컬 개발 환경 |

### 3.2. 로컬 개발 환경 분리

유망주는 **로컬 개발 환경과 운영 환경의 실행 방식을 분리**하여 구성

- Backend / Frontend → 로컬에서 직접 실행

- MySQL / Redis / MongoDB 등 인프라 → Docker Compose로 실행

- phpMyAdmin 등 개발용 관리 도구 → Docker Compose의 `dev` 프로필로 실행

- Spring Boot 로컬 설정 → `local` 프로필 사용

### 3.2.1. Docker Compose 프로필을 이용한 개발용 서비스 분리

`docker-compose.yaml`에서는 운영에 필요하지 않은 개발용 서비스를 Docker Compose의 `dev` 프로필로 분리

예를 들어 phpMyAdmin은 다음과 같이 설정

```yaml
yoomang-phpmyadmin:
  image: phpmyadmin:latest
  container_name: yoomang_phpmyadmin
  restart: always
  depends_on:
    - yoomang-mysql
  ports:
    - "28082:80"
  environment:
    PMA_HOST: yoomang-mysql
    PMA_PORT: 3306
    PMA_ARBITRARY: 0
    TZ: ${TZ}
  networks:
    - yoomang-net
  profiles: ["dev"]
```

따라서 Docker Compose에서 `dev` 프로필을 활성화하면 개발용 서비스도 함께 실행

```bash
docker compose --profile dev up -d
```

### 3.2.2. Docker Network 구성

Docker 컨테이너들은 `yoomang-net` 네트워크에 연결하여 컨테이너 간 통신이 가능하도록 구성

```plain text
yoomang-net

MySQL
Redis
MongoDB
phpMyAdmin
...
```

컨테이너 간 통신에서는 서비스 이름을 Host로 사용할 수 있음

```plain text
yoomang-mysql:3306
yoomang-redis:6379
yoomang-mongodb:27017
```

반면 IntelliJ에서 직접 실행하는 Backend는 Docker Container가 아니므로 `yoomang-net`에 직접 연결되지 않음.

따라서 로컬에서 실행하는 Backend가 Docker 컨테이너의 DB와 Redis 등에 접근할 수 있도록 필요한 포트를 호스트에 연결

```yaml
yoomang-mysql:
  ports:
    - "127.0.0.1:3306:3306"

yoomang-redis:
  ports:
    - "127.0.0.1:6379:6379"

yoomang-mongodb:
  ports:
    - "127.0.0.1:27017:27017"
```

결과적으로 로컬 Backend에서는 다음과 같이 접근

```plain text
Spring Boot
(로컬 실행)
      │
      ├── 127.0.0.1:3306  → Docker MySQL
      ├── 127.0.0.1:6379  → Docker Redis
      └── 127.0.0.1:27017 → Docker MongoDB
```

### 3.2.3. `application-local.yml`을 이용한 Spring Boot 로컬 설정

Spring Boot는 `local` 프로필을 사용하여 로컬 개발 환경에 필요한 설정을 별도로 관리

IntelliJ 실행 설정에서 다음과 같이 `local` 프로필을 활성화

```plain text
-Dspring.profiles.active=local
```

그러면 Spring Boot 실행 시:

```plain text
application.yml
      +
application-local.yml
      ↓
local 프로필 설정 적용
```

`application-local.yml`에서는 로컬 PC에서 실행되는 Backend가 Docker 컨테이너의 인프라에 접근하도록 `127.0.0.1`을 사용

```yaml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/${MYSQL_DATABASE}

  data:
    mongodb:
      uri: mongodb://${MONGO_ROOT_USERNAME}:${MONGO_ROOT_PASSWORD}@127.0.0.1:27017/${MONGO_INITDB_DATABASE}?authSource=admin

    redis:
      host: 127.0.0.1
      password: ***
```

또한 Spring Boot의 Docker Compose 연동 기능을 활성화

```yaml
spring:
  docker:
    compose:
      enabled: true
      file:
        - docker-compose.yaml
        - docker-compose.override.yaml
```

이를 통해 로컬 Spring Boot 실행 환경과 Docker Compose 기반 인프라를 함께 사용할 수 있도록 구성

### 3.2.4. `docker-compose.override.yml`을 이용한 로컬 환경 설정

`docker-compose.override.yml`을 별도로 두어 로컬 환경에서 필요한 Compose 설정을 추가하거나 덮어쓸 수 있도록 구성

```yaml
services:
  yoomang-backend:
    build: ./be
    image: yoomang-be-local

  nginx:
    build: ./fe
    image: yoomang-fe-local

  yoomang-mysql:
    ports:
      - "127.0.0.1:3306:3306"

  yoomang-redis:
    ports:
      - "127.0.0.1:6379:6379"

  yoomang-mongodb:
    ports:
      - "127.0.0.1:27017:27017"
```

이 설정을 통해 Docker Compose를 이용해 로컬 환경 전체를 구성할 수 있는 기반을 마련하고, DB·Redis·MongoDB 등의 포트를 로컬 호스트에 연결

> 실제 개발에서는 Backend와 Frontend를 이 Compose 설정으로 실행하기보다 **IntelliJ와 npm을 이용해 로컬에서 직접 실행**하는 방식으로 사용

### 3.2.5. 실제 로컬 개발 방식

실제 개발 과정에서는 코드 변경과 디버깅이 편리하도록 Backend와 Frontend를 로컬에서 직접 실행하고, 인프라만 Docker로 실행

```plain text
┌─────────────────────────────────────────────┐
│                  로컬 PC                    │
│                                             │
│  IntelliJ                  npm              │
│     │                       │               │
│     ↓                       ↓               │
│ Spring Boot               React             │
│ Backend                  Frontend           │
│     │                                       │
│     │ localhost                             │
│     ↓                                       │
│  ┌─────────────────────────────────────┐    │
│  │          Docker Compose             │    │
│  │                                     │    │
│  │ MySQL   Redis   MongoDB             │    │
│  │ phpMyAdmin 등 개발용 서비스          │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

Backend

IntelliJ에서 Spring Boot 애플리케이션을 직접 실행

```plain text
Spring Boot
└── local profile
    └── application-local.yml
```

Frontend

React 프로젝트를 로컬에서 npm 명령어로 실행

```bash
npm install
npm run dev
```

Infrastructure

DB 및 캐시, 개발용 관리 도구 등은 Docker Compose로 실행

```bash
docker compose --profile dev up -d
```

따라서 개발 중에는 소스 코드를 수정한 후 Backend와 Frontend를 즉시 재실행하거나 Hot Reload를 활용하고, DB·Redis·MongoDB 등의 실행 환경은 Docker로 통일하여 사용

## 4️⃣ AI 환경을 별도로 분리

AI 서버는 Backend와 별도의 FastAPI 애플리케이션으로 구성되어 있으며, 배포 환경도 별도로 관리

### 4.1. 별도 Jenkins Job 구성

AI 개발 환경과 Backend 개발 환경의 Branch 및 환경 설정이 달라 별도의 Jenkins Job으로 관리

```plain text
Backend / Frontend
        ↓
   Jenkins Job
        ↓
 yoomang-env
        ↓
docker-compose.yaml


AI Server
        ↓
   Jenkins Job
        ↓
yoomang-env-ai
        ↓
docker-compose.ai.yml
```

### 4.2. 환경 변수 분리

Jenkins Credentials에 환경 변수를 각각 등록

```plain text
yoomang-env
yoomang-env-ai
```

이를 통해 Backend / Frontend와 AI 서버의 환경 설정을 분리

## 5️⃣ 무중단 배포 검토

프로젝트에서 배포 중 서비스 중단을 줄이기 위해 무중단 배포 방식도 검토

대표적인 방식

- Rolling Deployment

- Blue-Green Deployment

하지만 프로젝트 규모와 배포 상황을 고려하여 별도의 무중단 배포 구조는 적용하지 않음

- Build 시간이 긴 AI 서버가 존재

- 동시에 여러 Pipeline을 실행할 경우 Build 충돌 가능성 존재

- 팀원의 Merge 상황을 확인하면서 Pipeline을 순차적으로 실행

- 프로젝트 후반부에는 별도의 배포 전략을 추가하기보다 현재 CI/CD 구조를 유지

따라서 최종적으로는 **Jenkins + Docker + Docker Compose 기반의 배포 구조와 Health Check / Rollback을 적용**
