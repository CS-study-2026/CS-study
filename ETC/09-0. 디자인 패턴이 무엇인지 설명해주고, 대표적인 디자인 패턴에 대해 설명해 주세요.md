# 9-0. 디자인 패턴이 무엇인지 설명해주고, 대표적인 디자인 패턴에 대해 설명해 주세요.

# 1. 디자인 패턴이란?

### 한 문장 정의

- 자주 만나는 설계 문제에 대한, 이름 붙은 모범 답안

### 비유로 이해하기

디자인 패턴은 요리의 **레시피**와 비슷합니다.

- "볶음밥" 레시피를 알면, 집집마다 재료는 달라도 만드는 **방식**은 같습니다.

- 마찬가지로 "싱글톤 패턴"을 알면, 프로젝트마다 코드는 달라도 **해결 방식**은 같습니다.

- 디자인 패턴은 **복붙하는 코드(라이브러리)가 아니라 설계 아이디어**입니다.

### 왜 사용할까?

- **재사용성**: 이미 검증된 방법이라 시행착오를 줄일 수 있습니다.

- **유지보수성**: 변경에 유연한 구조가 되어 기능 추가와 수정이 쉬워집니다.

- **의사소통**: "여기 옵저버 패턴 쓰자" 한마디로 설계 의도가 전달됩니다.

### 주의할 점

- 패턴은 수단이지 목적이 아닙니다. 문제가 없는데 억지로 적용하면 코드만 복잡해집니다.

- 대부분의 패턴은 OOP의 **SOLID 원칙**(특히 개방-폐쇄 원칙, 의존 역전 원칙)을 실천하는 방법입니다.

### 배경 지식: GoF

1994년 에릭 감마 등 4명의 저자(Gang of Four)가 쓴 『Design Patterns』에서 23가지 패턴을 정리했고, 지금 말하는 디자인 패턴은 대부분 이 책에서 나왔습니다.

# 2. 디자인 패턴의 분류

| 분류 | 한마디로 | 대표 패턴 |
| --- | --- | --- |
| **생성 패턴** (Creational) | 객체를 **어떻게 만들지** | 싱글톤, 팩토리 메서드, 빌더 |
| **구조 패턴** (Structural) | 클래스와 객체를 **어떻게 조립할지** | 어댑터, 데코레이터, 프록시 |
| **행위 패턴** (Behavioral) | 객체끼리 **어떻게 일을 나누고 소통할지** | 전략, 옵저버, 템플릿 메서드 |

### [생성] 싱글톤 패턴 (Singleton)

**문제 상황**

설정 정보나 DB 커넥션 풀처럼 프로그램 전체에서 **딱 하나만** 있어야 하는 객체가 있습니다. `new`를 여러 번 하면 객체가 여러 개 생겨 메모리 낭비나 데이터 불일치가 생깁니다.

**해결 아이디어**

  - 생성자를 `private`으로 막아 외부에서 `new`를 못 하게 합니다.

  - 클래스 안에 유일한 인스턴스를 만들어 두고, `getInstance()`로만 꺼내 쓰게 합니다.

```java
public class Settings {
    // 1. 클래스가 로딩될 때 단 하나의 인스턴스를 만든다
    private static final Settings INSTANCE = new Settings();

    // 2. 외부에서 new Settings()를 못 하도록 막는다
    private Settings() {}

    // 3. 항상 같은 인스턴스를 돌려준다
    public static Settings getInstance() {
        return INSTANCE;
    }
}

// 사용
Settings a = Settings.getInstance();
Settings b = Settings.getInstance();
System.out.println(a == b); // true (같은 객체)
```

  - **실제 사용 예**: Spring의 Bean(기본이 싱글톤), `Runtime.getRuntime()`

  - **장점**: 메모리 절약, 어디서든 같은 객체에 접근 가능

  - **단점**: 전역 상태처럼 쓰여 결합도가 높아지고 테스트가 어렵습니다. 멀티스레드 환경에서 잘못 구현하면 인스턴스가 2개 생길 수 있습니다.

### [생성] 팩토리 메서드 패턴 (Factory Method)

**문제 상황**

코드 곳곳에서 `new KakaoPay()`, `new NaverPay()`처럼 구체 클래스를 직접 생성하면, 결제 수단이 추가될 때마다 그 코드를 전부 찾아 고쳐야 합니다.

**해결 아이디어**

객체를 **만드는 일**을 별도의 메서드(공장)에 맡기고, 사용하는 쪽은 **인터페이스**만 바라보게 합니다.

```java
interface Payment {
    void pay(int amount);
}

class KakaoPay implements Payment {
    public void pay(int amount) { System.out.println("카카오페이 결제: " + amount); }
}

class NaverPay implements Payment {
    public void pay(int amount) { System.out.println("네이버페이 결제: " + amount); }
}

// 객체 생성을 전담하는 공장
class PaymentFactory {
    public static Payment create(String type) {
        return switch (type) {
            case "kakao" -> new KakaoPay();
            case "naver" -> new NaverPay();
            default -> throw new IllegalArgumentException("지원하지 않는 결제 수단");
        };
    }
}

// 사용: 구체 클래스를 몰라도 된다
Payment payment = PaymentFactory.create("kakao");
payment.pay(10000);
```

> 참고: 위 예시는 이해를 돕기 위한 "간단한 팩토리" 형태입니다. GoF의 정식 팩토리 메서드는 **생성 메서드를 추상 메서드로 두고, 하위 클래스가 어떤 객체를 만들지 결정**하는 방식입니다.

  - **실제 사용 예**: `Calendar.getInstance()`, `List.of()`, Spring의 `BeanFactory`

  - **장점**: 생성 코드가 한곳에 모여, 새 타입을 추가해도 사용하는 코드를 고치지 않아도 됩니다.

  - **단점**: 클래스 수가 늘어납니다.

### [생성] 빌더 패턴 (Builder)

**문제 상황**

필드가 많은 객체를 생성자로 만들면 `new User("kim", 25, null, null, "seoul", true)`처럼 **어떤 값이 어떤 필드인지** 알아보기 어렵습니다.

**해결 아이디어**

값을 하나씩 **이름 붙여** 설정한 뒤 마지막에 `build()`로 완성합니다.

```java
public class User {
    private final String name;
    private final int age;
    private final String city;

    private User(Builder builder) {
        this.name = builder.name;
        this.age = builder.age;
        this.city = builder.city;
    }

    public static class Builder {
        private String name;
        private int age;
        private String city;

        public Builder name(String name) { this.name = name; return this; }
        public Builder age(int age) { this.age = age; return this; }
        public Builder city(String city) { this.city = city; return this; }
        public User build() { return new User(this); }
    }
}

// 사용: 어떤 값이 무엇인지 한눈에 보인다
User user = new User.Builder()
        .name("kim")
        .age(25)
        .city("seoul")
        .build();
```

  - **실제 사용 예**: `StringBuilder`, Lombok의 `@Builder`

  - **장점**: 가독성이 좋고, 필요한 값만 골라 설정할 수 있으며, 불변 객체를 만들기 쉽습니다.

  - **단점**: 코드량이 늘어납니다(Lombok으로 해결 가능).

### [구조] 어댑터 패턴 (Adapter)

**문제 상황**

우리 시스템은 `Printer` 인터페이스를 쓰는데, 새로 가져온 외부 라이브러리는 메서드 이름과 형식이 달라 그대로 끼울 수 없습니다.

**해결 아이디어**

해외여행 때 쓰는 돼지코(변환 어댑터)처럼, 중간에서 인터페이스를 맞춰 주는 클래스를 만듭니다.

```java
// 우리 시스템이 사용하는 인터페이스
interface Printer {
    void print(String text);
}

// 수정할 수 없는 외부 라이브러리 클래스
class OldPrinter {
    public void printOld(String text) {
        System.out.println("[구형 프린터] " + text);
    }
}

// 어댑터: OldPrinter를 Printer 형식으로 감싼다
class PrinterAdapter implements Printer {
    private final OldPrinter oldPrinter;

    public PrinterAdapter(OldPrinter oldPrinter) {
        this.oldPrinter = oldPrinter;
    }

    @Override
    public void print(String text) {
        oldPrinter.printOld(text); // 호출을 변환해서 전달
    }
}

// 사용
Printer printer = new PrinterAdapter(new OldPrinter());
printer.print("hello");
```

  - **실제 사용 예**: `Arrays.asList()`(배열 → List), `InputStreamReader`(바이트 스트림 → 문자 스트림), Spring MVC의 `HandlerAdapter`

  - **장점**: 기존 코드를 수정하지 않고 호환되지 않는 클래스를 함께 쓸 수 있습니다.

  - **단점**: 중간 클래스가 하나 더 생깁니다.

### [구조] 데코레이터 패턴 (Decorator)

**문제 상황**

커피에 우유 추가, 시럽 추가, 우유+시럽 추가... 조합마다 클래스를 만들면 `MilkSyrupCoffee` 같은 클래스가 폭발적으로 늘어납니다.

**해결 아이디어**

원본 객체를 **포장지처럼 감싸서** 기능을 하나씩 덧붙입니다. 포장은 몇 겹이든 겹칠 수 있습니다.

```java
interface Coffee {
    int cost();
    String description();
}

class BasicCoffee implements Coffee {
    public int cost() { return 3000; }
    public String description() { return "커피"; }
}

// 데코레이터: Coffee를 감싸면서 자신도 Coffee다
class MilkDecorator implements Coffee {
    private final Coffee coffee;
    public MilkDecorator(Coffee coffee) { this.coffee = coffee; }
    public int cost() { return coffee.cost() + 500; }
    public String description() { return coffee.description() + " + 우유"; }
}

class SyrupDecorator implements Coffee {
    private final Coffee coffee;
    public SyrupDecorator(Coffee coffee) { this.coffee = coffee; }
    public int cost() { return coffee.cost() + 300; }
    public String description() { return coffee.description() + " + 시럽"; }
}

// 사용: 원하는 만큼 겹쳐서 감싼다
Coffee coffee = new SyrupDecorator(new MilkDecorator(new BasicCoffee()));
System.out.println(coffee.description()); // 커피 + 우유 + 시럽
System.out.println(coffee.cost());        // 3800
```

  - **실제 사용 예**: Java I/O의 `new BufferedReader(new InputStreamReader(System.in))`

  - **장점**: 상속 없이 실행 중에 기능을 자유롭게 조합할 수 있습니다.

  - **단점**: 작은 객체가 여러 겹 생겨 디버깅이 어려울 수 있습니다.

### [구조] 프록시 패턴 (Proxy)

**문제 상황**

실제 객체를 쓰기 전후로 권한 체크, 로깅, 캐싱, 지연 로딩 같은 부가 작업을 하고 싶은데, 실제 객체 코드는 건드리고 싶지 않습니다.

**해결 아이디어**

실제 객체와 **같은 인터페이스**를 가진 대리인(Proxy)을 앞에 세워, 요청을 대신 받아 처리한 뒤 실제 객체에 넘깁니다.

```java
interface Image {
    void display();
}

class RealImage implements Image {
    private final String file;
    public RealImage(String file) {
        this.file = file;
        System.out.println("무거운 이미지 로딩: " + file);
    }
    public void display() { System.out.println("이미지 표시: " + file); }
}

// 프록시: 실제로 필요할 때까지 로딩을 미룬다 (지연 로딩)
class ImageProxy implements Image {
    private final String file;
    private RealImage realImage;

    public ImageProxy(String file) { this.file = file; }

    public void display() {
        if (realImage == null) {
            realImage = new RealImage(file); // 처음 사용할 때만 생성
        }
        realImage.display();
    }
}
```

  - **실제 사용 예**: Spring AOP(`@Transactional`), JPA의 지연 로딩(Lazy Loading)

  - **장점**: 실제 객체를 수정하지 않고 접근 제어와 부가 기능을 추가할 수 있습니다.

  - **단점**: 한 단계를 더 거치므로 구조가 복잡해질 수 있습니다.

### [행위] 전략 패턴 (Strategy)

**문제 상황**

할인 방식이 "정액 할인", "정률 할인" 등으로 늘어날 때마다 `if-else`가 길어지고, 기존 코드를 매번 고쳐야 합니다.

**해결 아이디어**

바뀌는 부분(알고리즘)을 **인터페이스로 분리**해서, 실행 중에 **갈아끼울 수 있게** 합니다. 게임 캐릭터가 무기를 바꿔 드는 것과 비슷합니다.

```java
interface DiscountStrategy {
    int apply(int price);
}

class FixedDiscount implements DiscountStrategy {
    public int apply(int price) { return price - 1000; }
}

class RateDiscount implements DiscountStrategy {
    public int apply(int price) { return (int) (price * 0.8); }
}

class Order {
    private DiscountStrategy strategy;

    public Order(DiscountStrategy strategy) { this.strategy = strategy; }
    public void setStrategy(DiscountStrategy strategy) { this.strategy = strategy; }

    public int finalPrice(int price) {
        return strategy.apply(price); // 어떤 전략인지 몰라도 된다
    }
}

// 사용
Order order = new Order(new FixedDiscount());
System.out.println(order.finalPrice(10000)); // 9000
order.setStrategy(new RateDiscount());
System.out.println(order.finalPrice(10000)); // 8000
```

  - **실제 사용 예**: `Collections.sort(list, comparator)`의 `Comparator`

  - **장점**: 새 전략을 추가해도 기존 코드를 수정하지 않습니다(개방-폐쇄 원칙). `if-else` 분기가 사라집니다.

  - **단점**: 전략 클래스가 많아지고, 사용하는 쪽이 어떤 전략이 있는지 알아야 합니다.

### [행위] 옵저버 패턴 (Observer)

**문제 상황**

유튜브 채널에 새 영상이 올라오면 구독자 모두에게 알림을 보내야 합니다. 구독자가 계속 "새 영상 있어요?"라고 물어보는 건 비효율적입니다.

**해결 아이디어**

관찰 대상(Subject)이 구독자(Observer) 목록을 가지고 있다가, **상태가 바뀌면 직접 알려줍니다**. "구독과 알림" 구조입니다.

```java
import java.util.ArrayList;
import java.util.List;

interface Subscriber {
    void update(String videoTitle);
}

class User implements Subscriber {
    private final String name;
    public User(String name) { this.name = name; }
    public void update(String videoTitle) {
        System.out.println(name + "님, 새 영상: " + videoTitle);
    }
}

class Channel {
    private final List<Subscriber> subscribers = new ArrayList<>();

    public void subscribe(Subscriber s) { subscribers.add(s); }
    public void unsubscribe(Subscriber s) { subscribers.remove(s); }

    public void upload(String title) {
        for (Subscriber s : subscribers) {
            s.update(title); // 모든 구독자에게 알림
        }
    }
}

// 사용
Channel channel = new Channel();
channel.subscribe(new User("철수"));
channel.subscribe(new User("영희"));
channel.upload("디자인 패턴 정리");
```

  - **실제 사용 예**: 이벤트 리스너(버튼 클릭 등), Spring의 `ApplicationEvent`, MVC에서 Model → View 갱신

  - **장점**: 주체와 구독자가 느슨하게 연결되어, 구독자를 자유롭게 추가·제거할 수 있습니다.

  - **단점**: 알림 순서를 보장하기 어렵고, 구독 해제를 잊으면 메모리 누수가 생길 수 있습니다.

### [행위] 템플릿 메서드 패턴 (Template Method)

**문제 상황**

커피와 차를 만드는 과정은 "물 끓이기 → 우리기 → 컵에 따르기 → 첨가물 넣기"로 순서가 같고, 일부 단계만 다릅니다. 두 클래스에 같은 코드가 중복됩니다.

**해결 아이디어**

전체 **순서(뼈대)는 부모 클래스에 고정**하고, 달라지는 단계만 자식 클래스가 구현하게 합니다.

```java
abstract class Beverage {
    // 템플릿 메서드: 순서를 고정 (final로 오버라이드 금지)
    public final void make() {
        boilWater();
        brew();
        pourInCup();
        addCondiments();
    }

    private void boilWater() { System.out.println("물 끓이기"); }
    private void pourInCup() { System.out.println("컵에 따르기"); }

    // 자식이 구현할 단계
    protected abstract void brew();
    protected abstract void addCondiments();
}

class Coffee extends Beverage {
    protected void brew() { System.out.println("커피 내리기"); }
    protected void addCondiments() { System.out.println("설탕 넣기"); }
}

class Tea extends Beverage {
    protected void brew() { System.out.println("찻잎 우리기"); }
    protected void addCondiments() { System.out.println("레몬 넣기"); }

new Coffee().make();
```

# 5. 면접 질문 대비

**Q. 디자인 패턴이 무엇인지 설명해주고, 대표적인 디자인 패턴에 대해 설명해 주세요.**

디자인 패턴은 소프트웨어를 설계할 때 자주 반복되는 문제들에 대해, 선배 개발자들이 검증해 둔 **해결 방법의 틀**입니다. GoF(Gang of Four)가 정리한 23가지 패턴이 가장 유명하며, 목적에 따라 **생성 / 구조 / 행위** 패턴으로 나뉩니다. 대표적으로 객체를 하나만 만드는 **싱글톤**, 객체 생성을 대신해 주는 **팩토리**, 알고리즘을 갈아끼울 수 있게 하는 **전략**, 상태 변화를 여러 객체에 알려주는 **옵저버** 패턴 등이 있습니다.

**Q. 멀티스레드 환경에서 싱글톤을 안전하게 만드는 방법은?**

`getInstance()` 안에서 `if (instance == null) instance = new ...`처럼 늦게 생성하면, 두 스레드가 동시에 들어와 인스턴스가 2개 생길 수 있습니다. 해결 방법은 ① 클래스 로딩 시점에 미리 생성(Eager), ② `synchronized` 사용(성능 저하), ③ `volatile` + Double-Checked Locking, ④ **정적 내부 클래스(Holder) 방식**, ⑤ **enum 싱글톤**이 있고, 실무에서는 ④나 ⑤를 많이 권장합니다.

**Q. 전략 패턴과 템플릿 메서드 패턴의 차이는?**

둘 다 "바뀌는 알고리즘을 분리"하지만, 템플릿 메서드는 **상속**으로 일부 단계를 바꾸고, 전략은 조합(인터페이스 주입)으로 알고리즘 전체를 갈아끼웁니다. 전략은 실행 중에도 교체할 수 있어 더 유연합니다.

**Q. 데코레이터와 프록시의 차이는?**

같은 인터페이스로 감싸는 구조는 거의 같지만 **목적**이 다릅니다. 데코레이터는 **기능을 덧붙이는 것**, 프록시는 **접근을 제어하는 것**(지연 로딩, 권한, 캐싱 등)이 목적입니다.

**Q. 어댑터와 데코레이터의 차이는?**

어댑터는 **인터페이스를 바꿔서** 호환되게 만들고, 데코레이터는 **인터페이스는 그대로 두고** 기능만 추가합니다.

**Q. 디자인 패턴과 SOLID 원칙의 관계는?**

SOLID가 "좋은 설계의 원칙"이라면, 디자인 패턴은 그 원칙을 지키는 "구체적인 방법"입니다. 예를 들어 전략 패턴은 개방-폐쇄 원칙(OCP)을, 팩토리 패턴은 의존 역전 원칙(DIP)을 실천합니다.
