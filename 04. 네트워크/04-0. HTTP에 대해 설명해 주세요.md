# 4-0. HTTP에 대해 설명해 주세요.

## **HTTP란?**

> HTTP(HyperText Transfer Protocol)는

**클라이언트와 서버가 웹에서 데이터를 주고받기 위한 애플리케이션 계층 프로토콜**입니다.

웹 브라우저(Client)가 요청(Request)을 보내면 서버(Server)가 응답(Response)을 반환하는 **Request-Response 방식**으로 동작

```plain text
Client
   │ Request
   ▼
Server
   │ Response
   ▼
Client
```

---

# **HTTP의 주요 특징**

## **1. Stateless**

HTTP는 **서버가 클라이언트의 상태를 저장하지 않는 프로토콜**입니다.

예를 들어,

```plain text
1. 로그인 요청
2. 상품 조회 요청
3. 장바구니 조회 요청
```

이 들어오더라도 서버는

```plain text
"이 사용자가 조금 전에 로그인했었지?"
```

를 기억하지 않습니다.

모든 요청은 독립적으로 처리됩니다.

### **장점**

- 서버 확장성 향상

- 서버 메모리 사용 감소

- 장애 복구 용이

### **단점**

- 로그인 상태 유지 어려움

그래서 실제 서비스에서는

- Cookie

- Session

- JWT

등을 사용하여 상태를 관리합니다.

---

## **2. Connectionless**

HTTP는 요청과 응답이 끝나면 연결을 종료합니다.

```plain text
Request
↓
Response
↓
Connection Close
```

덕분에 많은 사용자를 효율적으로 처리할 수 있습니다.

_다만 매번 TCP 연결을 생성하면 비효율적이기 때문에 HTTP/1.1부터는 Keep-Alive를 통해 연결을 재사용합니다._

---

# **HTTP 메시지 구조**

HTTP 메시지는 크게 4부분으로 구성됩니다.

```plain text
Start Line
Headers
Blank Line
Body
```

---

## **HTTP Request 예시**

```plain text
POST /login HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 42

{
  "id":"user1",
  "pw":"1234"
}
```

---

## **1. Start Line**

첫 번째 줄로 요청의 핵심 정보를 담고 있습니다.

```plain text
POST /login HTTP/1.1
```

구성

```plain text
Method URI Version
```

### **Method**

무슨 작업을 할 것인가

```plain text
GET
POST
PUT
PATCH
DELETE
```

### **URI**

어떤 자원(Resource)을 요청하는가

```plain text
/login
```

### **Version**

HTTP 버전

```plain text
HTTP/1.1
```

---

## **2. Header**

요청 또는 응답에 대한 부가 정보(Metadata)를 담습니다.

예시

```plain text
Host: example.com
Content-Type: application/json
Authorization: Bearer xxx
Cookie: JSESSIONID=ABC123
```

대표 Header

| **Header** | **역할** |
| --- | --- |
| Host | 요청 대상 서버 |
| Content-Type | Body 데이터 형식 |
| Content-Length | Body 크기 |
| Authorization | 인증 정보 |
| Cookie | 쿠키 정보 |

---

## **3. Blank Line**

Header와 Body를 구분하는 빈 줄입니다.

```plain text
Content-Type: application/json

{
  "id":"user1"
}
```

서버는

```plain text
빈 줄 전 = Header
빈 줄 후 = Body
```

로 해석합니다.

---

## **4. Body**

실제 전송 데이터가 들어가는 부분입니다.

예시

### **JSON**

```json
{
  "name":"Kim"
}
```

### **HTML**

```html
<html>
<body>Hello</body>
</html>
```

### **이미지**

```plain text
PNG 바이너리 데이터
```

---

# **HTTP 메시지는 텍스트인가요?**

### **HTTP/1.1**

기본적으로 텍스트 기반 프로토콜입니다.

예시

```plain text
GET /users HTTP/1.1
Host: example.com
```

사람이 읽을 수 있는 형태입니다.

---

### **Body는 바이너리도 가능**

예를 들어

```plain text
Content-Type: image/png
```

이면 Body에는 이미지의 바이너리 데이터가 들어갑니다.

---

### **HTTP/2 이상**

엄밀히 말하면

```plain text
HTTP/1.0, HTTP/1.1
→ 텍스트 기반

HTTP/2, HTTP/3
→ 바이너리 프레임 기반

같은 정보를 작은 단위인 Frame(프레임) 으로 분해한 뒤,
01010101 00101010 ...
바이너리(0과 1) 형태로 전송합니다.
```

입니다.

하지만 논리적인 메시지 구조는 동일합니다.

---

# **HTTP 버전별 특징**

| **버전** | **특징** |
| --- | --- |
| HTTP/1.0 | 요청마다 TCP 연결 생성 |
| HTTP/1.1 | Keep-Alive 기본 지원 |
| HTTP/2 | 멀티플렉싱 지원 |
| HTTP/3 | QUIC(UDP 기반) 사용 |

---

# **1. TCP 연결**

TCP는 **신뢰성 있는 데이터 전송을 제공하는 전송 계층 프로토콜**입니다.

데이터가

  - 순서대로 도착하는지

  - 중간에 유실되지 않았는지

  - 중복되지 않았는지

를 보장합니다.

HTTP/1.1, HTTP/2는 TCP 위에서 동작합니다.

```plain text
HTTP
 ↓
TCP
 ↓
IP
```

### **한 줄 설명**

TCP 연결은 클라이언트와 서버가 신뢰성 있게 데이터를 주고받기 위해 맺는 연결입니다.

---

# **2. Keep-Alive**

Keep-Alive는 **한 번 생성한 TCP 연결을 여러 요청에서 재사용하는 기능**입니다.

### **HTTP/1.0**

```plain text
요청1
↓
TCP 연결 생성
↓
응답1
↓
연결 종료

요청2
↓
TCP 연결 생성
↓
응답2
↓
연결 종료
```

매번 연결 생성/종료

---

### **HTTP/1.1**

```plain text
TCP 연결 생성

요청1 → 응답1
요청2 → 응답2
요청3 → 응답3

연결 종료
```

한 번 만든 연결을 계속 사용

### **장점**

  - TCP 연결 생성 비용 감소

  - 응답 속도 향상

### **한 줄 설명**

Keep-Alive는 TCP 연결을 종료하지 않고 재사용하여 성능을 높이는 기술입니다.

---

# **3. 멀티플렉싱(Multiplexing)**

멀티플렉싱은 **하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리하는 기술**입니다.

### **HTTP/1.1**

```plain text
요청1 → 응답1

요청2 → 응답2

요청3 → 응답3
```

순차 처리

---

### **HTTP/2**

```plain text
요청1 ┐
요청2 ├ 동시에 전송
요청3 ┘

응답도 병렬 처리
```

### **장점**

  - 대기 시간 감소

  - 웹 페이지 로딩 속도 향상

### **한 줄 설명**

멀티플렉싱은 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리하는 기술입니다.

---

# **4. QUIC (UDP 기반)**

QUIC은 **Google이 개발한 차세대 전송 프로토콜**로, HTTP/3의 기반이 됩니다.

기존 HTTP는 TCP를 사용했지만

```plain text
HTTP/1.1
HTTP/2
 ↓
TCP
```

HTTP/3는

```plain text
HTTP/3
 ↓
QUIC
 ↓
UDP
```

구조를 사용합니다.

---

### **왜 만들었을까?**

TCP는 패킷 하나가 손실되면

```plain text
패킷1
패킷2
패킷3 (손실)
패킷4
```

패킷3이 복구될 때까지 뒤의 데이터도 기다려야 합니다.

이를 **HOL Blocking(Head Of Line Blocking)** 이라고 합니다.

QUIC은 이를 개선하여 더 빠르게 데이터를 전송합니다.

---

### **장점**

  - 연결 수립 속도 향상

  - 패킷 손실 영향 감소

  - HTTP/2보다 빠른 성능

### **한 줄 설명**

QUIC은 UDP 기반의 전송 프로토콜로, TCP의 지연 문제를 개선하여 HTTP/3의 성능을 높인 기술입니다.

---

# **면접용 초압축 버전**

  - **TCP 연결**: 클라이언트와 서버가 신뢰성 있게 데이터를 주고받기 위해 맺는 연결

  - **Keep-Alive**: 하나의 TCP 연결을 여러 요청에서 재사용하는 기술

  - **멀티플렉싱**: 하나의 연결에서 여러 요청과 응답을 동시에 처리하는 기술

  - **QUIC**: UDP 기반의 차세대 전송 프로토콜로, HTTP/3에서 사용되며 TCP의 지연 문제를 개선한 기술

---

### **관계도**

```plain text
HTTP/1.0
 └─ TCP 연결 매번 생성

HTTP/1.1
 └─ Keep-Alive

HTTP/2
 └─ Keep-Alive + 멀티플렉싱

HTTP/3
 └─ QUIC(UDP 기반)
```

이 흐름으로 이해하면 HTTP 버전 변화까지 한 번에 연결해서 설명할 수 있습니다.

---

# **HTTP와 HTTPS 차이**

| **HTTP** | **HTTPS** |
| --- | --- |
| 암호화 X | 암호화 O |
| 평문 전송 | SSL/TLS 사용 |
| 80 포트 | 443 포트 |

HTTPS는 HTTP 위에 SSL/TLS를 적용하여 데이터를 암호화한 프로토콜입니다.

---

# **면접 답변 예시**

HTTP는 HyperText Transfer Protocol의 약자로, 클라이언트와 서버가 웹에서 데이터를 주고받기 위한 애플리케이션 계층 프로토콜입니다.

HTTP는 요청-응답 방식으로 동작하며, 대표적인 특징으로 Stateless와 Connectionless가 있습니다. Stateless 특성 때문에 서버는 클라이언트 상태를 저장하지 않으며, 로그인 상태 유지를 위해 쿠키, 세션, JWT 등을 사용합니다.

HTTP 메시지는 Start Line, Header, Blank Line, Body로 구성됩니다. Start Line에는 요청 방식, URI, HTTP 버전이 포함되고, Header에는 Content-Type이나 Authorization과 같은 메타데이터가 포함됩니다. Body에는 실제 전송 데이터가 들어갑니다.

또한 HTTP/1.1은 Keep-Alive를 지원하여 연결을 재사용하고, HTTP/2는 멀티플렉싱을 지원하며, HTTP/3는 QUIC 기반으로 동작하여 성능을 개선했습니다.

---

# **한 줄 정리**

HTTP는 웹에서 클라이언트와 서버가 데이터를 주고받기 위한 애플리케이션 계층 프로토콜이며, Request-Response 방식으로 동작하고 Stateless, Connectionless라는 특징을 가진다. 또한 HTTP 메시지는 Start Line, Header, Blank Line, Body로 구성된다.
