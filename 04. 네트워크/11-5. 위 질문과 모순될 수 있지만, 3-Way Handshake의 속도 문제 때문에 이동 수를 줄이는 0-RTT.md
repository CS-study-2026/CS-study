# 11-5. 위 질문과 모순될 수 있지만, 3-Way Handshake의 속도 문제 때문에 이동 수를 줄이는 0-RTT 기법을 많이 적용하고 있습니다. 어떤 방식으로 가능한 걸까요?

# 0. RTT(Round Trip Time)란?

**클라이언트가 서버로 요청을 보내고, 응답을 받을 때까지 걸리는 왕복 시간**

```plain text
Client -------> Server
        요청

Client <------- Server
        응답
```

위와 같이 요청과 응답이 한 번 왕복하는 시간이 **1 RTT**

예를 들어 서울에서 미국 서버까지 편도가 150ms라면,

- 요청 : 150ms

- 응답 : 150ms

총 **1 RTT = 300ms(왕복 시간) **이며

TLS Handshake가 1 RTT라면 약 300**ms**를 기다려야 한다는 의미로,  RTT가 많아질수록 사용자는 페이지가 늦게 열린다고 느낌

⇒ 최근 프로토콜들은 **RTT를 줄이는 것**을 매우 중요하게 여기는 편

---

# 1. TCP Handshake와 TLS Handshake

0-RTT를 이해하려면 먼저 TCP와 TLS의 차이를 알아야 한다.

## TCP의 목적 : 연결 생성

TCP는

> **"우리가 통신할 준비가 되었는지 확인하자."**

가 목적이다.

3-Way Handshake 과정

```plain text
Client                  Server

SYN ------------------------>

 <-------------------- SYN + ACK

ACK ------------------------>
```

확인하는 내용은

- 상대가 살아있는가? (SYN)

- 나도 살아있다. ( SYN + ACK)

- 그럼 연결하자. ( ACK + 연결)

즉, 암호화 X / 인증 X / 키 교환 X

→ 오직 **연결 생성**만

---

## TLS의 목적 : 보안 설정

TCP 연결이 끝난 후 TLS Handshake가 수행

목적은

> **"이 연결을 안전하게 사용하자."**

TLS에서는

- 서버 인증

- 암호 알고리즘 협상

- 세션 키(Session Key) 생성

을 수행한다.

이후 HTTP 요청은 `GET /index.html`이 아니라 `암호화된 데이터`형태로 전송

---

## HTTPS 구조

`HTTPS = HTTP + TLS + TCP`이며,  HTTPS 연결 과정은 `TCP -> TLS -> HTTP 요청` 순서임

즉, 사용자는 TCP와 TLS가 모두 끝날 때까지 HTTP 요청조차 보낼 수 X

이 초기 지연을 줄이기 위해 등장한 기술이

- TCP Fast Open

- TLS 1.3 0-RTT

---

# 3. TLS 1.3의 0-RTT

## 3-1. 0-RTT란?

**Zero Round Trip Time Resumption**

TLS 1.3에서 추가된 기능으로,

**이전에 연결했던 서버라면 TLS Handshake 완료를 기다리지 않고 데이터를 먼저 보낼 수 있는 기술**

여기서 가장 중요한 점은

> **TCP를 생략하는 기술이 아니라 TLS RTT를 줄이는 기술이라는 것**

즉,

- TCP Handshake : 반드시 수행

- TLS Handshake : 일부 생략

---

## 기본 아이디어

처음 연결

```plain text
Client

↓

TLS 연결 완료

↓

Session Ticket 발급
```

서버가

```plain text
다음에 올 때 이 Ticket을 가져와.
```

라는 정보를 준다.

클라이언트는 이를 저장한다.

<details>
<summary>TLS 핸드세이크 과정 자세히</summary>

TLS 1.3 기준

```plain text
Client                                     Server

ClientHello ----------------------------->

                           <------------- ServerHello
                           <------------- Certificate
                           <------------- CertificateVerify
                           <------------- Finished

(인증서 검증)
(세션 키 생성 및 서버 Finished 검증)

Finished ------------------------------->

(Handshake 완료)

========= 이후부터 HTTP 요청 =========
```

### 각 단계에서 하는 일

### 1. ClientHello

클라이언트(브라우저)가

  - 지원하는 TLS 버전

  - 지원하는 암호 알고리즘

  - 랜덤 값(Client Random)

  - (재연결이라면) Session Ticket(PSK)

---

### 2. ServerHello

서버가

  - 사용할 TLS 버전

  - 선택한 암호 알고리즘

  - 랜덤 값(Server Random)

이 시점부터 양쪽은 키 교환에 필요한 정보를 갖게 됩니다.

---

### 3. Certificate

서버가 자신의 인증서를 보냅니다.

브라우저는

  - 신뢰할 수 있는 CA가 발급했는지

  - 인증서가 만료되지 않았는지

  - 접속한 도메인과 일치하는지

  - 폐기된 인증서가 아닌지

등을 검증합니다.

---

### 4. CertificateVerify

서버는

> **"이 인증서의 개인키를 내가 정말 가지고 있다."**

는 것을 디지털 서명으로 증명합니다.

인증서만 보내면 누구나 복사해서 보낼 수 있기 때문에, **개인키를 실제로 소유하고 있음을 증명**

---

### 5. Server Finished

서버가

> "나는 Handshake를 정상적으로 끝냈다."

이 메시지는 **세션 키로 무결성 보호**되어 있으므로, 클라이언트는 키가 올바르게 만들어졌는지 함께 확인

---

### 6. 브라우저 검증

브라우저는

  - 인증서 유효성 검사

  - 서버의 Finished 검증

  - 세션 키 생성

문제가 없으면 아래를 서버에 전송

```plain text
Client Finished
```

---

### 7. Client Finished

클라이언트도 Finished를 보내면

```plain text
TLS Handshake 완료
```

이제부터 HTTP 요청을 암호화해서 보낼 수 있습니다.

## 단점 : Replay Attack

문제는 클라이언트가 보낸 데이터를 공격자가 그대로 재전송할 수 있다는 것

예를 들어

```plain text
POST /pay
```

가 캡처되면

```plain text
POST /pay

POST /pay

POST /pay
```

를 다시 보낼 수도 있다.

= 결제가 여러 번 발생할 수 있다.

---

## 해결 방법

### ① Idempotent 요청만 허용

대표적으로

```plain text
GET

HEAD
```

만 허용

---

### ② POST는 1-RTT 강제

```plain text
POST

PUT

PATCH
```

는 TLS Handshake 완료 후 처리

---

### ③ Anti Replay

- Session Ticket

- Timestamp

- Nonce

등을 이용하여 같은 요청이면 거부

# 4. TCP Fast Open

## Fast Open이란?

TCP 연결이 끝날 때까지 기다리지 않고 **SYN 패킷에 애플리케이션 데이터를 함께 실어 보내는 기술**

기존

```plain text
SYN

↓

SYN+ACK

↓

ACK

↓

GET
```

을

```plain text
SYN

+

GET
```

으로 바꾼 것

---

## 핵심 아이디어

기존

```plain text
TCP 완료

↓

데이터
```

Fast Open

```plain text
TCP 진행 중

↓

데이터도 같이 전송
```

---

## 특징

- TCP 계층 기술

- 이전 연결에서 받은 **TFO Cookie** 사용

- TCP RTT 감소

단, TLS는 여전히 수행해야 한다.

---

# 5. TCP Fast Open vs TLS 0-RTT

| 구분 | TCP Fast Open | TLS 1.3 0-RTT |
| --- | --- | --- |
| 동작 계층 | TCP | TLS |
| 줄이는 RTT | TCP | TLS |
| 사용하는 정보 | TFO Cookie | Session Ticket(PSK) |
| 함께 보내는 것 | SYN + 데이터 | ClientHello + 데이터 |
| TCP Handshake | 진행 중 | 완료 후 |
| TLS Handshake | 그대로 수행 | 일부 생략 |

# 6. 면접 멘트

> 0-RTT는 TCP 3-Way Handshake를 없애는 기술이 아니라, TLS 1.3에서 TLS Handshake의 RTT를 줄이는 기술입니다. 이전 연결에서 서버가 발급한 Session Ticket(PSK)을 클라이언트가 저장해 두었다가 재연결 시 이를 함께 전송합니다. 그러면 TLS Handshake가 완료되기 전에 ClientHello와 함께 암호화된 애플리케이션 데이터를 먼저 보낼 수 있어 초기 지연 시간을 줄일 수 있습니다. 다만 TCP 3-Way Handshake 자체는 여전히 수행해야 하며, 0-RTT는 TLS 단계의 RTT를 줄이는 기술입니다.

- **TCP Fast Open** → **TCP 연결이 끝나기 전에 SYN과 함께 데이터를 전송하는 기술**

- **TLS 1.3 0-RTT** → **이전 세션 정보를 이용해 TLS Handshake 완료 전부터 데이터를 전송하는 기술**

- **QUIC 0-RTT** → **TCP를 제거하고 연결, 보안, 데이터 전송을 하나의 프로토콜에서 처리하는 기술**
