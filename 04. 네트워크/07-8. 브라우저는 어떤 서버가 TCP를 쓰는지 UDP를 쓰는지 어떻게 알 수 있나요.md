# 7-8. **브라우저는 어떤 서버가 TCP를 쓰는지 UDP를 쓰는지 어떻게 알 수 있나요?**

**7-8. 브라우저는 어떤 서버가 TCP를 쓰는지 UDP를 쓰는지 어떻게 알 수 있나요?**

**1. 결론부터**

브라우저는 서버에 접속한 다음 TCP인지 UDP인지 알아내는 것이 아닙니다.

브라우저는 접속하기 전에 다음 정보를 바탕으로 어떤 전송 프로토콜을 사용할지 결정합니다.

1. URL의 스킴

2. 해당 애플리케이션 프로토콜의 표준

3. 기본 포트 또는 URL에 명시된 포트

4. TLS의 ALPN 협상 결과

5. 서버가 이전 응답에서 제공한 Alt-Svc 정보

6. DNS의 HTTPS 레코드

7. 브라우저가 이전 연결에서 저장한 정보

즉, TCP와 UDP 중 무엇을 사용할지는 서버의 IP 주소만 보고 판단하는 것이 아니라, 사용하려는 애플리케이션 프로토콜과 서버가 제공한 연결 정보를 기반으로 결정합니다.

⸻

**2. IP 주소와 포트만으로 TCP와 UDP를 구분할 수 있나요?**

IP 주소만으로는 구분할 수 없습니다.

203.0.113.10

이 주소는 서버의 위치를 나타낼 뿐, 해당 서버가 TCP를 쓰는지 UDP를 쓰는지는 알려주지 않습니다.

포트 번호도 그 자체만으로는 완전한 답이 아닙니다.

예를 들어 443번 포트는 일반적으로 HTTPS에 사용되지만 다음 두 형태가 모두 가능합니다.

TCP 443

→ HTTPS의 HTTP/1.1 또는 HTTP/2

UDP 443

→ QUIC을 사용하는 HTTP/3

TCP와 UDP는 각각 별도의 포트 공간을 사용하므로, 하나의 서버가 같은 숫자의 포트를 두 프로토콜에서 동시에 사용할 수 있습니다.

TCP 443에서 대기하는 서버 소켓

UDP 443에서 대기하는 서버 소켓

→ 동시에 존재 가능

따라서 정확한 통신 대상은 단순히 포트 번호만으로 구분되지 않습니다.

개념적으로 다음 정보가 함께 필요합니다.

전송 프로토콜 + IP 주소 + 포트 번호

예를 들어 다음 둘은 서로 다른 엔드포인트입니다.

TCP / 203.0.113.10 / 443

UDP / 203.0.113.10 / 443

⸻

**3. 애플리케이션 프로토콜의 표준이 전송 방식을 정한다**

보통 어떤 애플리케이션 프로토콜을 사용할지는 미리 정해져 있습니다.

예를 들어 전통적인 HTTPS는 다음 구조를 사용합니다.

HTTP/1.1 또는 HTTP/2

↓

TLS

↓

TCP

↓

IP

HTTP/3는 다음 구조를 사용합니다.

HTTP/3

↓

QUIC

↓

UDP

↓

IP

따라서 브라우저가 HTTP/2를 사용하기로 했다면 TCP 연결을 만들고, HTTP/3를 사용하기로 했다면 UDP 위에서 QUIC 연결을 만듭니다.

브라우저가 TCP와 UDP 중 아무거나 임의로 골라 같은 방식으로 데이터를 보내는 것은 아닙니다.

⸻

**4. URL은 어떤 정보를 주나요?**

사용자가 다음 주소에 접속한다고 하겠습니다.

https://example.com

브라우저는 URL의 https 스킴을 보고 다음 사실을 알 수 있습니다.

HTTP 의미를 사용하는 보안 연결이 필요하다.

기본 포트는 443이다.

서버 인증과 암호화가 필요하다.

하지만 https만 보고 HTTP/2인지 HTTP/3인지까지 확정되는 것은 아닙니다.

같은 HTTPS 주소라도 실제 연결은 다음 중 하나가 될 수 있습니다.

HTTPS over HTTP/1.1 + TLS + TCP

HTTPS over HTTP/2 + TLS + TCP

HTTPS over HTTP/3 + QUIC + UDP

즉, URL은 서비스의 큰 종류와 기본 포트를 알려주지만, 세부 HTTP 버전과 전송 방식은 추가적인 협상 또는 발견 과정으로 결정될 수 있습니다.

⸻

**5. HTTP/1.1과 HTTP/2는 어떻게 구분하나요?**

HTTP/1.1과 HTTP/2는 둘 다 일반적으로 TCP 위에서 동작합니다.

브라우저는 먼저 TCP 연결을 만들고 TLS Handshake를 진행하면서 **ALPN**을 사용해 어떤 애플리케이션 프로토콜을 사용할지 협상할 수 있습니다.

ALPN은 Application-Layer Protocol Negotiation의 약자입니다.

클라이언트는 자신이 지원하는 프로토콜을 서버에 알립니다.

브라우저가 제안:

h2

http/1.1

서버는 자신이 지원하는 것 중 하나를 선택합니다.

서버가 선택:

h2

여기서 대표적인 식별자는 다음과 같습니다.

h2

→ HTTP/2

http/1.1

→ HTTP/1.1

따라서 HTTP/1.1과 HTTP/2 중 무엇을 사용할지는 TLS 연결 과정에서 협상할 수 있습니다.

중요한 점은 ALPN이 TCP냐 UDP냐를 직접 시험하는 절차라기보다는, 만들어진 보안 연결에서 어떤 애플리케이션 프로토콜을 사용할지 합의하는 장치라는 것입니다.

⸻

**6. HTTP/3는 어떻게 발견하나요?**

HTTP/3는 TCP가 아니라 QUIC과 UDP를 사용합니다.

따라서 이미 만들어진 TCP 연결 안에서 HTTP/2 대신 HTTP/3로 단순히 바꾸는 구조는 아닙니다.

브라우저는 서버가 HTTP/3를 지원한다는 사실을 별도로 알아야 합니다.

대표적인 방법은 다음과 같습니다.

1. Alt-Svc 응답 헤더

2. DNS HTTPS 레코드

3. 이전 연결에서 저장해둔 HTTP/3 지원 정보

⸻

**6-1. Alt-Svc**

서버가 HTTP/1.1 또는 HTTP/2 응답에서 다음과 비슷한 정보를 보낼 수 있습니다.

Alt-Svc: h3=":443"; ma=86400

의미를 단순화하면 다음과 같습니다.

이 서버는 HTTP/3도 지원합니다.

UDP 443번 포트를 통해 접속할 수 있습니다.

이 정보는 일정 시간 동안 기억해도 됩니다.

처음 접속에서는 브라우저가 TCP 기반 HTTP/1.1 또는 HTTP/2를 사용했더라도, 이 정보를 받은 뒤 다음 연결부터 HTTP/3를 시도할 수 있습니다.

첫 접속:

브라우저

→ TCP 443 연결

→ HTTP/2 사용

← Alt-Svc: HTTP/3 지원

다음 접속:

브라우저

→ UDP 443으로 QUIC/HTTP/3 연결 시도

즉, 서버가 “나는 HTTP/3도 지원한다”고 브라우저에게 알려주는 방식입니다.

⸻

**6-2. DNS HTTPS 레코드**

일반적인 DNS의 A 또는 AAAA 레코드는 주로 도메인에 대응하는 IP 주소를 알려줍니다.

example.com

→ 203.0.113.10

하지만 HTTPS DNS 레코드는 연결에 필요한 추가 정보를 제공할 수 있습니다.

예를 들어 개념적으로 다음과 같은 정보를 포함할 수 있습니다.

이 서비스가 지원하는 애플리케이션 프로토콜

대체 포트

대체 서버 주소

HTTP/2 또는 HTTP/3 지원 정보

이를 통해 브라우저는 첫 HTTP 응답을 받기 전에도 서버가 HTTP/3를 지원한다는 사실을 알 수 있습니다.

다만 실제 사용 여부는 브라우저, DNS 서버, 네트워크 환경 및 서버 설정에 따라 달라집니다.

⸻

**6-3. 이전 접속 정보**

브라우저는 이전에 해당 서버로부터 받은 Alt-Svc 정보를 일정 기간 저장할 수 있습니다.

example.com은 HTTP/3를 지원한다.

UDP 443으로 연결할 수 있다.

따라서 같은 사이트에 다시 방문했을 때 처음부터 QUIC 연결을 시도할 수 있습니다.

⸻

**7. 브라우저는 HTTP/3만 시도하나요?**

반드시 한 방식만 고집하는 것은 아닙니다.

브라우저는 네트워크 지연을 줄이기 위해 다음과 같은 전략을 사용할 수 있습니다.

HTTP/3 연결 시도

+

TCP 기반 HTTP/2 연결도 준비

HTTP/3 연결이 성공하면 이를 사용하고, 실패하거나 너무 오래 걸리면 TCP 기반 HTTP/2 또는 HTTP/1.1로 전환할 수 있습니다.

왜냐하면 일부 네트워크에서는 UDP 통신이 차단되거나 제한될 수 있기 때문입니다.

방화벽이 UDP를 차단

공유기나 NAT 장비가 QUIC을 제대로 처리하지 못함

회사 네트워크 정책상 UDP 제한

서버의 QUIC 설정 오류

이런 상황에서도 웹사이트에 접속할 수 있도록 TCP 기반 프로토콜을 대체 경로로 사용할 수 있습니다.

⸻

**8. 서버는 자신이 어떤 프로토콜을 사용하는지 어떻게 정하나요?**

서버 측에서는 해당 프로토콜을 처리할 프로그램이 실제로 포트를 열고 기다리고 있어야 합니다.

예를 들어 다음 구성이 가능합니다.

TCP 443

→ Nginx가 HTTP/1.1과 HTTP/2 처리

UDP 443

→ Nginx 또는 별도 QUIC 서버가 HTTP/3 처리

서버 설정에서 HTTP/3를 활성화하지 않았다면 브라우저가 UDP 443으로 패킷을 보내도 정상적인 QUIC 연결이 만들어지지 않습니다.

즉, 다음 두 조건이 모두 필요합니다.

클라이언트:

해당 프로토콜을 지원하고 사용하기로 결정

서버:

해당 전송 프로토콜과 포트에서 실제로 요청을 처리하도록 설정

⸻

**9. 커스텀 프로토콜이라면 브라우저나 클라이언트는 어떻게 아나요?**

직접 만든 프로토콜에서는 TCP인지 UDP인지 프로토콜 명세나 애플리케이션 설정으로 미리 정해야 합니다.

예를 들어 게임 클라이언트 설정에 다음 정보가 포함될 수 있습니다.

서버 주소: game.example.com

전송 프로토콜: UDP

포트: 30000

또는 프로토콜 자체를 다음처럼 정의할 수 있습니다.

MyGame Protocol v1

- UDP 사용

- 서버 기본 포트 30000

클라이언트는 이 규칙을 알고 있기 때문에 UDP 소켓을 생성합니다.

DatagramSocket socket = new DatagramSocket();

TCP 기반으로 정한 프로토콜이라면 TCP 소켓을 생성합니다.

Socket socket = new Socket(host, port);

즉, 일반적인 클라이언트가 서버의 IP와 포트에 아무 패킷이나 보내보고 TCP인지 UDP인지 자동으로 추측하는 것이 아닙니다.

⸻

**10. 질문에 대한 최종 답변**

브라우저는 서버에 접속한 뒤 TCP와 UDP 중 무엇을 사용하는지 알아내는 것이 아닙니다. URL의 스킴과 해당 프로토콜의 표준을 바탕으로 기본 연결 방식을 정하고, TLS의 ALPN, 서버가 전달한 Alt-Svc 정보, DNS HTTPS 레코드, 이전 접속 기록 등을 이용해 구체적인 HTTP 버전을 선택합니다. HTTP/1.1과 HTTP/2는 일반적으로 TCP를 사용하고, HTTP/3는 QUIC을 통해 UDP를 사용합니다. 서버가 HTTP/3를 지원한다는 정보가 있으면 브라우저는 UDP 기반 QUIC 연결을 시도하고, 실패하면 TCP 기반 HTTP/2나 HTTP/1.1로 대체할 수 있습니다.
