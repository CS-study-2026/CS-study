# 6-0. HTTP/1.1과 HTTP/2의 차이점은 무엇인가요?

## 1. 전체 흐름

HTTP/1.1과 HTTP/2는 서로 완전히 다른 웹 기능을 제공하는 프로토콜이 아닙니다.

두 버전 모두 다음과 같은 HTTP의 기본 의미를 그대로 사용합니다.

```plain text
GET, POST, PUT, DELETE 등의 Method
200, 404, 500 등의 상태 코드
Header와 Body로 구성된 요청과 응답
URI를 통한 리소스 식별
```

HTTP/2에서 바뀐 핵심은 HTTP의 의미가 아니라, 요청과 응답을 네트워크로 표현하고 전달하는 방식입니다.

```plain text
HTTP/1.1
→ 텍스트 기반 메시지를 TCP 연결을 통해 전송

HTTP/2
→ HTTP 메시지를 바이너리 프레임으로 나눠
   여러 스트림을 통해 하나의 TCP 연결에서 다중화
```

즉, HTTP/2의 목적은 기존 HTTP의 사용 방식을 유지하면서 네트워크 사용 효율과 응답 속도를 개선하는 것입니다.

---

# 2. HTTP/1.1의 특징

## 2-1. 텍스트 기반 메시지

HTTP/1.1 요청은 사람이 읽을 수 있는 텍스트 형태로 표현됩니다.

```plain text
GET /users/1 HTTP/1.1
Host: example.com
Accept: application/json
```

응답도 비슷합니다.

```plain text
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{"id":1,"name":"Youngbin"}
```

이 방식은 사람이 이해하기 쉽지만, 문자열을 구분하고 해석하는 파싱 과정이 필요합니다.

여기서 주의할 점은 다음과 같습니다.

> HTTP/2가 바이너리 형식이라는 것은 암호화된다는 뜻이 아닙니다.

바이너리 프레이밍은 메시지 표현 방식이고, 암호화 여부는 TLS와 관련된 별개의 문제입니다.

---

## 2-2. 지속 연결

HTTP/1.1은 기본적으로 하나의 TCP 연결을 여러 요청과 응답에 재사용할 수 있습니다.

```plain text
TCP 연결 생성

요청 1 → 응답 1
요청 2 → 응답 2
요청 3 → 응답 3

TCP 연결 종료
```

매 요청마다 새로운 TCP 연결을 만드는 것보다 연결 생성 비용을 줄일 수 있습니다.

하지만 한 연결에서 여러 요청을 동시에 효율적으로 처리하기에는 제약이 있습니다.

---

## 2-3. HTTP Pipelining

HTTP/1.1에는 이전 요청의 응답을 기다리지 않고 여러 요청을 먼저 보내는 Pipelining 방식이 있습니다.

```plain text
클라이언트 → 요청 A
클라이언트 → 요청 B
클라이언트 → 요청 C
```

서버가 요청들을 병렬로 처리하더라도 응답은 요청 순서에 맞춰 보내야 합니다.

```plain text
응답 순서:

응답 A
응답 B
응답 C
```

만약 요청 A의 처리가 오래 걸리고 B와 C의 처리가 먼저 끝났더라도, B와 C의 응답은 A의 응답을 앞질러 보낼 수 없습니다.

```plain text
요청 A: 처리 시간 5초
요청 B: 처리 시간 0.1초
요청 C: 처리 시간 0.1초

완료 시점:
B, C는 먼저 완료

전송 순서:
A가 전송될 때까지 B와 C도 대기
```

이것이 HTTP/1.1에서 발생할 수 있는 애플리케이션 계층의 HOL Blocking입니다.

이 문제를 피하기 위해 여러 TCP 연결을 동시에 사용하는 방법이 활용될 수 있지만, 연결이 많아지면 다음과 같은 비용이 생깁니다.

```plain text
TCP 연결 생성 비용 증가
서버가 관리할 소켓과 연결 상태 증가
각 연결이 별도의 혼잡 제어를 수행
네트워크 자원 사용 증가
```

# 3. HTTP/2의 핵심 변화

HTTP/2의 대표적인 변화는 다음과 같습니다.

```plain text
1. 바이너리 프레이밍
2. 스트림과 멀티플렉싱
3. 하나의 연결을 효율적으로 활용
4. 헤더 압축
```

---

## 3-1. 바이너리 프레이밍

HTTP/2에서는 HTTP 메시지를 하나의 긴 텍스트 덩어리로 전송하지 않습니다.

메시지를 여러 개의 작은 바이너리 프레임으로 나눕니다.

대표적인 프레임은 다음과 같습니다.

```plain text
HEADERS Frame
→ 요청·응답 헤더 전달

DATA Frame
→ 본문 데이터 전달

SETTINGS Frame
→ 연결 설정 정보 교환

WINDOW_UPDATE Frame
→ 흐름 제어에 사용
```

예를 들어 하나의 HTTP 응답은 다음처럼 전송될 수 있습니다.

```plain text
HTTP 응답
├─ HEADERS Frame
├─ DATA Frame
├─ DATA Frame
└─ DATA Frame
```

프레임마다 어떤 스트림의 데이터인지 식별할 수 있는 정보가 포함됩니다.

따라서 하나의 연결 안에서 여러 요청의 프레임을 섞어서 전송할 수 있습니다.

---

## 3-2. 스트림

HTTP/2에서 하나의 요청과 응답 교환은 하나의 스트림에 연결됩니다.

```plain text
Stream 1 → HTML 요청과 응답
Stream 3 → CSS 요청과 응답
Stream 5 → JavaScript 요청과 응답
Stream 7 → 이미지 요청과 응답
```

각 스트림은 논리적으로 서로 구분됩니다.

---

## 3-3. 멀티플렉싱

멀티플렉싱은 하나의 TCP 연결에서 여러 스트림의 프레임을 번갈아 전송하는 방식입니다.

예를 들어 다음 세 요청이 있다고 하겠습니다.

```plain text
Stream 1 → index.html
Stream 3 → style.css
Stream 5 → image.png
```

HTTP/2에서는 다음과 같이 프레임을 섞어서 전송할 수 있습니다.

```plain text
Stream 1 HEADERS
Stream 3 HEADERS
Stream 1 DATA
Stream 5 HEADERS
Stream 3 DATA
Stream 5 DATA
Stream 1 DATA
```

수신 측은 각 프레임의 스트림 번호를 보고 원래 요청과 응답으로 다시 조립합니다.

따라서 특정 요청의 전체 응답이 끝날 때까지 다른 요청이 무조건 기다릴 필요가 없습니다.

```plain text
HTTP/1.1의 순서 중심 처리

요청 A → 응답 A 완료
요청 B → 응답 B 완료
요청 C → 응답 C 완료
```

```plain text
HTTP/2의 다중화

요청 A의 일부 응답
요청 B의 일부 응답
요청 C의 일부 응답
요청 A의 나머지 응답
...
```

이로 인해 HTTP/1.1의 애플리케이션 계층 HOL Blocking을 완화할 수 있습니다.

---

## 3-4. TCP 연결 수 감소

HTTP/1.1에서는 여러 요청을 병렬로 처리하기 위해 여러 TCP 연결을 사용할 수 있습니다.

```plain text
TCP 연결 1 → HTML
TCP 연결 2 → CSS
TCP 연결 3 → JavaScript
TCP 연결 4 → 이미지
```

HTTP/2에서는 한 TCP 연결 안에 여러 스트림을 만들 수 있습니다.

```plain text
TCP 연결 1
├─ Stream 1 → HTML
├─ Stream 3 → CSS
├─ Stream 5 → JavaScript
└─ Stream 7 → 이미지
```

따라서 HTTP/2는 동일한 서버와 통신할 때 필요한 TCP 연결 수를 줄이고, 하나의 연결을 더 효율적으로 활용할 수 있습니다.

다만 HTTP/2가 반드시 모든 상황에서 TCP 연결을 정확히 하나만 사용한다는 뜻은 아닙니다.

핵심은 다음과 같습니다.

> 여러 요청을 동시에 처리하기 위해 요청마다 별도의 TCP 연결을 만들 필요가 줄어든다.

---

## 3-5. 헤더 압축

HTTP 요청과 응답의 헤더에는 반복되는 값이 많습니다.

```plain text
Host: example.com
User-Agent: ...
Accept: application/json
Cookie: ...
Authorization: ...
```

같은 서버로 요청을 반복하면 비슷한 헤더가 계속 전송됩니다.

HTTP/1.1은 이러한 헤더를 요청마다 텍스트로 반복해서 전달합니다.

HTTP/2는 **HPACK**이라는 방식으로 헤더를 압축합니다.

개념적으로는 반복되는 헤더를 테이블에 등록한 후, 다음부터는 전체 문자열 대신 인덱스나 변경된 값만 보내는 방식입니다.

```plain text
첫 번째 요청:

1 → Host: example.com
2 → Accept: application/json
3 → User-Agent: Browser
```

다음 요청에서는 다음처럼 표현할 수 있습니다.

```plain text
헤더 1번 사용
헤더 2번 사용
헤더 3번 사용
```

이를 통해 반복되는 헤더의 전송량을 줄일 수 있습니다.

# 4. HTTP/1.1과 HTTP/2 비교

| 구분 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 메시지 표현 | 텍스트 기반 | 바이너리 프레임 기반 |
| 기반 전송 프로토콜 | TCP | TCP |
| 연결 재사용 | 지속 연결 지원 | 지속 연결을 더 적극적으로 활용 |
| 동시 요청 처리 | 제한적, 여러 연결 사용 가능 | 하나의 연결에서 여러 스트림 다중화 |
| 응답 순서 | Pipelining 시 요청 순서를 따라야 함 | 스트림별로 독립적인 응답 가능 |
| 헤더 압축 | 기본적으로 없음 | HPACK 사용 |
| 애플리케이션 계층 HOL | 발생 가능 | 스트림 다중화로 완화 |
| TCP 계층 HOL | 발생 가능 | 여전히 발생 가능 |

---

# 5. HTTP/2에서 바뀌지 않은 것

HTTP/2가 도입되었다고 해서 웹 애플리케이션의 HTTP 사용 방법이 전부 바뀐 것은 아닙니다.

다음 의미는 그대로 유지됩니다.

```plain text
GET은 리소스를 조회한다.
POST는 데이터를 전송하거나 처리를 요청한다.
200은 요청 성공을 의미한다.
404는 리소스를 찾지 못했음을 의미한다.
Header와 Body가 존재한다.
HTTP는 기본적으로 요청과 응답 구조를 사용한다.
```

즉, 애플리케이션 개발자가 사용하는 HTTP의 의미는 유지되고, 그 아래의 전송 표현 방식이 최적화된 것입니다.

## Q1. HTTP/2는 HTTP/1.1보다 항상 빠른가요?

항상 그렇지는 않습니다.

HTTP/2는 요청이 많고 헤더가 반복되며 네트워크 연결 비용이 중요한 환경에서 유리할 수 있습니다.

반대로 요청이 매우 적거나 이미 연결이 만들어져 있으며 네트워크 상태가 좋은 단순한 상황에서는 차이가 크지 않을 수 있습니다.

프로토콜의 이론적인 장점과 실제 서비스의 성능은 서버 구현, 네트워크 지연, 패킷 손실률, 콘텐츠 구조 등에 따라 달라집니다.

---

## Q2. HTTP/2는 요청을 완전히 병렬로 처리하나요?

전송 관점에서는 여러 스트림을 동시에 진행할 수 있습니다.

하지만 서버 애플리케이션이 실제로 요청을 병렬 처리하는지는 별개의 문제입니다.

```plain text
HTTP/2 멀티플렉싱
→ 요청과 응답 프레임을 동시에 전달할 수 있음

서버의 병렬 처리
→ 서버의 스레드, 이벤트 루프, 애플리케이션 구조에 따라 결정
```

즉, 전송의 다중화와 서버 내부 실행의 병렬성은 같은 개념이 아닙니다.

---

## Q3. HTTP/2의 바이너리 프레이밍은 암호화인가요?

아닙니다.

바이너리 프레이밍은 HTTP 메시지를 컴퓨터가 처리하기 좋은 프레임 구조로 표현하는 방식입니다.

암호화와 인증은 TLS가 담당합니다.

```plain text
바이너리 프레이밍
= 데이터 표현 형식

TLS
= 암호화, 무결성, 인증
```

---

## Q4. HTTP/2는 반드시 HTTPS로만 사용할 수 있나요?

HTTP/2의 핵심 구조 자체와 TLS는 서로 다른 개념입니다.

다만 실제 웹 브라우저 환경에서 HTTP/2는 주로 TLS와 함께 사용됩니다.

따라서 면접에서는 다음처럼 답하는 것이 안전합니다.

> HTTP/2의 프로토콜 구조 자체가 암호화를 의미하는 것은 아니지만, 실제 브라우저 기반 웹 환경에서는 대부분 HTTPS를 통해 사용됩니다.

---

## Q5. HTTP/2에서 한 스트림이 느리면 다른 스트림은 정말 영향을 받지 않나요?

애플리케이션 계층에서는 스트림이 독립적이므로 한 스트림의 처리가 느리다고 다른 스트림이 반드시 기다릴 필요는 없습니다.

그러나 TCP 패킷이 유실되면 같은 TCP 연결의 모든 스트림이 재전송을 기다릴 수 있습니다.

```plain text
서버 처리 지연
→ 해당 HTTP/2 스트림 위주로 영향

TCP 패킷 유실
→ 같은 연결의 여러 스트림에 영향 가능
```
