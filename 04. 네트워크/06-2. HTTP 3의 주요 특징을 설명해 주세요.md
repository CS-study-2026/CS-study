# 6-2. HTTP/3의 주요 특징을 설명해 주세요.

표준 명칭은 보통 `HTTP/3.0`보다 **HTTP/3**라고 씁니다.

## 1. HTTP/3는 QUIC을 사용한다

HTTP/1.1과 HTTP/2는 일반적으로 TCP를 기반으로 동작합니다.

HTTP/3는 TCP 대신 **QUIC**이라는 전송 프로토콜 위에서 동작합니다.

```plain text
HTTP/1.1

HTTP/1.1
TLS
TCP
IP
```

```plain text
HTTP/2

HTTP/2
TLS
TCP
IP
```

```plain text
HTTP/3

HTTP/3
QUIC
UDP
IP
```

QUIC은 UDP 데이터그램 위에서 구현되지만, 단순한 UDP 통신과 같지는 않습니다.

QUIC은 자체적으로 다음 기능을 제공합니다.

```plain text
연결 관리
신뢰성 있는 데이터 전달
패킷 손실 감지와 재전송
혼잡 제어
흐름 제어
다중 스트림
암호화
```

따라서 다음 설명은 틀립니다.

```plain text
HTTP/3는 UDP를 사용하므로 데이터 전달을 보장하지 않는다.
```

정확한 설명은 다음과 같습니다.

> UDP 자체는 신뢰성을 제공하지 않지만, QUIC이 UDP 위에서 신뢰성·재전송·혼잡 제어 등의 기능을 구현합니다.

---

## 2. 스트림 단위 독립성

HTTP/3에서는 요청과 응답이 각각 독립된 QUIC 스트림을 사용합니다.

```plain text
QUIC Connection
├─ Stream A → HTML
├─ Stream B → CSS
├─ Stream C → JavaScript
└─ Stream D → 이미지
```

한 스트림에 속한 패킷이 유실되면 해당 스트림은 재전송을 기다릴 수 있습니다.

하지만 다른 스트림은 계속 진행할 수 있습니다.

```plain text
Stream A 패킷 유실
→ Stream A는 재전송 대기

Stream B
→ 계속 진행

Stream C
→ 계속 진행
```

이는 HTTP/2와 차이가 있습니다.

```plain text
HTTP/2:
TCP 패킷 하나 유실
→ 같은 TCP 연결의 여러 스트림이 함께 대기할 수 있음

HTTP/3:
특정 QUIC 스트림의 데이터 유실
→ 일반적으로 해당 스트림 위주로 대기
→ 다른 스트림은 계속 진행 가능
```

이를 통해 HTTP/2의 TCP 계층 HOL Blocking 문제를 완화합니다.

---

## 3. 연결 설정 지연 감소

TCP 기반 HTTPS 연결에서는 개념적으로 다음 과정이 필요합니다.

```plain text
TCP 연결 설정
→ TLS 보안 연결 설정
→ HTTP 요청 전송
```

QUIC은 전송 계층 연결 설정과 TLS 보안 협상을 밀접하게 결합합니다.

따라서 새로운 연결을 설정할 때 필요한 왕복 횟수를 줄일 수 있습니다.

이전에 같은 서버와 연결한 정보가 있는 경우에는 조건에 따라 **0-RTT**로 애플리케이션 데이터를 빠르게 보낼 수도 있습니다.

하지만 0-RTT가 모든 요청과 모든 연결에서 항상 사용되는 것은 아닙니다.

```plain text
처음 연결
→ 서버와의 사전 정보가 없으므로 일반 연결 설정 필요

재연결
→ 이전 연결 정보가 있고 조건이 맞으면 0-RTT 가능
```

TLS 인증서 검증이나 세부 Handshake 과정은 HTTPS 발표 범위에서 다루는 것이 자연스럽습니다.

여기서는 다음 정도로 정리할 수 있습니다.

> HTTP/3는 QUIC이 전송 연결 설정과 TLS 협상을 통합하여 연결 설정 지연을 줄일 수 있습니다.

---

## 4. 연결 마이그레이션

TCP 연결은 일반적으로 다음 정보의 조합으로 구분됩니다.

```plain text
출발지 IP
출발지 Port
목적지 IP
목적지 Port
```

모바일 기기가 Wi-Fi에서 LTE나 5G로 전환되면 IP 주소가 달라질 수 있습니다.

기존 TCP 연결은 네트워크 경로가 바뀌면 유지하기 어려울 수 있습니다.

QUIC은 연결을 IP와 포트의 조합만으로 식별하지 않고 **Connection ID**를 사용합니다.

따라서 클라이언트의 IP 주소나 네트워크 경로가 바뀌어도 같은 QUIC 연결을 계속 유지할 수 있습니다.

```plain text
Wi-Fi 사용
IP 주소 A
QUIC Connection ID = 1234

↓ LTE로 전환

LTE 사용
IP 주소 B
QUIC Connection ID = 1234

기존 연결을 이어갈 수 있음
```

이를 연결 마이그레이션이라고 합니다.

모바일 환경처럼 네트워크 변경이 자주 발생하는 상황에서 유용할 수 있습니다.

---

## 5. TLS 1.3 통합

QUIC은 보안 기능을 선택적으로 덧붙이는 구조가 아니라 TLS 1.3을 연결 설정 과정에 통합합니다.

HTTP/3 통신은 QUIC이 제공하는 다음 보호를 사용합니다.

```plain text
기밀성
무결성
상대방 인증
```

다만 이 발표에서는 공개키, 대칭키, 인증서 검증 과정을 자세히 설명하지 않습니다.

HTTP/3 관점에서 중요한 것은 다음입니다.

> QUIC은 보안 협상과 전송 연결 설정을 함께 처리하도록 설계되어 있습니다.

---

## 6. QPACK 헤더 압축

HTTP/2는 HPACK으로 헤더를 압축합니다.

HTTP/3는 **QPACK**을 사용합니다.

QUIC 스트림은 서로 독립적으로 진행되기 때문에, HTTP/2의 HPACK을 그대로 사용하면 헤더 압축 상태의 순서 의존성 때문에 다시 Blocking이 발생할 수 있습니다.

QPACK은 QUIC의 독립적인 스트림 구조에 맞게 설계된 헤더 압축 방식입니다.

```plain text
HTTP/2 → HPACK
HTTP/3 → QPACK
```

다만 QPACK도 압축 테이블의 특정 항목에 의존하는 경우 헤더 디코딩이 잠시 대기할 수 있습니다.

따라서 HTTP/3가 세상의 모든 형태의 Blocking을 완전히 없앤다고 표현하면 부정확합니다.

# 10. HTTP/3가 HOL Blocking을 완전히 제거했나요?

완전히 제거했다고 말하면 안 됩니다.

HTTP/3가 크게 해결한 것은 HTTP/2의 **TCP 연결 단위 HOL Blocking**입니다.

다음과 같은 Blocking은 여전히 있을 수 있습니다.

### 하나의 스트림 내부 순서

한 스트림 내부의 데이터는 순서대로 조립되어야 합니다.

```plain text
Stream A의 데이터 1
Stream A의 데이터 2
Stream A의 데이터 3
```

데이터 2가 유실되면 같은 Stream A의 데이터 3을 애플리케이션이 바로 처리하지 못할 수 있습니다.

다만 다른 Stream B와 Stream C는 계속 진행할 수 있습니다.

### 헤더 압축 의존성

QPACK 동적 테이블의 항목이 아직 도착하지 않았다면, 해당 항목을 참조하는 헤더의 디코딩이 대기할 수 있습니다.

### 애플리케이션 의존성

HTML을 받은 뒤에야 어떤 JavaScript 파일이 필요한지 알 수 있다면, 프로토콜이 독립 스트림을 제공해도 애플리케이션 구조상 순서 의존성이 존재할 수 있습니다.

따라서 가장 정확한 표현은 다음과 같습니다.

> HTTP/3는 QUIC의 독립적인 스트림을 통해 한 스트림의 패킷 손실이 다른 스트림까지 막는 연결 단위 HOL Blocking을 해결합니다. 그러나 개별 스트림 내부의 순서 대기나 헤더 압축 및 애플리케이션 수준의 의존성까지 모두 사라지는 것은 아닙니다.

# 11. HTTP 버전별 발전 과정 👍

```plain text
HTTP/1.1

문제:
한 연결에서 요청과 응답 순서의 제약
병렬 처리를 위해 여러 TCP 연결 사용
반복되는 텍스트 헤더

개선 목표:
하나의 연결을 더 효율적으로 사용
```

```plain text
HTTP/2

개선:
바이너리 프레이밍
스트림 다중화
HPACK 헤더 압축
HTTP 계층 HOL Blocking 완화

남은 문제:
기반이 TCP이므로 패킷 손실 시
여러 스트림이 함께 대기하는 TCP HOL Blocking
```

```plain text
HTTP/3

개선:
TCP 대신 QUIC 사용
스트림별 독립적인 손실 복구
TLS 1.3 통합
연결 설정 지연 감소
연결 마이그레이션
QPACK 헤더 압축
```

# 12. 최종 비교표

| 구분 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 전송 기반 | TCP | TCP | QUIC over UDP |
| 메시지 형식 | 텍스트 | 바이너리 프레임 | 바이너리 프레임 |
| 다중화 | 사실상 제한적 | HTTP 스트림 다중화 | QUIC 스트림 다중화 |
| 헤더 압축 | 기본 제공 없음 | HPACK | QPACK |
| HTTP 계층 HOL | 발생 가능 | 크게 완화 | 크게 완화 |
| 연결 단위 전송 HOL | TCP로 인해 발생 | TCP로 인해 발생 | 독립 스트림으로 완화 |
| 보안 | HTTPS 사용 시 TLS | 주로 TLS와 함께 사용 | QUIC에 TLS 통합 |
| 연결 이동 | TCP 연결 재설정 가능성 | TCP 연결 재설정 가능성 | Connection ID 기반 마이그레이션 가능 |
| 연결 설정 | TCP 후 필요 시 TLS | TCP 후 주로 TLS | QUIC과 TLS 협상 통합 |

## Q7. HTTP/3에서는 패킷 순서가 뒤섞여도 되나요?

QUIC 스트림끼리는 서로 독립적으로 전달될 수 있습니다.

하지만 하나의 스트림 내부에서는 HTTP/3가 신뢰성 있고 순서가 맞는 바이트 전달을 사용합니다.

```plain text
Stream A와 Stream B 사이
→ 전달 순서가 서로 독립적

Stream A 내부
→ 데이터 순서 보장
```

---

## Q8. HTTP/3는 HOL Blocking을 완전히 해결했나요?

아닙니다.

서로 다른 스트림 사이에서 발생하는 TCP 연결 단위 HOL Blocking을 해결한 것입니다.

한 스트림 내부의 순서 대기, QPACK 헤더 의존성, 애플리케이션의 작업 순서 의존성은 남을 수 있습니다.

---

## Q9. HTTP/3의 0-RTT는 항상 사용할 수 있나요?

아닙니다.

클라이언트와 서버 사이에 이전 연결 정보가 있어야 하며, 서버와 요청 조건에 따라 사용할 수 있습니다.

첫 연결부터 무조건 0-RTT로 통신하는 것은 아닙니다.

---

## Q10. 네트워크가 Wi-Fi에서 LTE로 바뀌면 HTTP/3 연결은 왜 유지될 수 있나요?

QUIC은 연결을 IP 주소와 포트의 조합만으로 식별하지 않고 Connection ID를 사용합니다.

따라서 클라이언트 IP가 바뀌어도 Connection ID를 기반으로 기존 연결을 이어갈 수 있습니다.

---

## Q11. HTTP/3에서도 GET, POST와 상태 코드는 그대로 사용하나요?

그대로 사용합니다.

HTTP/3는 HTTP의 의미를 바꾸는 버전이 아니라, HTTP 메시지를 QUIC 위에서 효율적으로 전달하는 방식입니다.

```plain text
HTTP Method
상태 코드
Header
Body
URI
캐시 의미
```

등의 핵심 HTTP 의미는 유지됩니다.

---

## Q12. HPACK과 QPACK의 차이는 무엇인가요?

둘 다 반복되는 HTTP 헤더를 압축하기 위한 방식입니다.

```plain text
HPACK
→ HTTP/2의 TCP 기반 순서 전달에 맞게 설계

QPACK
→ HTTP/3의 독립적인 QUIC 스트림에 맞게 설계
```

HTTP/3에서 HPACK을 그대로 사용하면 헤더 압축 테이블의 순서 의존성이 독립 스트림의 장점을 방해할 수 있기 때문에 QPACK을 사용합니다.

---

## Q13. HTTP/3가 있는데 HTTP/1.1과 HTTP/2는 사라지나요?

바로 사라지는 것은 아닙니다.

클라이언트, 서버, 프록시, 방화벽, 네트워크 환경이 지원하는 버전이 다를 수 있기 때문에 여러 버전이 함께 사용될 수 있습니다.

HTTP/3 연결이 불가능하면 HTTP/2나 HTTP/1.1로 통신할 수 있습니다.

---

## Q14. HTTP/3는 모든 네트워크에서 HTTP/2보다 빠른가요?

항상 빠른 것은 아닙니다.

HTTP/3의 장점은 특히 다음과 같은 환경에서 두드러질 수 있습니다.

```plain text
패킷 손실이 발생하는 환경
지연 시간이 큰 환경
모바일 네트워크 전환이 잦은 환경
동시에 많은 요청을 처리하는 환경
```

반면 패킷 손실이 거의 없고 네트워크가 안정적이라면 HTTP/2와 성능 차이가 크지 않을 수도 있습니다.
