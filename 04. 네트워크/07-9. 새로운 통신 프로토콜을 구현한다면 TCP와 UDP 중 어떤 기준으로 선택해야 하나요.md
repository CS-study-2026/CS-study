# 7-9. **새로운 통신 프로토콜을 구현한다면 TCP와 UDP 중 어떤 기준으로 선택해야 하나요?**

**7-9. 새로운 통신 프로토콜을 구현한다면 TCP와 UDP 중 어떤 기준으로 선택해야 하나요?**

**1. 단순히 속도만 보고 선택하면 안 된다**

흔히 다음처럼 외우기 쉽습니다.

TCP

→ 느리지만 안정적

UDP

→ 빠르지만 불안정

완전히 틀린 설명은 아니지만, 실제 프로토콜 설계 기준으로는 지나치게 단순합니다.

TCP와 UDP를 선택할 때는 다음 질문을 함께 살펴봐야 합니다.

데이터 손실을 허용할 수 있는가?

순서가 반드시 보장되어야 하는가?

지연과 정확성 중 무엇이 더 중요한가?

메시지 경계를 보존해야 하는가?

재전송이 의미 있는가?

연결 상태를 유지해야 하는가?

혼잡 제어를 누가 구현할 것인가?

보안은 어떻게 제공할 것인가?

방화벽과 NAT 환경에서 잘 동작해야 하는가?

개발과 운영 복잡도를 감당할 수 있는가?

⸻

**2. TCP를 선택하기 좋은 경우**

다음 조건이 중요하다면 TCP가 적합할 가능성이 높습니다.

1. 데이터가 빠짐없이 도착해야 한다.

2. 전송 순서가 중요하다.

3. 중복 데이터가 제거되어야 한다.

4. 연결 상태를 유지해야 한다.

5. 직접 재전송과 혼잡 제어를 구현하고 싶지 않다.

TCP는 애플리케이션에 신뢰성 있는 순서 보장 바이트 스트림을 제공합니다.

송신:

A → B → C

수신 애플리케이션:

A → B → C

중간에 B가 유실되면 TCP가 이를 감지하고 재전송합니다.

A 도착

B 유실

C 도착

→ B 재전송

→ 애플리케이션에는 A, B, C 순서로 전달

⸻

**2-1. TCP가 적합한 예시**

**파일 전송**

파일의 일부가 빠지거나 순서가 뒤바뀌면 파일이 손상될 수 있습니다.

원본 파일:

1번 블록, 2번 블록, 3번 블록

수신:

1번 블록, 3번 블록

→ 정상적인 파일이 아님

따라서 정확한 전달이 중요합니다.

**결제 요청**

결제 데이터가 유실되거나 중복 처리되면 안 됩니다.

다만 TCP가 애플리케이션의 중복 결제까지 해결해주는 것은 아닙니다. TCP는 연결 구간의 바이트 전달을 보장할 뿐, 비즈니스 요청의 멱등성과 중복 처리는 애플리케이션에서 별도로 관리해야 합니다.

**채팅 메시지**

일반적인 텍스트 채팅에서는 메시지가 누락되거나 순서가 뒤바뀌는 것보다 약간 늦게 도착하는 편이 낫습니다.

**원격 명령 및 데이터베이스 통신**

명령어와 결과의 정확한 전달이 중요하므로 신뢰성과 순서 보장이 필요합니다.

⸻

**3. UDP를 선택하기 좋은 경우**

다음 조건이라면 UDP가 적합할 수 있습니다.

1. 일부 데이터 손실을 허용할 수 있다.

2. 오래된 데이터를 재전송하는 것보다 최신 데이터가 중요하다.

3. 지연 시간을 최소화해야 한다.

4. 메시지 단위 전송이 필요하다.

5. 연결 설정 없이 빠르게 데이터를 보내고 싶다.

6. 애플리케이션이 필요한 신뢰성만 선택적으로 구현하려 한다.

7. 브로드캐스트나 멀티캐스트가 필요하다.

UDP는 데이터그램 단위로 전송합니다.

보낸 데이터그램 A

보낸 데이터그램 B

보낸 데이터그램 C

수신 측에서는 다음과 같이 될 수도 있습니다.

A 도착

C 도착

B 유실

또는 순서가 바뀔 수도 있습니다.

C

A

B

UDP 자체는 이를 다시 정렬하거나 재전송하지 않습니다.

⸻

**3-1. UDP가 적합한 예시**

**실시간 음성 통화**

음성 패킷 하나가 유실됐다고 몇 초 뒤 재전송되면 이미 재생 시점이 지나 의미가 없습니다.

현재 재생 시점: 10초

8초 시점의 음성 패킷이 늦게 도착

→ 재생할 가치가 낮음

이 경우 완벽한 전달보다 낮은 지연이 더 중요할 수 있습니다.

**실시간 영상**

영상 프레임 일부가 손실되더라도 다음 프레임을 빠르게 받는 것이 더 중요할 수 있습니다.

**실시간 게임 상태**

플레이어 위치가 다음과 같이 계속 갱신된다고 하겠습니다.

1초: x=10

1.1초: x=12

1.2초: x=15

x=10 패킷이 유실되었다고 늦게 다시 받아도 이미 최신 위치 x=15가 있으므로 의미가 없을 수 있습니다.

**DNS 질의**

전통적인 짧은 DNS 요청과 응답은 연결 설정 없이 빠르게 처리하는 것이 유리합니다. 다만 응답이 크거나 신뢰성·보안 요구가 추가되면 TCP 또는 암호화된 다른 전송 방식을 사용할 수도 있습니다.

**DHCP**

아직 자신의 IP 주소와 통신 상대를 완전히 알지 못하는 초기 상황에서 브로드캐스트 기반 통신이 필요할 수 있으므로 UDP가 사용됩니다.

⸻

**4. 신뢰성이 필요하면 무조건 TCP인가요?**

반드시 그렇지는 않습니다.

UDP를 기반으로 하면서 애플리케이션이나 별도의 전송 프로토콜이 필요한 신뢰성을 구현할 수 있습니다.

대표적인 사례가 QUIC입니다.

QUIC

→ UDP 위에서 동작

→ 재전송 지원

→ 손실 감지

→ 흐름 제어

→ 혼잡 제어

→ 암호화

→ 독립적인 스트림

따라서 다음 표현은 부정확합니다.

UDP를 사용하면 신뢰성을 구현할 수 없다.

정확한 표현은 다음과 같습니다.

UDP 자체는 신뢰성을 제공하지 않지만, UDP 위에 구현한 프로토콜이 필요한 신뢰성을 제공할 수 있습니다.

다만 직접 구현해야 할 기능이 많아지기 때문에 설계와 검증 비용이 크게 증가합니다.

⸻

**5. UDP 위에 신뢰성을 직접 구현한다면 필요한 것**

UDP로 새로운 신뢰성 프로토콜을 만들려면 다음 기능을 고려해야 합니다.

패킷 번호

ACK

재전송

재전송 타이머

중복 패킷 제거

순서 재조립

흐름 제어

혼잡 제어

연결 상태 관리

MTU와 단편화 처리

암호화와 인증

NAT 경로 유지

연결 종료 처리

예를 들어 단순히 ACK와 재전송만 추가하면 끝나는 것이 아닙니다.

혼잡 제어가 없다면 네트워크가 혼잡할 때 더 많은 패킷을 보내 상황을 악화시킬 수 있습니다.

패킷 손실 발생

→ 무조건 대량 재전송

→ 네트워크 혼잡 증가

→ 더 많은 패킷 손실

그래서 특별한 이유가 없다면 검증된 TCP, QUIC 또는 관련 라이브러리를 사용하는 것이 안전합니다.

⸻

**6. 데이터 손실 허용 여부**

가장 먼저 판단할 기준입니다.

**손실을 허용할 수 없는 경우**

파일

결제 정보

명령어

텍스트 메시지

데이터베이스 요청

이런 데이터는 일부가 빠지면 전체 의미가 손상될 수 있습니다.

TCP가 자연스러운 선택입니다.

**일부 손실을 허용할 수 있는 경우**

음성 샘플

영상 프레임 일부

짧은 주기의 위치 정보

센서의 반복 측정값

최신 데이터가 계속 들어오고 과거 데이터의 가치가 빠르게 사라진다면 UDP가 유리할 수 있습니다.

⸻

**7. 순서 보장 필요 여부**

TCP는 바이트를 순서대로 전달합니다.

보낸 순서:

A B C

애플리케이션이 받는 순서:

A B C

UDP는 각 데이터그램이 독립적이므로 순서가 바뀔 수 있습니다.

보낸 순서:

A B C

도착 순서:

B C A

따라서 다음을 판단해야 합니다.

앞선 데이터가 없으면 뒤의 데이터를 처리할 수 없는가?

각 메시지가 독립적으로 처리 가능한가?

최신 메시지가 이전 메시지를 대체할 수 있는가?

각 메시지가 독립적이고 최신 상태가 과거 상태를 대체한다면 UDP가 적합할 수 있습니다.

⸻

**8. 메시지 경계가 필요한가?**

TCP는 바이트 스트림을 제공합니다.

송신 측에서 두 번 send()했다고 수신 측에서도 두 번의 read()로 정확히 나뉘는 것이 아닙니다.

송신:

send("ABC")

send("DEF")

수신에서는 다음처럼 읽힐 수 있습니다.

read() → "ABCDEF"

또는 다음처럼 나뉠 수 있습니다.

read() → "AB"

read() → "CDE"

read() → "F"

따라서 TCP 기반 프로토콜은 애플리케이션 계층에서 메시지 경계를 정의해야 합니다.

대표적인 방법은 다음과 같습니다.

고정 길이

길이 필드

구분자

TLV 구조

반면 UDP는 데이터그램 경계를 보존합니다.

UDP 데이터그램 A

UDP 데이터그램 B

→ 각각 별도 메시지로 수신

다만 데이터그램이 네트워크 MTU보다 지나치게 크면 IP 단편화나 손실 위험이 커질 수 있으므로 크기를 신중히 설계해야 합니다.

⸻

**9. 연결 설정 지연**

TCP는 통신 전에 연결 설정이 필요합니다.

TCP Handshake

→ 데이터 전송

UDP는 일반적으로 연결 설정 없이 바로 데이터그램을 보낼 수 있습니다.

데이터그램 전송

그래서 한 번만 빠르게 요청하고 응답받는 단순한 통신에서는 UDP가 유리할 수 있습니다.

하지만 실제 전체 지연은 다음 요소도 함께 봐야 합니다.

TLS Handshake

DNS 조회

재전송

서버 처리 시간

네트워크 경로

애플리케이션 프로토콜 오버헤드

따라서 UDP를 쓴다는 이유만으로 전체 서비스가 항상 빨라지는 것은 아닙니다.

⸻

**10. HOL Blocking을 허용할 수 있는가?**

TCP는 하나의 순서 있는 바이트 스트림을 제공합니다.

앞쪽 바이트가 유실되면 그 뒤의 데이터가 이미 도착했더라도 애플리케이션에는 순서대로 전달되어야 합니다.

1번 데이터 도착

2번 데이터 유실

3번 데이터 도착

→ 2번 재전송 대기

→ 3번도 애플리케이션 전달 대기

서로 독립적인 여러 데이터 흐름을 하나의 TCP 연결에 넣으면 하나의 손실이 다른 흐름까지 지연시킬 수 있습니다.

독립적인 스트림 처리와 낮은 지연이 중요하다면 다음을 고려할 수 있습니다.

여러 TCP 연결

UDP 기반 자체 프로토콜

QUIC

⸻

**11. 흐름 제어와 혼잡 제어가 필요한가?**

TCP는 기본적으로 흐름 제어와 혼잡 제어를 제공합니다.

흐름 제어

→ 수신자가 처리할 수 있는 속도에 맞춤

혼잡 제어

→ 네트워크 상태에 따라 송신 속도를 조절

UDP는 이를 기본 제공하지 않습니다.

UDP 기반 프로토콜이 많은 데이터를 빠르게 보낸다면 애플리케이션이 직접 속도를 제한하고 네트워크 혼잡에 대응해야 합니다.

따라서 다음처럼 판단할 수 있습니다.

직접 제어 알고리즘을 구현하고 검증할 여력이 없다.

→ TCP 또는 QUIC 사용을 우선 고려

전송 특성에 맞는 세밀한 제어가 반드시 필요하다.

→ UDP 기반 설계를 검토

⸻

**12. 보안**

TCP와 UDP 자체는 애플리케이션 데이터 암호화를 기본적으로 제공하지 않습니다.

일반적인 선택은 다음과 같습니다.

TCP

→ TLS와 결합

UDP

→ DTLS 또는 QUIC과 결합

직접 만든 암호화 방식을 사용하는 것은 피해야 합니다.

프로토콜을 설계할 때는 다음 항목이 필요합니다.

서버 인증

필요한 경우 클라이언트 인증

암호화

무결성 검증

재전송 공격 방지

키 교환

키 갱신

⸻

**13. 방화벽과 NAT 호환성**

TCP는 많은 네트워크 장비에서 오래전부터 일반적으로 처리되어 왔습니다.

UDP는 환경에 따라 다음 문제가 있을 수 있습니다.

UDP 전체 차단

특정 UDP 포트 차단

NAT 매핑의 빠른 만료

대량 UDP 트래픽 제한

따라서 공공망과 기업망을 포함해 넓은 환경에서 반드시 동작해야 한다면 TCP가 배포 측면에서 더 안전할 수 있습니다.

UDP나 QUIC을 사용할 때는 TCP 기반 대체 경로를 두는 것도 고려할 수 있습니다.

⸻

**14. 브로드캐스트와 멀티캐스트**

UDP는 브로드캐스트와 멀티캐스트 통신에 사용할 수 있습니다.

브로드캐스트

→ 같은 네트워크의 여러 장비에 전송

멀티캐스트

→ 특정 그룹에 가입한 여러 장비에 전송

TCP는 일대일 연결을 기반으로 하므로 일반적인 브로드캐스트나 멀티캐스트에 적합하지 않습니다.

따라서 로컬 네트워크에서 장치를 발견하거나 여러 수신자에게 동시에 데이터를 보내야 한다면 UDP를 고려할 수 있습니다.

⸻

**15. TCP와 UDP 선택표**

| **기준** | **TCP가 적합한 경우** | **UDP가 적합한 경우** |
| --- | --- | --- |

| 데이터 형태 | 연속적인 바이트 스트림 | 독립된 메시지 |

TCP 기반 HTTP

**17. 실제 선택 순서**

새 프로토콜을 설계한다면 다음 순서로 판단할 수 있습니다.

1. 반드시 모든 데이터가 도착해야 하는가?

└─ 그렇다면 TCP 또는 신뢰성을 제공하는 QUIC 우선 검토

2. 전송 순서가 중요한가?

└─ 그렇다면 TCP 또는 순서를 구현한 프로토콜 필요

3. 오래된 데이터도 재전송할 가치가 있는가?

└─ 없다면 UDP가 유리할 수 있음

4. 수십 밀리초의 지연도 중요한가?

└─ 그렇다면 UDP/QUIC 검토

5. 메시지마다 필요한 신뢰성 수준이 다른가?

└─ QUIC 또는 UDP 기반 선택적 신뢰성 검토

6. 브로드캐스트나 멀티캐스트가 필요한가?

└─ UDP 검토

7. 혼잡 제어와 보안을 직접 구현할 수 있는가?

└─ 어렵다면 검증된 TCP, TLS, QUIC 사용

8. UDP가 제한된 네트워크에서도 동작해야 하는가?

└─ TCP fallback 검토

**18. “UDP가 더 빠르다”는 표현의 문제점**

UDP의 헤더가 단순하고 연결 설정이 없다는 것은 사실입니다.

하지만 UDP를 사용한다고 애플리케이션 전체가 무조건 빨라지는 것은 아닙니다.

UDP 위에 다음 기능을 다시 구현하면 비용이 추가됩니다.

재전송

순서 보장

ACK

흐름 제어

혼잡 제어

암호화

연결 관리

결국 TCP와 비슷한 기능을 미숙하게 다시 만들 수 있습니다.

따라서 더 정확한 표현은 다음과 같습니다.

UDP는 전송 기능이 단순해서 애플리케이션이 지연과 신뢰성 정책을 더 자유롭게 설계할 수 있습니다. 하지만 필요한 기능을 직접 구현해야 하므로 항상 TCP보다 빠르거나 단순한 것은 아닙니다.

⸻

**19. 최종 답변**

새로운 프로토콜을 구현할 때는 데이터 손실과 순서 변경을 허용할 수 있는지, 지연과 정확성 중 무엇이 중요한지, 오래된 데이터를 재전송할 가치가 있는지, 흐름 제어와 혼잡 제어를 직접 구현할 수 있는지를 기준으로 TCP와 UDP를 선택하겠습니다. 파일, 결제, 명령처럼 모든 데이터의 정확한 전달과 순서가 중요하다면 TCP를 사용하겠습니다. 반면 실시간 음성, 영상, 게임 위치처럼 일부 손실을 허용할 수 있고 오래된 데이터보다 최신 데이터와 낮은 지연이 중요하다면 UDP를 고려하겠습니다. 다만 UDP 위에 신뢰성, 혼잡 제어, 보안 기능이 필요하다면 이를 직접 만들기보다는 QUIC처럼 이미 검증된 프로토콜을 우선 검토하겠습니다.

⸻

**두 질문 핵심 요약**

**7-8 요약**

브라우저가 서버를 보고 TCP/UDP를 추측하는 것은 아니다.

URL과 프로토콜 표준으로 기본 연결 방식을 결정하고,

ALPN, Alt-Svc, DNS HTTPS 레코드,

이전 접속 정보를 통해 구체적인 HTTP 버전을 선택한다.

HTTP/1.1, HTTP/2

→ 일반적으로 TCP

HTTP/3

→ QUIC over UDP

HTTP/3 연결 실패 시

→ TCP 기반 HTTP/2 또는 HTTP/1.1로 대체 가능

**7-9 요약**

TCP 선택 기준:

- 손실 불가

- 순서 중요

- 재전송 필요

- 흐름·혼잡 제어 필요

- 구현 안정성 중요

UDP 선택 기준:

- 일부 손실 허용

- 최신 데이터 중요

- 낮은 지연 중요

- 메시지 단위 처리

- 브로드캐스트/멀티캐스트 필요

- 필요한 신뢰성을 직접 선택적으로 구현

주의:

UDP가 무조건 빠른 것은 아니며,

필요한 신뢰성과 보안을 직접 구현하면 복잡도가 크게 증가한다.

**예상 꼬리 질문**

**Q1. 같은 443번 포트에서 TCP와 UDP를 동시에 사용할 수 있나요?**

가능합니다.

TCP와 UDP는 서로 독립적인 포트 공간을 사용합니다.

TCP 443

UDP 443

은 서로 다른 엔드포인트이므로 동시에 사용할 수 있습니다.

HTTP/2는 TCP 443을, HTTP/3는 UDP 443을 사용하는 구성이 대표적입니다.

⸻

**Q2. DNS의 A 레코드를 보면 TCP인지 UDP인지 알 수 있나요?**

아닙니다.

A 레코드는 IPv4 주소를, AAAA 레코드는 IPv6 주소를 알려줍니다.

A

→ IPv4 주소

AAAA

→ IPv6 주소

전송 프로토콜은 애플리케이션의 표준이나 별도 설정으로 결정됩니다.

다만 HTTPS 또는 SVCB DNS 레코드는 지원 프로토콜과 대체 엔드포인트 등에 관한 추가 정보를 제공할 수 있습니다.

⸻

**Q3. 포트 번호만 알면 어떤 프로토콜인지 알 수 있나요?**

관례상 추정은 가능하지만 확정할 수는 없습니다.

80

→ 일반적으로 HTTP

443

→ 일반적으로 HTTPS

53

→ 일반적으로 DNS

하지만 서버 관리자는 다른 포트에서 서비스를 실행할 수 있고, 같은 포트 번호를 TCP와 UDP에서 각각 사용할 수도 있습니다.

정확한 통신 규약은 프로토콜 명세와 서버 설정을 알아야 합니다.

⸻

**Q4. ALPN은 TCP와 UDP 중 하나를 고르는 기능인가요?**

정확히는 아닙니다.

ALPN은 TLS 연결에서 어떤 애플리케이션 프로토콜을 사용할지 협상하는 기능입니다.

h2

http/1.1

h3

같은 식별자를 사용할 수 있지만, HTTP/3는 QUIC 연결 자체가 필요하므로 HTTP/3 엔드포인트를 발견하고 QUIC 연결을 만드는 과정도 필요합니다.

⸻

**Q5. 브라우저가 UDP 패킷을 먼저 보내보고 응답이 없으면 TCP를 쓰나요?**

브라우저 구현과 저장된 정보에 따라 여러 전략이 가능합니다.

다만 아무 정보 없이 모든 서버에 무작정 UDP 패킷을 보내는 것으로 이해하면 부정확합니다.

일반적으로 Alt-Svc, DNS HTTPS 레코드 또는 이전 연결 정보 등을 통해 HTTP/3 지원 가능성을 확인한 뒤 QUIC 연결을 시도할 수 있습니다.

실패하면 TCP 기반 HTTP/2나 HTTP/1.1을 사용할 수 있습니다.

⸻

**Q6. TCP를 사용하면 메시지가 중복 처리되지 않는 것이 보장되나요?**

TCP는 한 연결에서 애플리케이션에 같은 바이트를 중복 전달하지 않도록 처리합니다.

하지만 애플리케이션 요청 자체의 중복 실행까지 막아주는 것은 아닙니다.

예를 들어 클라이언트가 응답을 받지 못해 결제 요청을 다시 보내면 서버는 두 개의 별도 요청으로 받을 수 있습니다.

TCP의 책임

→ 바이트 스트림의 신뢰성

애플리케이션의 책임

→ 요청 중복 방지와 멱등성

결제 식별자나 멱등 키 등을 별도로 사용해야 합니다.

⸻

**Q7. UDP는 정말 순서를 보장하지 않나요?**

UDP는 데이터그램의 도착 순서를 보장하지 않습니다.

필요하다면 애플리케이션이 패킷마다 순서 번호를 넣고 재정렬해야 합니다.

sequence=1

sequence=2

sequence=3

다만 순서를 기다리도록 구현하면 지연이 증가할 수 있으므로 서비스 요구사항에 따라 선택해야 합니다.

⸻

**Q8. UDP에서도 재전송할 수 있나요?**

가능합니다.

송신자와 수신자가 패킷 번호와 ACK를 사용해 재전송 로직을 구현할 수 있습니다.

하지만 재전송뿐 아니라 중복 제거, 타이머, 혼잡 제어, 흐름 제어도 함께 고려해야 합니다.

그래서 직접 구현하기보다 QUIC 같은 검증된 프로토콜을 사용하는 것이 일반적으로 안전합니다.

⸻

**Q9. 게임에서는 TCP와 UDP 중 무엇을 사용해야 하나요?**

데이터 종류에 따라 다릅니다.

실시간 위치·방향

→ UDP가 적합할 수 있음

로그인·아이템 구매·게임 결과

→ 신뢰성 있는 전달 필요

채팅

→ 순서와 전달 보장이 중요

게임 전체에 무조건 하나만 선택하기보다 데이터 특성별로 다른 전달 정책을 사용할 수 있습니다.

⸻

**Q10. WebSocket은 TCP와 UDP 중 무엇을 사용하나요?**

일반적인 WebSocket은 TCP 위에서 동작합니다.

WebSocket

→ HTTP 기반 Handshake

→ TCP 연결을 지속적으로 사용

따라서 메시지의 순서와 신뢰성은 TCP의 특성을 따릅니다.

⸻

**Q11. UDP에서는 왜 연결 설정이 없다고 하나요?**

UDP는 TCP처럼 상대방과 Handshake를 통해 연결 상태를 합의하지 않고 데이터그램을 전송할 수 있기 때문입니다.

프로그래밍 API에서 UDP 소켓에 connect()를 호출할 수는 있지만, 이는 보통 기본 목적지 설정과 수신 패킷 필터링을 위한 로컬 설정입니다.

TCP와 같은 네트워크상의 연결 설정 Handshake가 생기는 것은 아닙니다.

⸻

**Q12. QUIC을 사용하면 TCP는 필요 없어지나요?**

그렇지는 않습니다.

일부 네트워크는 UDP를 제한할 수 있고, 기존 시스템과 서비스는 TCP를 기반으로 구축되어 있습니다.

또한 모든 애플리케이션이 QUIC의 독립 스트림과 연결 이동 기능을 필요로 하는 것도 아닙니다.

요구사항과 배포 환경에 따라 TCP와 QUIC이 함께 사용될 수 있습니다.

⸻

**Q13. UDP가 TCP보다 헤더가 작으니 항상 효율적인가요?**

UDP 헤더 자체는 단순합니다.

하지만 애플리케이션이 신뢰성, 보안, 혼잡 제어를 구현하기 위해 별도 헤더와 상태를 추가하면 전체 오버헤드가 커질 수 있습니다.

따라서 기본 헤더 크기만으로 실제 효율을 판단하면 안 됩니다.

⸻

**Q14. 실시간 서비스에서는 무조건 UDP가 좋은가요?**

아닙니다.

지연에 민감하면서 일부 손실을 허용할 수 있는 데이터에는 UDP가 적합할 수 있습니다.

하지만 다음 상황에서는 TCP나 QUIC이 더 적절할 수 있습니다.

전송량이 적음

손실을 허용할 수 없음

구현 단순성이 중요함

일반적인 브라우저 환경에서 동작해야 함

방화벽 호환성이 중요함

실시간이라는 이유만으로 UDP를 선택하는 것이 아니라, 데이터의 수명과 손실 허용도를 함께 판단해야 합니다.

⸻

**Q15. TCP와 UDP를 동시에 사용할 수도 있나요?**

가능합니다.

하나의 애플리케이션에서 데이터 특성에 따라 TCP와 UDP를 모두 사용할 수 있습니다.

TCP

→ 로그인, 채팅, 중요 명령

UDP

→ 실시간 위치, 음성, 상태 갱신

다만 연결 관리, 보안, 장애 처리, 서버 구조가 복잡해질 수 있으므로 얻는 이점이 충분한지 검토해야 합니다.
