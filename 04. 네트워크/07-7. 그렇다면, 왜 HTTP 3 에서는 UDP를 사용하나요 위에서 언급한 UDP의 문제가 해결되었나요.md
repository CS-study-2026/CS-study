# 7-7. 그렇다면, 왜 HTTP/3 에서는 UDP를 사용하나요? 위에서 언급한 UDP의 문제가 해결되었나요?

# 0. 간단히 보는 사전 지식

## 1. TLS (Transport Layer Security)

  - 정의

    - 인터넷 상에서 **통신 보안을 제공하기 위해 설계된 암호화 프로토콜**. 과거에 사용되던 SSL(Secure Sockets Layer)의 결함을 보완하며 발전한 상위 버전인데, 현업에서도 관습적으로 SSL/TLS를 혼용해서 부르기도 함.

  - 역할 및 용도

    - **데이터 암호화**: 클라이언트와 서버가 주고받는 데이터를 암호화하여 중간에 누군가 패킷을 가로채더라도 내용을 알 수 없게 함

    - **무결성 검증**: 전송 중에 데이터가 변조되지 않았음을 보증

    - **인증**: 접속한 서버가 신뢰할 수 있는 진짜 서버인지 인증서(Certificate)를 통해 확인.

    - **주요 용도**: HTTPS → HTTP에 TLS를 얹은 것. 

      - 로그인, 결제 등 보안이 필요한 모든 웹 통신의 표준.

## 2. HoL Blocking (Head-of-Line Blocking)

  - 정의

    - 네트워크나 큐(Queue) 구조에서 맨 앞에 있는 첫 번째 데이터(패킷)의 처리가 지연되거나 유실되면, 그 뒤에 있는 정상적인 데이터들까지 전부 전송이 막혀서 대기하게 되는 병목 현상

  - 발생 위치에 따른 구분

    - **L7 (애플리케이션 계층) HoL Blocking**: HTTP/1.1에서 하나의 TCP 연결로 여러 요청을 보낼 때, 앞선 요청의 응답이 늦어지면 뒤의 응답들도 줄줄이 대기하는 현상

    - **L4 (전송 계층) HoL Blocking**: HTTP/2에서 하나의 TCP 연결 안에 여러 스트림을 쪼개서 보낼 때 발생. 스트림 A의 패킷 하나가 유실되면, TCP는 순서대로 데이터를 상위 계층에 올려보내야 하므로 아무 문제 없는 스트림 B, C의 데이터까지 수신 버퍼에서 대기

## 3. HTTP 뒤에 붙는 숫자의 의미와 특징

HTTP 뒤의 숫자는 프로토콜의 버전을 의미.

웹 기술이 발전하며 전송 속도와 효율성을 높이기 위해 규격을 개정해 온 역사로 이해하자.

### HTTP/1.1

  - 특징: 텍스트 기반 프로토콜. 동시 전송이 불가능해서 하나의 TCP 연결에서 요청과 응답이 순차적으로만 이루어짐. 이 때문에 L7 HoL Blocking 문제가 심했음.

  - 용도: 과거 웹 표준의 기반이었으며, 현재도 고속 전송이 필요 없는 단순 레거시 시스템이나 내부 API 통신 등에서 여전히 사용.

### HTTP/2

  - 특징: 데이터 형식을 텍스트에서 바이너리(Binary Frame)로 바꾸고, 하나의 TCP 연결 안에서 여러 개의 독립적인 스트림을 통해 데이터를 동시에 주고받는 멀티플렉싱(Multiplexing)을 도입. L7 레벨의 HoL Blocking은 해결했지만, 앞서 말한 L4(TCP) 레벨의 HoL Blocking 한계가 있음

  - 용도: 현대 대다수의 일반적인 웹 서비스와 이미지, CSS 등 자원이 많이 필요한 웹 페이지 로딩 성능을 높이기 위해 표준으로 널리 쓰임

### HTTP/3

  - 특징: 전송 계층을 TCP에서 UDP(QUIC 프로토콜)로 완전히 바꾼 최신 규격. 스트림별로 독립적인 패킷 번호를 부여하여 L4 레벨의 HoL Blocking마저 완벽히 해결. 연결 수립 과정(Handshake)을 최소화해서 첫 데이터가 나가는 속도도 획기적으로 감소

  - 용도: 구글, 유튜브, 네이버 등 대규모 트래픽을 처리하는 글로벌 웹 서비스에서 주로 사용. 특히 사용자가 이동하면서 기기의 IP가 자주 바뀌는 모바일 환경이나 대용량 미디어 스트리밍 환경에서 압도적 성능 발휘

> **핵심 요약**
TCP가 신뢰성을 위해 유지해 온 메커니즘들이 현대의 대용량·고속 웹 환경에서는 오히려 **성능 병목(지연 시간 증가, HoL Blocking)**을 일으키는 원인이 됨.

HTTP/3는 아무런 기능이 없는 가벼운 **UDP** 위에 **QUIC** 프로토콜을 얹어 속도와 신뢰성을 모두 확보

### 1. 기존 TCP의 구조적 한계 (HTTP/3 등장 배경)

- **연결 설정 지연 (Handshake Overhead)**

  - TCP 위에서 보안 통신(HTTPS)을 하려면 TCP Handshake(1 RTT)와 TLS Handshake(1~2 RTT)가 순차적으로 일어나야 하므로, 데이터를 보내기 전 최소 **2~3 RTT의 지연 시간**이 발생

- **전송 계층의 HoL (Head-of-Line) Blocking**

  - HTTP/2는 하나의 TCP 연결 내에서 여러 스트림을 동시에 전송(Multiplexing)

  - 그러나 TCP 관점에서는 전체가 하나의 파이프라인이기 때문에, **스트림 A의 패킷 하나만 유실되어도 수신측 버퍼가 잠겨** 정상 도착한 스트림 B, C의 데이터까지 대기해야 하는 병목이 발생

- **IP 모빌리티 문제**

  - TCP는 `송신 IP/포트, 수신 IP/포트` 조합으로 연결을 식별합니다. 사용자가 Wi-Fi에서 LTE로 전환되어 IP가 바뀌면 기존 연결이 끊어지고 Handshake를 처음부터 다시 해야 합니다.

### 2. HTTP/3가 UDP를 선택한 이유

- UDP는 기능이 없는 빈 도화지 같은 프로토콜.

- 흐름 제어도, 연결 설정도 없음.

- 구글과 IETF는 이 점을 역이용하여, **커널 영역을 수정할 필요 없이 애플리케이션 계층에서 개발자가 원하는 대로 신뢰성 제어 로직을 직접 구현하기 위해** UDP를 선택.

- 이 UDP 기반의 새로운 전송 프로토콜이 바로 **QUIC(Quick UDP Internet Connections).**

### 3. UDP의 문제점(신뢰성 부재)은 해결되었나요?

**UDP 자체는 변하지 않았지만 상위 레이어인 QUIC 프로토콜을 통해 완벽하게 해결됨!**

- **자체 신뢰성 및 혼잡 제어 구현**

  - QUIC 레이어에서 패킷마다 고유 번호를 부여하고, 패킷 유실 시 자체적으로 재전송을 제어하여 **TCP와 동등한 수준의 신뢰성을 보장**

- **독립적 스트림을 통한 HoL Blocking 완벽 해제**

  - QUIC은 **각 스트림별로 독립적인 시퀀스 번호 소유**하여, 스트림 A의 패킷이 유실되어 재전송되더라도, 스트림 B와 C는 아무런 방해를 받지 않고 상위 계층으로 즉시 전달

- **Handshake 지연 시간 단축 (1 RTT / 0 RTT)**

  - QUIC은 전송 연결과 암호화(TLS 1.3) 과정을 하나로 통합. 첫 연결 시 단 **1 RTT**만에 데이터 전송이 가능하며, **재연결 시에는 이전 세션 정보를 활용해 핸드셰이크 없이 데이터를 보내**는 **0 RTT**를 실현

- **Connection ID를 통한 연결 마이그레이션 (Connection Migration)**

  - IP 주소가 아닌, 고유한 **Connection ID**로 연결을 식별. Wi-Fi에서 셀룰러로 망이 바뀌어 IP가 변경되더라도 끊김 없이 통신을 유지

### 📊 [참고] TCP vs QUIC(HTTP/3) 핵심 비교 요약

| 비교 항목 | TCP (HTTP/1.1, HTTP/2) | QUIC / UDP 기반 (HTTP/3) |
| --- | --- | --- |
| **연결 수립 지연** | 최소 2~3 RTT (TCP + TLS 각각 수행) | **1 RTT** (통합 수행) / 재연결 시 **0 RTT** |
| **HoL Blocking** | 전송 계층 유실 시 전체 스트림 병목 발생 | **스트림 독립 제어**로 HoL Blocking 제거 |
| **연결 식별 기준** | IP 주소 + 포트 번호 조합 | **Connection ID** (IP 변경돼도 세션 유지) |
| **구현 영역** | OS 커널 영역 (수정 및 업데이트 대단히 어려움) | **애플리케이션(사용자) 영역** (유연한 기능 개선 가능) |
