# 1-2. HTTP의 특성인 Stateless에 대해 설명해 주세요.

## **Stateless란?**

Stateless는 **서버가 클라이언트의 이전 요청 상태를 기억하지 않는 특성**을 의미합니다.

즉, HTTP에서 각 요청은 서로 독립적이며, 서버는 현재 요청만 보고 처리합니다.

---

## **예시**

사용자가 쇼핑몰에서 다음과 같은 요청을 보낸다고 가정해보겠습니다.

```plain text
1. 로그인 요청
2. 상품 조회 요청
3. 장바구니 조회 요청
```

Stateless한 HTTP에서는 서버가

```plain text
"이 사용자가 조금 전에 로그인했었지?"
```

를 기억하지 않습니다.

따라서 모든 요청은 독립적으로 처리됩니다.

---

## **왜 Stateless로 설계되었을까?**

### **1. 서버 확장성이 좋아진다**

서버가 사용자 상태를 기억하지 않으므로

```plain text
사용자 A → 서버 1
사용자 A → 서버 2
사용자 A → 서버 3
```

어느 서버가 요청을 받아도 처리할 수 있습니다.

즉, 로드밸런싱과 서버 증설이 쉬워집니다.

---

### **2. 서버 메모리 사용량 감소**

Stateful이라면

```plain text
사용자 100만 명
→ 서버가 100만 명 상태 저장
```

이 필요하지만,

Stateless는 요청 자체에 필요한 정보가 포함되므로

서버가 별도의 사용자 상태를 유지할 필요가 없습니다.

---

### **3. 장애 복구가 쉽다**

특정 서버가 죽더라도

```plain text
서버1 장애 발생
↓
서버2가 요청 처리
```

가 가능합니다.

상태가 서버 내부에 없기 때문입니다.

---

# **Stateless의 문제점**

로그인 상태를 유지하기 어렵습니다.

예를 들어

```plain text
1. 로그인 성공
2. 마이페이지 요청
```

에서 서버는 사용자가 로그인했는지 기억하지 못합니다.

따라서 인증 정보를 매 요청마다 전달해야 합니다.

이를 해결하기 위해 사용하는 것이

- 쿠키(Cookie)

- 세션(Session)

- JWT

등의 인증 방식입니다.

---

# **Stateful vs Stateless**

| **구분** | **Stateful** | **Stateless** |
| --- | --- | --- |
| 상태 저장 | 서버 | 저장하지 않음 |
| 이전 요청 기억 | O | X |
| 서버 확장성 | 낮음 | 높음 |
| 장애 대응 | 어려움 | 쉬움 |
| 예시 | TCP 연결 상태, 세션 서버 | HTTP |

---

# **면접 답변 예시**

HTTP의 Stateless란 서버가 클라이언트의 상태를 저장하지 않는 특성입니다.

따라서 각 HTTP 요청은 서로 독립적으로 처리되며, 서버는 이전 요청 정보를 기억하지 않습니다.

이러한 구조는 서버의 확장성과 장애 대응 측면에서 유리하지만, 로그인 상태와 같은 사용자 정보를 유지하기 어렵다는 단점이 있습니다.

그래서 실제 서비스에서는 쿠키, 세션, JWT 등을 활용하여 인증 상태를 관리합니다.

---

# **꼬리 질문 대비**

## **Q1. Stateless인데 왜 세션을 사용하나요?**

HTTP 자체는 Stateless이지만,

애플리케이션 레벨에서 로그인 상태를 유지해야 하는 요구사항이 있습니다.

그래서 서버가 별도로 세션 저장소를 두고 상태를 관리합니다.

즉,

```plain text
HTTP → Stateless
애플리케이션 → 필요에 따라 Stateful하게 구현
```

하는 것입니다.

---

## **Q2. 세션을 사용하면 Stateful 아닌가요?**

맞습니다.

세션 기반 인증은 서버가 사용자 상태를 저장하므로 Stateful 방식입니다.

따라서 서버 확장 시

```plain text
- 세션 클러스터링 (여러 대의 서버가 동일한 세션 정보를 공유하도록 만드는 기술)
- Redis 세션 저장소
```

같은 추가적인 관리가 필요합니다.

---

## **Q3. JWT가 등장한 이유는 무엇인가요?**

세션은 서버가 상태를 저장해야 하므로 확장성에 제약이 있습니다.

JWT는 사용자 정보를 토큰에 담아 클라이언트가 보관하므로 서버가 상태를 저장하지 않아도 됩니다.

즉,

```plain text
세션 → Stateful
JWT → Stateless
```

구조를 만들 수 있습니다.

---

# **면접에서 많이 나오는 함정**

### **❌ “HTTP는 상태를 저장할 수 없습니다.”**

틀린 표현입니다.

HTTP 프로토콜 자체는 Stateless이지만,

애플리케이션은 쿠키, 세션, JWT 등을 통해 상태를 관리할 수 있습니다.

정확한 표현은

**HTTP는 기본적으로 Stateless 프로토콜이며, 상태 유지는 별도의 메커니즘을 통해 구현한다.**

입니다.

---

# **한 줄 정리**

HTTP의 Stateless란 서버가 클라이언트의 이전 요청 상태를 기억하지 않는 특성으로, 각 요청은 독립적으로 처리되며 확장성과 장애 대응에 유리하지만 상태 유지가 어려워 쿠키, 세션, JWT 등의 기술을 함께 사용한다.
