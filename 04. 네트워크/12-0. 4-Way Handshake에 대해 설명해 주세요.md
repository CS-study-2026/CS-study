# 12-0. 4-Way Handshake에 대해 설명해 주세요

## 1. 먼저 결론

**4-Way Handshake는 TCP 연결을 정상적으로 종료하기 위한 과정**입니다.

TCP는 양방향 통신을 지원합니다.

즉, 한 번 연결이 만들어지면 양쪽이 모두 데이터를 보낼 수 있습니다.

```plain text
Client  → Server
Client  ← Server
```

그래서 연결을 종료할 때도 단순히 한 번에 끊는 것이 아니라, **각 방향의 데이터 전송을 따로 종료**해야 합니다.

한쪽이 “나는 더 이상 보낼 데이터가 없다”고 말하더라도, 반대쪽은 아직 보낼 데이터가 남아 있을 수 있습니다.

이 때문에 TCP 종료 과정은 보통 다음 네 단계로 설명합니다.

```plain text
1. FIN
2. ACK
3. FIN
4. ACK
```

이 과정을 흔히 **4-Way Handshake**라고 부릅니다.

---

# 2. 왜 4번의 과정이 필요한가?

TCP 연결은 양방향입니다.

```plain text
A → B 방향
B → A 방향
```

이 두 방향은 논리적으로 따로 닫힐 수 있습니다.

예를 들어 클라이언트가 서버에게 요청을 다 보냈다고 해도, 서버는 아직 응답 데이터를 보내는 중일 수 있습니다.

```plain text
Client:
나는 더 이상 보낼 데이터가 없음

Server:
나는 아직 보낼 데이터가 남아 있음
```

그래서 TCP에서는 한쪽이 먼저 `FIN`을 보내도, 반대쪽은 바로 연결 전체를 끊지 않고 `ACK`로 확인한 뒤 남은 데이터를 마저 보낼 수 있습니다.

이 상태를 **Half-Close**라고 볼 수 있습니다.

```plain text
한쪽 방향은 닫힘
반대 방향은 아직 열려 있음
```

---

# 3. 4-Way Handshake 기본 흐름

클라이언트가 먼저 연결 종료를 요청한다고 가정하겠습니다.

```plain text
Client                                Server
  |                                     |
  |  1. FIN ------------------------->  |
  |                                     |
  |  <------------------------- 2. ACK  |
  |                                     |
  |  <------------------------- 3. FIN  |
  |                                     |
  |  4. ACK ------------------------->  |
  |                                     |
```

각 단계의 의미는 다음과 같습니다.

---

## 3-1. 1단계: Client → Server, FIN

클라이언트가 서버에게 `FIN`을 보냅니다.

```plain text
Client:
나는 더 이상 보낼 데이터가 없습니다.
```

이때 중요한 점은 **클라이언트가 데이터를 더 이상 보내지 않겠다는 뜻**이지, 서버도 당장 보내기를 멈춰야 한다는 뜻은 아닙니다.

```plain text
Client → Server 방향 종료 요청
```

---

## 3-2. 2단계: Server → Client, ACK

서버는 클라이언트의 `FIN`을 받았다는 의미로 `ACK`를 보냅니다.

```plain text
Server:
종료 요청을 확인했습니다.
```

이 시점에서 클라이언트에서 서버로 가는 방향은 닫히는 흐름에 들어갑니다.

하지만 서버는 아직 클라이언트에게 데이터를 보낼 수 있습니다.

```plain text
Client → Server 방향:
종료됨

Server → Client 방향:
아직 가능
```

---

## 3-3. 3단계: Server → Client, FIN

서버도 보낼 데이터를 모두 보냈다면 클라이언트에게 `FIN`을 보냅니다.

```plain text
Server:
나도 이제 더 이상 보낼 데이터가 없습니다.
```

이제 서버도 자신의 송신 방향을 닫겠다고 알리는 것입니다.

```plain text
Server → Client 방향 종료 요청
```

---

## 3-4. 4단계: Client → Server, ACK

클라이언트는 서버의 `FIN`을 받았다는 의미로 `ACK`를 보냅니다.

```plain text
Client:
서버의 종료 요청을 확인했습니다.
```

이제 양쪽 모두 더 이상 보낼 데이터가 없다는 것이 확인되었고, TCP 연결은 종료됩니다.

---

# 4. 상태 변화로 보는 4-Way Handshake

TCP는 연결 종료 중에도 상태를 관리합니다.

클라이언트가 먼저 종료를 요청하는 경우를 단순화하면 다음과 같습니다.

```plain text
Client 측:

ESTABLISHED
→ FIN_WAIT_1
→ FIN_WAIT_2
→ TIME_WAIT
→ CLOSED
```

서버 측은 대략 다음 흐름을 가질 수 있습니다.

```plain text
Server 측:

ESTABLISHED
→ CLOSE_WAIT
→ LAST_ACK
→ CLOSED
```

각 상태를 간단히 보면 다음과 같습니다.

| 상태 | 의미 |
| --- | --- |
| ESTABLISHED | 연결이 정상적으로 열려 있는 상태 |
| FIN_WAIT_1 | 내가 FIN을 보내고 ACK를 기다리는 상태 |
| FIN_WAIT_2 | 내 FIN에 대한 ACK는 받았고, 상대 FIN을 기다리는 상태 |
| CLOSE_WAIT | 상대의 FIN을 받았고, 애플리케이션이 종료 처리를 해야 하는 상태 |
| LAST_ACK | 나도 FIN을 보냈고, 마지막 ACK를 기다리는 상태 |
| TIME_WAIT | 마지막 ACK를 보낸 뒤 일정 시간 대기하는 상태 |
| CLOSED | 연결이 완전히 종료된 상태 |

단, 여기서 `TIME_WAIT`의 자세한 이유는 별도 질문인 12-4에서 다루는 것이 자연스럽습니다.

이 발표에서는 다음 정도만 말하면 충분합니다.

> 먼저 종료를 요청한 쪽은 마지막 ACK를 보낸 뒤 바로 사라지지 않고 TIME_WAIT 상태로 잠시 대기할 수 있습니다.

---

# 5. 왜 3-Way가 아니라 4-Way인가?

연결을 만들 때는 3-Way Handshake를 사용합니다.

```plain text
SYN
SYN + ACK
ACK
```

하지만 종료는 보통 4단계로 설명합니다.

```plain text
FIN
ACK
FIN
ACK
```

이 차이는 **TCP 연결이 양방향 통신이라는 점** 때문에 생깁니다.

연결을 만들 때는 양쪽이 연결 의사를 확인하면 됩니다.

하지만 연결을 끊을 때는 다음 두 가지를 각각 확인해야 합니다.

```plain text
1. A가 더 이상 보낼 데이터가 없는가?
2. B가 더 이상 보낼 데이터가 없는가?
```

한쪽이 종료 요청을 보냈다고 해서 반대쪽도 즉시 종료할 준비가 되어 있다고 보장할 수 없습니다.

따라서 한쪽의 FIN에 대해 ACK를 먼저 보내고, 반대쪽도 준비가 되었을 때 별도로 FIN을 보낼 수 있습니다.

---

# 6. 항상 정확히 패킷 4개인가?

개념적으로는 4-Way Handshake라고 부르지만, 실제 네트워크 패킷이 항상 정확히 4개로만 나뉘는 것은 아닙니다.

예를 들어 서버가 클라이언트의 FIN을 받았을 때 이미 보낼 데이터가 없고 바로 종료할 준비가 되어 있다면, `ACK`와 `FIN`을 하나의 TCP 세그먼트에 함께 담아 보낼 수 있습니다.

```plain text
Client                                Server
  |                                     |
  |  FIN ---------------------------->  |
  |                                     |
  |  <----------------------- FIN + ACK |
  |                                     |
  |  ACK ---------------------------->  |
  |                                     |
```

이 경우 실제로는 3개의 세그먼트처럼 보일 수 있습니다.

하지만 논리적으로는 다음 두 동작이 모두 일어난 것입니다.

```plain text
상대 FIN에 대한 ACK
+
내 송신 방향 종료를 알리는 FIN
```

따라서 중요한 것은 “패킷이 무조건 4개”가 아니라, **양쪽 송신 방향을 각각 종료하고 확인한다는 구조**입니다.
