# 4-1. 공개키와 대칭키에 대해 설명해 주세요.

## 암호화가 필요한 이유

HTTP는 기본적으로 데이터를 평문(Plain Text)으로 전송합니다.

예를 들어 로그인 요청이 있다면

```plain text
id=user1
password=1234
```

와 같은 정보가 네트워크를 통해 그대로 전달될 수 있습니다.

이를 방지하기 위해 데이터를 암호화하여 전송

대표적인 방식이 **대칭키 암호화**와 **공개키 암호화**입니다.

---

# **1. 대칭키 암호화**

대칭키 암호화는

암호화와 복호화에 동일한 키를 사용하는 방식

입니다.

```plain text
평문
 ↓
[비밀키]
 ↓
암호문
 ↓
[비밀키]
 ↓
평문
```

---

## **예시**

철수와 영희가 같은 비밀번호를 알고 있다고 가정합니다.

```plain text
비밀키 = 1234
```

철수

```plain text
HELLO
↓
1234로 암호화
↓
암호문 전송
```

영희

```plain text
암호문 수신
↓
1234로 복호화
↓
HELLO
```

---

## **장점**

- 암호화 속도가 빠름

- 대용량 데이터 처리에 적합

---

## **단점**

- 키를 안전하게 전달하기 어려움

예를 들어

```plain text
암호화 키 = 1234
```

를 상대방에게 보내는 과정에서 탈취되면 암호화 의미가 없어집니다.

이를 **키 교환 문제(Key Exchange Problem)** 라고 합니다.

---

## **대표 알고리즘**

- AES

- DES

- 3DES

실무에서는 대부분 AES 사용

---

# **2. 공개키 암호화 (비대칭키 암호화)**

암호화 키와 복호화 키가 서로 다른 방식

```plain text
공개키(Public Key)
개인키(Private Key)
```

를 한 쌍으로 사용합니다.

---

## **기본 원리**

```plain text
공개키로 암호화
↓
개인키로 복호화
```

공개키는 누구나 알아도 되지만,

개인키는 소유자만 가지고 있습니다.

---

## **예시**

서버가

```plain text
공개키
개인키
```

를 가지고 있다고 가정합니다.

사용자는 서버의 공개키를 받습니다.

```plain text
비밀번호
↓
공개키로 암호화
↓
전송
```

서버는

```plain text
암호문
↓
개인키로 복호화
↓
비밀번호 확인
```

합니다.

공개키가 노출되어도 개인키가 없으면 복호화할 수 없습니다.

---

## **장점**

- 키 교환 문제 해결

- 안전하게 통신 시작 가능

---

## **단점**

- 연산량이 많음

- 암호화 속도가 느림

---

## **대표 알고리즘**

- RSA

- ECC(Elliptic Curve Cryptography)

---

# **대칭키 vs 공개키 비교**

| **구분** | **대칭키** | **공개키** |
| --- | --- | --- |
| 사용 키 | 1개 | 2개 |
| 암호화/복호화 | 동일 키 | 서로 다른 키 |
| 속도 | 빠름 | 느림 |
| 보안성 | 키 전달 문제 존재 | 키 전달 문제 해결 |
| 사용 목적 | 데이터 암호화 | 키 교환, 인증 |

### ❓속도차이가 나는 이유는?

> **공개키 암호화는 수학적으로 훨씬 복잡한 연산을 수행하기 때문입니**

# **대칭키는 왜 빠를까?**

AES 같은 대칭키 암호화는

```plain text
XOR
치환(Substitution)
비트 연산
```

위주의 단순한 연산을 반복합니다.

컴퓨터 CPU가 매우 빠르게 처리할 수 있습니다.

그래서

```plain text
수 MB
수 GB
```

단위 데이터도 빠르게 암호화할 수 있습니다.

---

# **공개키는 왜 느릴까?**

RSA 같은 공개키 암호화는

```plain text
엄청 큰 소수
모듈러 연산
거듭제곱 연산
```

을 수행합니다.

예를 들어 RSA는 내부적으로

```plain text
123456789^65537 mod N
```

같은 계산을 수행합니다.

이런 연산은 CPU 입장에서 매우 비쌉니다.

---

> Note 

### ❓사용 목적?

---

대칭키(AES)
→ 실제 데이터 암호화 담당
→ 빠름
→ 하지만 키를 어떻게 전달할지가 문제

공개키(RSA, ECC)
→ 대칭키를 안전하게 전달하는 역할
→ 서버 신원 인증 역할
→ 하지만 느림

---

# **HTTPS에서는 어떻게 사용할까?**

실무에서는 둘을 함께 사용합니다.

왜냐하면

```plain text
공개키 → 안전하지만 느림
대칭키 → 빠르지만 키 교환 문제 존재
```

하기 때문입니다.

---

## **HTTPS 통신 과정**

### **1단계**

서버가 공개키를 제공

```plain text
Client ← Public Key ← Server
```

---

### **2단계**

클라이언트가 랜덤한 대칭키 생성

```plain text
대칭키 = ABCD
```

---

### **3단계**

대칭키를 공개키로 암호화

```plain text
ABCD
↓
공개키 암호화
↓
서버 전송
```

---

### **4단계**

서버가 개인키로 복호화

```plain text
암호문
↓
개인키 복호화
↓
ABCD 획득
```

---

### **5단계**

이후 통신

```plain text
클라이언트 ↔ 서버

대칭키(ABCD) 사용
```

으로 빠르게 통신

---

# **면접 답변 예시**

대칭키 암호화는 암호화와 복호화에 동일한 키를 사용하는 방식으로, 속도가 빠르지만 키를 안전하게 전달해야 한다는 문제가 있습니다.

공개키 암호화는 공개키와 개인키를 사용하는 비대칭키 방식으로, 공개키로 암호화한 데이터는 개인키로만 복호화할 수 있습니다. 키 교환 문제를 해결할 수 있지만 연산 비용이 높다는 단점이 있습니다.

따라서 HTTPS에서는 공개키 암호화를 이용해 대칭키를 안전하게 교환한 뒤, 실제 데이터 통신은 속도가 빠른 대칭키 암호화를 사용합니다.

---

# **꼬리 질문 대비**

## **Q. HTTPS는 공개키 암호화만 사용하나요?**

아닙니다.

실제 데이터 통신은 대칭키를 사용하고,

공개키는 대칭키를 안전하게 교환하기 위해 사용합니다.

---

## **Q. 공개키가 노출되어도 괜찮나요?**

괜찮습니다.

공개키는 원래 공개를 목적으로 만들어졌으며,

복호화는 개인키로만 가능합니다.

---

## **Q. 왜 공개키로 모든 데이터를 암호화하지 않나요?**

공개키 암호화는 연산 비용이 매우 크고 느립니다.

그래서 실제 데이터 통신은 AES 같은 대칭키 암호화를 사용합니다.

---

# **한 줄 정리**

대칭키 암호화는 하나의 키로 암호화와 복호화를 수행하는 빠른 방식이고, 공개키 암호화는 공개키와 개인키를 사용하는 안전한 방식이며, HTTPS는 두 방식을 함께 사용하여 보안성과 성능을 모두 확보한다.
