# 14-2. UDP와 TCP 중 어떤 것을 사용하나요?

> 💡 DNS는 상황과 조건에 따라 UDP와 TCP를 모두 사용하는 **하이브리드 프로토콜**

  - 기본 질의에는 UDP를 기본값으로 사용

  - 특정 조건이 발생하면 포트 번호 53번을 그대로 유지한 채 TCP 연결로 전환

    - 포트 번호 53번은 특정 전송 프로토콜(UDP) 전용 번호가 아니라, DNS라는 서비스에 예약된 번호

    - 따라서 통신 상황의 필요에 따라 UDP 53번 포트와 TCP 53번 포트를 유연하게 오가며 사용한다고 이해해야 네트워크 인프라 관점에서 완벽하게 정확한 답변이 됩니다.

### 상황별 프로토콜 선택 기준

| **프로토콜** | **주 사용 시나리오** | **선택의 기술적 이유** |
| --- | --- | --- |
| UDP | 일반적인 클라이언트의 단발성 도메인 주소 질의 및 응답 | 연결 설정 과정이 없어 오버헤드가 매우 낮고 속도가 빠름. 요청과 응답이 각각 단 하나의 패킷으로 종결되므로 지연 시간이 최소화. |
| TCP | DNS 존 트랜스퍼 (서버 간 동기화) 및 512바이트 초과 데이터 전송 | 마스터와 슬레이브 서버 간의 데이터베이스 동기화는 단 1비트의 손실도 허용하지 않는 절대적 신뢰성 필요. 또한 응답 크기가 UDP 한계를 넘으면 데이터 유실 방지를 위해 강제 전환. |

### 세부 전환 메커니즘 설명

> 💡 

일반 조회 시 **UDP를 최우선으로 고집**하는 이유

  - TCP라면?

    - 인터넷 상의 수많은 단말이 끊임없이 DNS 요청을 보냄

    - 만약 매번 주소를 찾을 때마다 TCP의** 3-way handshake**를 수행해야 한다면, 전 세계 네임 서버들은 수만 개의 **가상 연결 세션을 유지하느라 메모리와 CPU 연산 자원이 즉시 고갈**될 것

---

  - 그럼 UDP는?

    - 세션 연결 없이 패킷 하나만 던지고 답을 받으면 끝

    - 그렇기에 서버 자원을 극도로 아낄 수 있어 대규모 트래픽 처리에 훨씬 유리

    - 만약 중간에 패킷이 유실되면, 클라이언트 측에서 일정 시간 후 다시 UDP 재요청을 보내면 되므로 전송 계층의 무거운 제어 로직이 불필요

> 💡 

TCP로 강제 전환되는 메커니즘 (Truncation)

  - 전통적인 표준 UDP DNS 응답 패킷의 최대 유효 크기는 512바이트로 제한

  - 만약 권한 있는 네임 서버가 반환해야 하는 응답 데이터(예: 대량의 IPv6 주소 레코드 목록 또는 DNSSEC 암호화 서명 값 등)가 너무 커서 512바이트를 초과하게 되는 상황이 발생하면 **특수한 흐름**이 시작

---

  - **특수한 흐름(TCP 폴백 메커니즘)**

    - 네임 서버는 우선 512바이트까지만 데이터를 채운 뒤, DNS 헤더 내부의 TC(Truncated, 잘림) 플래그 비트를 1로 설정하여 클라이언트에게 전송

    - 이 응답을 받은 리커시브 리졸버는 데이터가 중간에 잘려서 유실되었음을 감지

    - 리졸버는 즉시 해당 네임 서버의 53번 포트로 TCP 핸드셰이크를 수행하여 논리적 연결 수립

    - 이후 신뢰성이 보장되고 용량 제한이 없는 TCP 세그먼트 파이프라인을 통해 전체 도메인 데이터를 안전하게 다시 수신

최근에는 확장 규격인 EDNS0를 통해 **UDP에서도 512바이트 이상을 전송하는 기법이 보편화**되었으나, 이를 지원하지 않는 환경이나 보안 서명이 거대한 경우에는 여전히 이 **TCP 폴백(Fallback) 메커니즘**이 핵심 안정 장치로 작동하고 있습니다.
