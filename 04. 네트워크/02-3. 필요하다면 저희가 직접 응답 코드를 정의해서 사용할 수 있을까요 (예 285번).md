# 2-3. 필요하다면 저희가 직접 응답 코드를 정의해서 사용할 수 있을까요? (예: 285번)

## 🚨 결론부터 말씀드리면:

**기술적으로는 동작하지만, 절대 그렇게 사용하면 안됨. (치명적인 안티 패턴)**

> **안티 패턴(Anti-Pattern)이란?**

실무에서 많이 사용되는 것 같지만, 실제로는 비효율적이거나 나중에 큰 문제를 일으킬 수 있어서 '피해야 하는 나쁜 코딩 습관/구조'를 의미

### ❌ 커스텀 상태 코드를 쓰면 안 되는 이유 (상호 운용성 파괴)

HTTP 상태 코드는 전 세계 웹 생태계가 공통으로 지키기로 한** '국제 표준 약속(RFC 9110)'**입니다. 클라이언트와 서버 중간에 있는 수많은 네트워크 장비들은 이 표준 코드만 알아듣습니다.

1. **브라우저 및 클라이언트 라이브러리의 혼란:**

  - 크롬, 사파리 같은 브라우저나 데이터를 받아오는 라이브러리(Axios, Fetch 등)는 `285`라는 코드를 모릅니다.

  - "이게 성공이야, 실패야?" 하고 혼란을 겪다가 알 수 없는 에러를 뱉어내거나, 앞자리 `2`만 보고 그냥 일반적인 `200`처럼 뭉뚱그려 처리해 버릴 수 있습니다.

1. **프록시(Proxy) 및 CDN 장비의 오작동:**

  - **프록시/CDN:** 서버 앞단에서 트래픽을 분산하거나 데이터를 캐싱(임시 저장)해 주는 장비들입니다.

  - 이 장비들은 `200` 코드를 보면 "아, 이 데이터는 정상적이니 임시 저장해둬야지!" 하지만, `285`를 보면 해석하지 못하고 비정상적인 응답으로 간주해 캐싱 기능을 꺼버리거나 연결을 끊어버릴 수 있습니다.

### 💡 올바른 해결책: "비즈니스 상태 코드(Business Status Code) 사용하기"

표준 HTTP 상태 코드는 지키되, **'우리 서비스만의 상세한 상태'는 응답 본문(Body) 안에 JSON 데이터로 담아서 보내는 것**이 실무적인 정답입니다.

**[ 올바른 응답 예시 ]**

- **HTTP 상태 코드:** `200 OK` (네트워크 통신 자체는 성공했음을 알림)

- **응답 본문 (Body):**

```plain text
{
  "status": 285,        -> 이러면 그저 json 속성중 하나일 뿐
  "message": "사용자 맞춤형 특별 성공 케이스입니다.",
  "data": { ... }
}
```

이렇게 설계하면, 네트워크 장비나 브라우저는 `200`을 보고 정상적인 통신으로 인식하고, 실제 프론트엔드 개발자는 JSON 본문 안의 `"status": 285`를 읽고 그에 맞는 맞춤형 화면을 보여줄 수 있습니다.
