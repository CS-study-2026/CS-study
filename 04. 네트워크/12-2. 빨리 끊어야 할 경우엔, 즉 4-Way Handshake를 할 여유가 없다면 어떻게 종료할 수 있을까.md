# 12-2. 빨리 끊어야 할 경우엔, 즉 4-Way Handshake를 할 여유가 없다면 어떻게 종료할 수 있을까요?

## 1. 정상 종료와 강제 종료

TCP 연결을 종료하는 방법은 크게 두 가지로 볼 수 있습니다.

```plain text
정상 종료
→ FIN 기반 종료
→ 4-Way Handshake

강제 종료
→ RST 기반 종료
→ 즉시 연결 리셋
```

4-Way Handshake는 정상적인 종료입니다.

```plain text
나 더 이상 보낼 데이터 없어.
확인했어.
나도 더 이상 보낼 데이터 없어.
확인했어.
```

반면 빨리 끊어야 하거나 비정상 상황이 발생한 경우에는 `RST`를 사용할 수 있습니다.

---

## 2. RST란?

`RST`는 Reset의 의미입니다.

TCP 헤더의 `RST` 플래그가 설정된 세그먼트는 다음과 같은 의미를 가집니다.

```plain text
이 연결은 더 이상 유효하지 않다.
즉시 연결을 중단하라.
```

정상적인 FIN 기반 종료는 남은 데이터를 처리할 여지를 남깁니다.

하지만 RST는 상대에게 즉시 연결을 리셋하라고 알리는 방식입니다.

```plain text
FIN:
정상적으로 닫자.

RST:
이 연결은 즉시 끊는다.
```

---

## 3. RST가 사용되는 경우

RST는 보통 다음과 같은 상황에서 사용될 수 있습니다.

```plain text
1. 존재하지 않는 포트로 TCP 연결을 시도한 경우
2. 이미 닫힌 연결로 데이터가 온 경우
3. 애플리케이션이 연결을 강제로 종료한 경우
4. 비정상 패킷이나 예상하지 못한 세그먼트를 받은 경우
5. 더 이상 연결 상태를 유지할 수 없는 경우
```

예를 들어 서버의 8080 포트에서 아무 프로세스도 대기하지 않는데 클라이언트가 TCP 연결을 시도하면 서버는 RST로 응답할 수 있습니다.

```plain text
Client → Server: SYN to 8080
Server → Client: RST
```

이 의미는 다음과 같습니다.

```plain text
해당 포트에는 연결을 받을 프로세스가 없다.
연결을 만들 수 없다.
```

---

## 4. RST는 왜 빠른가?

RST는 FIN처럼 양방향 종료 확인을 기다리지 않습니다.

```plain text
FIN 방식:

FIN
ACK
FIN
ACK
```

RST 방식:

```plain text
RST
```

상대방이 RST를 받으면 해당 연결은 즉시 비정상 종료된 것으로 처리됩니다.

그래서 4-Way Handshake를 기다릴 여유가 없거나, 더 이상 정상적인 연결 상태를 유지할 수 없을 때 사용할 수 있습니다.

---

## 5. RST의 단점

RST는 빠르지만 안전한 정상 종료는 아닙니다.

문제는 다음과 같습니다.

```plain text
1. 아직 전송되지 않은 데이터가 버려질 수 있다.
2. 상대방이 아직 읽지 못한 데이터가 사라질 수 있다.
3. 애플리케이션에서는 연결 리셋 오류가 발생할 수 있다.
4. 정상 종료처럼 우아하게 마무리되지 않는다.
```

예를 들어 클라이언트가 서버에 데이터를 보내는 중에 RST로 끊으면, 서버는 일부 데이터만 받고 연결이 리셋될 수 있습니다.

```plain text
Client → Server: 데이터 1
Client → Server: 데이터 2
Client → Server: RST

Server:
데이터 3은 받지 못함
연결 리셋 감지
```

따라서 일반적인 종료에서는 FIN 기반 4-Way Handshake를 사용하는 것이 맞습니다.

RST는 빠르게 끊어야 하거나 비정상 상황을 처리하기 위한 방식으로 이해해야 합니다.

---

## 6. 애플리케이션에서의 예시

프로그래밍 언어에서 소켓을 닫을 때 일반적으로 `close()`를 호출하면 정상 종료 흐름이 진행될 수 있습니다.

```plain text
close()
→ 일반적으로 FIN 기반 종료
```

반면 특정 옵션을 사용하면 RST에 가까운 종료를 유도할 수 있습니다.

예를 들어 소켓의 linger 옵션을 0으로 설정한 뒤 닫으면, 운영체제는 남은 데이터를 정상적으로 보내기보다 연결을 리셋하는 방식으로 처리할 수 있습니다.

개념적으로는 다음과 같습니다.

```plain text
정상 close
→ 남은 데이터 처리 후 FIN

강제 close
→ 남은 데이터 버리고 RST
```

다만 구체적인 동작은 운영체제와 소켓 옵션에 따라 다를 수 있으므로, 실무에서는 신중하게 사용해야 합니다.

---

# 7. FIN과 RST 비교

| 구분 | FIN | RST |
| --- | --- | --- |
| 의미 | 정상 종료 요청 | 연결 즉시 리셋 |
| 종료 방식 | 양방향 종료 확인 | 즉시 중단 |
| 데이터 처리 | 남은 데이터 처리 가능 | 남은 데이터 손실 가능 |
| 상대방 입장 | 정상 EOF로 인식 가능 | 연결 리셋 오류로 인식 |
| 사용 상황 | 일반적인 연결 종료 | 비정상 상황, 강제 종료 |
| Handshake | 4-Way Handshake | 별도 종료 Handshake 없음 |

---

# 8. 주의: RST는 무조건 좋은 빠른 종료가 아니다

RST는 빠르지만, 정상 종료의 대체재로 아무 때나 쓰면 안 됩니다.

정상적인 TCP 종료에서는 FIN을 사용해 양쪽이 더 이상 보낼 데이터가 없음을 확인합니다.

하지만 RST는 연결 상태를 즉시 제거하므로, 애플리케이션 데이터가 손실될 수 있습니다.

따라서 기준은 다음과 같습니다.

```plain text
정상적으로 마무리할 수 있다.
→ FIN 기반 4-Way Handshake

정상 종료를 기다릴 수 없거나 연결 상태가 비정상이다.
→ RST 기반 강제 종료
```

---

# 9. 최종 답변

> 4-Way Handshake는 TCP 연결을 정상적으로 종료하는 과정입니다. TCP는 양방향 통신이기 때문에 한쪽이 더 이상 데이터를 보내지 않겠다고 해서 반대쪽도 바로 종료할 수 있는 것은 아닙니다. 그래서 먼저 종료하려는 쪽이 FIN을 보내고, 상대가 ACK로 확인합니다. 이후 상대도 보낼 데이터를 모두 처리한 뒤 FIN을 보내고, 처음 종료를 요청했던 쪽이 ACK를 보내면서 양방향 연결이 종료됩니다.

이 과정의 패킷은 TCP 헤더의 FIN, ACK 플래그를 통해 확인할 수 있습니다. FIN은 더 이상 보낼 데이터가 없음을 의미하고, ACK는 상대의 FIN을 확인했다는 의미로 사용됩니다. 패킷 캡처에서는 보통 `[FIN, ACK]`, `[ACK]`, `[FIN, ACK]`, `[ACK]`와 같은 흐름으로 볼 수 있습니다.

만약 4-Way Handshake를 기다릴 여유가 없거나 비정상 상황이라면 RST 플래그를 사용해 연결을 즉시 리셋할 수 있습니다. RST는 빠르게 연결을 끊을 수 있지만, 아직 처리되지 않은 데이터가 손실될 수 있으므로 일반적인 정상 종료에는 FIN 기반 종료를 사용하는 것이 맞습니다.


# 예상 꼬리 질문

## Q1. 4-Way Handshake는 항상 패킷 4개로 이루어지나요?

항상 그렇지는 않습니다.

상대방이 FIN을 받은 직후 자신도 종료할 준비가 되어 있다면, ACK와 FIN을 하나의 세그먼트에 함께 실어 보낼 수 있습니다.

```plain text
FIN
FIN + ACK
ACK
```

이 경우 실제 패킷은 3개처럼 보일 수 있습니다.

하지만 논리적으로는 다음 네 동작이 모두 일어난 것입니다.

```plain text
내 FIN
상대의 ACK
상대의 FIN
내 ACK
```

---

## Q2. FIN을 보내면 바로 연결이 끊기나요?

아닙니다.

FIN은 “나는 더 이상 보낼 데이터가 없다”는 의미입니다.

상대방은 ACK를 보낸 뒤에도 자신이 보낼 데이터가 남아 있다면 계속 보낼 수 있습니다.

즉, 한쪽 방향만 먼저 닫힌 상태가 될 수 있습니다.

이를 Half-Close라고 볼 수 있습니다.

---

## Q3. FIN과 ACK가 같이 붙어 있는 이유는 무엇인가요?

TCP 연결 중에는 대부분의 세그먼트에 ACK 플래그가 함께 설정됩니다.

따라서 종료 요청도 보통 단순한 FIN이 아니라 `[FIN, ACK]` 형태로 보일 수 있습니다.

이때 FIN은 “내가 종료하겠다”는 의미이고, ACK는 “상대가 이전에 보낸 데이터는 여기까지 받았다”는 의미입니다.

---

## Q4. FIN도 시퀀스 번호를 사용하나요?

네.

FIN은 TCP 시퀀스 번호를 하나 소비합니다.

예를 들어 상대가 다음과 같은 FIN을 보냈다면:

```plain text
FIN
Seq = 100
```

이에 대한 ACK는 보통 다음과 같습니다.

```plain text
Ack = 101
```

즉, ACK 번호를 보면 상대방의 FIN을 정상적으로 확인했는지도 알 수 있습니다.

---

## Q5. RST와 FIN의 가장 큰 차이는 무엇인가요?

FIN은 정상 종료이고, RST는 강제 종료입니다.

```plain text
FIN
→ 정상적으로 연결을 닫자

RST
→ 이 연결은 즉시 무효다
```

FIN은 남은 데이터를 처리할 수 있지만, RST는 남은 데이터를 버리고 연결을 리셋할 수 있습니다.

---

## Q6. RST를 받으면 애플리케이션에서는 어떻게 보이나요?

보통 정상적인 EOF가 아니라 연결 리셋 오류로 보일 수 있습니다.

예를 들어 다음과 같은 오류가 발생할 수 있습니다.

```plain text
Connection reset by peer
```

즉, 상대가 정상적으로 닫은 것이 아니라 연결을 강제로 리셋했다고 볼 수 있습니다.

---

## Q7. 서버에서 CLOSE_WAIT이 많이 쌓이면 무슨 문제인가요?

`CLOSE_WAIT`은 상대방의 FIN을 받고 ACK까지 보냈지만, 내 애플리케이션이 아직 소켓을 닫지 않은 상태입니다.

즉, 서버 코드가 소켓을 제대로 close하지 않았을 가능성이 있습니다.

```plain text
상대 FIN 수신
→ ACK 전송
→ 애플리케이션이 close해야 함
→ close하지 않으면 CLOSE_WAIT 지속
```

CLOSE_WAIT이 많이 쌓이면 파일 디스크립터와 소켓 자원이 낭비될 수 있습니다.

---

## Q8. 먼저 종료를 요청한 쪽이 항상 클라이언트인가요?

아닙니다.

클라이언트가 먼저 종료할 수도 있고 서버가 먼저 종료할 수도 있습니다.

중요한 것은 누가 먼저 종료 요청을 보냈는지입니다.

먼저 FIN을 보낸 쪽이 active close를 수행한 쪽이고, 보통 그쪽이 TIME_WAIT 상태로 들어갈 수 있습니다.

단, TIME_WAIT의 자세한 이유는 별도 질문에서 다루는 것이 좋습니다.

---

## Q9. 4-Way Handshake와 3-Way Handshake의 차이는 무엇인가요?

3-Way Handshake는 TCP 연결을 생성하는 과정입니다.

```plain text
SYN
SYN + ACK
ACK
```

4-Way Handshake는 TCP 연결을 종료하는 과정입니다.

```plain text
FIN
ACK
FIN
ACK
```

연결 생성은 양쪽이 연결 의사를 확인하면 되지만, 연결 종료는 양쪽 송신 방향을 각각 닫아야 하기 때문에 보통 4단계로 설명합니다.

---

## Q10. 4-Way Handshake 도중 데이터가 전송될 수도 있나요?

가능합니다.

한쪽이 FIN을 보낸 뒤에도 반대쪽은 아직 보낼 데이터가 남아 있을 수 있습니다.

예를 들어 클라이언트가 더 이상 보낼 데이터가 없어서 FIN을 보냈더라도, 서버는 남은 응답 데이터를 보낸 뒤 FIN을 보낼 수 있습니다.

---

## Q11. RST를 쓰면 TIME_WAIT이 없어지나요?

RST 기반 강제 종료는 정상적인 FIN 종료 흐름과 다르게 처리되므로 일반적인 4-Way Handshake의 TIME_WAIT 흐름을 따르지 않을 수 있습니다.

하지만 이를 TIME_WAIT을 피하기 위한 일반적인 방법으로 사용하면 안 됩니다.

RST는 비정상 종료이므로 데이터 손실이나 애플리케이션 오류를 유발할 수 있습니다.

---

## Q12. 사용자가 브라우저 탭을 닫으면 항상 4-Way Handshake가 일어나나요?

항상 단순하게 말하기는 어렵습니다.

정상적으로 소켓을 닫으면 FIN 기반 종료가 일어날 수 있습니다.

하지만 브라우저, OS, 네트워크 상태, 아직 전송 중인 데이터, 프로세스 종료 방식 등에 따라 RST가 발생하거나 연결이 일정 시간 후 타임아웃으로 정리될 수도 있습니다.

---

## Q13. `close()`와 `shutdown()`은 어떤 차이가 있나요?

개념적으로 `shutdown()`은 소켓의 읽기 방향 또는 쓰기 방향을 선택적으로 닫을 수 있습니다.

예를 들어 쓰기 방향만 닫으면 더 이상 데이터를 보내지 않겠다는 FIN을 보낼 수 있지만, 상대방이 보내는 데이터는 계속 읽을 수 있습니다.

```plain text
shutdown write
→ 나는 더 이상 보내지 않음
→ 상대 데이터는 받을 수 있음
```

`close()`는 일반적으로 소켓 사용 자체를 종료하는 의미입니다.

구체적인 동작은 OS와 소켓 옵션에 따라 달라질 수 있습니다.

---

## Q14. 4-Way Handshake에서 ACK가 사라지면 어떻게 되나요?

TCP는 신뢰성 있는 전송을 위해 재전송 타이머를 사용합니다.

예를 들어 FIN에 대한 ACK가 오지 않으면 FIN을 보낸 쪽은 일정 시간 후 FIN을 재전송할 수 있습니다.

자세한 타임아웃과 재전송 정책은 TCP 구현에 따라 다를 수 있습니다.

## Q15. 패킷이 4-Way Handshake 목적이라는 것은 포트 번호로 알 수 있나요?

아닙니다.

포트 번호는 어떤 애플리케이션 프로세스와 통신하는지 식별하는 데 사용됩니다.

4-Way Handshake 목적 여부는 TCP 헤더의 FIN, ACK, RST 같은 플래그와 시퀀스/ACK 번호 흐름을 보고 판단합니다.
