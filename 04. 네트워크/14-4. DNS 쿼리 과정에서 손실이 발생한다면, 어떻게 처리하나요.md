# 14-4. DNS 쿼리 과정에서 손실이 발생한다면, 어떻게 처리하나요?

# **14-4. DNS 쿼리 과정에서 손실이 발생하면 어떻게 처리하나요?**

DNS는 일반적인 조회에서 **UDP**를 사용한다. UDP 자체에는 패킷이 손실되었을 때 이를 재전송하는 기능이 없기 때문에, **DNS 클라이언트 또는 DNS Resolver가 타임아웃과 재질의를 통해 처리**한다.

> 💡 

### DNS Resolver

사실 **DNS Resolver = Local DNS**라고 생각하면 된다.

정확히 말하면,

    - **Local DNS**는 역할을 설명하는 표현이고,

    - DNS Resolver(특히 Recursive Resolver)는 기능을 설명하는 표현이다.

실무와 면접에서는 거의 같은 의미로 사용된다.

---

# **Resolver란?**

Resolver는 영어로

**“해결하는 사람(또는 시스템)”**

이라는 뜻이다.

DNS에서는

**도메인 이름을 IP 주소로 해결(resolve)하는 역할**을 하는 시스템을 의미한다.

예를 들어

```plain text
www.google.com

↓

142.250.xxx.xxx
```

이렇게 변환해 주는 것이 Resolver이다.

---

# **DNS Resolver는 무슨 일을 할까?**

사용자가

```plain text
www.google.com
```

을 입력하면

Resolver가

    1. 캐시에 있는지 확인

    1. 없으면 Root DNS 조회

    1. TLD DNS 조회

    1. Authoritative DNS 조회

    1. IP를 사용자에게 반환

을 수행한다.

```plain text
사용자
    │
    ▼
DNS Resolver
    │
    ├── Cache 확인
    ├── Root DNS
    ├── TLD DNS
    ├── Authoritative DNS
    ▼
최종 IP 반환
```

즉,

**사용자를 대신해서 DNS 조회를 수행하는 서버**이다.

---

# **왜 Local DNS라고도 부를까?**

예를 들어 네 컴퓨터가 KT 인터넷을 사용한다면

```plain text
내 PC
    │
    ▼
KT DNS 서버
```

이 KT DNS 서버가

    - Local DNS

    - DNS Resolver

    - Recursive Resolver

모두 같은 서버를 가리킨다.

또는

```plain text
8.8.8.8
```

(Google Public DNS)

```plain text
1.1.1.1
```

(Cloudflare DNS)

도 모두 DNS Resolver이다.

---

# **Resolver와 DNS 서버는 같은 말일까?**

엄밀히는 아니다.

DNS 서버는 크게 역할이 나뉜다.

| **종류** | **역할** |
| --- | --- |
| **Recursive Resolver(Local DNS)** | 사용자를 대신해 끝까지 조회 |
| **Root DNS** | TLD DNS를 알려줌 |
| **TLD DNS** | Authoritative DNS를 알려줌 |
| **Authoritative DNS** | 실제 IP 정보를 보유 |

즉,

**Resolver도 DNS 서버의 한 종류**이다.

---

# **쉽게 비유하면**

전화번호를 찾는다고 생각해보자.

```plain text
나
 │
 ▼
비서 (Resolver)
 │
 ├── 안내소(Root)
 ├── 회사 안내(TLD)
 ├── 담당부서(Authoritative)
 │
 ▼
전화번호 알려줌
```

비서가 직접 여러 곳에 전화해서 알아온 뒤

최종 결과만 나에게 알려주는 것이다.

---

# **면접에서는 이렇게 기억하면 된다.**

**DNS Resolver(Recursive Resolver)는 사용자의 DNS 요청을 받아 캐시를 확인하고, 필요한 경우 Root DNS, TLD DNS, Authoritative DNS를 차례대로 조회하여 최종 IP 주소를 반환하는 DNS 서버입니다. 일반적으로 Local DNS와 거의 같은 의미로 사용됩니다.**

---

### **용어 정리**

```plain text
사용자
    │
    ▼
DNS Resolver
(= Local DNS
 = Recursive Resolver)
    │
    ▼
Root DNS
    │
    ▼
TLD DNS
    │
    ▼
Authoritative DNS
```

**CS 면접에서는 ****`Local DNS = DNS Resolver = Recursive Resolver`****로 이해하고 있어도 무방하다.** 단, 엄밀히 표현하면 “Resolver는 Local DNS가 수행하는 역할(기능)“이라고 설명하면 가장 정확하다.

---

## **1. 일정 시간 동안 응답을 기다린다**

클라이언트가 DNS 서버에 쿼리를 보낸 뒤 응답을 기다린다.

```plain text
Client              DNS Server
   │                      │
   │── DNS Query ────────▶│
   │                      │
   │     응답 손실 ✕      │
   │                      │
   │── Timeout 발생 ──────│
```

정해진 시간 안에 응답이 도착하지 않으면 쿼리 또는 응답이 손실되었다고 판단한다.

단, **재시도 횟수와 타임아웃 시간은 운영체제나 DNS Resolver 구현에 따라 다르며 DNS가 하나의 값으로 고정하지 않는다.**

---

## **2. 같은 DNS 서버에 다시 질의한다**

응답을 받지 못하면 동일한 DNS 서버로 쿼리를 재전송할 수 있다.

```plain text
Client              DNS Server
   │                      │
   │── 첫 번째 Query ────▶│
   │       손실 ✕         │
   │                      │
   │── 재전송 Query ─────▶│
   │◀──── Response ───────│
```

UDP가 재전송하는 것이 아니라, **UDP를 사용하는 DNS 애플리케이션이 새로운 쿼리를 다시 보내는 것**이다.

DNS 메시지에는 **Transaction ID**가 포함되어 있어 클라이언트가 응답을 자신이 보낸 쿼리와 대응시킬 수 있다.

---

## **3. 다른 DNS 서버로 질의한다**

같은 DNS 서버에서 계속 응답이 오지 않으면 보조 DNS 서버로 요청할 수 있다.

예를 들어 컴퓨터의 DNS 설정이 다음과 같다고 하자.

```plain text
기본 DNS: 8.8.8.8
보조 DNS: 8.8.4.4
```

기본 DNS가 응답하지 않으면 Resolver는 보조 DNS에 다시 질의할 수 있다.

```plain text
Client
   │
   ├──▶ 기본 DNS 서버 ── 응답 없음
   │
   └──▶ 보조 DNS 서버 ── 응답 반환
```

Root DNS, TLD DNS, Authoritative DNS도 일반적으로 여러 서버를 운영하므로, Recursive Resolver가 다른 서버 주소로 재시도할 수 있다.

---

## **4. 필요한 경우 TCP를 사용한다**

DNS는 TCP도 사용할 수 있지만, **UDP 패킷이 한 번 손실됐다고 반드시 TCP로 전환하는 것은 아니다.**

일반적인 UDP 손실은 우선 UDP 재질의로 처리한다. TCP 전환은 대표적으로 다음과 같은 상황에서 사용된다.

- DNS 응답이 너무 커서 잘린 경우

- 서버가 응답의 `TC(Truncated)` 플래그를 설정한 경우

- 해당 DNS 통신이 처음부터 TCP를 사용하도록 구성된 경우

TCP를 사용하면 TCP가 다음 기능을 제공한다.

- 패킷 수신 확인

- 손실된 데이터 재전송

- 순서 보장

- 오류 검출

```plain text
UDP 응답 손실
    │
    ├── 일반적 처리: UDP로 다시 질의
    │
    └── 큰 응답 등 특정 조건: TCP로 다시 질의
```

따라서 **“DNS는 패킷이 손실되면 무조건 TCP로 바꾼다”는 설명은 정확하지 않다.**

---

## **데이터가 손상된 경우**

패킷 손실과 데이터 손상은 구분해야 한다.

UDP에는 **Checksum**이 있어 전송 중 데이터가 변형되었는지 검사할 수 있다. 손상된 패킷은 일반적으로 폐기되므로 DNS 클라이언트에는 응답이 오지 않은 것처럼 보일 수 있다.

```plain text
데이터 손상
    ↓
Checksum 검사 실패
    ↓
패킷 폐기
    ↓
DNS 응답 Timeout
    ↓
DNS 쿼리 재시도
```

Checksum은 오류를 **검출**할 뿐, 손상된 데이터를 직접 수정하지는 않는다.

---

# **전체 처리 과정**

```plain text
DNS Query 전송
      │
      ▼
응답 대기
      │
      ├── 응답 도착 ─────────▶ 조회 완료
      │
      └── 응답 없음
              │
              ▼
          Timeout 발생
              │
              ▼
      같은 DNS 서버에 재질의
              │
              ├── 성공 ──────▶ 조회 완료
              │
              └── 실패
                      │
                      ▼
              다른 DNS 서버에 질의
                      │
                      ├── 성공 ▶ 조회 완료
                      └── 최종 실패 ▶ DNS 오류 반환
```

---

# **핵심 정리**

| **상황** | **처리 방법** |
| --- | --- |
| UDP 쿼리 또는 응답 손실 | 타임아웃 후 DNS 쿼리 재전송 |
| 같은 DNS 서버가 계속 응답하지 않음 | 다른 DNS 서버에 질의 |
| 패킷 데이터 손상 | Checksum으로 검출 후 폐기하고 재질의 |
| UDP 응답이 너무 커서 잘림 | TCP로 다시 질의 |
| TCP 통신 중 패킷 손실 | TCP가 손실된 데이터를 재전송 |

---

# **면접 답변**

DNS는 일반적인 조회에서 UDP를 사용하므로 UDP 자체가 손실된 패킷을 재전송하지는 않습니다. 대신 DNS Resolver가 일정 시간 동안 응답을 기다린 뒤 타임아웃이 발생하면 같은 DNS 서버에 쿼리를 다시 보내거나 다른 DNS 서버로 질의합니다. 패킷이 손상된 경우에는 UDP Checksum으로 오류를 검출해 폐기하고 다시 질의할 수 있습니다. 응답이 너무 커서 잘린 경우 등에는 TCP로 재질의하며, 이때는 TCP가 손실된 데이터의 재전송과 순서 보장을 담당합니다.
