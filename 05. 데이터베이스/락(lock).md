# 락(lock)

# 1. 락(lock)이란?

- 데이터베이스나 멀티스레드 환경에서 여러 사용자가** 동시에 동일한 데이터에 접근**할 때, 데이터의 일관성과 무결성을 유지하기 위해 사용하는 제어 메커니즘

# 2. 낙관적 락(Optimistic Lock)

- 데이터 충돌이 거의 발생하지 않을 것이라고 가정합니다.

- 데이터를 읽을 때는 락을 걸지 않고, **수정 시점에 내가 읽었던 데이터가 변했는지 확인**하는 방식

- **특징:** DB 수준의 락이 아닌 애플리케이션 수준에서 관리됩니다. 충돌이 적은 환경에서 성능이 매우 좋습니다.

- **구현 방식**

  - **Version/Timestamp 사용:** 테이블에 version 컬럼을 둡니다.

  - **프로세스:**

    1. 데이터를 읽을 때 `version`이 1임을 확인합니다.

    1. 수정 시점에 `WHERE id = ? AND version = 1` 조건으로 업데이트를 시도합니다.

    1. 그사이 다른 사용자가 수정해서 `version`이 2가 되었다면 업데이트에 실패하고, 애플리케이션에서 롤백이나 재시도를 처리합니다.

# 3. 비관적 락(Pessimistic Lock)

- 데이터 충돌이 반드시 발생할 것이라고 가정하고, 데이터를 읽는 시점부터 먼저 락을 거는 방식

- 다른 트랜잭션이 해당 데이터에 접근하지 못하도록 강력하게 제어합니다.

- **특징:** 데이터 무결성을 확실히 보장하지만, 대기 시간이 길어져 성능(Throughput)이 저하될 수 있고 데드락(Deadlock) 위험이 있습니다.

- **구현 방식:**

  - **Shared Lock (S-Lock, 공유 락):** "읽기 락"입니다. 다른 트랜잭션이 읽는 것은 허용하지만, 수정하는 것은 막습니다.

  - **Exclusive Lock (X-Lock, 배타 락):** "쓰기 락"입니다. 다른 트랜잭션이 읽거나 쓰는 것 모두를 막습니다.

  - **SQL 예시:** `SELECT ... FOR UPDATE` 구문을 사용하여 특정 행에 즉시 배타 락을 겁니다.

  - JPA에서 @Lock(LockModeType.PESSIMISTIC_WRITE)을 사용하여 간단하게 구현할 수 있습니다.

  - **PESSIMISTIC_READ**: 다른 트랜잭션이 읽기는 가능하지만, 수정/삭제는 못 하게 공유 락(Shared Lock)을 겁니다.

  - **PESSIMISTIC_WRITE**: 다른 트랜잭션이 읽기, 쓰기 모두 못 하게 배타 락(Exclusive Lock)을 겁니다. (가장 많이 사용됨)

  - **PESSIMISTIC_FORCE_INCREMENT**: 비관적 락을 걸면서 엔티티의 버전 정보까지 강제로 올립니다.

# 4. 데드락

- 데드락(Deadlock, 교착 상태)이란, 두 개 이상의 작업(프로세스나 트랜잭션)이 **서로 상대방이 가진 자원의 락(Lock)이 풀리기를 무한히 기다리며, 결국 아무도 다음 단계로 진행하지 못하고 멈춰버리는 현상**을 말합니다.

- 데드락이 발생하는 4가지 필수 조건(하나만 깨뜨려도 예방할 수 있습니다.)

  1. **상호 배제 (Mutual Exclusion):** 자원은 한 번에 한 명만 사용할 수 있음.

  1. **점유와 대기 (Hold and Wait):** 최소한 하나의 자원을 가진 채로, 다른 사람이 가진 자원을 추가로 기다림.

  1. **비선점 (No Preemption):** 남이 가진 자원을 강제로 뺏어올 수 없음.

  1. **순환 대기 (Circular Wait):** 대기 중인 프로세스들이 원형으로 서로를 기다림 (A → B → C → A).

- 실제 데이터베이스에서의 예시 (송금 로직)

  - **상황:** 1번 계좌(A)에서 2번 계좌(B)로 송금하고, 동시에 B에서 A로 송금할 때.

  - **흐름**

    1. **트랜잭션 1:** A 계좌를 조회하며 락을 겁니다. (A 점유)

    1. **트랜잭션 2:** B 계좌를 조회하며 락을 겁니다. (B 점유)

    1. **트랜잭션 1:** 이제 입금을 위해 B 계좌의 락을 기다립니다. (B 대기)

    1. **트랜잭션 2:** 이제 입금을 위해 A 계좌의 락을 기다립니다. (A 대기)

  - **결과:** 트랜잭션 1은 2가 끝나길 기다리고, 2는 1이 끝나길 기다리며 **무한 대기**에 빠집니다.

- **데드락을 해결하는 방법**

| **해결 전략** | **방식 설명** |
| --- | --- |
| **예방(Prevention)** | 위 4가지 조건 중 하나를 미리 차단합니다. (예: 자원 획득 순서 정렬) |
| **회피(Avoidance)** | 자원 할당 시 데드락 가능성을 검사합니다. (예: 은행원 알고리즘) |
| **탐지 및 복구(Detection)** | 데드락이 생기면 시스템이 이를 감지하고, 하나를 강제 종료(Rollback) 시킵니다. |
| **무시(Ignorance)** | 발생 확률이 매우 낮다면 그냥 둡니다. (대부분의 OS나 DB는 탐지 방식을 사용함) |

- 데드락을 해결하기 위한 간단한 방법으로 두 개의 자원(계좌)에 락을 걸어야 할 때, **무조건 ID 값이 작은 계좌부터 락을 획득**하도록 로직을 사용하는 경우가 많다고 합니다.

# 5. **분산 락 (Distributed Lock)**

- 데이터베이스가 여러 대이거나 서버 인스턴스가 여러 개인 분산 환경에서, 공통된 자원에 대한 접근을 제어하기 위해 사용합니다.

- 단일 서버라면 서버 내부의 메모리(Java의 `synchronized` 등)를 쓰면 되지만, 서버가 2대 이상이면 서로의 메모리를 볼 수 없기 때문에 제3의 장소(Redis, Zookeeper)에 열쇠를 두고 누가 가져갔는지 기록하는 것입니다.

- **특징:** DB 자체의 락만으로는 여러 서버 간의 동기화를 맞추기 어려울 때 사용합니다.

- **구현 방식:**

  - **Redis (Redlock):** `setnx` (Set if Not Exists) 명령어를 이용해 특정 키가 없으면 점유하고, 작업 후 삭제하는 방식으로 구현합니다. (주로 Redisson 라이브러리 활용)

  - **Zookeeper:** 노드(Znode)의 생성 및 소멸을 통해 락을 관리합니다.

# 6. 각 락의 장단점

| **구분** | **장점** | **단점** | **주요 사용처** |
| --- | --- | --- | --- |
| **낙관적 락** | - 별도의 락을 잡지 않아 성능이 좋음
- 데드락 위험이 거의 없음 | - 충돌 발생 시 롤백/재시도 로직을 직접 구현해야 함 | **공지사항 수정, 프로필 관리
**(동시 수정이 드문 일반적인 서비스) |
| **비관적 락** | - 데이터 정합성이 완벽히 보장됨
- 충돌 발생 시 즉각적으로 대기함 | - 성능 저하 (대기 시간 발생)
- 데드락(Deadlock) 위험 존재 | **금융 시스템, 재고 관리** 
(데이터가 한 치의 오차도 없어야 할 때) |
| **분산 락** | - 여러 서버/DB 환경에서도 동기화 가능
- 타임아웃 설정이 쉬움 | - Redis 등 외부 시스템 의존성 발생
- 구현 복잡도가 높음 | **선착순 이벤트, MSA 환경**의 공통 자원 접근 제어 |
