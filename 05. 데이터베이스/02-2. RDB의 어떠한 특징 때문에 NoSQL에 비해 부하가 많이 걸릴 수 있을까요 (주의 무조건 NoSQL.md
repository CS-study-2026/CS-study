# 2-2. RDB의 어떠한 특징 때문에 NoSQL에 비해 부하가 많이 걸릴 "수" 있을까요? (주의: 무조건 NoSQL이 RDB 보다 빠르다라고 생각하면 큰일 납니다!)

## 핵심 답변

RDB가 NoSQL에 비해 부하가 많이 걸릴 **수 있는 이유**는 RDB가 보통 다음 특징들을 강하게 보장하기 때문입니다.

- 정규화된 테이블 구조

- JOIN 기반 조회

- ACID 트랜잭션

- 강한 일관성

- 스키마 제약 조건

- 수직 확장 중심의 구조

- 복잡한 인덱스 및 쿼리 최적화

다만 이것은 _**항상 RDB가 NoSQL보다 느리다는 뜻이 아닙니다**_**.**

RDB는 데이터 정합성과 복잡한 관계 처리에 강하고, NoSQL은 특정 상황에서 단순 조회, 대용량 분산 처리, 유연한 구조에 강합니다.

---

## 1. 정규화 구조로 인한 조회 비용

RDB는 데이터 중복을 줄이고 정합성을 높이기 위해 정규화를 사용합니다.

```plain text
정규화된 RDB 구조

User ──< Post ──< Comment
             └──< Like
```

장점은 명확합니다.

- 데이터 중복 감소

- 수정 시 일관성 유지 용이

- 무결성 보장

- 관계 표현이 명확함

하지만 읽기 요청이 많은 서비스에서는 매번 여러 테이블을 조합해야 하므로 부하가 커질 수 있습니다.

반대로 NoSQL은 의도적으로 **반정규화**를 사용하는 경우가 많습니다.

```plain text
NoSQL 문서 구조

Post Document
- title
- authorName
- comments
- likeCount
```

즉, NoSQL은 데이터 중복을 감수하는 대신 특정 조회 패턴을 빠르게 만들 수 있습니다.

---

## 2. JOIN 연산으로 인한 부하

RDB는 데이터를 중복 없이 관리하기 위해 보통 **정규화**를 사용합니다.

예를 들어 게시글 목록을 조회할 때 다음 정보가 필요하다고 가정합니다.

- 게시글 제목

- 작성자 이름

- 댓글 수

- 좋아요 수

RDB에서는 데이터가 여러 테이블에 나뉘어 있을 수 있습니다.

```plain text
User
- id
- name

Post
- id
- user_id
- title

Comment
- id
- post_id
- content

Like
- id
- post_id
- user_id
```

이 경우 게시글 목록을 만들려면 여러 테이블을 JOIN하거나 집계해야 합니다.

```plain text
SELECT
  p.id,
  p.title,
  u.name,
  COUNT(c.id) AS comment_count
FROM post p
JOIN user u ON p.user_id = u.id
LEFT JOIN comment c ON p.id = c.post_id
GROUP BY p.id, u.name;
```

JOIN은 데이터 관계를 정확히 표현할 수 있다는 장점이 있지만, 데이터가 많아질수록 다음 비용이 증가할 수 있습니다.

- 테이블 탐색 비용

- 인덱스 조회 비용

- 정렬 비용

- 그룹화 비용

- 임시 테이블 생성 비용

- 디스크 I/O 비용

반면 NoSQL에서는 조회 성능을 위해 데이터를 미리 합쳐 저장하는 경우가 많습니다.

```plain text
{
  "postId": 1,
  "title": "DB 정리",
  "authorName": "Kim",
  "commentCount": 15,
  "likeCount": 32
}
```

이렇게 저장하면 게시글 목록 조회 시 JOIN 없이 한 번에 읽을 수 있습니다.

---

## 3. ACID 트랜잭션 보장 비용

RDB는 보통 ACID 트랜잭션을 강하게 지원합니다.

| 속성 |   | 의미 |
| --- | --- | --- |
| Atomicity | 원자성 | 작업이 모두 성공하거나 모두 실패해야 함 |
| Consistency | 일관성 | 트랜잭션 전후 데이터가 항상 유효해야 함 |
| Isolation | 고립성 | 동시에 실행되는 트랜잭션이 서로 간섭하지 않아야 함 |
| Durability | 지속성 | 커밋된 데이터는 장애가 발생해도 보존되어야 함 |

예를 들어 계좌 이체는 반드시 다음 조건을 만족해야 합니다.

```plain text
A 계좌에서 10,000원 차감
B 계좌에 10,000원 증가
```

둘 중 하나만 성공하면 안 됩니다.

그래서 RDB는 락, 로그, 격리 수준, 롤백 정보를 관리합니다.

<details>
<summary>_로그? 격리 수준? 롤백 정보?_</summary>

> 💡 RDB에서 트랜잭션을 안전하게 처리하기 위해 관리하는 대표 요소들이야.

| 용어 | 간단한 의미 |
| --- | --- |
| 로그 | DB 변경 내역을 기록해두는 정보 |
| 격리 수준 | 동시에 실행되는 트랜잭션들이 서로 얼마나 영향을 주지 않게 할지 정하는 규칙 |
| 롤백 정보 | 트랜잭션 실패 시 이전 상태로 되돌리기 위해 필요한 정보 |

## 1. 로그

RDB는 데이터를 변경할 때 바로 데이터 파일만 바꾸는 것이 아니라, 변경 내용을 **로그**로 먼저 기록해.

예를 들어 계좌 잔액을 바꾼다면:

```plain text
A 계좌 잔액: 10000원 -> 5000원
```

이 변경 내역을 로그에 남겨둔다.

로그가 필요한 이유는 장애 복구 때문이야.

```plain text
트랜잭션 실행
  ↓
로그 기록
  ↓
데이터 변경
  ↓
커밋
```

만약 DB 서버가 중간에 꺼지면, DB는 로그를 보고 다음을 판단할 수 있어.

    - 커밋된 작업은 다시 반영

    - 커밋되지 않은 작업은 취소

즉, 로그는 **장애가 나도 데이터가 깨지지 않도록 복구하기 위한 기록**이야.

---

## 2. 격리 수준

격리 수준은 여러 트랜잭션이 동시에 실행될 때, 서로의 작업을 얼마나 분리해서 볼 것인지 정하는 규칙이야.

예를 들어:

```plain text
트랜잭션 A: 상품 재고를 10개에서 9개로 변경 중
트랜잭션 B: 같은 상품 재고를 조회 중
```

이때 B가 A의 아직 커밋되지 않은 값을 볼 수 있는지, 아니면 커밋된 값만 볼 수 있는지가 격리 수준에 따라 달라져.

대표적인 격리 수준은 다음과 같아.

| 격리 수준 | 특징 |
| --- | --- |
| READ UNCOMMITTED | 커밋되지 않은 변경도 볼 수 있음 |
| READ COMMITTED | 커밋된 변경만 볼 수 있음 |
| REPEATABLE READ | 같은 트랜잭션 안에서는 같은 데이터를 다시 읽어도 같은 결과를 보장 |
| SERIALIZABLE | 트랜잭션을 거의 순서대로 실행한 것처럼 가장 강하게 격리 |

격리 수준이 강할수록 데이터 정합성은 좋아지지만, 락이나 대기 시간이 늘어 성능 부담이 커질 수 있어.

---

## 3. 롤백 정보

롤백 정보는 트랜잭션을 취소할 때 데이터를 이전 상태로 되돌리기 위한 정보야.

예를 들어:

```plain text
UPDATE account
SET balance = balance - 10000
WHERE id = 1;
```

이 작업을 실행했는데 이후 단계에서 오류가 나면, DB는 이 변경을 취소해야 해.

```plain text
변경 후: 90000원
롤백 시: 다시 100000원
```

이를 위해 DB는 “변경 전 값” 또는 “되돌리는 데 필요한 정보”를 따로 관리해.

즉, 롤백 정보는 **실패한 트랜잭션이 DB에 어중간하게 남지 않도록 되돌리기 위한 복구 정보**야.
</details>

이 과정에서 다음 부하가 생길 수 있습니다.

- 락 관리 비용

- 동시성 제어 비용

- 트랜잭션 로그 기록 비용

- 롤백을 위한 undo 정보 관리

- 디스크 동기화 비용

NoSQL도 트랜잭션을 지원하는 제품들이 있지만, 많은 NoSQL 시스템은 특정 상황에서 강한 트랜잭션보다 **성능, 확장성, 가용성**을 우선하도록 설계되었습니다.

---

## 4. 강한 일관성 보장으로 인한 부하

RDB는 일반적으로 데이터를 읽었을 때 최신 상태를 보장하는 **강한 일관성**을 중요하게 다룹니다.

```plain text
쓰기 발생
   ↓
모든 사용자가 최신 데이터 조회
```

이런 구조는 정합성이 중요한 시스템에 적합합니다.

예:

- 결제

- 주문

- 재고

- 계좌

- 포인트

- 예약

하지만 분산 환경(DB가 여러 대)에서는 강한 일관성을 유지하기 위해 노드(DB) 간 동기화 비용이 커질 수 있습니다.

반면 일부 NoSQL은 **최종적 일관성(Eventual Consistency)** 을 선택합니다.

```plain text
쓰기 발생
   ↓
일부 노드는 잠시 이전 데이터 조회 가능
   ↓
시간이 지나면 모든 노드가 같은 값으로 수렴
```

이 방식은 정합성을 약간 늦추는 대신 빠른 응답과 높은 가용성을 얻을 수 있습니다.

예:

- 조회수

- 좋아요 수

- 추천 피드

- 로그

- 알림 읽음 상태

- 상품 검색 인덱스

---

## 5. 스키마와 제약 조건 검사 비용

RDB는 테이블마다 명확한 스키마를 갖습니다.

```plain text
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  age INT CHECK (age >= 0)
);
```

데이터를 저장할 때 RDB는 여러 조건을 검사합니다.

- 타입이 맞는가?

- NOT NULL 조건을 만족하는가?

- UNIQUE 조건을 위반하지 않는가?

- 외래 키가 존재하는가?

- CHECK 조건을 만족하는가?

이러한 검사는 데이터 품질을 높여주지만, 쓰기 성능에는 추가 비용이 됩니다.

NoSQL은 상대적으로 스키마가 유연한 경우가 많아 이런 검사가 적거나 애플리케이션 레벨로 넘어가는 경우가 많습니다.

## 6. 수평 확장의 어려움

## 1. 수직 확장과 수평 확장

### 수직 확장, Scale Up

수직 확장은 **서버 한 대의 성능을 높이는 방식**이야.

예를 들어 DB 서버가 느려졌을 때:

```plain text
CPU 4코어 -> 16코어
RAM 16GB -> 64GB
SSD -> 더 빠른 SSD
```

처럼 기존 서버를 더 강한 장비로 바꾸는 방식이야.

```plain text
[DB 서버]
   ↓ 성능 업그레이드
[더 강한 DB 서버]
```

장점:

    - 구조가 단순함

    - 애플리케이션 변경이 적음

    - 한 서버 안에서 데이터 정합성 관리가 비교적 쉬움

단점:

    - 장비 성능에는 물리적 한계가 있음

    - 고성능 장비는 비용이 급격히 비싸짐

    - 서버 한 대에 의존하면 장애 시 영향이 큼

---

### 수평 확장, Scale Out

수평 확장은 **서버 대수를 늘려서 부하를 나누는 방식**이야.

예를 들어 DB 요청이 많아졌을 때:

```plain text
DB 서버 1대 -> DB 서버 3대 -> DB 서버 10대
```

처럼 여러 서버가 일을 나눠 처리하게 만드는 방식이야.

```plain text
          요청
           ↓
      [분산 처리]
      /    |    \
 [DB1]  [DB2]  [DB3]
```

장점:

    - 서버를 추가하면서 처리량을 늘릴 수 있음

    - 대규모 트래픽 처리에 유리함

    - 일부 서버 장애에도 전체 서비스가 버틸 수 있음

단점:

    - 데이터 분산 설계가 필요함

    - 여러 서버 간 일관성 유지가 어려움

    - JOIN, 트랜잭션 처리가 복잡해질 수 있음
</details>

RDB는 전통적으로 하나의 서버에서 강한 정합성과 관계형 연산을 처리하는 구조에 적합했습니다.

```plain text
RDB 확장 방식

더 좋은 CPU
더 많은 RAM
더 빠른 Disk
        ↑
    수직 확장
```

수직 확장은 단순하지만 한계가 있습니다.

- 장비 비용 증가

- 물리적 성능 한계 (무한히 성능을 높일 순 없음)

- 단일 장애 지점 가능성 (하나의 구성 요소가 실패했을 때 전체 시스템이 영향을 받는 지점)

- 대규모 트래픽 분산의 어려움

물론 RDB도 복제, 샤딩, 파티셔닝, 클러스터링을 통해 수평 확장이 가능합니다.

## 1. 샤딩

샤딩은 데이터를 여러 DB 서버에 **나누어 저장하는 방식**이야.

예를 들어 사용자 데이터를 `user_id` 기준으로 나눌 수 있어.

```plain text
user_id 1 ~ 1000     -> DB1
user_id 1001 ~ 2000  -> DB2
user_id 2001 ~ 3000  -> DB3
```

또는 해시를 이용해서 나눌 수도 있어.

```plain text
user_id % 3 = 0 -> DB1
user_id % 3 = 1 -> DB2
user_id % 3 = 2 -> DB3
```

그림으로 보면:

```plain text
User Table 전체
 ├── Shard 1: 일부 사용자 데이터
 ├── Shard 2: 일부 사용자 데이터
 └── Shard 3: 일부 사용자 데이터
```

샤딩의 목적:

    - 데이터 저장 공간 분산

    - 읽기/쓰기 부하 분산

    - 대용량 데이터 처리

주의할 점:

    - 샤드 기준을 잘못 잡으면 특정 서버에만 부하가 몰릴 수 있음

    - 여러 샤드에 걸친 JOIN이나 트랜잭션이 어려워짐

    - 샤드 개수 변경이 복잡할 수 있음

예를 들어 지역 기준으로 샤딩했는데 서울 사용자만 너무 많으면 서울 샤드에 부하가 몰릴 수 있어.

---

## 2. 파티셔닝

파티셔닝은 큰 테이블을 **논리적으로 작은 단위로 나누는 방식**이야.

샤딩과 비슷해 보이지만, 보통 파티셔닝은 **하나의 DB 안에서 큰 테이블을 쪼개는 것**을 말하는 경우가 많아.

예를 들어 주문 테이블을 날짜 기준으로 나눌 수 있어.

```plain text
orders_2026_01
orders_2026_02
orders_2026_03
```

또는 내부적으로 이렇게 관리될 수 있어.

```plain text
Orders Table
 ├── 2026년 1월 주문
 ├── 2026년 2월 주문
 └── 2026년 3월 주문
```

파티셔닝의 목적:

    - 큰 테이블 조회 성능 개선

    - 오래된 데이터 관리 용이

    - 특정 범위만 빠르게 조회

    - 인덱스 크기 감소

예를 들어 최근 1개월 주문만 자주 조회한다면, 전체 주문 테이블을 다 보는 것보다 `2026년 7월 파티션`만 보는 것이 효율적이야.

주의할 점:

    - 파티션 기준을 잘못 잡으면 성능 이점이 작음

    - 모든 파티션을 다 조회하면 오히려 비용이 커질 수 있음

    - 운영과 설계 복잡도가 증가함

---

## 3. 클러스터링

클러스터링은 여러 서버를 묶어서 **하나의 시스템처럼 동작하게 하는 구성**이야.

```plain text
        Application
             ↓
      [DB Cluster]
      /     |     \
   DB1    DB2    DB3
```

목적은 크게 두 가지야.

### 1. 고가용성

서버 하나가 죽어도 다른 서버가 대신 처리하게 만드는 것.

```plain text
DB1 장애 발생
   ↓
DB2가 대신 처리
```

이런 구성을 통해 서비스 중단 가능성을 줄일 수 있어.

### 2. 부하 분산

읽기 요청이나 일부 작업을 여러 서버에 나누어 처리하는 것.

```plain text
쓰기 요청 -> Primary DB
읽기 요청 -> Replica DB1, Replica DB2
```

예:

```plain text
Primary DB
 ├── Replica DB1
 └── Replica DB2
```

클러스터링의 장점:

    - 장애 대응에 유리함

    - 읽기 부하를 분산할 수 있음

    - 서비스 안정성이 높아짐

주의할 점:

    - 서버 간 데이터 동기화가 필요함

    - 복제 지연이 발생할 수 있음

    - 장애 전환 처리 로직이 필요함

    - 구성과 운영이 복잡해짐

---

## 샤딩, 파티셔닝, 클러스터링 차이

| 개념 | 핵심 의미 | 주 목적 |
| --- | --- | --- |
| 샤딩 | 데이터를 여러 DB 서버에 나눠 저장 | 수평 확장, 부하 분산 |
| 파티셔닝 | 큰 테이블을 작은 단위로 나눔 | 조회/관리 성능 개선 |
| 클러스터링 | 여러 서버를 하나의 시스템처럼 묶음 | 고가용성, 부하 분산 |

---

## 비유로 정리

도서관으로 비유하면:

| 개념 | 비유 |
| --- | --- |
| 수직 확장 | 도서관 하나를 더 크게 짓고 직원을 늘림 |
| 수평 확장 | 도서관 지점을 여러 개 만듦 |
| 샤딩 | 책을 주제별로 다른 지점에 나눠 보관 |
| 파티셔닝 | 한 도서관 안에서 책장을 분야/연도별로 나눔 |
| 클러스터링 | 여러 도서관 지점이 하나의 통합 시스템처럼 운영됨 |
</details>

하지만 JOIN, 트랜잭션, 일관성 보장까지 함께 유지하려면 구조가 복잡해질 수 있습니다.

NoSQL은 처음부터 분산 저장과 수평 확장을 고려해 설계된 경우가 많습니다.

```plain text
NoSQL 확장 방식

데이터 분산
 ├── Node 1
 ├── Node 2
 ├── Node 3
 └── Node 4
```

그래서 대량의 단순 조회나 쓰기 요청을 여러 노드에 나누어 처리하기 쉽습니다.

## 7. 복잡한 쿼리 최적화 비용

RDB는 SQL을 통해 매우 복잡한 질의를 처리할 수 있습니다.

```plain text
SELECT ...
FROM ...
JOIN ...
WHERE ...
GROUP BY ...
HAVING ...
ORDER BY ...
```

쿼리가 복잡해질수록 DBMS는 최적의 실행 계획을 선택해야 합니다.

이 과정에서 고려하는 요소는 다음과 같습니다.

- 어떤 인덱스를 사용할지

- 어떤 테이블을 먼저 읽을지

- JOIN 순서를 어떻게 할지

- 정렬을 메모리에서 할지 디스크에서 할지

- 통계 정보가 최신인지

쿼리 자체가 복잡하거나 인덱스가 적절하지 않으면 DB에 큰 부하가 걸릴 수 있습니다.

NoSQL은 보통 특정 접근 패턴에 맞춰 데이터를 설계하기 때문에 복잡한 질의는 어렵지만, 정해진 키 기반 조회는 매우 빠르게 처리할 수 있습니다.

---

## 비교 정리

| 항목 | RDB | NoSQL |
| --- | --- | --- |
| 데이터 구조 | 테이블, 행, 열 | 문서, 키-값, 컬럼 패밀리, 그래프 등 |
| 스키마 | 엄격함 | 유연한 경우가 많음 |
| 관계 처리 | JOIN에 강함 | JOIN이 약하거나 없음 |
| 트랜잭션 | ACID 강함 | 제품마다 다름 |
| 일관성 | 강한 일관성 중심 | 최종적 일관성 선택 가능 |
| 확장 방식 | 수직 확장 중심, 수평 확장도 가능하나 복잡 | 수평 확장에 유리한 경우 많음 |
| 장점 | 정합성, 관계 표현, 복잡한 쿼리 | 대용량 분산, 빠른 단순 조회, 유연한 구조 |
| 부하가 커질 수 있는 지점 | JOIN, 락, 트랜잭션, 제약 조건, 복잡한 쿼리 | 중복 데이터 관리, 정합성 보정, 제한된 질의 |

---

## 주의할 점: NoSQL이 무조건 빠른 것은 아니다

"NoSQL이 RDB보다 빠르다"는 말은 위험합니다.

성능은 DB 종류보다 다음 요소에 더 크게 좌우됩니다.

- 데이터 모델링

- 인덱스 설계

- 쿼리 패턴

- 트래픽 특성

- 읽기/쓰기 비율

- 데이터 크기

- 캐시 전략

- 샤딩/파티셔닝 구조

- 일관성 요구사항

예를 들어 다음 상황에서는 RDB가 더 적합하거나 더 빠를 수 있습니다.

- 복잡한 JOIN이 필요한 업무 데이터

- 강한 정합성이 필요한 결제/주문 시스템

- 데이터 관계가 명확한 시스템

- SQL 기반 분석이 필요한 서비스

- 트랜잭션 실패가 치명적인 도메인

반대로 다음 상황에서는 NoSQL이 유리할 수 있습니다.

- 대량 로그 저장

- 실시간 이벤트 수집

- 단순 key-value 조회

- 유연한 JSON 문서 저장

- 빠른 수평 확장이 필요한 서비스

- 데이터 구조가 자주 바뀌는 서비스

---

## 면접 답변 예시

RDB가 NoSQL에 비해 부하가 많이 걸릴 수 있는 이유는 RDB가 데이터 정합성과 관계 표현을 강하게 보장하기 때문입니다. RDB는 보통 정규화된 테이블 구조를 사용하므로 데이터를 조회할 때 여러 테이블을 JOIN해야 하는 경우가 많고, 이 과정에서 인덱스 탐색, 정렬, 그룹화 비용이 발생할 수 있습니다.

또한 RDB는 ACID 트랜잭션, 외래 키, UNIQUE, CHECK 같은 제약 조건, 락 기반 동시성 제어를 제공하기 때문에 쓰기 작업에서도 추가적인 검증과 동기화 비용이 발생합니다. 특히 강한 일관성을 유지해야 하는 분산 환경에서는 노드 간 동기화나 트랜잭션 처리 비용이 더 커질 수 있습니다.

반면 NoSQL은 특정 조회 패턴에 맞게 데이터를 중복 저장하거나, 최종적 일관성을 선택하거나, 수평 확장을 쉽게 가져가는 방식으로 성능을 확보하는 경우가 많습니다. 다만 NoSQL이 항상 RDB보다 빠른 것은 아니고, 정합성이 중요하거나 복잡한 관계형 쿼리가 필요한 경우에는 RDB가 더 적합할 수 있습니다. 결국 중요한 것은 DB 종류가 아니라 서비스의 데이터 구조, 조회 패턴, 정합성 요구사항에 맞는 선택입니다.
