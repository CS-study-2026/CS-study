# 5-3. ORDER BY/GROUP BY 연산의 동작 과정을 인덱스의 존재여부와 연관지어서 설명해 주세요.

## 핵심 답변

`ORDER BY`와 `GROUP BY`는 모두 데이터를 **정렬하거나 묶는 작업**이기 때문에 비용이 큰 연산이 될 수 있습니다.

하지만 정렬 기준이나 그룹 기준에 맞는 **인덱스가 존재하면**, DB는 이미 정렬된 인덱스 구조를 활용할 수 있습니다.

반대로 적절한 인덱스가 없다면 DB는 조건에 맞는 데이터를 읽은 뒤 별도로 정렬하거나 그룹화해야 하므로 더 많은 메모리, CPU, 디스크 I/O가 발생할 수 있습니다.

---

## 1. 인덱스가 ORDER BY에 미치는 영향

### 인덱스가 없는 경우

예를 들어 게시글을 생성일 기준으로 최신순 조회한다고 가정합니다.

```plain text
SELECT *
FROM post
ORDER BY created_at DESC;
```

`created_at`에 인덱스가 없다면 DB는 보통 다음 과정을 거칩니다.

```plain text
1. post 테이블 전체 또는 조건에 맞는 행을 읽는다.
2. 읽은 결과를 메모리에 올린다.
3. created_at 기준으로 정렬한다.
4. 정렬 결과를 반환한다.
```

데이터가 적으면 큰 문제가 없지만, 데이터가 많아지면 정렬 비용이 커집니다.

```plain text
Table Scan
   ↓
Sort
   ↓
Result
```

특히 정렬 대상이 메모리에 다 올라가지 못하면 디스크에 임시 파일을 만들 수 있습니다.

MySQL 기준으로는 이런 상황에서 `Using filesort`가 나타날 수 있습니다.

<details>
<summary>`Using filesort`</summary>

> 💡 `Using filesort`는 MySQL의 실행 계획(`EXPLAIN`)에서 볼 수 있는 표현으로,

> **인덱스에 저장된 순서를 그대로 사용할 수 없어서, MySQL이 데이터를 별도로 정렬했다는 뜻**이야.

예를 들어:

```plain text
SELECT *
FROM post
ORDER BY created_at;
```

### 인덱스가 없는 경우

`created_at` 기준으로 데이터가 정렬되어 있지 않으므로:

```plain text
데이터 조회
   ↓
created_at 기준으로 별도 정렬  ← Using filesort
   ↓
결과 반환
```

### 적절한 인덱스가 있는 경우

```plain text
CREATE INDEX idx_created_at ON post(created_at);
```

인덱스가 이미 `created_at` 순서로 정렬되어 있으므로:

```plain text
인덱스를 순서대로 읽음
   ↓
결과 반환
```

별도의 정렬이 필요 없어서 `Using filesort`를 피할 수 있어.

**주의:** 이름에 `file`이 들어가지만 **무조건 디스크 파일을 사용한다는 뜻은 아니야.** 메모리에서 정렬할 수도 있어.

**한 줄 정리:**

**`Using filesort`**** = 인덱스 순서로 해결하지 못해서 MySQL이 추가적인 정렬 작업을 수행함.**
</details>

---

### 인덱스가 있는 경우

```plain text
CREATE INDEX idx_post_created_at ON post(created_at);
```

`created_at` 인덱스가 있다면 인덱스 자체가 이미 정렬된 구조이기 때문에, DB는 인덱스를 순서대로 읽어서 결과를 만들 수 있습니다.

```plain text
Index Scan
   ↓
Result
```

예를 들어 B+Tree 인덱스는 키 값이 정렬된 상태로 저장됩니다.

```plain text
created_at index

2026-08-01
2026-08-02
2026-08-03
2026-08-04
```

오름차순은 앞에서부터 읽고, 내림차순은 뒤에서부터 읽으면 됩니다.

```plain text
SELECT *
FROM post
ORDER BY created_at DESC;
```

이 경우 별도의 정렬 작업 없이 인덱스 순서를 활용할 수 있습니다.

---

## 2. ORDER BY에서 인덱스가 항상 사용되는 것은 아니다

인덱스가 있어도 항상 정렬에 사용되는 것은 아닙니다.

예를 들어:

```plain text
CREATE INDEX idx_post_created_at ON post(created_at);

SELECT *
FROM post
WHERE category = 'DB'
ORDER BY created_at DESC;
```

`created_at` 인덱스만 있으면 정렬에는 도움이 될 수 있지만, `category` 조건을 먼저 걸러야 합니다.

이 경우 더 적절한 인덱스는 다음과 같습니다.

```plain text
CREATE INDEX idx_post_category_created_at
ON post(category, created_at);
```

그러면 DB는 `category = 'DB'`인 데이터 범위 안에서 이미 `created_at` 순서로 정렬된 결과를 읽을 수 있습니다.

```plain text
(category, created_at) index

('DB', 2026-08-01)
('DB', 2026-08-02)
('DB', 2026-08-03)
('OS', 2026-08-01)
('OS', 2026-08-02)
```

즉, `WHERE` 조건과 `ORDER BY` 컬럼 순서가 인덱스 설계와 잘 맞아야 합니다.

## 3. 인덱스가 GROUP BY에 미치는 영향

### 인덱스가 없는 경우

예를 들어 카테고리별 게시글 수를 구한다고 가정합니다.

```plain text
SELECT category, COUNT(*)
FROM post
GROUP BY category;
```

`category`에 인덱스가 없다면 DB는 보통 다음 과정을 거칩니다.

```plain text
1. post 테이블 전체를 읽는다.
2. category 값별로 데이터를 묶는다.
3. 각 그룹의 COUNT를 계산한다.
4. 결과를 반환한다.
```

그룹화 방식은 DBMS에 따라 다를 수 있습니다.

대표적으로:

<details>
<summary>정렬 기반 그룹화</summary>

> 💡 먼저 `category`를 기준으로 **정렬해서 같은 값들을 붙여놓은 다음** 그룹화하는 방식이야.

```plain text
원본
DB
OS
DB
Network
OS
DB

     ↓ category 기준 정렬

DB
DB
DB
Network
OS
OS

     ↓ 순서대로 읽으면서 집계

DB      → 3
Network → 1
OS      → 2
```

즉,

```plain text
데이터 읽기
 → 정렬
 → 같은 값끼리 집계
 → 결과
```

인덱스가 없다면 별도의 정렬 작업이 필요할 수 있지만, `category` 인덱스가 있다면 이미 같은 값들이 모여 있으므로 **정렬 비용을 줄일 수 있어.**
</details>

<details>
<summary>해시 기반 그룹화</summary>

> 💡 이번에는 정렬하지 않고 **Hash Table을 만들어서 바로 집계**하는 방식이야.

DB가 데이터를 하나씩 읽으면서:

```plain text
DB      → { DB: 1 }

OS      → { DB: 1, OS: 1 }

DB      → { DB: 2, OS: 1 }

Network → { DB: 2, OS: 1, Network: 1 }

OS      → { DB: 2, OS: 2, Network: 1 }

DB      → { DB: 3, OS: 2, Network: 1 }
```

최종적으로:

```plain text
DB      → 3
OS      → 2
Network → 1
```

가 되는 거야.

즉,

```plain text
데이터 읽기
 → category를 Hash Key로 사용
 → Hash Table에서 바로 COUNT 증가
 → 결과
```

**정렬할 필요가 없다는 장점**이 있어. 대신 그룹 종류가 매우 많으면 Hash Table 자체가 커지면서 메모리를 많이 사용할 수 있어.
</details>

<details>
<summary>임시 테이블 기반 그룹화</summary>

> 💡 DB가 GROUP BY 결과를 만들기 위해 **내부적으로 임시 테이블을 만들어 사용하는 방식**이야.

개념적으로는:

```plain text
데이터 읽기
       ↓
[내부 임시 테이블]

category | count
---------+------
DB       | 3
OS       | 2
Network  | 1

       ↓
결과 반환
```

임시 테이블은 메모리에서 처리될 수도 있고, 조건이나 데이터 크기에 따라 디스크를 사용할 수도 있어.

MySQL에서 실행 계획의 `Extra`에

```plain text
Using temporary
```

가 나타난다면 **쿼리 처리 과정에서 내부 임시 테이블을 사용했다**는 의미야.
</details>

정렬 기반이라면 다음처럼 동작합니다.

```plain text
Table Scan
   ↓
Sort by category
   ↓
Group Aggregate
   ↓
Result
```

해시 기반이라면 다음처럼 동작할 수 있습니다.

```plain text
Table Scan
   ↓
Hash Aggregate
   ↓
Result
```

인덱스가 없다면 전체 데이터를 읽고 추가적인 그룹화 작업을 해야 하므로 비용이 커질 수 있습니다.

---

### 인덱스가 있는 경우

```plain text
CREATE INDEX idx_post_category ON post(category);
```

`category` 인덱스가 있다면 같은 category 값들이 인덱스에서 모여 있습니다.

```plain text
category index

DB
DB
DB
Network
Network
OS
OS
```

DB는 인덱스를 순서대로 읽으면서 같은 값끼리 묶을 수 있습니다.

```plain text
Index Scan
   ↓
Group Aggregate
   ↓
Result
```

즉, 별도의 정렬 비용을 줄일 수 있습니다.

특히 다음 쿼리에서는 효과가 큽니다.

```plain text
SELECT category, COUNT(*)
FROM post
GROUP BY category;
```

만약 `category`만 필요하다면 테이블 데이터까지 가지 않고 인덱스만 읽는 **커버링 인덱스**가 될 수도 있습니다.

<details>
<summary>_커버링 인덱스?_</summary>

> 💡 

> **쿼리에 필요한 모든 컬럼이 인덱스 안에 있어서, 실제 테이블까지 접근하지 않고 인덱스만으로 조회를 끝내는 경우**야.

예를 들어 다음 인덱스가 있다고 해보자.

```plain text
CREATE INDEX idx_post_category
ON post(category);
```

### 커버링 인덱스가 되는 경우

```plain text
SELECT category
FROM post
WHERE category = 'DB';
```

필요한 `category`가 인덱스 안에 있으니까:

```plain text
인덱스 조회
   ↓
category 확인
   ↓
바로 결과 반환
```

**테이블에 접근할 필요가 없어.**

### 커버링 인덱스가 아닌 경우

```plain text
SELECT title
FROM post
WHERE category = 'DB';
```

`category`는 인덱스에 있지만 `title`은 없기 때문에:

```plain text
인덱스에서 category 검색
   ↓
실제 테이블 접근
   ↓
title 조회
```

추가적인 테이블 접근이 필요해.

### 왜 빠를까?

핵심은 **테이블 접근을 줄일 수 있기 때문**이야.

```plain text
일반 인덱스 조회
인덱스 → 테이블 → 결과

커버링 인덱스
인덱스 → 결과
```

**한 줄 정리:**

👉 커버링 인덱스 = **쿼리에 필요한 데이터를 인덱스가 전부 가지고 있어서 테이블을 읽지 않아도 되는 경우**.
</details>

## 4. ORDER BY와 GROUP BY에서 복합 인덱스가 중요한 이유

실제 쿼리는 보통 `WHERE`, `ORDER BY`, `GROUP BY`가 함께 사용됩니다.

예를 들어:

```plain text
SELECT category, COUNT(*)
FROM post
WHERE status = 'PUBLISHED'
GROUP BY category
ORDER BY category;
```

이 경우 다음 인덱스가 도움이 될 수 있습니다.

```plain text
CREATE INDEX idx_post_status_category
ON post(status, category);
```

인덱스 구조는 대략 다음과 같습니다.

```plain text
(status, category) index

('DRAFT', 'DB')
('DRAFT', 'OS')
('PUBLISHED', 'DB')
('PUBLISHED', 'DB')
('PUBLISHED', 'Network')
('PUBLISHED', 'OS')
```

DB는 먼저 `status = 'PUBLISHED'` 범위를 찾고, 그 안에서 `category` 순서대로 데이터를 읽을 수 있습니다.

```plain text
Index Range Scan
   ↓
Group Aggregate
   ↓
이미 category 순서
   ↓
Result
```

이렇게 되면 `WHERE` 필터링, `GROUP BY`, `ORDER BY`를 하나의 인덱스로 효율적으로 처리할 가능성이 높아집니다.

## 5. 인덱스를 활용하기 어려운 경우

다음과 같은 경우에는 인덱스가 있어도 `ORDER BY`나 `GROUP BY`에 잘 활용되지 않을 수 있습니다.

### 1. 정렬 컬럼에 함수가 적용된 경우

```plain text
SELECT *
FROM post
ORDER BY DATE(created_at);
```

인덱스는 `created_at` 원본 값 기준으로 정렬되어 있는데, 쿼리는 `DATE(created_at)` 결과로 정렬합니다.

이 경우 일반적인 `created_at` 인덱스를 그대로 활용하기 어렵습니다.

---

### 2. 복합 인덱스의 컬럼 순서와 쿼리가 맞지 않는 경우

```plain text
CREATE INDEX idx_post_status_created_at
ON post(status, created_at);
```

이 인덱스는 다음 쿼리에 유리합니다.

```plain text
SELECT *
FROM post
WHERE status = 'PUBLISHED'
ORDER BY created_at;
```

하지만 다음 쿼리에는 애매할 수 있습니다.

```plain text
SELECT *
FROM post
ORDER BY created_at;
```

인덱스가 `(status, created_at)` 순서로 정렬되어 있기 때문입니다.

```plain text
(status, created_at)

('DRAFT', 2026-08-01)
('DRAFT', 2026-08-03)
('PUBLISHED', 2026-08-02)
('PUBLISHED', 2026-08-04)
```

전체적으로 보면 `created_at` 순서가 아닙니다.

---

### 3. 정렬 방향이 복합 인덱스와 맞지 않는 경우

```plain text
CREATE INDEX idx_post_category_created_at
ON post(category ASC, created_at ASC);
```

다음 쿼리는 인덱스를 활용하기 쉽습니다.

```plain text
ORDER BY category ASC, created_at ASC
```

또는 DB에 따라 역방향 스캔으로 다음도 가능할 수 있습니다.

```plain text
ORDER BY category DESC, created_at DESC
```

하지만 방향이 섞이면 어려울 수 있습니다.

```plain text
ORDER BY category ASC, created_at DESC
```

이 경우에는 별도 정렬이 필요할 수 있습니다.

다만 MySQL 8.0 이상에서는 내림차순 인덱스를 지원하므로 다음처럼 설계할 수 있습니다.

```plain text
CREATE INDEX idx_post_category_created_at_desc
ON post(category ASC, created_at DESC);
```

---

### 4. WHERE 조건에서 범위 조건 이후 컬럼을 정렬에 쓰는 경우

```plain text
CREATE INDEX idx_post_category_created_at
ON post(category, created_at);

SELECT *
FROM post
WHERE category > 'DB'
ORDER BY created_at;
```

`category`가 범위 조건이면 여러 category 범위가 섞입니다.

각 category 내부에서는 `created_at` 순서일 수 있지만, 전체 결과가 `created_at` 순서라고 보장되지는 않습니다.

그래서 별도 정렬이 필요할 수 있습니다.

---

## 6. 실행 계획에서 확인할 수 있는 것

실제로 인덱스가 사용되는지는 실행 계획으로 확인해야 합니다.

MySQL 기준:

```plain text
EXPLAIN
SELECT category, COUNT(*)
FROM post
WHERE status = 'PUBLISHED'
GROUP BY category
ORDER BY category;
```

확인할 포인트:

| 항목 | 의미 |
| --- | --- |
| `key` | 실제 사용한 인덱스 |
| `type` | 접근 방식 |
| `rows` | 예상으로 읽을 행 수 |
| `Extra` | 추가 작업 여부 |

`Extra`에 다음이 보이면 추가 비용이 있을 수 있습니다.

| Extra | 의미 |
| --- | --- |
| `Using filesort` | 인덱스 순서만으로 정렬하지 못해 별도 정렬 수행 |
| `Using temporary` | GROUP BY 등을 위해 임시 테이블 사용 |
| `Using index` | 커버링 인덱스로 테이블 접근 없이 처리 가능 |

---

## ORDER BY/GROUP BY 비교 정리

| 구분 | 인덱스 없음 | 적절한 인덱스 있음 |
| --- | --- | --- |
| `ORDER BY` | 데이터를 읽은 뒤 별도 정렬 | 인덱스 순서대로 읽어 정렬 비용 감소 |
| `GROUP BY` | 정렬/해시/임시 테이블로 그룹화 | 같은 값이 모인 인덱스를 순서대로 읽으며 그룹화 가능 |
| 비용 | CPU, 메모리, 디스크 I/O 증가 가능 | 정렬/그룹화 비용 감소 가능 |
| 실행 계획 | `Using filesort`, `Using temporary` 가능 | `Using index`, index scan 가능 |

## 면접 답변 예시

`ORDER BY`와 `GROUP BY`는 모두 데이터의 순서를 맞추거나 같은 값끼리 묶어야 하기 때문에 비용이 큰 연산입니다. 인덱스가 없다면 DB는 조건에 맞는 데이터를 먼저 읽은 뒤, 정렬을 수행하거나 임시 테이블 또는 해시 구조를 사용해 그룹화를 수행합니다. 데이터가 많으면 메모리뿐 아니라 디스크 I/O까지 발생할 수 있습니다.

반면 정렬 기준이나 그룹 기준에 맞는 인덱스가 있으면 DB는 인덱스가 이미 정렬되어 있다는 점을 활용할 수 있습니다. 예를 들어 `ORDER BY created_at` 쿼리에서 `created_at` 인덱스가 있다면 별도의 정렬 없이 인덱스를 순서대로 읽을 수 있습니다. `GROUP BY category`도 `category` 인덱스가 있다면 같은 category 값들이 인덱스상에 모여 있기 때문에 순차적으로 읽으면서 그룹화할 수 있습니다.

다만 인덱스가 있다고 항상 사용되는 것은 아닙니다. `WHERE`, `ORDER BY`, `GROUP BY`에 사용되는 컬럼 순서가 복합 인덱스의 순서와 맞아야 하고, 함수가 적용되거나 범위 조건이 섞이면 인덱스를 정렬 용도로 활용하지 못할 수 있습니다. 그래서 실제로는 `EXPLAIN`을 통해 `Using filesort`, `Using temporary`, `Using index` 같은 실행 계획을 확인해야 합니다.
