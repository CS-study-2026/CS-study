# 10-1. 그렇다면, B+Tree가 B-Tree에 비해 반드시 좋다고 할 수 있을까요? 그렇지 않다면 어떤 단점이 있을까요?

> B+Tree가 B-Tree보다 무조건 좋다고 할 수는 없습니다.

B+Tree는 실제 데이터가 리프 노드에만 존재하고 리프 노드끼리 연결되어 있기 때문에 **범위 검색과 순차 접근에는 더 유리**합니다.

하지만 단일 데이터를 조회할 때는 차이가 있을 수 있습니다. B-Tree는 데이터가 내부 노드에도 저장될 수 있기 때문에 운이 좋다면 **리프까지 내려가지 않고 내부 노드에서 바로 데이터를 찾을 수 있습니다.** 반면 B+Tree는 데이터가 리프에만 있기 때문에 검색 키를 발견하더라도 최종적으로 리프까지 내려가야 합니다.

또한 B+Tree는 리프 노드를 연결하기 위한 포인터가 추가로 필요하고, 키가 내부 노드와 리프 노드에 중복해서 저장될 수 있어 공간적인 오버헤드도 발생할 수 있습니다.

따라서 **범위 검색과 순차 접근이 중요한 데이터베이스 인덱스에서는 B+Tree가 유리하지만, 모든 상황에서 B+Tree가 우월하다고 볼 수는 없습니다.**

---

## 1️⃣ B+Tree의 장점

### ✅ 1. 범위 검색에 유리

Leaf Node가 서로 연결되어 있기 때문에

```plain text
[10 | 20] → [30 | 40] → [50 | 60] → [70 | 80]
```

특정 위치를 찾은 후 다음 데이터를 순차적으로 읽을 수 있다.

ex) `WHERE age BETWEEN 20 AND 50`

➡️ 범위 검색에 적합

---

### ✅ 2. 내부 노드에 더 많은 Key 저장 가능

B+Tree의 내부 노드는 데이터 자체를 저장하지 않고

**탐색을 위한 Key만 저장**

하기 때문에 하나의 노드에 더 많은 Key를 저장할 수 있다.

➡️ 트리의 높이를 낮추는 데 유리

➡️ 디스크 I/O 감소

---

### ✅ 3. 순차 탐색에 유리

Leaf Node가 연결되어 있기 때문에

```plain text
Leaf 1 → Leaf 2 → Leaf 3 → Leaf 4
```

순서대로 데이터를 읽기 쉽다.

---

## 2️⃣ B+Tree의 단점

### ⚠️ 1. 단일 데이터 검색에서는 불리할 수 있음

B-Tree에서는 내부 노드에도 실제 데이터가 저장될 수 있다.

```plain text
          [50 | DATA]
         /           \
      ...             ...
```

만약 찾는 값이 `50`이라면

```plain text
Root
 ↓
50 발견
 ↓
끝
```

리프까지 내려갈 필요가 없다.

반면 B+Tree에서

```plain text
        [50]
          ↓
        Leaf
          ↓
        Data
```

내부 노드의 `50`은 탐색을 위한 키일 뿐,
실제 데이터는 Leaf에 있으므로 **Leaf까지 내려가야 한다.**

---

### ⚠️ 2. 키 중복 및 추가 포인터 오버헤드

B+Tree에서는 내부 노드의 Key가 **탐색을 위한 인덱스 역할**을 하고,

Leaf에도 동일한 Key가 존재할 수 있다.

```plain text
        [ 30  |  60 ]
        /     |     \
       ↓      ↓      ↓
    [10|30]→[30|50]→[60|70]
```

또한 리프 노드끼리 연결하기 위한 포인터도 필요하다.

➡️ B-Tree보다 추가적인 공간이 필요할 수 있음

<details>
<summary>메모리 요구량에 대한 주의</summary>

B+Tree의 단점으로

> "모든 중간 노드를 메모리에 유지해야 한다"

라고 설명하는 경우가 있지만,
이는 정확한 표현은 아니다.

DB는 일반적으로 필요한 인덱스 페이지를
**버퍼 풀(Buffer Pool)**에 캐싱한다.

즉,

```plain text
Disk
 ↓
필요한 페이지
 ↓
Buffer Pool
 ↓
탐색
```

형태로 동작한다.

따라서 B+Tree 자체의 본질적인 단점이라기보다는
**인덱스 자체가 추가적인 저장 공간을 필요로 한다**고 이해하는 것이 적절하다.
</details>

> 💡 다만 실제 DB에서는 이러한 공간 오버헤드보다 **낮은 트리 높이와 효율적인 범위 검색, 디스크 I/O 감소**라는 장점이 더 중요할 수 있다.

---

### ⚠️ 3. 구조가 상대적으로 복잡

Leaf Node 연결을 관리해야 하고,

삽입·삭제 과정에서

- 노드 분할

- 노드 병합

- Key 이동

- Leaf 연결 관리

등을 수행해야 한다.

---

## 3️⃣ B-Tree vs B+Tree

| 상황 | 유리한 구조 |
| --- | --- |
| 단일 Key 검색 | B-Tree가 유리할 수 있음 |
| 범위 검색 | **B+Tree** |
| 순차 접근 | **B+Tree** |
| DB 인덱스 | **B+Tree가 일반적으로 유리** |
| 디스크 I/O 최소화 | **B+Tree** |

> 

  <details>
  <summary>💡 **B+Tree가 B-Tree보다 무조건 좋은 것이 아니라, 데이터베이스에서 중요하게 요구되는 범위 검색과 디스크 I/O 효율 측면에서 장점이 크기 때문에 많이 사용된다.**</summary>

B+Tree가 좋은 이유는 단순히 "B-Tree보다 탐색 시간복잡도가 더 낮기 때문"이 아니다.

두 구조 모두 균형이 유지되면
일반적으로 **O(log N)** 수준이다.

핵심은

### 💡 디스크 I/O와 접근 패턴

```plain text
여러 키를 하나의 노드에 저장
        ↓
트리 높이 감소
        ↓
디스크 페이지 접근 횟수 감소
        ↓
대규모 데이터 탐색에 유리
```

그리고 B+Tree는

```plain text
Leaf → Leaf → Leaf → Leaf
```

연결 구조를 이용하여
범위 검색을 효율적으로 처리할 수 있다.
  </details>

## 🎯 예상 꼬리 질문

### Q. B+Tree는 왜 검색할 때 항상 Leaf까지 가나요?

실제 데이터가 Leaf에만 저장되기 때문이다.

내부 노드는 데이터를 저장하는 공간이 아니라 **검색 경로를 결정하는 인덱스 역할**을 한다.
