# 8-0. View가 무엇이고, 언제 사용할 수 있나요?

## 1. View란?

> **View(뷰)**는 하나 이상의 테이블을 기반으로 만들어지는 **가상의 테이블(Virtual Table)**입니다.

일반적인 테이블처럼 `SELECT`로 조회할 수 있지만, 대부분의 경우 **데이터 자체를 별도로 저장하는 것이 아니라 SELECT 쿼리를 저장**해 둡니다.

예를 들어 다음과 같은 테이블이 있다고 해봅시다.

```plain text
EMPLOYEE - 사원
┌────────┬──────────┬─────────┬──────────┐
│ EMP_ID │ EMP_NAME │ DEPT_ID │ SALARY   │
├────────┼──────────┼─────────┼──────────┤
│ 1      │ 김철수    │ 10      │ 4000000  │
│ 2      │ 이영희    │ 20      │ 5000000  │
└────────┴──────────┴─────────┴──────────┘

DEPARTMENT - 부서
┌─────────┬────────────┐
│ DEPT_ID │ DEPT_NAME  │
├─────────┼────────────┤
│ 10      │ 개발팀      │
│ 20      │ 인사팀      │
└─────────┴────────────┘
```

사원 이름과 부서 이름을 조회하려면 매번 다음과 같은 JOIN을 작성해야 합니다.

```sql
SELECT E.EMP_ID,
       E.EMP_NAME,
       D.DEPT_NAME
FROM EMPLOYEE E
JOIN DEPARTMENT D
  ON E.DEPT_ID = D.DEPT_ID;
```

자주 사용하는 쿼리라면 이를 View로 만들어 둘 수 있습니다.

```sql
CREATE VIEW EMPLOYEE_VIEW AS
SELECT E.EMP_ID,
       E.EMP_NAME,
       D.DEPT_NAME
FROM EMPLOYEE E
JOIN DEPARTMENT D
  ON E.DEPT_ID = D.DEPT_ID;
```

그러면 이후에는 일반 테이블처럼 간단하게 조회할 수 있습니다.

```sql
SELECT *
FROM EMPLOYEE_VIEW;
```

결과적으로 다음과 같은 구조로 생각할 수 있습니다.

```plain text
사용자
  │
  │ SELECT * FROM EMPLOYEE_VIEW
  ▼
┌───────────────────────────┐
│       EMPLOYEE_VIEW       │
│   "저장된 SELECT 쿼리"      │
└─────────────┬─────────────┘
              │
        실제 데이터 조회
              │
       ┌──────┴──────┐
       ▼             ▼
  EMPLOYEE       DEPARTMENT
  실제 테이블       실제 테이블
```

즉, _**View는 실제 데이터를 가지고 있는 새로운 테이블이라기보다 실제 테이블을 바라보는 하나의 창(window)**_이라고 이해하면 쉽습니다.

## 2. View에는 데이터가 저장되어 있지 않은가?

일반적인 View에는 **조회 ****결과**** 데이터가 별도로 저장되지 않습니다.**

예를 들어

```sql
CREATE VIEW DEV_EMPLOYEE AS
	SELECT EMP_ID, EMP_NAME
	FROM EMPLOYEE
	WHERE DEPT_ID = 10;
```

라고 만들었다면 DB에는 대략적으로

> `EMPLOYEE 테이블에서 DEPT_ID = 10인 데이터를 조회한다`

라는 **쿼리 정의****가 저장**됩니다.

따라서 원본 `EMPLOYEE` 테이블의 데이터가 변경되면 View를 다시 조회했을 때 변경된 결과가 나타납니다.

```plain text
View 생성
   │
   ▼
SELECT ... FROM EMPLOYEE WHERE ...
   │
   └── 쿼리 정의 저장

나중에 View 조회
   │
   ▼
SELECT * FROM DEV_EMPLOYEE
   │
   ▼
원본 EMPLOYEE 테이블 조회
   │
   ▼
현재 데이터를 기반으로 결과 반환
```

> 단, **Materialized View(구체화 뷰)**는 예외입니다. 조회 결과 자체를 실제로 저장하는 별도의 개념입니다.

## Materialized View(구체화 뷰)란?

**Materialized View는 일반 View와 달리, SELECT 쿼리의 ****실행 결과****를 실제로 저장해두는 View**입니다.

```plain text
일반 View
SELECT 쿼리만 저장
      ↓
조회할 때마다 원본 테이블에서 데이터 조회

Materialized View
SELECT 쿼리 + 조회 결과 저장
      ↓
저장된 결과를 바로 조회
```

### 왜 사용할까?

복잡한 `JOIN`, `GROUP BY`, 집계 연산처럼 **실행 비용이 큰 쿼리의 결과를 미리 저장**해두면 빠르게 조회할 수 있습니다.

예를 들어 수천만 건의 주문을 매번 집계하는 대신,

```sql
SELECT PRODUCT_ID, SUM(PRICE)
FROM ORDERS
GROUP BY PRODUCT_ID;
```

그 결과를 Materialized View에 저장해두고 재사용하는 방식입니다.

### 단점: 최신 데이터와 차이가 날 수 있음

원본 테이블이 변경되어도 저장된 결과가 **항상 즉시 변경되는 것은 아닙니다.**

```plain text
ORDERS 원본 데이터 변경
        ↓
Materialized View
        ↓
기존 데이터가 남아있을 수 있음
        ↓
Refresh
        ↓
최신 데이터 반영
```

그래서 일정 주기 또는 특정 시점에 **Refresh(갱신)**가 필요합니다. 갱신 방식과 지원 기능은 DBMS마다 다릅니다.

### 핵심 비교

|   | 일반 View | Materialized View |
| --- | --- | --- |
| 쿼리 정의 저장 | O | O |
| **조회 결과 저장** | X | **O** |
| 조회 성능 | 원본 쿼리에 영향받음 | **빠를 수 있음** |
| 최신 데이터 | 기본적으로 원본 기준 | 갱신 시점에 따라 차이 가능 |
| 저장 공간 | 거의 필요 없음 | **필요함** |

> **한 줄 요약:**

**Materialized View = 복잡한 쿼리의 결과를 실제로 저장해두어 조회 성능을 높이는 View**입니다.

# 3. 그렇다면 View는 왜 사용할까?

View의 대표적인 목적은 **복잡한 쿼리 단순화, 보안, 데이터 추상화**입니다.

### ① 복잡한 쿼리를 단순하게 만들기

여러 테이블을 JOIN하고 조건을 적용하는 복잡한 쿼리를 매번 작성하지 않아도 됩니다.

```sql
SELECT *
FROM EMPLOYEE_VIEW;
```

처럼 간단하게 사용할 수 있습니다.

특히 여러 곳에서 **동일한 JOIN이나 조회 로직을 반복해서 사용하는 경우** 유용합니다.

---

### ② 보안을 위해 특정 데이터만 공개하기

View를 이용하면 원본 테이블의 일부 컬럼만 사용자에게 보여줄 수 있습니다.

예를 들어 직원 테이블에 다음 정보가 있다고 해봅시다.

```plain text
EMPLOYEE 테이블
---------------
EMP_ID
EMP_NAME
DEPT_ID
PHONE
ADDRESS
SALARY
```

일반 직원에게 급여와 주소를 공개하고 싶지 않다면

```sql
CREATE VIEW EMPLOYEE_PUBLIC AS
	SELECT EMP_ID,
	       EMP_NAME,
	       DEPT_ID
	FROM EMPLOYEE;
```

처럼 View를 만들 수 있습니다.

그리고 사용자에게 `EMPLOYEE` 테이블에 대한 직접 접근 권한은 주지 않고 `EMPLOYEE_PUBLIC` View에 대한 권한만 줄 수 있습니다.

```plain text
사용자
  │
  ▼
EMPLOYEE_PUBLIC View
  │
  ├── EMP_ID      O
  ├── EMP_NAME    O
  ├── DEPT_ID     O
  │
  ▼
EMPLOYEE 원본 테이블
  ├── PHONE       X
  ├── ADDRESS     X
  └── SALARY      X
```

따라서 View는 **DB 접근 제어를 위한 수단 중 하나**로 사용할 수 있습니다.

---

### ③ 실제 테이블 구조를 숨길 수 있다

사용자는 실제 DB가 어떻게 구성되어 있는지 몰라도 View를 사용할 수 있습니다.

예를 들어 실제 DB에서는

```plain text
EMPLOYEE
DEPARTMENT
POSITION
```

세 개의 테이블을 JOIN해야 하더라도,

사용자에게는

```sql
SELECT *
FROM EMPLOYEE_INFO;
```

라는 단순한 인터페이스만 제공할 수 있습니다.

이를 **데이터 추상화(Data Abstraction)**라고 볼 수 있습니다.

---

### ④ 자주 사용하는 조회 조건을 재사용할 수 있다

예를 들어 재직 중인 직원만 계속 조회해야 한다면

```sql
CREATE VIEW ACTIVE_EMPLOYEE AS
	SELECT *
	FROM EMPLOYEE
	WHERE STATUS = 'ACTIVE';
```

View를 만들어 놓고

```sql
SELECT *
FROM ACTIVE_EMPLOYEE;
```

로 반복해서 사용할 수 있습니다.

## 4. View의 장점과 단점

| 구분 | 내용 |
| --- | --- |
| 장점 | 복잡한 SQL을 단순화할 수 있음 |
|   | 자주 사용하는 조회 로직을 재사용 가능 |
|   | 특정 컬럼/행만 공개하여 접근을 제한할 수 있음 |
|   | 실제 테이블 구조를 사용자에게 숨길 수 있음 |
| 단점 | View가 많아지면 의존관계 관리가 복잡해질 수 있음 |
|   | 복잡한 View를 중첩해서 사용하면 성능 문제나 쿼리 분석의 어려움이 생길 수 있음 |
| 주의 | 일반 View 자체가 조회 결과를 저장해 성능을 높여주는 것은 아님 |

특히 마지막 부분이 중요합니다.

```plain text
View = 쿼리 결과 저장소 ❌
View = 쿼리를 재사용하기 위한 가상의 테이블 ⭕
```

따라서 **View를 만든다고 무조건 조회 속도가 빨라지는 것은 아닙니다.**

## View의 의존관계란?

**의존관계(Dependency)**란 어떤 DB 객체가 **다른 DB 객체를 기반으로 동작하는 관계**를 의미합니다.

예를 들어:

```plain text
EMPLOYEE 테이블
      ↓
EMPLOYEE_VIEW
      ↓
ACTIVE_EMPLOYEE_VIEW
```

`EMPLOYEE_VIEW`가 `EMPLOYEE` 테이블을 조회한다면,

> `EMPLOYEE_VIEW`는 `EMPLOYEE` 테이블에 **의존한다**

고 표현합니다.

### 왜 View가 많아지면 문제가 될까?

View가 다른 View를 참조하는 식으로 복잡해질 수 있기 때문입니다.

```plain text
EMPLOYEE ──→ EMPLOYEE_VIEW
                   ↓
             ACTIVE_EMPLOYEE_VIEW
                   ↓
             REPORT_VIEW
```

이 상태에서 `EMPLOYEE`의 컬럼을 삭제하거나 이름을 변경하면,

```plain text
EMPLOYEE 변경
   ↓
EMPLOYEE_VIEW 문제 발생
   ↓
ACTIVE_EMPLOYEE_VIEW 영향
   ↓
REPORT_VIEW 영향
```

처럼 **연쇄적으로 여러 View에 영향을 줄 수 있습니다.**

따라서 **의존관리를 한다**는 것은,

> "이 테이블이나 View를 변경하면 어떤 View들이 영향을 받는가?"

를 파악하고 관리하는 것을 의미합니다.

### 한 줄 정리

**의존관계 = "이 객체가 동작하기 위해 어떤 다른 객체가 필요한가?"라는 관계**

View가 많고 View끼리 중첩될수록 이 관계가 복잡해져서 **테이블 구조 변경 시 영향 범위를 파악하기 어려워지는 것**이 단점입니다.
</details>

# 5. 핵심 정리

> **View는 하나 이상의 실제 테이블을 기반으로 만들어지는 가상의 테이블이다.**

일반적인 View는 데이터를 직접 저장하는 것이 아니라 **SELECT 쿼리의 정의를 저장**하며, 조회할 때 원본 테이블을 기반으로 결과를 반환한다.

주로 **복잡한 쿼리의 단순화, 반복되는 조회 로직의 재사용, 데이터 접근 제한(보안), 실제 테이블 구조의 추상화**를 위해 사용한다.

### 한 문장으로

> **View = 자주 사용하는 SELECT 쿼리에 이름을 붙여 테이블처럼 사용할 수 있게 만든 객체**
