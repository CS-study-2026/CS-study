# 11-2. 물리적인 Lock을 건다면, 만약 이를 수행중인 요청에 문제가 생겨 비정상 종료되면 Lock이 절대 해제되지 않는 문제가 생길 수도 있을 것 같습니다. DB는 이를 위한 해결책이 있나요? 없다면, 우리가 이 문제를 해결할 수 없을까요?

# **0. 결론**

## **질문의 본질**

**“락(Lock)의 소유권과 생명주기, 그리고 장애 발생 시 자동 해제와 애플리케이션 차원의 안전장치를 이해하나?”**

## **의문:** 

트랜잭션 도중 애플리케이션이 비정상 종료(`Crash`)되면 락이 영원히 남아 고아(`Orphan`)가 되지 않을까?

## 핵**심 답변:**

> 

**[DB가 비정상 종료를 감지하는 경우]
**프로세스가 죽어 DB 커넥션이 끊어지면, **DB는 이를 감지하고 트랜잭션 롤백 및 락을 자동 해제**

**[DB가 비정상 종료를 감지하지 못하는 경우]**

OS나 네트워크 이슈로 인해 **DB가 커넥션 단절을 즉시 감지하지 못하면 락이 유지**
→ 개발자  :
(1) `idle_in_transaction_session_timeout` 설정
일을 하지 않고 락만 쥔 채 유휴 상태인 좀비 세션을 DB가 주기적으로 감지하여 강제 세션 `KILL`, 락 수거
(2)애플리케이션 단에서 트랜잭션 범위와 시간을 최소화
(3) `Timeout`을 명시하여 시스템이 무한 대기에 빠지는 것을 원천 차단

## **[사전 지식] 데드락 및 고아락이란?**

- **데드락 (교착 상태):** 
두 개 이상의 트랜잭션이 서로가 가진 락을 얻으려고 무한히 대기하며 시스템이 멈추는 현상
(DB 엔진이 이를 감지하면 한쪽 트랜잭션을 강제로 롤백하여 해결)

- **고아락 (고스트 락): **
락 획득 주체(애플리케이션)가 락을 해제하기 전에 비정상 종료되어 시스템에 영원히 남아있는 락

---

# **1. 락 종류별 동작 과정 및 장애 전파**

## **(1) 낙관적 락(Optimistic Lock) 동작 과정**

실제 물리적인 자원을 점유하지 않고, 애플리케이션의 조건문 변수(Version) 필드로 동시성을 제어하므로, 고아 락 문제를 유발하지 않습니다.

정상 흐름

1. 데이터를 조회할 때 `Version` 번호도 함께 읽어옴

1. 수정 시점에 `WHERE version = 최초버전` 조건으로 업데이트를 시도

  1. 성공 → 버전을 1++

  1. 실패(다른 사용자가 먼저 수정했다면 버전이 맞지 않아 `0 row updated`) → 애플리케이션 예외 발생

장애 발생 시 (애플리케이션 비정상 종료)

물리적으로 락을 쥐고 있는 것이 아니므로 다른 서버나 세션에 아무런 장애를 전파하지 X
(작업만 유실될 뿐 시스템은 안전)

---

## **(2) 비관적 락 (Pessimistic Lock) 동작 과정**

**정상 흐름**

1. 애플리케이션이 DB 커넥션을 획득하고 트랜잭션을 시작

1. `SELECT ... FOR UPDATE` 쿼리를 실행하여 특정 데이터 로우(Row)에 **물리적인 배타적 락 **

1. 데이터 수정 후 `COMMIT` / `ROLLBACK` 시점에 DB가 락 자동 해제

**장애 발생 시 (애플리케이션 비정상 종료)**

- **DB가 단절을 즉시 인지 :** DB가 자동으로 수행 및 복구
애플리케이션 프로세스가 죽으면 TCP 소켓이 닫힘
→ DB는 커넥션 유실 즉시 감지, 해당 세션 트랜잭션을 **자동 롤백하며 락 즉시 해제**

- **네트워크 장애 등으로 감지하지 못한 경우 :** 개발자 제어 및 개입
DB는 세션이 살아있다고 오해하여 락을 계속 쥐고 있음

이때 다른 트랜잭션들이 해당 데이터에 접근하려 하면 `lock_wait_timeout`에 걸려 에러 발생
(락을 쥔 좀비 트랜잭션은 여전히 살아있음)

**⇒ 해결책:** 
DB에 **`idle_in_transaction_session_timeout(PostgreSQL)`**이나
**`innodb_kill_idle_transaction`**`(MySQL)`설정해, 
일을 안 하고 락만 쥔 채 멈춰있는 유휴 세션을 강제로 KILL & 락 회수

---

## **(3) 분산 락 (Distributed Lock) 동작 과정**

**정상 흐름**

1. 분산 환경서 여러 서버가 공통자원 제어를 위해 **Redis 같은 외부 공유 메모리에 특정 Key 선점(Lock 획득)**

1. 비즈니스 로직 수행 및 DB 반영

1. 작업이 끝나면 애플리케이션이 Redis의 Key를 직접 삭제해 Lock 해제

**장애 발생 시 (애플리케이션 비정상 종료)**

DB 트랜잭션 세션과 무관하므로 Redis는 애플리케이션이 죽었는지 알 방법이 없으며, 자동으로 해제해 주지 X**즉, 순수 자동 복구 불가능**

- **TTL(Time-To-Live) 지정** : 개발자 제어 및 개입
프로세스가 죽어도 지정된 시간이 지나면 Redis가 Key를 자동으로 삭제하여 고아락 소멸

  <details>
  <summary>**`Watchdog`**</summary>

작업이 예상보다 길어져 TTL이 먼저 끝나버리면 락 유실
→ 자바의 `Redisson` 라이브러리는 **Watchdog(와치독)**이라는 백그라운드 스레드를 띄움

애플리케이션이 살아있는 동안에는 주기적으로 TTL을 연장해주다가, 
**애플리케이션이 비정상 종료되면 연장 작업이 중단되어 안전하게 TTL 만료로 락이 해제**되도록 제어
  </details>

## **락의 주체에 따른 복구 책임 비교**

| **구분** | **낙관적 락 (Optimistic)** | **비관적 락 (Pessimistic)** | **분산 락 (Distributed)** |
| --- | --- | --- | --- |
| **락의 실체** | 데이터의 `Version` 필드 값 | DB 메모리 내 트랜잭션 세션 | 외부 저장소(Redis)의 Key-Value |
| **정상 해제 주체** | 애플리케이션 로직 검증 종료 | `COMMIT` / `ROLLBACK` | 애플리케이션의 Key 삭제 (`DEL`) |
| **비정상 종료 시 현상** | 영향 없음 (고아 락 발생 안 함) | 커넥션 미감지 시 좀비 락 유지 | 락을 쥔 주체가 사라져 **영구 고립** |
| **1) DB 자동 복구** | 해당 없음 | **커넥션 유실 즉시 감지 후 롤백** | **불가능 (Redis는 프로세스 생사를 모름)** |
| **2) 사용자 제어(해결책)** | 실패 시 예외 처리 및 재시도 구현 | **유휴 세션 타임아웃 설정 필수** | **Key에 TTL 설정 및 Watchdog 활용** |

---

# 2. 심화 개념 : `lock_wait_timeout` 에 대한 오해

많은 개발자가 `lock_wait_timeout`을 설정하면 비정상 종료 시 고아 락이 해결된다고 착각합니다. 
하지만 이 옵션은 **락을 얻기 위해 줄을 서서 "기다리는(Wait) 쪽"의 타임아웃으로,** 락을 쥐고 있는 좀비 트랜잭션 자체를 죽여서 고아 락을 해제하는 옵션이 아닙니다. 
고아 락을 해결하려면 락을 쥐고 숨어버린 세션을 파괴하는 **유휴 트랜잭션 타임아웃(****`Idle Timeout`****)** 설정필수

---

# 3. 면접 답변 정리

> 낙관적 락은 물리적인 자원 점유가 아니므로 고아락 문제를 유발하지 않는다.

비관적 락은 DB가 비정상 종료를 감지하는 경우 자동 롤백 및 락 해제를 수행하며, 
감지하지 못하는 경우를 고려해 timeout 설정 및 트랜잭션 범위 최소화 설계를 해야한다.

분산 락은 DB가 개입할 수 없으므로, Key에 TTL을 걸어 고아 락을 원천 차단해야 한다.
