# 5-8. (A, B) 와 같은 방식으로 인덱스를 설정한 테이블에서, A 조건 없이 B 조건만 사용하여 쿼리를 요청했습니다. 해당 쿼리는 인덱스를 탈까요?

## 핵심 답변

일반적으로 `(A, B)` 형태의 복합 인덱스가 있을 때, `A` 조건 없이 `B` 조건만 사용하면 **인덱스를 효율적으로 타기 어렵습니다.**

이유는 복합 인덱스가 다음 순서로 정렬되어 있기 때문입니다.

```plain text
A 기준 정렬
  └── 같은 A 안에서 B 기준 정렬
```

즉, `(A, B)` 인덱스는 전체적으로 `B` 기준으로 정렬된 구조가 아닙니다.

따라서 `WHERE B = ?` 조건만으로는 원하는 값을 바로 찾기 어렵습니다.

---

## 예시

다음과 같은 테이블이 있다고 하겠습니다.

```plain text
CREATE TABLE post (
    id BIGINT PRIMARY KEY,
    category VARCHAR(50),
    created_at DATETIME,
    title VARCHAR(255)
);

CREATE INDEX idx_post_category_created_at
ON post(category, created_at);
```

여기서 복합 인덱스는 `(category, created_at)`입니다.

인덱스는 대략 다음처럼 정렬됩니다.

```plain text
(category, created_at)

('DB',      '2026-08-01')
('DB',      '2026-08-03')
('Network', '2026-08-02')
('Network', '2026-08-05')
('OS',      '2026-08-01')
('OS',      '2026-08-04')
```

이 인덱스는 먼저 `category` 기준으로 정렬되고, 같은 `category` 안에서 `created_at` 기준으로 정렬됩니다.

---

## A 조건이 있는 경우

```plain text
SELECT *
FROM post
WHERE category = 'DB'
  AND created_at = '2026-08-03';
```

이 경우에는 `(category, created_at)` 인덱스를 효율적으로 사용할 수 있습니다.

```plain text
category = 'DB' 범위로 이동
  ↓
그 안에서 created_at = '2026-08-03' 탐색
```

즉, 왼쪽 컬럼인 `category`부터 조건이 걸렸기 때문에 인덱스 탐색이 가능합니다.

---

## A 조건 없이 B 조건만 있는 경우

```plain text
SELECT *
FROM post
WHERE created_at = '2026-08-03';
```

이 경우에는 `category` 조건이 없습니다.

인덱스는 전체적으로 `created_at` 기준으로 정렬되어 있지 않습니다.

```plain text
('DB',      '2026-08-01')
('DB',      '2026-08-03')
('Network', '2026-08-02')
('Network', '2026-08-05')
('OS',      '2026-08-01')
('OS',      '2026-08-04')
```

`created_at = '2026-08-03'`인 값을 찾으려면 각 category 묶음을 모두 확인해야 합니다.

```plain text
DB 묶음 확인
Network 묶음 확인
OS 묶음 확인
...
```

그래서 `(category, created_at)` 인덱스를 효율적으로 사용하기 어렵습니다.

---

## 왼쪽 접두사 원칙

이 개념을 **왼쪽 접두사 원칙**, 또는 **Leftmost Prefix Rule**이라고 합니다.

복합 인덱스 `(A, B, C)`가 있다면 다음 조건은 인덱스를 효율적으로 활용할 수 있습니다.

```plain text
WHERE A = ?
WHERE A = ? AND B = ?
WHERE A = ? AND B = ? AND C = ?
```

또는 정렬에서도 다음처럼 사용할 수 있습니다.

```plain text
ORDER BY A
ORDER BY A, B
ORDER BY A, B, C
```

하지만 다음은 효율적으로 사용하기 어렵습니다.

```plain text
WHERE B = ?
WHERE C = ?
WHERE B = ? AND C = ?
ORDER BY B
ORDER BY C
```

왜냐하면 인덱스가 `A`부터 정렬되어 있기 때문입니다.

---

## 그럼 아예 인덱스를 안 타나요?

정확히 말하면 **DBMS에 따라 다릅니다.**

면접에서는 보통 이렇게 답하는 것이 좋습니다.

> 일반적으로는 `(A, B)` 복합 인덱스에서 선행 컬럼인 `A` 조건이 없고 `B` 조건만 있으면 인덱스를 효율적으로 사용하지 못합니다.

다만 DBMS나 옵티마이저에 따라 인덱스 전체를 스캔하거나, Skip Scan 같은 최적화를 사용할 수는 있습니다. 하지만 일반적인 인덱스 탐색처럼 빠르게 찾는 것은 아닙니다.

즉, 답은 다음처럼 구분하면 됩니다.

| 상황 | 설명 |
| --- | --- |
| 일반적인 인덱스 탐색 | 어렵다 |
| 인덱스 전체 스캔 | 가능할 수 있다 |
| Skip Scan 최적화 | DBMS에 따라 가능 |
| 효율적인 사용 | 보통 어렵다 |

---

## Index Full Scan과 Table Full Scan

`B` 조건만 있을 때 DB가 선택할 수 있는 방법은 크게 두 가지입니다.

### 1. Table Full Scan

테이블 전체를 읽으면서 `B` 조건을 검사합니다.

```plain text
Table Full Scan
  ↓
B = ? 필터링
```

### 2. Index Full Scan

`(A, B)` 인덱스 전체를 읽으면서 `B` 조건을 검사합니다.

```plain text
Index Full Scan
  ↓
B = ? 필터링
```

인덱스가 테이블보다 작거나, 쿼리에 필요한 컬럼이 인덱스 안에 있어서 커버링 인덱스가 된다면 DB가 Index Full Scan을 선택할 수도 있습니다.

하지만 이것은 `B` 값을 바로 찾아가는 탐색이 아니라, **인덱스를 처음부터 훑으면서 B 조건을 검사하는 것**에 가깝습니다.

---

## Skip Scan이란?

일부 DBMS는 Skip Scan을 지원합니다.

Skip Scan은 선행 컬럼 `A` 조건이 없어도, `A`의 가능한 값들을 내부적으로 나눠서 각각 `B`를 탐색하는 방식입니다.

```plain text
A = 값1 인 범위에서 B 검색
A = 값2 인 범위에서 B 검색
A = 값3 인 범위에서 B 검색
...
```

예를 들어 `(gender, email)` 인덱스가 있다고 해보겠습니다.

```plain text
gender 값: M, F
email 값: 매우 다양
```

`WHERE email = ?`만 있어도 DB는 내부적으로 이렇게 탐색할 수 있습니다.

```plain text
gender = M 범위에서 email 검색
gender = F 범위에서 email 검색
```

이 방식은 `A`의 종류가 적을 때 유리할 수 있습니다.

하지만 모든 상황에서 가능한 것은 아니고, DBMS와 실행 계획에 따라 달라집니다.

---

## 실무적으로 어떻게 해야 하나?

`B` 조건만 자주 사용한다면 `(A, B)` 인덱스에 기대면 안 됩니다.

다음 중 하나를 고려해야 합니다.

### 1. B 단일 인덱스 추가

```plain text
CREATE INDEX idx_post_created_at
ON post(created_at);
```

### 2. B가 앞에 오는 복합 인덱스 추가

```plain text
CREATE INDEX idx_post_created_at_category
ON post(created_at, category);
```

### 3. 쿼리 패턴에 맞게 인덱스 재설계

자주 쓰는 쿼리가 다음이라면:

```plain text
WHERE category = ?
ORDER BY created_at DESC
```

`(category, created_at)`이 적절합니다.

하지만 자주 쓰는 쿼리가 다음이라면:

```plain text
WHERE created_at = ?
```

`created_at` 단일 인덱스나 `(created_at, category)` 인덱스가 더 적절합니다.

---

## 정리

| 쿼리 조건 | `(A, B)` 인덱스 활용 |
| --- | --- |
| `WHERE A = ?` | 가능 |
| `WHERE A = ? AND B = ?` | 매우 유리 |
| `WHERE A = ? ORDER BY B` | 유리 |
| `WHERE B = ?` | 일반적으로 비효율적 |
| `WHERE B = ? AND C = ?` | `(A, B, C)`에서는 비효율적 |
| `ORDER BY B` | 일반적으로 비효율적 |

---

## 면접 답변 예시

`(A, B)` 형태의 복합 인덱스에서 `A` 조건 없이 `B` 조건만 사용하면 일반적으로 인덱스를 효율적으로 타기 어렵습니다. 복합 인덱스는 먼저 `A` 기준으로 정렬되고, 같은 `A` 값 안에서 다시 `B` 기준으로 정렬되는 구조이기 때문입니다.

예를 들어 `(category, created_at)` 인덱스가 있을 때 `WHERE category = ? AND created_at = ?` 조건은 인덱스를 잘 활용할 수 있습니다. 하지만 `WHERE created_at = ?`만 있으면 전체 인덱스가 `created_at` 기준으로 정렬된 것이 아니기 때문에 원하는 위치로 바로 이동하기 어렵습니다.

물론 DBMS에 따라 인덱스 전체를 스캔하거나 Skip Scan 같은 최적화를 사용할 수는 있습니다. 하지만 이것은 선행 컬럼부터 조건을 주는 일반적인 인덱스 탐색만큼 효율적이지 않습니다. 따라서 `B` 조건만 자주 조회한다면 `B` 단일 인덱스나 `(B, A)` 형태의 별도 인덱스를 고려하는 것이 좋습니다.
