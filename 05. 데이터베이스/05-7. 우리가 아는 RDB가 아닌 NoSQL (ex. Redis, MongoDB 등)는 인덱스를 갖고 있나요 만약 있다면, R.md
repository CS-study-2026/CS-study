# 5-7. 우리가 아는 RDB가 아닌 NoSQL (ex. Redis, MongoDB 등)는 인덱스를 갖고 있나요? 만약 있다면, RDB의 인덱스와는 어떤 차이가 있을까요?

### 일단 결론: 

> 네! NoSQL도 인덱스를 가질 수 있습니다!

하지만?

> NoSQL은 하나의 데이터 모델이 아니라 Key-Value, Document, Wide-Column 등 여러 형태를 포함하기 때문에 **제품과 데이터 모델에 따라 인덱스 구조와 사용 방식이 다릅니다.**

---

### NoSQL이란?

**NoSQL(Not Only SQL)**은 관계형 데이터베이스의 **테이블과 관계 중심 구조가 아닌 다양한 데이터 모델을 사용하는 데이터베이스**를 의미한다.

RDB가 데이터를 정해진 테이블 구조에 저장한다면,

```plain text
RDB

User Table
┌────┬──────┬─────┐
│ id │ name │ age │
├────┼──────┼─────┤
│ 1  │ Kim  │ 25  │
└────┴──────┴─────┘
```

NoSQL은 목적에 따라 데이터를 다양한 형태로 저장할 수 있다.

```plain text
NoSQL

Key-Value
key → value

Document
{
  "id": 1,
  "name": "Kim",
  "age": 25
}

Wide-Column
Column Family → Columns

Graph
Node → Relationship → Node
```

### NoSQL을 사용하는 이유

### RDB의 강점

> 정형화된 데이터와 데이터 간 관계를 다룸

하지만

서비스 규모  ↑ ( 대량 데이터 분산처리, 자주 변경되는 데이터 구조 등)

⇒ 유연한 데이터 모델이 필요

⇒ NoSQL은?

    - 다양한 데이터 모델 사용

    - 비교적 유연한 스키마

    - 수평 확장(Scale-out)을 고려한 제품이 많음 

    - 특정 조회 패턴이나 사용 목적에 최적화

# 1. MongoDB

> MongoDB는 RDB와 상당히 유사한 형태의 인덱스를 제공한다

MongoDB는 데이터를 Document 형태로 저장하지만, 특정 필드에 인덱스를 생성할 수 있습니다.

예를 들어:

```sql
{ "_id": 1, "name": "Kim",  "age": 25 }
{ "_id": 2, "name": "Lee",  "age": 30 }
{ "_id": 3, "name": "Park", "age": 20 }
{ "_id": 4, "name": "Choi", "age": 27 }
```

`age`를 자주 검색한다면:

```sql
db.users.createIndex({ age:1 }) // 1은 오름차순 인덱스
```

처럼 인덱스를 만들 수 있습니다.

기존 Document가 다시 정렬되는게 아니다!

Document와 별도로 인덱스 자료구조가 생성됩니다!

```sql
Collection

Document 1 → age: 25
Document 2 → age: 30
Document 3 → age: 20
Document 4 → age: 27


           createIndex({ age: 1 })
                     ↓

              별도의 Index

               20 → Document 3
               25 → Document 1
               27 → Document 4
               30 → Document 2
```

즉,

> 인덱싱한 Field의 값 + 해당 Document를 찾는 데 필요한 정보

가 저장이 됨.

기본적으로 모든 Document의 `_id` 필드에 **unique index를 자동 생성,**

일반적인 단일 필드 인덱스 외에도

| 종류 | 한 줄 설명 |
| --- | --- |
| **Compound Index** | 여러 Field를 묶어서 생성하는 복합 인덱스 |
| **Multikey Index** | 배열 Field의 각 요소를 검색하기 위한 인덱스 |
| **Text Index** | 문자열 Field의 텍스트 검색을 위한 인덱스 |
| **Geospatial Index** | 좌표 등 위치 기반 검색을 위한 공간 인덱스 |

의 다양한 인덱스를 지원

<details>
<summary>**인덱스가 없다면?**</summary>

**Collection Scan**

인덱스가 없다면 다음 쿼리를 실행했을 때,

```plain text
db.users.find({ age:27 })
```

MongoDB가 Collection의 Document들을 확인해야 할 수 있습니다.

```plain text
Kim  25 → 아니네
Lee  30 → 아니네
Park 20 → 아니네
Choi 27 → 찾았다
```

이를 **Collection Scan(COLLSCAN)**이라고 합니다.

데이터가 4개면 별문제가 없지만 1,000만 개라면 비효율적일 수 있습니다.

반대로 `age`에 인덱스가 존재하면,

```plain text
             age Index
                 │
        ┌────────┼────────┐
       20       25       27 ...
                          ↑
                       찾았다
                          │
                          ↓
                    Document 4
```

인덱스를 이용해 `27`이 있는 위치를 찾고 해당 Document에 접근할 수 있습니다.

### 왜?

MongoDB의 일반적인 인덱스는 **B-tree 계열의 정렬된 인덱스 구조**를 사용

⇒ 검색과 범위 조회를 효율적으로 처리
</details>

## 1-1. MongoDB 인덱스와 RDB 인덱스의 차이점

### 핵심 원리

핵심 원리는 상당히 비슷합니다.

```plain text
RDB

Table
 ├─ id
 ├─ name
 └─ age
      ↑
    Index
```

```plain text
MongoDB

Collection
 └─ Document
      ├─ _id
      ├─ name
      └─ age
           ↑
         Index
```

둘 다 결국

> **전체 데이터를 처음부터 끝까지 찾지 않고, 별도의 검색 구조를 이용해 원하는 데이터의 위치를 빠르게 찾는다.**

는 목적을 가집니다.

차이는 **데이터 모델**에서 발생합니다.

| 구분 | RDB | MongoDB |
| --- | --- | --- |
| 데이터 구조 | Table / Row | Collection / Document |
| 인덱스 대상 | Column | Document Field |
| 복합 인덱스 | 가능 | 가능 |
| 고유 인덱스 | 가능 | 가능 |
| 중첩 데이터 | 상대적으로 제한적 | 중첩 필드 인덱싱 가능 |
| 배열 | 일반적인 컬럼과 다름 | Multikey Index 지원 |
| 스키마 | 보통 고정적 | 유연한 Document 구조 |

즉, MongoDB는 **Document 내부의 중첩 필드나 배열까지 인덱싱할 수 있다는 점**이 특징입니다.

# 2. Redis

### 그러면 Redis도 인덱스를 갖고 있나요?

Redis의 기본적으로 Key → Value형태로, **Key를 통해 Value에 접근하는 **인메모리 데이터 저장소입다.

Redis는 내부적으로 Key를 관리하기 위해 **Hash Table을 사용**합니다.

```plain text
user:1001
    ↓
Hash Table에서 Key 검색
    ↓
{ name: Kim, age: 25 }
```

따라서 Key를 알고 있다면 일반적인 Key 조회를 **평균 O(1)**에 수행할 수 있습니다.

> **중요:** 여기서 Hash Table 자체를 RDB의 인덱스와 동일하다고 보면 안 됩니다.

RDB에서는 데이터가 저장된 테이블과 별도로 특정 Column에 **Secondary Index**를 생성하는 방식이 일반적입니다.

```plain text
RDB

Table
 │
 ├── id
 ├── name ← Index 생성
 └── age
```

반면 Redis의 기본적인 사용 방식은

별도의 Column Index를 생성해 조회하는 구조가 아니라,

데이터를 저장할 때 정의한 Key를 통해 Value에 직접 접근하는 방식이다.

⇒ 처음부터 **Key를 이용하여 데이터에 직접 접근하도록 데이터를 설계**

```sql
Redis

Key             Value

user:1001  →  { name: Kim, age: 25 }
user:1002  →  { name: Lee, age: 30 }
user:1003  →  { name: Park, age: 27 }
```

따라서 RDB처럼

```sql
users 테이블

id     name     age
--------------------
1001   Kim      25
1002   Lee      30
1003   Park     27

				↓

CREATE INDEX idx_user_nameON users(name);

				↓

[name Secondary Index]

Kim  → 해당 Row
Lee  → 해당 Row
Park → 해당 Row
```

특정 Column에 일반적인 보조 인덱스를 생성해서 데이터를 찾는 것이 **Redis의 기본 조회 방식은 아닙니다.**

---

## 그러면 Redis에는 인덱스가 없는 건가?

**그렇게 단정할 수는 없습니다.**

Redis는 여러 자료구조를 제공하며, 자료구조 자체를 이용하여 특정 조회를 효율적으로 만들 수 있습니다.

대표적으로 **Sorted Set**이 있습니다.

```plain text
ranking

100 → Kim
200 → Lee
300 → Park
```

Sorted Set은 내부적으로 **skip list 등의 자료구조**를 사용하여 정렬된 데이터의 범위 조회 등을 효율적으로 처리합니다.

예를 들어 게임 랭킹처럼

```plain text
점수가 높은 사용자 조회
특정 점수 범위 사용자 조회
순위 조회
```

같은 기능을 구현할 수 있습니다.

또한 별도의 **Redis Query Engine**을 사용하는 경우에는 Field를 대상으로 **Secondary Index**를 구성하여 검색하는 기능도 사용할 수 있습니다.

<details>
<summary>Redis Query Engine을 어떻게..?</summary>

Redis Query Engine을 이용하면 `age` 같은 필드에 **Secondary Index**를 구성하여 검색할 수 있습니다.

개념적으로 보면:

```plain text
Redis 데이터

user:1001 → { name: Kim,  age: 25 }
user:1002 → { name: Lee,  age: 30 }
user:1003 → { name: Park, age: 25 }

              +

       age Secondary Index

        25 → user:1001
             user:1003

        30 → user:1002
```

그러면 `age = 25` 같은 조건 검색을 효율적으로 수행할 수 있습니다.

### 그럼 RDB랑 똑같아지는 거 아니야?

**이 기능만 보면 상당히 비슷한 역할을 합니다.**

```plain text
RDB
Table
 ↓
Column
 ↓
Secondary Index


MongoDB
Document
 ↓
Field
 ↓
Index


Redis Query Engine
Hash / JSON 등의 데이터
 ↓
Field
 ↓
Secondary Index
```

다만 중요한 건 **Redis의 기본적인 Key-Value 조회와 Redis Query Engine을 이용한 검색을 구분하는 것**입니다.

Redis의 대표적인 기본 사용 방식은 여전히:

```plain text
Key → Value
```

이고 Query Engine은 여기에 **필드 기반 검색, 필터링 등을 가능하게 하는 검색 기능을 추가**한다고 보면 됩니다.
</details>

따라서 정확하게 표현하면,

> **Redis는 RDB처럼 Secondary Index를 만들어 조회하는 것이 기본 모델은 아니지만, 자료구조를 활용하거나 Redis Query Engine을 통해 인덱싱 기능을 사용할 수 있다.**

## 여기서 MongoDB와 비교하면

```plain text
RDB
Column
  ↓
Index
  ↓
Row 검색


MongoDB
Document Field
  ↓
Index
  ↓
Document 검색


Redis
Key
  ↓
Hash Table
  ↓
Value 직접 접근
```

즉,

**RDB / MongoDB**

```plain text
"어떤 값의 데이터를 찾아줘"
          ↓
       Index 검색
          ↓
       데이터 접근
```

**Redis의 기본 방식**

```plain text
"이 Key의 데이터를 줘"
          ↓
      Key 직접 조회
          ↓
        Value
```

이 차이가 핵심입니다.

### 그래서 왜 Redis는 이런 방식일까?

Redis는 캐시나 세션처럼 **Key를 미리 알고 조회하는 상황**에서 많이 사용됩니다.

예를 들어 로그인한 사용자의 세션을 조회한다면,

```plain text
session:ABC123
```

이라는 Key를 알고 있으므로,

```plain text
session:ABC123 → 세션 데이터
```

바로 조회하면 됩니다.

따라서 Redis에서는 **"어떤 Key로 저장하고 조회할 것인가"라는 Key 설계 자체가 중요**합니다.

---

### 한 줄 핵심

**RDB:** `Column을 빠르게 찾기 위한 별도의 인덱스`

**MongoDB:** `Document의 Field를 빠르게 찾기 위한 인덱스`

**Redis:** `Key 직접 조회가 기본이며, 필요에 따라 자료구조·검색 기능을 활용`
