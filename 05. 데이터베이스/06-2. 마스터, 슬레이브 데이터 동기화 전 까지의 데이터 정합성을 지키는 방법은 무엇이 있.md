# 6-2. 마스터, 슬레이브 데이터 동기화 전 까지의 데이터 정합성을 지키는 방법은 무엇이 있을까요?

### 일단 결론

> **Master-Slave 비동기 복제에서는 복제 지연(Replication Lag)이 발생할 수 있기 때문에, 동기화 전까지 Master와 Slave의 데이터가 일시적으로 다를 수 있습니다.**

따라서 정합성이 중요한 요청은 **Master에서 읽거나**, 복제가 완료될 때까지 **읽기를 제어하는 방식**을 사용합니다.

---

### Master-Slave란?

> 하나의 데이터베이스를 **Master(주 DB)**와 **Slave(복제 DB)**로 나누고, Master의 데이터를 Slave에 복제하여 사용하는 구조입니다.

보통 역할은 이렇게 나눕니다.

```plain text
              Application
             /           \
        데이터 변경      데이터 조회
       INSERT/UPDATE       SELECT
            ↓                ↓
        Master DB  ─────→  Slave DB
                    복제
```

### Master

**원본 데이터를 관리하는 DB**입니다.

주로 데이터 변경을 담당합니다.

  - `INSERT`

  - `UPDATE`

  - `DELETE`

예를 들어 회원이 닉네임을 변경하면:

```plain text
닉네임 변경
    ↓
Master DB
Kim → Lee
```

### Slave

Master의 데이터를 **복제해서 가지고 있는 DB**입니다.

주로 조회를 담당합니다.

  - `SELECT`

Master에서 변경된 데이터가 Slave로 전달됩니다.

```plain text
Master
name = "Lee"
    ↓ 복제
Slave
name = "Lee"
```

# 1. 왜 데이터 정합성 문제가 발생할까?

일반적인 Master-Slave 구조에서는 다음과 같이 역할을 나눕니다.

```plain text
        Application
          ↓     ↓
       Write   Read
          ↓     ↓
       Master → Slave
              복제
```

- **Master**: INSERT, UPDATE, DELETE

- **Slave**: 주로 SELECT

- Master의 변경 사항을 Slave로 복제

문제는 이 복제가 **비동기(Asynchronous)** 방식일 경우입니다.

예를 들어 사용자가 닉네임을 변경했다고 해보겠습니다.

```plain text
1. 사용자: 닉네임 "Kim" → "Lee" 변경

2. Master
   name = "Lee"

3. Slave
   name = "Kim"   ← 아직 복제되지 않음

4. 사용자가 바로 조회

5. Slave에서 조회
   → "Kim" 반환
```

사용자는 분명 닉네임을 `"Lee"`로 변경했는데 바로 조회하면 이전 값인 `"Kim"`이 보일 수 있습니다.

이처럼 복제가 완료되기까지 걸리는 시간을 **Replication Lag(복제 지연)**이라고 합니다.

---

# 2. 방법 ① 정합성이 중요한 Read는 Master에서 조회

가장 이해하기 쉬운 방법입니다.

```plain text
Write
 ↓
Master

Read
 ↓
Master
```

특히 **데이터를 변경한 직후의 조회**를 Master로 보내면 됩니다.

```plain text
UPDATE User
    ↓
  Master

사용자가 바로 조회
    ↓
  Master
    ↓
최신 데이터 반환
```

Master에는 이미 변경 사항이 반영되어 있기 때문에 Slave의 복제 완료 여부를 기다릴 필요가 없습니다.

이를 이용해 **Read-after-Write Consistency**를 제공할 수 있습니다.

### Read-after-Write Consistency

> 사용자가 자신이 방금 변경한 데이터를 다시 조회했을 때 최신 변경 결과를 볼 수 있도록 보장하는 것

예:

```plain text
프로필 수정
    ↓
Master에 Write
    ↓
바로 프로필 조회
    ↓
Master에서 Read
```

다만 모든 조회를 Master로 보내면 **Read Replica를 사용하는 의미가 줄어들고 Master 부하가 증가**합니다.

따라서 보통 정합성이 중요한 조회에 선택적으로 적용합니다.

---

# 3. 방법 ② 일정 시간 Master에서 읽기

Write 이후 일정 시간 동안 해당 사용자의 Read를 Master로 보내는 방법도 있습니다.

```plain text
Write 발생
   ↓
Master 저장
   ↓
일정 시간 동안
Read → Master
   ↓
시간 경과
   ↓
Read → Slave
```

예를 들어:

```plain text
게시글 작성

0초      Master Write
 ↓
0~3초    Master에서 Read
 ↓
3초 이후 Slave에서 Read
```

복제가 충분히 완료되었을 것이라고 예상되는 시점부터 다시 Slave를 사용합니다.

구현은 비교적 간단하지만 **“3초면 반드시 복제가 끝난다”는 보장은 없다는 단점**이 있습니다.

---

# 4. 방법 ③ 복제 완료 여부를 확인한 뒤 Slave에서 읽기

시간을 임의로 정하는 것보다 강하게 보장하려면 **해당 Write가 Slave까지 반영되었는지 확인한 후 조회**할 수 있습니다.

개념적으로는 다음과 같습니다.

```plain text
Master Write
     ↓
복제 위치 기록
     ↓
Slave가 해당 위치까지
복제했는지 확인
     ↓
   완료
     ↓
Slave Read
```

즉,

> "몇 초 기다려 보자"

가 아니라

> "내가 방금 쓴 데이터가 Replica까지 실제로 도착했는지 확인하고 읽자"

라는 접근입니다.

DBMS에 따라 **LSN****, ****WAL**** 위치, ****GTID**** 등의 복제 위치 정보**를 활용할 수 있습니다.

정합성은 더 강하게 보장할 수 있지만 대기 시간이 생기고 구현 및 운영이 복잡해질 수 있습니다.

---

# 5. 방법 ④ 동기식 / 반동기식 복제 사용

애초에 Master가 Write 성공을 반환하는 시점을 늦추는 방법도 있습니다.

### 비동기 복제

```plain text
Client
  ↓ Write
Master
  ↓
Client에게 성공 응답
  ↓
Slave 복제
```

Master는 Slave의 복제를 기다리지 않기 때문에 빠르지만 복제 지연이 발생할 수 있습니다.

### 동기식 복제

```plain text
Client
  ↓
Master
  ↓
Replica 반영/확인
  ↓
성공 응답
```

Replica 측의 처리를 확인한 후 성공을 반환하도록 하면 정합성을 더 강하게 가져갈 수 있습니다.

대신 **쓰기 지연시간 증가, Replica 장애가 Write에 영향을 줄 가능성** 등의 비용이 발생합니다.

여기서 중요한 점은 DBMS마다 **“동기식” 또는 “반동기식”이 정확히 무엇까지 보장하는지가 다르다**는 것입니다. 단순히 Slave가 데이터를 받았다는 것과 실제 조회 가능한 상태까지 반영했다는 것은 구분해야 합니다.

---

# 그렇다면 실무에서는?

정합성과 성능의 **Trade-off**를 고려해 데이터 특성에 따라 다르게 처리합니다.

| 데이터 | 읽기 전략 |
| --- | --- |
| 결제 직후 결과 | Master |
| 계좌 잔액 | Master 또는 강한 정합성 보장 |
| 프로필 수정 직후 | Master |
| 일반 게시글 목록 | Slave |
| 상품 목록 | Slave |
| 통계/조회 데이터 | Slave |

즉, 모든 데이터를 무조건 강한 정합성으로 처리하는 것이 아니라,

```plain text
정합성 중요
   ↓
Master Read / 복제 완료 확인

정합성보다 조회 성능 중요
   ↓
Slave Read
```

처럼 구분합니다.
