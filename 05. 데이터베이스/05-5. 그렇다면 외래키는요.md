# 5-5. 그렇다면 외래키는요?

외래키(FK)도 기본키와 마찬가지로 **인덱스와는 목적 자체가 다릅니다.** 다만 PK와 달리, **외래키를 설정한다고 항상 인덱스가 자동 생성되는 것은 DBMS마다 다릅니다.**

### 5-5. 그렇다면 외래키는 인덱스일까요?

**외래키(Foreign Key)는 인덱스가 아닙니다.**

외래키는 다른 테이블의 PK나 UNIQUE KEY 등을 참조해서 **테이블 간의 참조 무결성을 보장하기 위한 제약조건**입니다.

예를 들어,

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

여기서

```plain text
users
id(PK)
 1  김철수
 2  이영희
     ↑
     │ 참조
     │
orders
id   user_id(FK)
101     1
102     1
103     2
```

`orders.user_id`의 역할은 **"이 주문의 사용자가 실제 users 테이블에 존재하는가?"**를 보장하는 것입니다.

따라서 다음과 같이 존재하지 않는 사용자를 참조하려고 하면 FK 제약조건에 의해 거부됩니다.

```sql
INSERT INTO orders(id, user_id)
VALUES (104, 999);
```

`users.id = 999`가 없다면 삽입할 수 없습니다.

### PK와 FK의 가장 큰 차이

| 구분 | 기본키(PK) | 외래키(FK) |
| --- | --- | --- |
| 목적 | 자신의 행을 유일하게 식별 | 다른 테이블과의 관계 및 참조 무결성 보장 |
| 중복 | 불가능 | 가능 |
| NULL | 불가능 | 설정에 따라 가능 |
| 참조 | 기준이 되는 키 | 다른 테이블의 키를 참조 |
| 인덱스 | 일반적으로 자동 생성 | **DBMS마다 다름** |

예를 들어 한 사용자가 주문을 여러 개 할 수 있으므로 FK에는 중복값이 자연스럽게 존재할 수 있습니다.

```plain text
order_id    user_id(FK)
101         1
102         1
103         1
```

### 그러면 FK에 인덱스는 왜 걸까요?

실무에서는 FK 컬럼으로 JOIN하거나 조회하는 경우가 많습니다.

```sql
SELECT *
FROM orders
WHERE user_id = 1;
```

또는

```sql
SELECT *
FROM users u
JOIN orders o
    ON u.id = o.user_id
WHERE u.id = 1;
```

`orders.user_id`에 인덱스가 있다면 특정 사용자의 주문을 빠르게 찾을 수 있습니다.

또 하나 중요한 이유는 **부모 데이터의 DELETE/UPDATE 처리**입니다.

```sql
DELETE FROM users
WHERE id = 1;
```

DB는 `orders`에 `user_id = 1`인 데이터가 존재하는지 확인해야 합니다. FK 컬럼에 적절한 인덱스가 없다면 자식 테이블을 많이 탐색해야 할 수 있어 성능 문제가 발생할 수 있습니다.

단, **MySQL InnoDB처럼 FK 제약조건에 필요한 인덱스를 요구하고, 없으면 자동 생성하는 DBMS도 있습니다.** 따라서 "`FK를 만들면 인덱스가 자동 생성된다/안 된다`"라고 DBMS 구분 없이 단정하면 안 됩니다.

### 한 줄 정리

> **외래키는 다른 테이블을 참조하여 참조 무결성을 보장하는 제약조건이며 인덱스 자체는 아니다. 다만 JOIN, 조회 및 부모 행 DELETE/UPDATE 시 참조 확인 성능을 위해 FK 컬럼에 인덱스를 사용하는 경우가 많으며, 자동 생성 여부는 DBMS에 따라 다르다.**

### 추가 질문 + 답변

**Q1. 외래키에는 중복값이 들어갈 수 있나요?**

네. 가능합니다. 예를 들어 한 명의 사용자가 여러 주문을 할 수 있으므로 여러 `orders`가 동일한 `user_id`를 가질 수 있습니다.

**Q2. 외래키에는 NULL이 들어갈 수 있나요?**

네. 해당 FK 컬럼에 `NOT NULL` 제약조건을 설정하지 않았다면 일반적으로 가능합니다. `NULL`은 특정 부모 행을 참조하지 않는다는 의미로 볼 수 있습니다.

**Q3. 외래키를 사용하면 어떤 장점이 있나요?**

DB 차원에서 **참조 무결성**을 보장할 수 있습니다. 존재하지 않는 회원의 주문처럼 잘못된 관계가 저장되는 것을 방지할 수 있습니다.

**Q4. 외래키에 인덱스를 거는 이유는 무엇인가요?** ⭐

FK 컬럼은 JOIN이나 조건 검색에 자주 사용되고, 부모 데이터의 DELETE/UPDATE 시 자식 데이터 존재 여부도 확인해야 합니다. 따라서 인덱스를 사용하면 이러한 탐색을 빠르게 할 수 있습니다.

**Q5. 부모 데이터를 삭제하면 자식 데이터는 어떻게 되나요?** ⭐

FK 설정에 따라 달라집니다. `RESTRICT/NO ACTION`은 자식이 존재하면 삭제를 막고, `CASCADE`는 자식도 함께 삭제하며, `SET NULL`은 자식의 FK 값을 `NULL`로 변경합니다.

```plain text
FOREIGNKEY (user_id)REFERENCES users(id)ONDELETECASCADE;
```

**Q6. 외래키를 사용하면 성능이 떨어질 수도 있나요?**

네. `INSERT`, `UPDATE`, `DELETE` 시 DB가 참조 무결성을 확인해야 하므로 추가 비용이 발생합니다. 대신 데이터 정합성을 DB 수준에서 보장할 수 있다는 장점이 있습니다.

**Q7. 외래키 없이 애플리케이션에서만 관계를 관리하면 안 되나요?** ⭐

가능하지만 DB 자체에서는 잘못된 참조를 막을 수 없습니다. 애플리케이션 버그나 직접 SQL 실행 등으로 무결성이 깨질 가능성이 있기 때문에 **정합성과 성능, 운영 환경 등을 고려해서 결정**해야 합니다.

**Q8. FK는 반드시 다른 테이블의 PK만 참조할 수 있나요?**

아닙니다. DBMS의 규칙을 만족하는 **UNIQUE한 후보키**를 참조할 수도 있습니다. 핵심은 참조 대상 행을 유일하게 식별할 수 있어야 한다는 것입니다.
