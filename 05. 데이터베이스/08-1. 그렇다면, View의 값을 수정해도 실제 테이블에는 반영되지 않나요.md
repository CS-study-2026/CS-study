# 8-1. 그렇다면, View의 값을 수정해도 실제 테이블에는 반영되지 않나요?

> **수정 가능한 View라면 View를 ****`INSERT`****, ****`UPDATE`****, ****`DELETE`****했을 때 실제 원본 테이블에도 반영됩니다.**

하지만 **모든 View가 수정 가능한 것은 아닙니다.**

---

## 1. View는 데이터를 따로 가지고 있지 않다

일반 View는 실제 데이터를 별도로 저장하지 않고, **원본 테이블을 조회하는 SELECT 쿼리**를 가지고 있습니다.

예를 들어 다음과 같은 테이블이 있다고 해봅시다.

```plain text
EMPLOYEE
┌────┬─────────┬─────────┐
│ ID │ NAME    │ DEPT_ID │
├────┼─────────┼─────────┤
│ 1  │ 김철수   │ 10      │
│ 2  │ 이영희   │ 20      │
└────┴─────────┴─────────┘
```

다음 View를 생성합니다.

```sql
CREATE VIEW EMPLOYEE_VIEW AS
	SELECT ID, NAME, DEPT_ID
	FROM EMPLOYEE;
```

이 View에서 다음과 같이 수정한다면,

```sql
UPDATE EMPLOYEE_VIEW
	SET NAME = '김민수'
	WHERE ID = 1;
```

DBMS가 이 View의 행을 원본 테이블의 행과 명확하게 연결할 수 있기 때문에 실제로는 다음과 같이 원본 `EMPLOYEE`가 변경됩니다.

```plain text
UPDATE EMPLOYEE_VIEW
        │
        ▼
   EMPLOYEE_VIEW
        │
        │ 원본 행을 찾을 수 있음
        ▼
   EMPLOYEE 테이블
        │
        ▼
김철수 → 김민수
```

즉,

```plain text
SELECT * FROM EMPLOYEE;
```

를 실행해도 `김민수`로 변경되어 있습니다.

**View에 별도의 복사본이 있어서 그것만 수정되는 것이 아닙니다.**

---

# 2. 그런데 모든 View를 수정할 수 있는 것은 아니다

핵심은 DBMS가

> **"View의 이 행을 수정한다는 것이 원본 테이블의 어떤 행을 수정한다는 것인지 명확하게 판단할 수 있는가?"**

입니다.

단순한 View는 비교적 명확합니다.

```sql
CREATE VIEW EMPLOYEE_VIEW AS
	SELECT ID, NAME
	FROM EMPLOYEE;
```

```plain text
View의 ID=1
    ↓
EMPLOYEE의 ID=1
```

따라서 수정하기 쉽습니다.

반면 다음과 같이 집계한 View를 생각해봅시다.

```sql
CREATE VIEW DEPT_SALARY_VIEW AS
	SELECT DEPT_ID, AVG(SALARY) AS AVG_SALARY
	FROM EMPLOYEE
	GROUP BY DEPT_ID;
```

결과가 다음과 같다고 합시다.

```plain text
DEPT_ID | AVG_SALARY
--------|-----------
10      | 4,000,000
20      | 5,000,000
```

여기서

```sql
UPDATE DEPT_SALARY_VIEW
	SET AVG_SALARY = 4500000
	WHERE DEPT_ID = 10;
```

이라고 하면 문제가 생깁니다.

부서 10의 평균 급여를 450만 원으로 만들기 위해 **원본 직원들의 급여를 어떻게 수정해야 하는지 알 수 없기 때문입니다.**

```plain text
View
부서 10 평균급여 = 400만원

        UPDATE 450만원?
              ↓

원본 EMPLOYEE

A → 300만원
B → 400만원
C → 500만원

누구의 급여를 얼마로 변경해야 하지?
              ↓
          알 수 없음
```

이런 View는 일반적으로 직접 수정할 수 없습니다.

---

# 3. 수정 가능한 View와 수정하기 어려운 View

세부 규칙은 **Oracle, MySQL, PostgreSQL 등 DBMS마다 차이가 있습니다.** 다만 일반적으로 다음과 같이 이해하면 됩니다.

| View 형태 | 수정 가능성 |
| --- | --- |
| 하나의 테이블을 단순 조회 | ⭕ 가능 |
| 일부 컬럼만 조회 | ⭕ 가능한 경우가 많음 |
| `WHERE` 조건 사용 | ⭕ 가능한 경우가 많음 |
| `GROUP BY` | ❌ 일반적으로 불가능 |
| `SUM`, `AVG`, `COUNT` 등 집계 | ❌ 일반적으로 불가능 |
| `DISTINCT` | ❌ 일반적으로 불가능 |
| 여러 테이블 `JOIN` | ⚠️ DBMS와 View 구조에 따라 제한 |
| 계산된 컬럼 | ⚠️ 해당 계산 컬럼은 일반적으로 직접 수정 불가 |

따라서 "JOIN이 있으면 무조건 수정 불가능"처럼 외우는 것은 정확하지 않습니다.

---

# 4. WHERE 조건이 있는 View를 수정하면?

예를 들어 개발팀 직원만 보여주는 View가 있다고 해봅시다.

```sql
CREATE VIEW DEV_EMPLOYEE AS
	SELECT ID, NAME, DEPT_ID
	FROM EMPLOYEE
	WHERE DEPT_ID = 10;
```

다음 수정은 자연스럽습니다.

```sql
UPDATE DEV_EMPLOYEE
	SET NAME = '홍길동'
	WHERE ID = 1;
```

원본 `EMPLOYEE` 테이블의 데이터가 수정됩니다.

그런데 다음과 같이 수정한다면 어떨까요?

```sql
UPDATE DEV_EMPLOYEE
	SET DEPT_ID = 20
	WHERE ID = 1;
```

원본 데이터의 `DEPT_ID`가 20으로 변경되면서 해당 직원은 더 이상

```sql
WHERE DEPT_ID = 10
```

조건을 만족하지 않습니다.

따라서 **수정에는 성공했지만 수정 직후 View에서는 해당 행이 사라질 수 있습니다.**

이러한 상황을 막고 싶다면 DBMS가 지원하는 경우 `WITH CHECK OPTION`을 사용할 수 있습니다.

```sql
CREATE VIEW DEV_EMPLOYEE AS
	SELECT ID, NAME, DEPT_ID
	FROM EMPLOYEE
	WHERE DEPT_ID = 10
WITH CHECK OPTION;
```

그러면 View의 조건을 벗어나게 만드는 변경을 **제한**할 수 있습니다.

---

# 5. 핵심 정리

> **View를 수정하면 원본 테이블도 수정될 수 있습니다.**

일반 View는 별도의 데이터를 가지고 있는 것이 아니므로, **수정 가능한 View에 대한 ****`INSERT`****, ****`UPDATE`****, ****`DELETE`****는 결국 원본 테이블에 대한 변경으로 이어집니다.**

다만 View가 복잡해져서 **View의 데이터와 원본 테이블의 데이터를 명확하게 대응시키기 어려운 경우에는 수정이 제한됩니다.**

```plain text
단순 View
View의 행 ───────→ 원본 행
          명확함
             ↓
          수정 가능 ⭕


복잡한 View
View의 행 ──?──→ 어떤 원본 행?
          불명확
             ↓
          수정 제한 ❌
```

### 한 문장으로 정리

**View는 단순한 읽기 전용 객체가 아니며, 수정 가능한 View를 변경하면 실제 원본 테이블의 데이터가 변경된다. 단, 집계·중복 제거·복잡한 JOIN 등으로 원본 행과의 대응 관계가 불명확한 View는 수정이 제한될 수 있다.**
