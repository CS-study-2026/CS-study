# 15-1. 가끔은 인덱스를 타는 쿼리임에도 Table Full Scan 방식으로 동작하는 경우가 있습니다. 왜 그럴까요?

# 1. 인덱스가 있는데도 Table Full Scan이 발생하는 이유?

1. 쿼리 최적화기(Optimizer)의 선택

> Note 

  - 쿼리 최적화기(Optimizer)는 처리 시간과 I/O 비용(Cost)을 종합적으로 계산하여 가장 효율적인 실행 계획을 선택합니다.

  - 인덱스가 생성되어 있더라도, 데이터베이스 옵티마이저가 전체 I/O 비용 측면에서 테이블 풀 스캔이 더 빠르다고 판단하거나 구조적인 이유로 인덱스를 사용할 수 없을 때 풀 스캔 방식으로 동작하게 됩니다.

---

# 2. 손익분기점 (Break-Even Point) 초과

> Note 조회하려는 데이터의 양이 테이블 전체 데이터의 상당 부분(통상 10~15% 이상)을 차지할 때 발생합니다.

1. 작동 원리

> Note 

  - 인덱스를 통해 데이터를 찾으면 한 번에 하나의 블록만 읽어오는 Single Block I/O가 발생합니다(테이블 랜덤 액세스).

  - 읽어야 할 데이터가 많아지면 디스크를 무작위로 찌르는 비용이 기하급수적으로 늘어납니다.

1. 결과

> Note 옵티마이저는 차라리 디스크에서 한 번에 여러 블록을 퍼 올리는 Multiblock I/O 방식(풀 스캔)이 더 빠르다고 판단합니다.

---

# 3. 인덱스 컬럼의 가공 (함수 및 연산 적용)

> Note 쿼리의 WHERE 절에서 인덱스가 걸려 있는 컬럼 자체를 가공하여 조건 검색을 하는 경우입니다.

1. 작동 원리

> Note 

  - 인덱스는 컬럼의 원본 값을 기준으로 B+ Tree 구조에 정렬되어 있습니다.

  - 이때, 컬럼 값에 함수를 씌우거나 연산을 수행하면, 데이터베이스는 정렬된 인덱스를 참조할 수 없게 됩니다.

  - 코드 예시

```javascript
-- 컬럼 가공으로 인해 인덱스 사용 불가
SELECT * FROM employees WHERE SUBSTRING(emp_name, 1, 3) = 'kim';
SELECT * FROM employees WHERE salary * 2 > 10000;
```

1. 해결책

> Note 인덱스 컬럼은 그대로 두고, 비교하는 대상 값을 가공하는 형태로 쿼리를 수정해야 합니다.

---

# 4. 암시적 형변환 (Implicit Type Conversion)

> Note 인덱스 컬럼의 데이터 타입과 비교하려는 값의 데이터 타입이 다를 때 발생합니다.

1. 작동 원리

> Note 

  - 문자열 타입 컬럼에 숫자 값을 조건으로 주면, 데이터베이스 내부적으로 타입을 일치시키기 위해 컬럼 값에 형변환 함수를 암시적으로 적용합니다.

  - 코드 예시 (dept_id가 VARCHAR 타입인 경우):

```plain text
-- 데이터 타입 불일치로 인덱스 사용 불가
SELECT * FROM departments WHERE dept_id = 10;
```

1. 결과

> Note 컬럼이 가공된 것과 동일한 효과를 내어 인덱스를 사용할 수 없게 됩니다.

---

# 5. 부정형 조건 및 NULL 비교 사용

> Note `!=`, `<>`, `NOT IN` 등의 부정형 연산자나, 일부 환경에서 `IS NULL`, `IS NOT NULL`을 사용할 때 발생합니다.

1. 작동 원리

> Note 

  - 인덱스는 값을 순서대로 정렬해 두고 특정 '범위'를 빠르게 찾도록 설계되었습니다.

  - '~가 아닌 것'을 찾으려면 인덱스의 정렬된 순서를 활용하기 어려워 결국 전체를 뒤져야 합니다.

1. 주의점

> Note 데이터베이스 엔진(Oracle, MySQL 등)에 따라 NULL 값을 인덱스에 포함하는지 여부가 다르므로, NULL 검색 시 인덱스 작동 방식도 달라집니다.

---

# 6. 부정확한 테이블 통계 정보

> Note 데이터베이스 옵티마이저가 가지고 있는 테이블의 데이터 분포도(통계 정보)가 과거의 상태에 머물러 있을 때 발생합니다.

1. 작동 원리

> Note 

  - 옵티마이저는 해당 통계 정보를 바탕으로 쿼리 실행 비용을 계산합니다.

  - 최근 대량의 데이터 삽입, 삭제가 있었는데 통계 정보가 갱신되지 않았다면 잘못된 실행 계획(오판)을 내릴 수 있습니다.

1. 해결책

> Note 주기적인 통계 정보 갱신(예: ANALYZE TABLE 명령어 실행)이 필요합니다.

---

# 7. 테이블 데이터가 극히 적은 경우

> Note 테이블의 전체 데이터가 단 몇 개의 블록에 모두 담길 정도로 아주 작은 테이블인 경우입니다.

1. 작동 원리

> Note 인덱스 트리의 루트 노드, 브랜치 노드, 리프 노드를 차례로 거쳐 테이블 블록을 다시 찾아가는 복잡한 과정보다, 처음부터 테이블 블록 몇 개를 한 번에 메모리로 올리는 것이 압도적으로 빠릅니다.

---

# 8. 요약 및 시사점

> Note 

  - 인덱스를 생성하는 것만으로는 쿼리 성능이 보장되지 않습니다.

  - 옵티마이저의 동작 원리를 이해하고, 암시적 형변환이나 컬럼 가공이 일어나지 않도록 쿼리를 작성하는 것이 중요합니다.

  - 또한, 주기적인 통계 정보 갱신을 통해 옵티마이저가 올바른 판단을 내릴 수 있는 환경을 제공하는 등 시스템 전반을 책임감 있게 유지 및 관리해야 합니다.
