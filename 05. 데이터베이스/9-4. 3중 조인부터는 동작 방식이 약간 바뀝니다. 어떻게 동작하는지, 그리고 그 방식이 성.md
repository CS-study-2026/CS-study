# **9-4. 3중 조인부터는 동작 방식이 약간 바뀝니다. 어떻게 동작하는지, 그리고 그 방식이 성능에 어떠한 영향을 주는지 설명해 주세요**

테이블이 2개인 JOIN은 비교적 단순하게 생각할 수 있습니다.

```plain text
SELECT *
FROM orders o
JOIN users u
  ON o.user_id = u.id;
```

이 경우 DBMS는 두 테이블을 어떤 방식으로 연결할지 결정합니다.

하지만 JOIN 대상이 3개 이상이 되면 문제가 더 복잡해집니다.

```plain text
SELECT *
FROM orders o
JOIN users u
  ON o.user_id = u.id
JOIN payments p
  ON o.id = p.order_id;
```

이때 DBMS가 세 테이블을 한 번에 동시에 합치는 것은 아닙니다.

일반적으로는 **JOIN 순서를 정하고, 두 테이블씩 단계적으로 JOIN**합니다.

---

## 1. 3중 JOIN은 두 개씩 나누어 처리된다

예를 들어 다음 세 테이블이 있다고 하겠습니다.

```plain text
users
orders
payments
```

SQL에는 다음 순서로 작성되어 있을 수 있습니다.

```plain text
FROM users u
JOIN orders o
  ON u.id = o.user_id
JOIN payments p
  ON o.id = p.order_id
```

하지만 DBMS가 반드시 작성된 순서대로 실행하는 것은 아닙니다.

가능한 실행 순서는 여러 가지입니다.

```plain text
1. users와 orders를 먼저 JOIN
   → 그 결과를 payments와 JOIN

2. orders와 payments를 먼저 JOIN
   → 그 결과를 users와 JOIN

3. users와 payments를 먼저 고려
   → 가능한 조건이 있다면 이후 orders와 JOIN
```

즉, 3중 JOIN부터는 **어떤 테이블을 먼저 JOIN할 것인가**가 중요한 문제가 됩니다.

---

## 2. 중간 결과가 성능에 큰 영향을 준다

다중 JOIN에서는 중간 결과의 크기가 성능에 큰 영향을 줍니다.

예를 들어 다음 두 실행 계획을 비교해 보겠습니다.

## 계획 A

```plain text
1. users와 orders를 먼저 JOIN
   → 중간 결과 1,000,000건 생성

2. 중간 결과와 payments를 JOIN
   → 최종 결과 10,000건
```

## 계획 B

```plain text
1. orders와 payments를 먼저 JOIN
   → 중간 결과 20,000건 생성

2. 중간 결과와 users를 JOIN
   → 최종 결과 10,000건
```

최종 결과가 같더라도 중간 결과 크기는 크게 다를 수 있습니다.

```plain text
계획 A 중간 결과: 1,000,000건
계획 B 중간 결과: 20,000건
```

이 경우 계획 B가 훨씬 효율적일 가능성이 높습니다.

따라서 3개 이상의 테이블을 JOIN할 때는 최종 결과뿐만 아니라, **중간 과정에서 얼마나 많은 데이터가 만들어지고 처리되는지**가 중요합니다.

---

## 3. 옵티마이저가 JOIN 순서를 바꿀 수 있다

SQL에 적은 순서와 실제 실행 순서는 다를 수 있습니다.

예를 들어 SQL은 다음처럼 작성되어 있어도:

```plain text
FROM users u
JOIN orders o
  ON u.id = o.user_id
JOIN payments p
  ON o.id = p.order_id
```

옵티마이저는 비용이 더 낮다고 판단하면 내부적으로 다음 순서로 실행할 수 있습니다.

```plain text
orders와 payments 먼저 JOIN
→ 그 결과를 users와 JOIN
```

옵티마이저가 이런 결정을 할 때 보는 정보는 다음과 같습니다.

```plain text
각 테이블의 row 수
조건절의 선택도
사용 가능한 인덱스
통계 정보
JOIN 조건
예상 중간 결과 크기
```

즉, 3중 JOIN부터는 단순히 JOIN 알고리즘 하나만 중요한 것이 아니라, **JOIN 순서 최적화**가 매우 중요해집니다.

---

## 4. JOIN 순서 후보가 급격히 늘어난다

테이블이 2개일 때는 선택지가 많지 않습니다.

```plain text
A JOIN B
B JOIN A
```

하지만 테이블이 3개가 되면 가능한 순서가 늘어납니다.

```plain text
(A JOIN B) JOIN C
(A JOIN C) JOIN B
(B JOIN C) JOIN A
...
```

테이블이 더 많아질수록 가능한 JOIN 순서가 급격히 증가합니다.

```plain text
테이블 3개
→ 선택할 수 있는 순서가 여러 개

테이블 5개
→ 훨씬 많은 조합

테이블 10개
→ 모든 경우를 완전 탐색하기 어려움
```

따라서 DBMS 옵티마이저는 통계 정보와 비용 모델을 바탕으로 현실적으로 좋은 실행 계획을 찾습니다.

이 과정에서 통계 정보가 부정확하면 좋지 않은 JOIN 순서가 선택될 수 있고, 성능이 크게 떨어질 수 있습니다.

---

## 5. 인덱스의 영향이 더 커진다

3개 이상의 테이블을 JOIN할 때는 인덱스의 영향도 더 커집니다.

각 JOIN 단계마다 조건에 맞는 행을 찾아야 하기 때문입니다.

```plain text
1단계 JOIN
→ users.id = orders.user_id

2단계 JOIN
→ orders.id = payments.order_id
```

이때 JOIN 컬럼에 인덱스가 없다면 각 단계에서 많은 데이터를 읽어야 할 수 있습니다.

반대로 적절한 인덱스가 있으면 중간 결과를 줄이고 다음 JOIN 단계의 비용도 낮출 수 있습니다.

```plain text
적절한 인덱스 있음
→ 각 단계에서 필요한 row를 빠르게 찾음
→ 중간 결과 감소
→ 다음 JOIN 비용 감소
```

즉, 다중 JOIN에서는 한 단계의 비효율이 다음 단계로 계속 전파될 수 있습니다.

---

## 6. 3중 JOIN이 성능에 주는 영향

3개 이상의 테이블을 JOIN하면 다음 이유로 성능 비용이 커질 수 있습니다.

```plain text
1. 읽어야 하는 테이블 수가 늘어난다.
2. JOIN 순서 후보가 많아진다.
3. 중간 결과가 커질 수 있다.
4. 각 JOIN 조건에 맞는 인덱스가 필요해진다.
5. 통계 정보가 부정확하면 잘못된 실행 계획이 선택될 수 있다.
6. 정렬, 임시 테이블, 해시 테이블 같은 추가 작업이 생길 수 있다.
```

특히 중간 결과가 커지면 메모리 사용량과 디스크 I/O가 증가할 수 있습니다.

```plain text
중간 결과 증가
→ 메모리 사용량 증가
→ 정렬/임시 테이블 증가
→ 디스크 I/O 증가
→ 응답 시간 증가
```

---

## 7. 성능을 개선하려면 무엇을 봐야 하나?

3중 JOIN 이상의 성능을 볼 때는 다음을 확인해야 합니다.

```plain text
1. 실행 계획에서 JOIN 순서 확인
2. 각 단계의 예상 row 수 확인
3. 실제 처리 row 수 확인
4. JOIN 조건 컬럼의 인덱스 확인
5. 불필요하게 큰 중간 결과가 생기는지 확인
6. WHERE 조건으로 먼저 줄일 수 있는 데이터가 있는지 확인
7. 통계 정보가 최신인지 확인
```

특히 `EXPLAIN`이나 `EXPLAIN ANALYZE`를 통해 실제로 어떤 순서로 JOIN되는지 확인하는 것이 중요합니다.

---

## 8. 질문에 대한 최종 답변

> 3개 이상의 테이블을 JOIN할 때는 DBMS가 모든 테이블을 한 번에 합치는 것이 아니라, JOIN 순서를 정한 뒤 두 테이블씩 단계적으로 JOIN합니다. 이때 SQL에 작성된 순서대로 실행되는 것이 아니라, 옵티마이저가 테이블 크기, 조건의 선택도, 인덱스, 통계 정보 등을 바탕으로 비용이 낮은 JOIN 순서를 선택할 수 있습니다.

다중 JOIN에서 중요한 것은 중간 결과의 크기입니다. 최종 결과가 같더라도 어떤 테이블을 먼저 JOIN하느냐에 따라 중간 결과가 수만 건이 될 수도 있고 수백만 건이 될 수도 있습니다. 중간 결과가 커지면 다음 JOIN 단계의 비용도 증가하고, 메모리 사용량이나 임시 테이블, 디스크 I/O가 늘어 성능이 크게 떨어질 수 있습니다.

따라서 3중 JOIN 이상에서는 JOIN 알고리즘뿐 아니라 JOIN 순서, 인덱스 유무, 통계 정보, 중간 결과 크기가 성능에 큰 영향을 줍니다. 성능을 확인할 때는 실행 계획을 통해 실제 JOIN 순서와 각 단계의 예상 row 수, 사용 인덱스를 확인해야 합니다.

