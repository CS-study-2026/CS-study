# 5-1. 일반적으로 인덱스는 수정이 잦은 테이블에선 사용하지 않기를 권합니다. 왜 그럴까요?

# 0. 결론

인덱스가 존재하면 **테이블의 데이터를 변경할 때 인덱스도 함께 유지해야 하기 때문**입니다.

인덱스는 조회 성능을 향상시키지만 `INSERT`, `UPDATE`, `DELETE`가 발생하면 관련 인덱스도 함께 변경해야 합니다.

특히 일반적인 DB 인덱스에서 사용하는 B+Tree는 Key가 정렬된 상태를 유지해야 하므로 데이터 변경 과정에서 추가적인 비용이 발생합니다.

따라서 수정이 잦은 테이블에서 인덱스를 **무조건 사용하지 않는 것이 아니라**, **조회 성능과 쓰기 성능의 트레이드오프를 고려하여 필요한 인덱스만 생성**하는 것이 좋습니다.

---

# 1. INSERT

B+Tree의 실제 인덱스 엔트리 삽입은 **Leaf Node에서 발생**

### (1) Leaf Node에 공간이 충분한 경우

정렬된 위치를 찾아 새로운 Key를 삽입

```plain text
[10, 20, 40]

[10, 20, 30, 40]
```

테이블에 데이터를 추가하는 것뿐만 아니라 인덱스에도 새로운 Key를 추가해야 하므로 추가적인 쓰기 비용 발생

### (2) Leaf Node가 가득 찬 경우

새로운 Key를 저장할 공간이 부족하면 **노드 분할(Split)** 발생

```plain text
[10 20 30 40]

[10 20 25 30 40]
        ↓
      Split
====================
[10 20] → [25 30 40]
```

분할된 노드를 탐색할 수 있도록 부모 노드의 Key와 Pointer 역시 조정해야

경우에 따라 부모 노드까지 가득 차 있다면 상위 노드에서도 연쇄적으로 Split이 발생

---

# 2. UPDATE

UPDATE에서는 **변경하는 컬럼이 인덱스에 포함되어 있는지가 중요**

예를 들어 `age`에 인덱스가 있다고 가정하면,

```sql
UPDATE users
SET age = 30
WHERE id = 1;
```

기존 값이 20이었다면 단순히 테이블의 값을 20 → 30으로 바꾸는 것만으로 끝나지 않고, 인덱스 역시 정렬된 상태를 유지해야 하므로 개념적으로 아래와 같은 인덱스 유지 작업이 필요

```plain text
기존 20에 해당하는 인덱스 엔트리 제거
              ↓
새로운 30에 해당하는 위치에 인덱스 엔트리 추가
```

반대로 변경하는 컬럼이 해당 인덱스에 포함되지 않았다면 그 인덱스의 Key를 변경할 필요는 X

따라서 **인덱스가 걸린 컬럼의 UPDATE가 빈번할수록 인덱스 유지 비용이 커질 수 O**

---

# 3. DELETE

테이블에서 데이터를 삭제하면 해당 Row를 가리키던 **인덱스 엔트리 역시 제거**해야

```plain text
[10, 20, 30, 40]

[10, 20, 40]
```

삭제한 Key가 부모 노드에서 탐색 기준으로 사용되고 있었다면 부모의 Key 역시 변경해야 할 수도

예를 들어

```plain text
부모
       [30]
      /    \
   [...]   [...]

Leaf
[10 20] → [30 40 50]
```

여기서 `30`이 삭제되고 오른쪽 Leaf의 최소값이 `40`이 되었다면 탐색을 위해 부모의 기준 Key 역시 변경될 수

또한 삭제가 반복되어 노드가 일정 기준 이하로 비게 되면 **재분배 또는 병합 **등의 추가 작업 발생

---

# 4. 인덱스의 Trade-off

인덱스는 **조회 성능**을 얻는 대신 **쓰기 성능**과 **저장 공간에 비용을 지불**하는 구조

```plain text
                인덱스 있음

SELECT      → 빨라질 수 있음

INSERT      → 인덱스 엔트리 추가
UPDATE      → 인덱스 Key 변경 가능
DELETE      → 인덱스 엔트리 제거

             ↓

추가적인 CPU / 메모리 / 디스크 I/O
+ B+Tree 구조 유지 비용
+ 추가 저장 공간
```

따라서 수정이 잦다는 이유만으로 인덱스를 사용하지 않는 것이 아니라,

**"이 인덱스로 얻는 조회 성능 향상이 데이터 변경 시 발생하는 유지 비용보다 가치가 있는가?"**

를 기준으로 판단해야 함

---

## 면접 답변

> 인덱스가 존재하면 테이블의 데이터가 변경될 때 관련 인덱스도 함께 유지해야 하기 때문입니다. 

예를 들어 INSERT 시에는 새로운 인덱스 엔트리를 추가해야 하고, UPDATE되면 기존 엔트리를 제거하고 새로운 위치에 반영해야 하며, DELETE 시에도 인덱스 엔트리를 제거해야 합니다. 

특히 B+Tree는 정렬된 트리 구조를 유지하기 위해 경우에 따라 노드 분할이나 병합 같은 추가 작업도 발생할 수 있습니다. 

따라서 수정이 잦은 테이블에서는 인덱스를 무조건 많이 생성하기보다는 조회 성능과 쓰기 성능의 트레이드오프를 고려하여 필요한 인덱스만 생성해야 합니다.
