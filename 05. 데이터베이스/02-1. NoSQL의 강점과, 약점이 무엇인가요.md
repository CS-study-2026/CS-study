# 2-1. NoSQL의 강점과, 약점이 무엇인가요?

## NoSQL의 강점

### 1. 데이터 구조를 유연하게 변경할 수 있다

RDB는 일반적으로 테이블의 열과 데이터형을 미리 정의

```plain text
회원 테이블
id | name | email
```

반면 문서형 NoSQL에서는 문서마다 일부 필드가 달라도 저장할 수 있다.

```plain text
{
  "id":1,
  "name":"은혜민",
  "email":"example@email.com"
}
```

```plain text
{
  "id":2,
  "name":"홍길동",
  "email":"example2@email.com",
  "interests": ["여행","개발"]
}
```

따라서 서비스 초기처럼 데이터 구조가 자주 바뀌거나, 사용자마다 서로 다른 속성을 저장해야 하는 경우 편리

---

### 2. 수평 확장이 비교적 쉽다

수평 확장은 서버 한 대의 성능을 높이는 것이 아니라, **서버의 개수를 늘려 데이터를 분산하는 방식**

```plain text
기존

데이터 → 서버 1대
```

```plain text
수평 확장

데이터 A → 서버 1
데이터 B → 서버 2
데이터 C → 서버 3
```

MongoDB는 샤딩을 통해 데이터와 읽기·쓰기 부하를 여러 서버에 분산하고,

새로운 샤드를 추가해 처리 용량을 확장할 수 있다.

대규모 사용자, 로그, 메시지, 센서 데이터처럼 데이터량과 요청량이 계속 증가하는 서비스에 유리

---

### 3. 특정 작업에서 높은 처리 성능을 낼 수 있다

NoSQL은 모든 형태의 질의를 지원하는 대신, 특정 데이터 접근 방식에 맞춰 구조를 설계하는 경우가 많다.

예를 들어 게시글을 조회할 때 작성자 정보를 매번 다른 테이블과 JOIN하지 않고 게시글 문서 안에 일부 정보를 함께 저장할 수 있다.

```plain text
{
  "postId":100,
  "title":"NoSQL 정리",
  "author": {
    "id":1,
    "name":"은혜민"
  }
}
```

한 번의 조회로 필요한 데이터를 가져올 수 있으므로, 잘 설계하면 빠르게 응답할 수 있다.

---

### 4. 분산 환경에서 높은 가용성을 구성하기 좋다

일부 NoSQL은 데이터를 여러 노드나 데이터센터에 복제

```plain text
서버 1 장애
     ↓
서버 2 또는 서버 3에서 요청 처리
```

예를 들어 Cassandra는 데이터를 여러 노드에 복제하여 일부 노드나 데이터센터에 장애가 발생해도 서비스를 계속 제공할 수 있도록 설계

---

### 5. 데이터 특성에 적합한 저장 모델을 선택할 수 있다

NoSQL은 목적에 따라 서로 다른 모델을 사용할 수 있다.

| 데이터 특성 | 적합한 모델 | 예시 |
| --- | --- | --- |
| JSON 형태의 사용자·상품 정보 | 문서형 | MongoDB |
| 세션, 캐시, 임시 데이터 | Key-Value형 | Redis |
| 대규모 로그·시계열 데이터 | Wide-Column형 | Cassandra |
| 친구 관계·추천·경로 탐색 | 그래프형 | Neo4j |

그래프 데이터베이스는 관계 자체를 데이터로 저장하기 때문에, 복잡한 관계를 반복적으로 탐색하는 작업에 적합

---

## NoSQL의 약점

### 1. 복잡한 JOIN과 관계 표현이 불편할 수 있다

RDB에서는 여러 테이블을 JOIN하여 원하는 데이터를 자유롭게 조회할 수 있다.

```plain text
SELECT*FROM orders oJOIN users uON o.user_id= u.id;
```

하지만 DynamoDB와 같은 NoSQL은 테이블 JOIN을 지원하지 않는다.

필요한 데이터를 한 문서나 항목에 중복 저장하거나, 애플리케이션에서 여러 번 조회해야 할 수 있다.

다만 그래프형 NoSQL처럼 관계 탐색을 목적으로 만들어진 데이터베이스는 예외

---

### 2. 데이터 중복이 발생하기 쉽다

JOIN을 줄이고 빠르게 조회하기 위해 같은 정보를 여러 곳에 저장하는 비정규화 방식을 많이 사용

```plain text
게시글 1 → 작성자 이름: 은혜민
게시글 2 → 작성자 이름: 은혜민
게시글 3 → 작성자 이름: 은혜민
```

작성자 이름이 바뀌면 여러 게시글 데이터를 모두 수정해야 할 수 있다.

즉, 조회는 빨라질 수 있지만 다음 문제가 생긴다.

- 저장 공간 증가

- 수정할 위치 증가

- 일부 데이터만 수정될 경우 불일치 발생

- 동기화 로직 필요

---

### 3. 데이터 무결성을 애플리케이션이 관리해야 할 수 있다

RDB에서는 다음과 같은 제약조건을 데이터베이스가 검사

```plain text
PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
```

일부 NoSQL은 외래키나 참조 무결성을 제공하지 않는다.

예를 들어 Cassandra는 분산 JOIN, 외래키, 참조 무결성, 파티션을 넘는 일반 트랜잭션을 지원하지 않는다.

따라서 다음과 같은 검증을 애플리케이션 코드에서 처리해야 할 수 있다.

```plain text
if (!userExists(userId)) {thrownewIllegalArgumentException("존재하지 않는 사용자입니다.");
}
```

---

### 4. 데이터가 일시적으로 일치하지 않을 수 있다

분산 데이터베이스는 여러 서버에 데이터가 복제되기 때문에, 모든 복제본에 변경 내용이 전달되기까지 시간이 걸릴 수 있다.

```plain text
서버 A: 이름 = 김민수
서버 B: 이름 = 김민수
서버 C: 이름 = 김민수

서버 A에서 이름 변경

서버 A: 이름 = 이민수
서버 B: 이름 = 김민수
서버 C: 이름 = 김민수
```

일정 시간이 지나면 모두 `이민수`가 되지만, 그사이 서버 B나 C에서 이전 값을 읽을 가능성이 있습니다. 이것이 **최종적 일관성(Eventual Consistency)**

Cassandra는 가용성과 분산 처리를 높이기 위해 최종적 일관성을 사용하며, 연산별 일관성 수준을 조절할 수 있다.

다만 **모든 NoSQL이 최종적 일관성만 제공하는 것은 아닙니다.** 제품에 따라 강한 일관성이나 ACID 트랜잭션을 지원

---

### 5. 복잡한 트랜잭션에 불리할 수 있다

은행 이체처럼 여러 데이터가 반드시 동시에 성공하거나 실패해야 하는 경우가 있다.

```plain text
A 계좌에서 10만 원 차감
+
B 계좌에 10만 원 증가
```

둘 중 하나만 실행되면 안 되므로 강한 트랜잭션 보장이 필요

현대적인 NoSQL도 트랜잭션을 지원하는 경우가 많지만, 범위가 제한되거나 분산 트랜잭션의 비용이 클 수 있다.

---

### 6. 조회 요구사항이 바뀌면 구조를 다시 설계해야 할 수 있다

RDB에서는 정규화된 데이터를 저장해 놓고, 나중에 새로운 SQL과 JOIN을 작성해 다양한 분석을 할 수 있다.

반면 일부 NoSQL은 **어떤 방식으로 조회할 것인지 먼저 결정한 뒤** 그 조회 방식에 맞게 데이터를 설계

새로운 조회 요구사항이 생기면 다음 작업이 필요할 수 있다.

- 보조 인덱스 추가

- 데이터 중복 저장

- 컬렉션 또는 테이블 구조 변경

- 기존 데이터 재가공

---

### 7. 제품마다 사용법과 기능 차이가 크다

SQL은 제품별 차이가 있더라도 기본적인 문법과 관계형 모델이 비슷

하지만 NoSQL은 다음처럼 모델 자체가 다르다.

```plain text
MongoDB   → Document
Redis     → Key-Value
Cassandra → Wide-Column
Neo4j     → Graph
```

따라서 한 NoSQL의 설계 방식과 쿼리 경험이 다른 NoSQL에 그대로 적용되지 않을 수 있다.

특정 제품에 대한 기술 종속성이 커질 수 있다는 뜻

---

## 한눈에 정리

| 강점 | 약점 |
| --- | --- |
| 유연한 데이터 구조 | 데이터 구조가 무질서해질 수 있음 |
| 수평 확장에 유리 | 분산 시스템 운영이 복잡함 |
| 대량 데이터와 트래픽 처리 | JOIN과 복잡한 관계 조회가 제한될 수 있음 |
| 특정 조회 패턴에서 빠른 성능 | 조회 패턴 변경 시 재설계가 필요할 수 있음 |
| 높은 가용성 구성 가능 | 일시적인 데이터 불일치 가능 |
| 다양한 데이터 모델 제공 | 제품마다 사용법과 기능 차이가 큼 |
| 빠른 개발과 변경에 유리 | 무결성 검증을 코드에서 처리할 수 있음 |
