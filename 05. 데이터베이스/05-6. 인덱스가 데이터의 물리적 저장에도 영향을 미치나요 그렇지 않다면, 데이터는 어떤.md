# 5-6. 인덱스가 데이터의 물리적 저장에도 영향을 미치나요? 그렇지 않다면, 데이터는 어떤 순서로 물리적으로 저장되나요?

**인덱스의 종류와 DBMS에 따라 다르다.**

일반적인 **보조 인덱스(Secondary Index)**는 실제 테이블 데이터의 물리적 저장 순서를 바꾸지 않고, 별도의 자료구조를 만들어 데이터의 위치를 빠르게 찾도록 한다.

반면 **클러스터드 인덱스(Clustered Index)**는 데이터의 물리적 저장 구조와 직접적인 관련이 있습니다.

## **Clustered vs Non-Clustered Index**

| 구분 | Clustered Index | Non-Clustered Index |
| --- | --- | --- |
| 데이터와 관계 | 실제 데이터 저장 구조와 밀접 | 실제 데이터와 별도 인덱스 구조 |
| 리프 노드 | 실제 데이터(Row) | Row를 찾기 위한 정보 |
| 개수 | 일반적으로 테이블당 1개 | 여러 개 가능 |
| 대표 예시 | MySQL InnoDB의 PK | InnoDB의 Secondary Index |

Clustered Index

**인덱스의 리프 노드 자체에 실제 데이터가 저장되는 구조**라고 이해하면 됨.

MySQL InnoDB에서는 **PK가 Clustered Index**가 된다.

```plain text
        PK B+Tree
           20
         /    \
       10      30
       ↓       ↓
    실제 Row  실제 Row
```

그래서 PK가 단순히 실제 데이터의 주소를 가리키는 게 아니라, **PK B+Tree의 리프 페이지에 실제 Row가 존재**한다.

Non-Clustered / Secondary Index

실제 데이터와 **별도의 인덱스 구조**를 만든다.

MySQL InnoDB의 Secondary Index를 예로 들면:

```plain text
name 인덱스
────────────
김철수 → PK 30
박민수 → PK 20
이영희 → PK 10
          ↓
    Clustered Index
          ↓
       실제 Row
```

즉,

```plain text
Secondary Index 탐색
        ↓
      PK 획득
        ↓
Clustered Index 탐색
        ↓
     실제 Row
```

이런 식으로 실제 데이터를 찾을 수 있다.

예를 들어 데이터가 다음 순서로 삽입되었다고 해보겠습니다.

```plain text
삽입 순서
id = 30
id = 10
id = 20
```

일반 인덱스라면 개념적으로 데이터와 인덱스가 별도로 존재합니다.

```plain text
[테이블 데이터]

30  김철수
10  이영희
20  박민수

        ↑ 참조

[인덱스]

10 → 데이터 위치
20 → 데이터 위치
30 → 데이터 위치
```

즉, **인덱스가 정렬되어 있다고 해서 실제 데이터까지 그 순서대로 저장된다는 뜻은 아닙니다.**

### 그렇다면 실제 데이터는 어떤 순서로 저장되나요?

여기서 중요한 점은 **"테이블 데이터는 기본적으로 특정 논리적 순서를 보장하지 않는다"**는 것입니다.

```sql
SELECT *
FROM users;
```

이렇게 `ORDER BY` 없이 조회하면 DB가 어떤 순서로 결과를 반환할지 보장되지 않습니다.

따라서 다음과 같이 명시해야 합니다.

```sql
SELECT *
FROM users
ORDER BY id;
```

즉,

> **데이터베이스에서 행의 순서를 보장받으려면 반드시 ****`ORDER BY`****를 사용해야 합니다.**

---

### 그런데 MySQL InnoDB는 조금 다릅니다.

MySQL InnoDB에서는 **PK가 클러스터드 인덱스**가 됩니다.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50)
);
```

개념적으로는 다음과 같은 B+Tree 구조 안에 실제 행 데이터가 저장됩니다.

```plain text
                [20]
               /    \
           [10]      [30]
            ↓         ↓
        실제 Row    실제 Row
```

정확히는 **클러스터드 인덱스 B+Tree의 리프 페이지에 실제 행 데이터가 저장**됩니다.

따라서 InnoDB에서는

> `PK 인덱스 → 실제 데이터 위치를 가리킨다`

보다는

> **`PK 클러스터드 인덱스의 리프 노드 = 실제 행 데이터`**

라고 이해하는 게 더 정확합니다.

그리고 Secondary Index는 실제 Row를 직접 가지고 있는 것이 아니라 일반적으로 **PK 값을 가지고 있습니다.**

```plain text
name 인덱스

김철수 → PK 30
박민수 → PK 20
이영희 → PK 10
           ↓
      PK B+Tree 탐색
           ↓
       실제 데이터
```

그래서 InnoDB에서 Secondary Index로 조회하면 상황에 따라 **Secondary Index 탐색 → PK 획득 → Clustered Index 탐색** 과정이 발생할 수 있습니다.

### PostgreSQL은?

PostgreSQL은 InnoDB와 구조가 다릅니다.

일반적으로 테이블 데이터는 **Heap**에 저장되고, 인덱스는 별도의 구조로 존재하면서 해당 Row의 위치를 가리킵니다.

```plain text
[Index]
10 ───────┐
20 ────┐  │
30 ─┐  │  │
    ↓  ↓  ↓

[Heap Table]
Page 1 → Row...
Page 2 → Row...
Page 3 → Row...
```

따라서 **"PK를 만들었으니까 실제 데이터가 PK 순으로 저장된다"라고 모든 DBMS에 일반화하면 안 됩니다.**

### 정리

| 경우 | 실제 데이터 저장에 영향 |
| --- | --- |
| 일반/Secondary Index | ❌ 일반적으로 저장 순서를 변경하지 않음 |
| Clustered Index | ⭕ 실제 데이터 저장 구조와 밀접하게 관련 |
| MySQL InnoDB PK | ⭕ PK가 Clustered Index |
| PostgreSQL 일반 Index | ❌ Heap과 Index가 별도로 존재 |

한 줄로 정리하면:

> **일반 인덱스는 실제 데이터와 별도의 자료구조이므로 물리적 저장 순서를 결정하지 않지만, 클러스터드 인덱스는 실제 데이터 저장 구조에 영향을 준다. 또한 SQL에서 데이터의 조회 순서는 보장되지 않으므로 특정 순서가 필요하면 반드시 ****`ORDER BY`****를 사용해야 한다.**

### 추가 질문 + 답변

**Q1. 클러스터드 인덱스는 왜 테이블당 하나만 가질 수 있나요?** ⭐

하나의 테이블 데이터를 서로 다른 두 가지 기준으로 동시에 물리적으로 구성할 수 없기 때문입니다.

**Q2. MySQL InnoDB에서 PK가 없으면 어떻게 저장하나요?** ⭐

사용 가능한 적절한 `UNIQUE NOT NULL` 인덱스를 클러스터링 키로 선택하고, 그것도 없다면 InnoDB가 내부적으로 숨겨진 Row ID를 만들어 사용합니다.

**Q3. Secondary Index는 실제 데이터를 어떻게 찾나요?** ⭐

InnoDB의 Secondary Index 리프에는 보통 **PK 값**이 들어 있습니다. 이를 이용해 다시 Clustered Index를 탐색하여 실제 Row를 찾습니다.

**Q4. 인덱스가 정렬되어 있는데 왜 ****`ORDER BY`****가 필요한가요?** ⭐⭐

DB가 반드시 해당 인덱스를 사용한다는 보장이 없기 때문입니다. 실행 계획이나 병렬 처리 등에 따라 결과 순서가 달라질 수 있으므로 **결과 순서를 보장하는 SQL 문법은 `ORDER BY`**입니다.

**Q5. PK를 AUTO_INCREMENT로 사용하는 것이 성능상 좋은 이유는 무엇인가요?**

InnoDB에서는 PK가 클러스터드 인덱스이므로 증가하는 값은 B+Tree의 끝부분에 순차적으로 삽입되는 경향이 있습니다. 랜덤한 값보다 페이지 분할과 랜덤 삽입을 줄이는 데 유리합니다.

**Q6. 그러면 UUID를 PK로 사용하면 왜 성능 문제가 생길 수 있나요?** ⭐

랜덤 UUID는 B+Tree의 여러 위치에 삽입될 수 있어 페이지 분할과 캐시 효율 저하를 유발할 수 있고, PK 자체가 크기 때문에 Secondary Index 크기도 증가할 수 있습니다.

**Q7. ****`SELECT * FROM table`****은 삽입 순서대로 나오나요?** ⭐⭐⭐

**보장되지 않습니다.** 우연히 삽입 순서나 PK 순서처럼 보일 수 있지만 실행 계획이나 데이터 재배치 등에 따라 달라질 수 있습니다. 순서가 중요하다면 반드시 `ORDER BY`를 사용해야 합니다.
