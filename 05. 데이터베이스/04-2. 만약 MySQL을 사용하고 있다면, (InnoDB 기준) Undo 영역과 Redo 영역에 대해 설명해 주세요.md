# 4-2. 만약 MySQL을 사용하고 있다면, (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명해 주세요.

## 4-2. (InnoDB 기준) Undo 영역과 Redo 영역에 대해 설명해 주세요.

InnoDB가 **트랜잭션의 ACID 속성을 보장**하고, **서버 장애 시 복구 능력**과 높은 **동시성 처리 성능**을 동시에 달성할 수 있는 비결

**→** Undo 영역과 Redo 영역이라는 두 가지 서로 다른 로그 시스템

### 1. Undo 영역 (Undo Log)

### 개념 정의

Undo 영역은 **데이터가 변경되기 이전의 원래 상태(과거 데이터)를 백업**해 두는 메모리 및 디스크 저장 공간

### 주요 역할 2가지

- 트랜잭션 롤백 (Atomicity - 원자성 보장)

  - 사용자가 트랜잭션 중간에 `ROLLBACK` 명령을 실행하거나, 작업 중 에러가 발생하면 Undo 영역에 저장해둔 변경 전 데이터를 사용하여 데이터를 원상복구시킵니다.

- MVCC 및 잠금 없는 읽기 (Isolation - 격리성 보장)

  - 특정 트랜잭션이 A 레코드를 수정하고 아직 커밋하지 않은 상태일 때, 다른 트랜잭션이 A 레코드를 조회하면 락을 걸어 대기시키지 않습니다.

    - 대신 **Undo 영역에 저장된 이전 버전의 A 레코드를 읽어서 반환**합니다 (Consistent Non-locking Read). 이를 통해 읽기 작업과 쓰기 작업이 서로를 방해하지 않고 동시에 실행될 수 있습니다.

### 생명 주기 (Purge)

Undo 영역에 저장된 데이터는 트랜잭션이 커밋되더라도 즉시 삭제되지 않을 수 있습니다. 해당 과거 버전을 참조하고 있는 **다른 오랫동안 실행 중인 트랜잭션이 모두 종료될 때** 비로소 백그라운드 스레드(Undo Purge Thread)에 의해 안전하게 메모리에서 삭제됩니다.

### 2. Redo 영역 (Redo Log)

### 개념 정의

Redo 영역은 변경된 데이터의 최신 내용을 디스크 데이터 파일에 영구 반영하기 전에, 변경된 이력을 순차적으로 기록해 두는 일종의 **백업 로그(Write-Ahead Log) 파일**

### 주요 역할 2가지

- 크래시 복구 (Durability - 영속성 보장)

  - 서버에 전원이 끊기거나 갑자기 다운되면, 메모리(InnoDB 버퍼 풀)에 저장되어 있던 최신 변경 데이터(Dirty Page)가 디스크 데이터 파일에 저장되지 못하고 날아갈 수 있습니다.

  - 서버가 재시작될 때 InnoDB는 Redo 로그 파일의 기록을 처음부터 다시 실행(Replay/Redo)하여 디스크 파일 상태를 커밋 완료 시점의 최신 데이터 상태로 100% 복구해 냅니다.

**해당 트랜잭션은 손실(취소)됩니다.**

하지만 이는 데이터베이스의 오작동이나 결함이 아니라, **ACID의 원자성(Atomicity)과 영속성(Durability)을 지키기 위한 지극히 정상적인 동작**입니다.

## 1. 클라이언트 관점: "커밋 성공을 보장받은 적이 없음"

InnoDB에서 트랜잭션 커밋(`COMMIT`)이 완결되는 결정적인 기준은 **Redo 로그가 디스크 파일에 완전히 쓰여지고 동기화(****`fsync`****)되는 순간**입니다.

    - **정상적인 커밋 흐름**

      1. 클라이언트가 `COMMIT` 요청

      1. Redo 로그 버퍼(메모리)에 이력 작성

      1. **Redo 로그 파일로 디스크 저장 및 동기화 (****`fsync`****)**

      1. 클라이언트에 "커밋 성공" 응답 반환

    - **디스크 저장 전 서버가 다운된 경우**

Redo 로그가 디스크에 적히지 않았다면, 데이터베이스는 클라이언트에게 "성공했다"는 응답을 **단 한 번도 보낸 적이 없습니다.**

따라서 애플리케이션(클라이언트) 입장에서는 해당 요청이 실패했거나 타임아웃이 난 것으로 처리되며, DB 입장에서도 커밋 완료를 약속한 적이 없으므로 데이터가 날아가도 영속성 보장 원칙에 위배되지 않습니다.

## 2. 서버 재시작 시 동작 (Crash Recovery)

전원이 다시 들어와서 DB가 켜지면 다음과 같이 복구가 진행됩니다.

    1. **디스크에 마지막으로 안전하게 기록된 Redo 로그**까지만 읽어와서 데이터 파일 상태를 복원합니다.

    1. 디스크에 적히지 못하고 메모리(Redo Log Buffer)에만 떠있다가 날아간 작업은 **아예 없었던 작업**으로 간주됩니다.

    1. 만약 전원이 나가는 순간에 Redo 로그를 쓰다가 일부만 잘려서 기록(Partial Write)된 경우, 체크섬(Checksum) 검사를 통해 깨진 로그임을 감지하고 해당 기록을 무시하여 깔끔하게 **취소(Rollback) 처리**합니다.

결과적으로 데이터베이스는 "마지막으로 완벽하게 커밋되어 디스크에 Redo 로그를 남긴 시점"으로 안전하게 돌아갑니다.

## 3. 변수: 설정 옵션 (`innodb_flush_log_at_trx_commit`)

만약 기본 설정을 변경했다면 예외적인 상황이 발생할 수 있습니다.

    - **옵션 ****`1`**** (기본값 - Strict ACID)**

트랜잭션 커밋 시마다 Redo 로그를 즉시 디스크에 기록합니다. 커밋 성공 응답을 받은 데이터는 **100% 안전**합니다.

    - **옵션 ****`0`**** 또는 ****`2`**** (성능 최적화 옵션)**

디스크 I/O를 줄이기 위해 Redo 로그를 메모리에 모아두었다가 **1초에 한 번씩** 디스크로 플러시합니다.

이 설정을 사용하면, 클라이언트는 "커밋 성공" 응답을 받았음에도 불구하고 1초 사이에 서버 전원이 나가면 **최대 1초 분량의 커밋 완료 데이터가 손실**될 수 있습니다.

> **결론 요약**

Redo 로그가 디스크에 적히기 전에 서버가 꺼지면 해당 작업은 취소되지만, DB가 클라이언트에게 "성공"이라고 응답하기 전이었으므로 데이터베이스 시스템상 완벽하게 정상적인 원자성/영속성 보장 과정입니다.
  </details>

- 디스크 I/O 성능 최적화 (Write-Ahead Logging)

  - 변경이 일어날 때마다 무거운 데이터 파일(Random I/O)을 직접 수정하면 성능이 극도로 떨어집니다.

  - 따라서 속도가 매우 빠른 **Redo 로그 파일(Sequential I/O) 끝에 변경 사항만 빠르게 적어두고 커밋을 완료** 처리합니다. 이후 데이터 파일로의 실제 반영은 백그라운드 스레드가 조용히 모아서 처리(Checkpointing)합니다.

### 특징 및 구조

Redo 로그는 크기가 고정된 여러 개의 파일이 동그란 고리 형태로 연결되어 동작하는 순환 버퍼(Circular Buffer) 구조를 갖습니다. 오래되어 데이터 파일에 이미 안전하게 기록이 끝난 영역은 재사용 가능한 상태가 되어 계속 덮어씌워집니다.

### Undo 영역 vs Redo 영역 핵심 비교

| **구분** | **Undo 영역 (Undo Log)** | **Redo 영역 (Redo Log)** |
| --- | --- | --- |
| 저장 내용 | 변경되기 이전의 옛날 데이터 (Before Image) | 변경된 이후의 최신 이력 데이터 (After Image) |
| 핵심 목적 | 트랜잭션 취소(Rollback) 및 MVCC 이전 데이터 제공 | 서버 장애 발생 시 최신 상태로 크래시 복구 (Recovery) |
| 보장 속성 | Atomicity (원자성), Isolation (격리성) | Durability (영속성) |
| 쓰기 방식 | 필요에 의해 동적 생성 및 트랜잭션 종료 후 Purge | 고정 크기의 파일에 순환(Circular)하며 연속 기록 |
