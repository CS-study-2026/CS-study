# 2-3. NoSQL을 활용한 경험이 있나요? 있다면, 왜 RDB를 선택하지 않고 해당 DB를 선택했는지 설명해 주세요.

## :shrew1:사보땃쥐

여기서 Redis는 RDB를 완전히 대체하기 위해 사용한 것이 아니라, **MySQL과 역할을 분리하기 위해 사용했습니다.**

- MySQL: 게임, 라운드, 플레이어, 아이템 사용 기록, AI 판정 결과처럼 영속성이 필요한 데이터 저장

- Redis: 게임 진행 중 자주 바뀌는 임시 상태, ACK, 채팅, 프롬프트 draft, 게스트 세션, 중복 이벤트 방지 락 저장

---

## 프로젝트에서 Redis를 사용한 부분

사보땃쥐는 실시간으로 여러 플레이어가 같은 게임 상태를 공유합니다.

예를 들어 다음과 같은 값들이 빠르게 바뀝니다.

- 현재 라운드 phase

- 현재 프롬프트 턴

- 현재 턴 제한 시간

- 플레이어별 프롬프트 글자 수 제한

- 작성 중인 프롬프트 draft

- 각 phase 완료 ACK

- 투표 결과

- 최근 채팅

- 게스트 세션 토큰

- 중복 이벤트 발행 방지 락

이런 데이터들은 대부분 **짧은 시간 동안만 필요하고, 자주 읽고 쓰이며, TTL로 자동 만료되어도 되는 데이터**입니다.

```plain text
[Client]
   ↓ REST / WebSocket
[Spring Boot Backend]
   ├── MySQL: 영속 데이터
   └── Redis: 실시간 임시 상태 / ACK / 캐시 / 락
```

---

## 왜 RDB만 사용하지 않았는가?

### 1. 실시간 게임 상태는 변경 빈도가 높기 때문

게임 진행 중에는 현재 턴, 현재 phase, 제출 인원 수, 제한 시간 등이 계속 바뀝니다.

예를 들어 프롬프트 phase에서는 다음 정보가 빠르게 갱신됩니다.

```plain text
currentTurnIndex
submittedCount
currentTurnToken
currentTurnStartedAtEpochMs
currentTurnDeadlineAtEpochMs
currentTurnTimeLimitSeconds
```

이런 값을 매번 MySQL에 저장하면 다음 비용이 커질 수 있습니다.

- UPDATE 쿼리 증가

- 트랜잭션 비용 증가

- 락 경합 가능성 증가

- 불필요한 영속 데이터 증가

반면 Redis는 메모리 기반 저장소라 이런 임시 상태를 빠르게 읽고 쓰기에 적합합니다.

---

### 2. ACK 집계처럼 임시성 강한 데이터에 적합했기 때문

사보땃쥐에서는 특정 phase가 끝났는지 확인하기 위해 플레이어들의 ACK를 모읍니다.

예를 들어:

```plain text
start-ready ACK
prompt-ready ACK
item-defense-ended ACK
vote-ended ACK
```

ACK는 “모두 준비됐는지” 판단하는 데만 필요하고, 영구 보관할 필요는 크지 않습니다.

Redis에서는 Set 자료구조를 사용하면 중복 없이 userId를 저장하고 개수를 바로 확인할 수 있습니다.

```plain text
sabottatge:round:ack:{roundId}:{ackType}
```

이런 데이터는 MySQL 테이블로 관리할 수도 있지만, 매 phase마다 INSERT/COUNT/DELETE를 반복하는 것보다 Redis Set + TTL 구조가 더 단순하고 빠릅니다.

---

### 3. TTL이 필요한 데이터가 많았기 때문

Redis를 선택한 큰 이유 중 하나는 TTL입니다.

사보땃쥐에서는 다음 데이터들이 일정 시간이 지나면 자동으로 사라져도 됩니다.

| 데이터 | TTL | 이유 |
| --- | --- | --- |
| 게스트 세션 | 1일 | 임시 사용자 인증 상태 |
| 채팅 | 6시간 | 최근 채팅만 유지 |
| 라운드 상태 | 12시간 | 게임 진행 중에만 필요 |
| 프롬프트 draft | 12시간 | 작성 중 임시 저장 |
| ACK | 10분 | phase 전환 판단 후 불필요 |
| 턴 중복 진행 방지 락 | 30초 | 짧은 중복 요청 방지 |

RDB에서도 만료 시간을 컬럼으로 두고 배치 삭제를 만들 수는 있습니다.

하지만 Redis는 TTL을 기본 기능으로 제공하기 때문에 임시 데이터 관리에 더 자연스럽습니다.

---

### 4. 작성 중인 프롬프트 draft 저장에 적합했기 때문

프롬프트 작성 중에는 클라이언트가 draft를 주기적으로 보낼 수 있습니다.

이런 데이터를 MySQL에 계속 UPDATE하면 DB 부하가 커질 수 있습니다.

```plain text
사용자가 입력 중
   ↓
100~300ms마다 draft 전송 가능
   ↓
Redis에 임시 저장
   ↓
최종 제출 시 MySQL에 저장
```

즉, Redis에는 “작성 중인 값”을 두고, 최종 제출된 프롬프트만 MySQL에 저장하는 구조가 더 적합합니다.

---

### 5. 중복 이벤트 방지 락이 필요했기 때문

실시간 게임에서는 같은 턴 종료 요청이나 타임아웃 처리가 중복으로 들어올 수 있습니다.

예를 들어:

```plain text
사용자 제출
타이머 만료
네트워크 재전송
```

이런 요청이 거의 동시에 들어오면 턴이 두 번 넘어가는 문제가 생길 수 있습니다.

이를 막기 위해 Redis의 `setIfAbsent`를 이용해 짧은 락을 걸 수 있습니다.

<details>
<summary>_`setIfAbsent`__ :  키가 없을 때만 값을 저장하는 명령_</summary>

```json
요청 A 들어옴
  ↓
Redis setIfAbsent(lockKey, "true", 30초)
  ↓ true
턴 종료 처리 실행

요청 B 들어옴
  ↓
Redis setIfAbsent(lockKey, "true", 30초)
  ↓ false
이미 처리 중이므로 무시
```
</details>

```plain text
sabottatge:round:turn-advance-lock:{roundId}:{turnToken}
TTL: 30초
```

RDB에서도 락을 구현할 수 있지만, 짧은 시간 동안만 필요한 분산 락 성격의 데이터는 Redis가 더 가볍고 적합합니다.

---

## RDB와 Redis의 역할 분리

| 구분 | MySQL / RDB | Redis / NoSQL |
| --- | --- | --- |
| 주요 목적 | 영속성, 정합성 | 빠른 임시 상태 관리 |
| 저장 데이터 | 사용자, 방, 게임, 라운드, 아이템, 결과 | 세션, ACK, 채팅, draft, 진행 상태, 락 |
| 데이터 성격 | 오래 보관해야 함 | 일정 시간 후 사라져도 됨 |
| 장점 | 관계 표현, 트랜잭션, 정합성 | 빠른 읽기/쓰기, TTL, 자료구조 |
| 사용 이유 | 최종 결과와 핵심 데이터 보존 | 실시간 게임 흐름 처리 |

---

## 면접 답변 예시

사보땃쥐 프로젝트에서 NoSQL로 Redis를 사용한 경험이 있습니다. 이 프로젝트는 실시간 멀티플레이어 소셜 추리 게임이라 WebSocket을 통해 게임 상태, 턴 변경, ACK, 채팅, 프롬프트 작성 상태가 빠르게 오가는 구조였습니다.

RDB인 MySQL은 게임, 라운드, 플레이어, 아이템 사용 기록, AI 판정 결과처럼 영속성과 정합성이 중요한 데이터를 저장하는 데 사용했습니다. 반면 Redis는 게스트 세션, 라운드 진행 상태, 플레이어별 프롬프트 제한값, 프롬프트 draft, ACK 집계, 채팅, 중복 이벤트 방지 락처럼 자주 바뀌고 일정 시간이 지나면 사라져도 되는 데이터를 저장하는 데 사용했습니다.

RDB만 사용하지 않은 이유는 이런 실시간 임시 데이터를 모두 MySQL에 저장하면 UPDATE, INSERT, COUNT 쿼리가 자주 발생하고 트랜잭션이나 락 비용이 커질 수 있기 때문입니다. 특히 ACK 집계나 draft 저장, 턴 중복 방지 락은 영구 보관이 목적이 아니라 빠르게 저장하고 조회한 뒤 TTL로 만료시키는 것이 더 적합했습니다.

따라서 Redis를 선택한 이유는 MySQL을 대체하기 위해서가 아니라, RDB가 잘하는 영속성과 정합성 영역은 MySQL에 맡기고, 실시간 상태 관리와 임시 데이터 처리는 Redis에 맡기는 방식으로 역할을 분리하기 위해서였습니다.
