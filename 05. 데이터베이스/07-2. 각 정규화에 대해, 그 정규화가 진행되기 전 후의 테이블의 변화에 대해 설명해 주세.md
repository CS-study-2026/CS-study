# 7-2. 각 정규화에 대해, 그 정규화가 진행되기 전/후의 테이블의 변화에 대해 설명해 주세요.

> 💡 정규화: 하나의 테이블에 섞여 있는 여러 종류의 종속 관계를 단계적으로 분리하는 과정

## 1. 제1정규형(1NF) — 한 칸에는 하나의 값만

### 정규화 전

학생 한 명이 여러 과목을 수강한다고 해보자.

| 학번 | 이름 | 수강과목 |
| --- | --- | --- |
| 1001 | 김철수 | DB, 운영체제 |
| 1002 | 이영희 | 네트워크 |

`수강과목` 하나의 칸에 **DB, 운영체제라는 여러 값**이 들어 있다.

즉,

> 하나의 속성에 여러 값이 들어 있는 상태

입니다.

### ↓ 1NF 진행

각 칸에는 **원자값(Atomic Value), 즉 하나의 값만** 들어가도록 바꾼다.

### 정규화 후

| 학번 | 이름 | 수강과목 |
| --- | --- | --- |
| 1001 | 김철수 | DB |
| 1001 | 김철수 | 운영체제 |
| 1002 | 이영희 | 네트워크 |

### 변화

**전**

```plain text
수강과목 = {DB, 운영체제}
```

**후**

```plain text
DB
운영체제
```

즉,

> **반복되는 값 / 다중값 → 하나의 값**

으로 바뀐다.

---

# 2. 제2정규형(2NF) — 부분 함수 종속 제거

2NF부터는 **함수적 종속성**을 봐야 한다.

다음 테이블의 기본키가 `(학번, 과목코드)`인 복합키라고 해보자.

| 학번 | 과목코드 | 학생이름 | 과목명 | 성적 |
| --- | --- | --- | --- | --- |
| 1001 | C01 | 철수 | DB | A |
| 1001 | C02 | 철수 | OS | B |
| 1002 | C01 | 영희 | DB | A |

기본키:

```plain text
(학번, 과목코드)
```

그런데 종속관계를 보면

```plain text
학번 → 학생이름
과목코드 → 과목명

(학번, 과목코드) → 성적
```

입니다.

문제는 `학생이름`이 기본키 전체가 아니라 **학번 하나만으로 결정**된다는 것

마찬가지로 `과목명`도 **과목코드 하나만으로 결정된다.**

이것을 **부분 함수 종속**이라고 한다.

### ↓ 2NF 진행

부분적으로 종속된 데이터를 따로 분리한다.

### 정규화 후

**학생**

| 학번 | 학생이름 |
| --- | --- |
| 1001 | 철수 |
| 1002 | 영희 |

**과목**

| 과목코드 | 과목명 |
| --- | --- |
| C01 | DB |
| C02 | OS |

**수강**

| 학번 | 과목코드 | 성적 |
| --- | --- | --- |
| 1001 | C01 | A |
| 1001 | C02 | B |
| 1002 | C01 | A |

### 변화

정규화 전에는

```plain text
(학번, 과목코드)
       ↓
학생이름 / 과목명 / 성적
```

처럼 보이지만 실제로는

```plain text
학번 → 학생이름
과목코드 → 과목명
```

이라는 부분 종속이 있었다.

정규화 후에는 각각 자기 결정자와 함께 분리된다.

> **2NF = 기본키의 일부에만 종속된 컬럼을 다른 테이블로 분리**

특히 중요한 점은 **복합 후보키가 없는 테이블에서는 일반적으로 부분 함수 종속 문제가 발생하지 않는다는 것**

---

# 3. 제3정규형(3NF) — 이행 함수 종속 제거

이번에는 다음과 같은 학생 테이블이 있다고 해보자.

| 학번 | 학생이름 | 학과코드 | 학과명 |
| --- | --- | --- | --- |
| 1001 | 철수 | CS | 컴퓨터공학과 |
| 1002 | 영희 | CS | 컴퓨터공학과 |
| 1003 | 민수 | BA | 경영학과 |

기본키는 `학번`이다.

종속관계를 보면

```plain text
학번 → 학과코드
학과코드 → 학과명
```

따라서

```plain text
학번 → 학과코드 → 학과명
```

이라는 관계가 생긴다.

즉 `학과명`은 학번에 직접 종속된 것이 아니라 **학과코드를 거쳐 간접적으로 종속**되어 있다.

이것이 **이행 함수 종속**이다.

### ↓ 3NF 진행

### 정규화 후

**학생**

| 학번 | 학생이름 | 학과코드 |
| --- | --- | --- |
| 1001 | 철수 | CS |
| 1002 | 영희 | CS |
| 1003 | 민수 | BA |

**학과**

| 학과코드 | 학과명 |
| --- | --- |
| CS | 컴퓨터공학과 |
| BA | 경영학과 |

### 변화

**전**

```plain text
학번 → 학과코드 → 학과명
```

**후**

```plain text
학생 테이블
학번 → 학과코드

학과 테이블
학과코드 → 학과명
```

즉,

> **3NF = 기본키가 아닌 속성이 다른 기본키가 아닌 속성을 결정하는 구조를 분리**

---

# 4. BCNF — 결정자가 후보키가 아니면 분리

BCNF는 **3NF보다 조금 더 엄격한 형태**

예를 들어 다음 관계가 있다고 해보자.

| 학생 | 과목 | 교수 |
| --- | --- | --- |
| 철수 | DB | 김교수 |
| 영희 | DB | 김교수 |
| 철수 | OS | 박교수 |

그리고 다음 규칙이 있다고 하자.

```plain text
(학생, 과목) → 교수

교수 → 과목
```

즉 **교수 한 명은 하나의 과목만 담당**한다고 가정한 것

여기에서 `교수 → 과목`이라는 함수 종속이 있는데,

```plain text
교수
```

는 이 테이블의 후보키가 아니다.

BCNF의 조건은

> 모든 함수적 종속 `X → Y`에서 X가 슈퍼키여야 한다.

따라서 분리한다.

### 정규화 후

**교수과목**

| 교수 | 과목 |
| --- | --- |
| 김교수 | DB |
| 박교수 | OS |

**수강교수**

| 학생 | 교수 |
| --- | --- |
| 철수 | 김교수 |
| 영희 | 김교수 |
| 철수 | 박교수 |

### 변화

```plain text
후보키가 아닌 결정자
교수 → 과목
```

를 별도 테이블로 빼낸다.

즉,

> **BCNF = 모든 결정자가 후보키가 되도록 분해**

---

# 5. 제4정규형(4NF) — 다치 종속 제거

4NF부터는 함수 종속이 아니라 **다치 종속(Multivalued Dependency)**을 본다.

한 학생이 여러 개의 `취미`와 여러 개의 `자격증`을 가지고 있고, 두 정보가 서로 독립적이라고 해보자.

### 정규화 전

| 학생 | 취미 | 자격증 |
| --- | --- | --- |
| 철수 | 축구 | SQLD |
| 철수 | 축구 | 정보처리기사 |
| 철수 | 독서 | SQLD |
| 철수 | 독서 | 정보처리기사 |

실제로는

```plain text
철수의 취미 = {축구, 독서}

철수의 자격증 = {SQLD, 정보처리기사}
```

일 뿐인데 하나의 테이블에 넣으면서 모든 조합이 생겼다.

```plain text
학생 ↠ 취미
학생 ↠ 자격증
```

두 다치 종속이 서로 독립적

### ↓ 4NF 진행

### 정규화 후

**학생취미**

| 학생 | 취미 |
| --- | --- |
| 철수 | 축구 |
| 철수 | 독서 |

**학생자격증**

| 학생 | 자격증 |
| --- | --- |
| 철수 | SQLD |
| 철수 | 정보처리기사 |

### 변화

**전**

```plain text
학생 × 취미 × 자격증

철수 축구 SQLD
철수 축구 기사
철수 독서 SQLD
철수 독서 기사
```

**후**

```plain text
학생-취미
학생-자격증
```

즉,

> **4NF = 서로 독립적인 다중값 관계를 각각의 테이블로 분리**

---

# 6. 제5정규형(5NF) — 조인 종속 제거

5NF는 **하나의 테이블을 여러 개로 분리했다가 JOIN했을 때 원래 관계를 정확하게 복원할 수 있는가**

예를 들어

```plain text
공급자 - 부품 - 프로젝트
```

관계를 하나의 테이블로 가지고 있다고 하자.

| 공급자 | 부품 | 프로젝트 |
| --- | --- | --- |
| A | CPU | P1 |
| A | RAM | P1 |
| B | CPU | P2 |

이 관계가 사실 다음 세 가지 독립적인 관계로 표현될 수 있다면

```plain text
공급자 - 부품
공급자 - 프로젝트
부품 - 프로젝트
```

테이블을 세 개로 분리할 수 있다.

### 정규화 전

```plain text
공급자 | 부품 | 프로젝트
```

### ↓ 5NF

### 정규화 후

```plain text
공급자-부품
공급자-프로젝트
부품-프로젝트
```

그리고 이 세 테이블을 JOIN했을 때 **불필요한 가짜 튜플이 생기지 않으면서 원래 관계가 복원**되어야 한다.

> **5NF = 조인 종속을 제거하고 더 작은 관계들로 분리**

---

## 정리하면

| 정규형 | 정규화 전 | 정규화 후 |
| --- | --- | --- |
| **1NF** | 한 컬럼에 여러 값 | 한 칸에 하나의 원자값 |
| **2NF** | 복합키 일부에 종속 | 부분 종속 속성을 별도 테이블로 분리 |
| **3NF** | 일반 속성이 다른 일반 속성을 결정 | 이행 종속 관계 분리 |
| **BCNF** | 후보키가 아닌 결정자 존재 | 모든 결정자가 후보키가 되도록 분리 |
| **4NF** | 독립적인 다치 종속 존재 | 다치 종속별로 테이블 분리 |
| **5NF** | 불필요한 조인 종속 존재 | 손실 없이 조인 가능한 최소 관계로 분리 |

```plain text
1NF : 한 칸에 하나
 ↓
2NF : 기본키 전체에 종속
 ↓
3NF : 기본키에 직접 종속
 ↓
BCNF : 결정자는 후보키
 ↓
4NF : 독립적인 다중값 분리
 ↓
5NF : 조인 관계 분리
```
