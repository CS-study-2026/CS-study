# 3-3. 읽기에는 트랜잭션을 걸지 않아도 될까요?

결론부터 말하면, 단순한 SELECT 한 번이라면 직접 트랜잭션을 걸지 않아도 됩니다. 다만 여러 조회가 하나의 일관된 데이터 상태를 봐야 한다면 명시적인 트랜잭션이 필요합니다.

# 조회 시 트랜잭션을 걸지 않으면 어떤 문제가 발생할 수 있을까?

조회(SELECT)는 데이터를 변경하지 않기 때문에 "트랜잭션이 필요 없다"고 생각하기 쉽습니다. 하지만 실제 서비스에서는 조회 과정에서도 여러 문제가 발생할 수 있으며, JPA에서는 이를 방지하기 위해 `@Transactional(readOnly = true)`를 사용하는 경우가 많습니다.

---

# 1. Lazy Loading 문제

JPA에서는 연관된 데이터를 모두 한 번에 가져오지 않고, **필요할 때만 조회하는 LAZY(지연 로딩)** 방식을 많이 사용합니다.

예를 들어 회원을 조회했을 때 주문 목록은 아직 가져오지 않고, 사용자가 실제로 주문 목록을 열었을 때 DB에서 조회합니다.

### 상황 예시

쇼핑몰에서 **마이페이지**를 열었다고 가정해보겠습니다.

```plain text
회원 정보 조회
↓

이름, 이메일 출력
↓

사용자가 "주문 내역 보기" 버튼 클릭
↓

주문 목록 조회
```

이때 조회 메서드의 트랜잭션이 이미 종료되었다면 JPA는 더 이상 데이터베이스에 접근할 수 없습니다.

결국

```plain text
LazyInitializationException
```

이 발생하면서 주문 목록을 가져오지 못합니다.

즉,

> 회원 정보는 보이는데, 주문 내역을 클릭하는 순간 오류가 발생하는 상황입니다.

그래서 조회 메서드에도 트랜잭션을 유지하여 필요한 순간에 추가 조회(Lazy Loading)가 가능하도록 합니다.

---

# 2. 조회 결과의 일관성이 깨질 수 있다

조회 중 다른 사용자가 데이터를 수정하면 **한 번의 요청 안에서도 서로 다른 시점의 데이터를 읽는 문제**가 발생할 수 있습니다.

### 상황 예시 ① - 쇼핑몰 주문 조회

관리자가 주문 현황을 조회하고 있습니다.

```plain text
① 주문 개수 조회
↓

② 주문 목록 조회
```

그런데 두 조회 사이에 다른 고객이 주문을 하나 더 했습니다.

결과는

```plain text
주문 개수 : 10개

주문 목록 : 11개
```

가 됩니다.

같은 화면인데 숫자가 맞지 않습니다.

사용자는

> "주문이 10개라면서 왜 목록은 11개지?"

라고 생각할 수 있습니다.

---

### 상황 예시 ② - 은행 계좌 조회

사용자가 계좌 화면을 열었습니다.

```plain text
잔액 조회
↓

최근 거래내역 조회
```

하지만 그 사이에 다른 기기에서 송금이 발생했습니다.

그러면

```plain text
잔액 : 100만원

거래내역 : 방금 출금된 내역 존재
```

처럼

잔액은 출금 전 상태인데

거래내역은 출금 후 상태가 될 수도 있습니다.

즉, 하나의 화면 안에서 서로 다른 시점의 데이터를 보여주게 됩니다.

---

### 이러한 현상을 읽기 이상(Read Anomaly)이라고 한다.

대표적으로

- **Non-repeatable Read**

  - 같은 데이터를 두 번 조회했는데 값이 달라지는 현상

- **Phantom Read**

  - 조건으로 조회했는데 새로운 행이 추가되어 결과 개수가 달라지는 현상

트랜잭션을 사용하면 DB의 **격리 수준(Isolation Level)** 에 따라 이러한 문제를 방지하거나 완화할 수 있습니다.

| 현상 | 무엇이 바뀌는가? | 예시 |
| --- | --- | --- |
| Dirty Read | Commit되지 않은 데이터 | 롤백될 데이터를 읽음 |
| Non-repeatable Read | 기존 Row의 값 변경 | 잔액 100 → 80 |
| Phantom Read | 새로운 Row 추가/삭제 | 예약 10건 → 11건 |

---

# 3. 성능 최적화

Spring에서는 조회 메서드에

```java
@Transactional(readOnly = true)
```

를 자주 사용합니다.

이는 단순히 "읽기 전용"이라는 의미만 있는 것이 아닙니다.

Hibernate는 기본적으로 엔티티를 조회하면

> "혹시 이 객체가 수정되지는 않았을까?"

를 계속 확인합니다.

이를 **Dirty Checking(변경 감지)** 이라고 합니다.

하지만 조회만 수행하는 메서드라면 이러한 작업은 모두 불필요합니다.

`readOnly = true`를 사용하면 Hibernate는

- Dirty Checking 생략

- Flush 준비 생략

등의 최적화를 수행하여 메모리 사용량과 실행 비용을 줄일 수 있습니다.

### 상황 예시

게시판에서 게시글을 읽는 기능이 있다고 가정해보겠습니다.

```plain text
사용자 10,000명이 게시글 조회
```

게시글은 수정하지 않는데도 Hibernate가 모든 객체를 계속 추적하면 불필요한 메모리와 CPU를 사용하게 됩니다.

반면

```plain text
@Transactional(readOnly = true)
```

를 적용하면

> "이 메서드는 조회만 수행한다."

고 판단하여 변경 감지를 하지 않으므로 더 효율적으로 동작합니다.

---

# 단순 조회라면 트랜잭션이 없어도 될까?

항상 필요한 것은 아닙니다.

예를 들어

- 회원 한 명 조회

- 게시글 하나 조회

- 상품 상세 조회

처럼 **SELECT 한 번 실행하고 바로 종료되는 단순 조회**라면 트랜잭션이 없어도 큰 문제가 없는 경우가 많습니다.

그래서 JDBC나 MyBatis에서는 단순 조회에 별도의 트랜잭션을 사용하지 않는 경우도 있습니다.

하지만 JPA에서는

- Lazy Loading

- 조회 일관성 유지

- Dirty Checking 최적화

등의 이유로 조회 메서드에도 `@Transactional(readOnly = true)`를 사용하는 것이 일반적인 관례입니다.

# 정리

| 문제 | 실제 서비스에서 발생하는 예 |
| --- | --- |
| Lazy Loading | 회원 정보는 보이지만 주문 내역을 클릭하는 순간 `LazyInitializationException` 발생 |
| 조회 일관성 | 주문 개수는 10개인데 목록은 11개, 잔액은 출금 전인데 거래내역은 출금 후 상태 |
| 성능 | 조회만 하는데도 Hibernate가 변경 감지를 수행하여 불필요한 메모리와 CPU 사용 |
| 해결 방법 | 조회 메서드에 `@Transactional(readOnly = true)`를 적용하여 안정성과 성능을 함께 확보 |
