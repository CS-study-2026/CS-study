# 14-1. DB와 Client가 Connection을 어떻게 구성하는지 설명해 주세요.

> Client가 DB Server와 통신할 수 있는 전용 통신 경로를 만드는 과정

예를 들어 Spring 서버가 MySQL에 접속한다고 해보자.

```plain text
Client(Application)
    Spring Boot
       │
       │  Connection 요청
       │
       ▼
   JDBC Driver
       │
       │  TCP 연결
       ▼
┌─────────────────┐
│   DB Server     │
│     MySQL       │
└─────────────────┘
```

### 1. Client가 DB 접속 정보를 가지고 있다

보통 이런 정보가 필요하다.

```plain text
DB 주소(IP/Host) : 192.168.0.10
Port             : 3306
Database         : shop
User             : user1
Password         : ****
```

Java에서는 예를 들면:

```plain text
jdbc:mysql://192.168.0.10:3306/shop
```

처럼 DB의 **주소 + Port + DB 이름**을 지정한다. JDBC에서는 `DriverManager.getConnection()` 등을 통해 DB 연결을 생성할 수 있다.

---

### 2. Client와 DB Server 사이에 TCP Connection을 만든다

DB도 결국 네트워크를 통해 통신하는 **서버 프로그램이**다.

```plain text
Client                            DB Server

IP : 192.168.0.5                  IP : 192.168.0.10
Port : 52341                      Port : 3306
     │                               │
     └──────── TCP Connection ───────┘
```

DB Server는 특정 Port를 열어두고 요청을 기다린다.

예를 들어 MySQL의 대표적인 기본 포트는 `3306`, PostgreSQL은 `5432`이다.

Client의 Port는 보통 OS가 임시로 하나를 할당한다.

따라서 실제 Connection은 대략 다음 정보로 구분된다.

```plain text
Client IP
Client Port
Server IP
Server Port
```

예를 들면:

```plain text
192.168.0.5:52341
       ↕
192.168.0.10:3306
```

이렇게 **하나의 네트워크 연결**이 만들어진다.

---

### 3. TCP 연결 후 바로 SQL을 보내는 것은 아니다

TCP 연결이 만들어지면 그 위에서 **DB 자체 프로토콜**을 이용한 초기 통신이 이루어진다.

예를 들어 PostgreSQL에서는 Client가 Server에 연결한 뒤:

```plain text
Client
   │
   │ TCP Connection
   ▼
DB Server
   │
   │
Client → 사용자명 / DB명 / 프로토콜 정보
   │
DB → 인증 요청
   │
Client → 비밀번호 등 인증 정보
   │
DB → 인증 성공
```

과 같은 Startup/Authentication 단계가 진행된다.

즉,

```plain text
TCP 연결
   ↓
DB 인증
   ↓
DB Session 생성
   ↓
Connection 사용 가능
```

이라고 이해하시면 된다.

---

### 4. 인증이 성공하면 DB Session이 만들어진다

여기서 **Connection과 Session을 구분**하면 좋다.

```plain text
Client
   │
   │ Connection
   ▼
DB Server
   │
   └── Session
         ├─ 사용자 정보
         ├─ Transaction 상태
         ├─ 설정값
         └─ 실행 중인 SQL 정보
```

쉽게 말하면,

**Connection = Client와 DB 사이의 통신 통로**

**Session = 그 Connection을 사용하는 동안 DB가 관리하는 작업 상태**

PostgreSQL도 인증이 완료되면 Startup 단계에서 Normal Operation 단계로 넘어가고, 이후 Client가 Query를 보내고 DB가 결과를 반환하는 구조를 사용한다.

---

### 5. 이제 SQL을 주고받는다

Connection이 완성되면 비로소 이런 통신을 한다.

```plain text
Client
   │
   │ SELECT * FROM member;
   ▼
DB Server
   │
   │ SQL 처리
   │
   ▼
Client
   │
   │ 결과 반환
   ▼

id | name
1  | Kim
2  | Lee
```

즉 하나의 Connection을 통해 여러 SQL을 실행할 수 있다.

```plain text
Connection 생성

SELECT ...
INSERT ...
UPDATE ...
COMMIT

Connection 종료
```

매 SQL마다 TCP Connection을 다시 만드는 것이 아니다.

---

## 전체 과정을 한 번에 보면

```plain text
① Client
   │
   │ DB 접속 요청
   │ IP + Port
   ▼
② DB Server
   │
   │ TCP Connection 생성
   ▼
③ Client ↔ DB
   │
   │ 사용자 / 비밀번호 인증
   ▼
④ DB Session 생성
   │
   │
⑤ SQL 실행
   │
   │ SELECT / INSERT / UPDATE
   ▼
⑥ 결과 반환
```

**"DB와 Client가 Connection을 어떻게 구성하나요?"**

> Client는 DB Server의 IP와 Port를 이용해 먼저 TCP Connection을 맺습니다. 이후 DB 고유 프로토콜을 통해 사용자 인증을 수행하고, 인증이 성공하면 DB Server가 해당 Client를 위한 Session을 생성합니다. 이후 Client는 생성된 Connection을 통해 SQL 요청을 보내고 DB는 결과를 반환합니다. Connection은 일반적으로 Client IP·Port와 Server IP·Port를 기반으로 네트워크 수준에서 구분됩니다.

그리고 여기서 **Connection Pool**이 이어진다.

```plain text
매 요청마다

TCP 연결
→ 인증
→ Session 생성
→ SQL
→ 연결 종료
```

를 반복하면 비용이 크기 때문에,

```plain text
           Connection Pool

        ┌─────────────┐
요청1 → │ Connection1 │
요청2 → │ Connection2 │
요청3 → │ Connection3 │
        └─────────────┘
               │
               ▼
              DB
```

처럼 **이미 만들어진 Connection을 재사용한**다.

### 핵심 암기

```plain text
Client
  ↓
IP + Port
  ↓
TCP Connection
  ↓
DB Protocol
  ↓
Authentication
  ↓
DB Session
  ↓
SQL Request / Response
```

**Connection = 통신 경로 / Session = DB가 관리하는 접속 상태**로 구분하면 된다.
