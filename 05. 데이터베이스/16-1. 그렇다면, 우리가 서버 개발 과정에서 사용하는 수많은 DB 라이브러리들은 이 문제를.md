# 16-1. 그렇다면, 우리가 서버 개발 과정에서 사용하는 수많은 DB 라이브러리들은 이 문제를 어떻게 해결할까요?

> 

서버 개발에서 사용하는 JDBC, JPA, MyBatis 같은 DB 접근 기술들은 기본적으로 **파라미터 바인딩**을 통해 SQL Injection 위험을 줄입니다.

JDBC에서는 PreparedStatement의 `?`에 값을 바인딩하고, JPA에서는 JPQL이나 메서드 기반 쿼리에서 파라미터를 바인딩합니다. MyBatis 역시 `#{}` 문법을 사용하면 파라미터를 바인딩하여 안전하게 처리할 수 있습니다.

중요한 것은 라이브러리가 단순히 입력값의 특수문자를 제거하는 것이 아니라, **SQL 문장과 사용자 입력값을 분리해서 DB에 전달한다는 점**입니다. 따라서 입력값에 SQL 문법이 포함되어 있더라도 일반적으로 SQL 코드로 실행되지 않고 데이터 값으로 처리됩니다.

다만 개발자가 문자열 연결이나 `${}` 같은 위험한 방식을 사용하면 라이브러리를 사용하더라도 SQL Injection이 발생할 수 있습니다. 따라서 **DB 라이브러리를 사용하는 것 자체보다 올바른 파라미터 바인딩 방식을 사용하는 것이 중요합니다.**

---

## 1️⃣ DB 라이브러리가 해결하는 핵심 문제

SQL Injection의 근본적인 문제는

```plain text
SQL 코드 + 사용자 입력
        ↓
하나의 SQL 문자열
```

로 합쳐지는 것이다.

DB 라이브러리는 이를

```plain text
SQL 구조
   +
파라미터 값
```

으로 분리하여 전달한다.

### 📌 핵심 원칙

> **Code와 Data를 분리한다.**

---

## 2️⃣ JDBC - PreparedStatement

Java에서 가장 기본적인 DB 접근 방식이다.

### ❌ 위험한 방식

```java
String sql =
    "SELECT * FROM users WHERE id = '" + userId + "'";

Statement statement = connection.createStatement();
statement.executeQuery(sql);
```

사용자 입력이 SQL 문자열에 직접 들어간다.

```plain text
사용자 입력
     ↓
문자열 연결
     ↓
SQL 완성
     ↓
DB 실행
```

➡️ SQL Injection에 취약

---

### ✅ 안전한 방식

```java
String sql =
    "SELECT * FROM users WHERE id = ?";

PreparedStatement pstmt =
    connection.prepareStatement(sql);

pstmt.setString(1, userId);

ResultSet rs = pstmt.executeQuery();
```

여기서

```plain text
SQL
SELECT * FROM users WHERE id = ?

            +

값
userId
```

가 분리되어 전달된다.

---

## 3️⃣ 왜 `?`가 안전한가?

예를 들어 사용자가

```plain text
' OR '1'='1
```

을 입력했다고 하자.

Parameterized Query에서는 이 값이

```plain text
SQL 문법
```

으로 해석되는 것이 아니라

```plain text
하나의 문자열 데이터
```

로 처리된다.

즉,

```plain text
SELECT ...
WHERE id = ?

        ↓

? = "' OR '1'='1"
```

이다.

➡️ 입력값 내부의 SQL 문법이 쿼리 구조를 변경하지 못한다.

---

## 4️⃣ JPA에서는?

Spring에서 많이 사용하는 JPA 역시 파라미터 바인딩을 지원한다.

### ✅ Spring Data JPA에서는?

Spring Data JPA를 사용하면
메서드 이름만으로 조회 조건을 표현할 수도 있다.

```java
Optional<User> findByName(String name);
```

➡️ 내부적으로 필요한 SQL을 생성하면서
파라미터를 안전하게 바인딩한다.

### ✅ JPQL + 파라미터 바인딩

JPA에서는 **JPQL**을 사용하여
Entity를 대상으로 직접 쿼리를 작성할 수도 있다.

```java
String jpql =
    "SELECT u FROM User u WHERE u.name = :name";

TypedQuery<User> query =
    entityManager.createQuery(jpql, User.class);

query.setParameter("name", userName);
```

➡️ 사용자 입력값을 JPQL 문자열에 직접 결합하지 않고
파라미터로 전달하기 때문에 SQL Injection을 방지한다.

---

## 5️⃣ QueryDSL에서는?

QueryDSL도 파라미터를 안전하게 처리할 수 있다.

예를 들어

```java
queryFactory
    .selectFrom(user)
    .where(user.name.eq(userName))
    .fetch();
```

와 같이 작성하면

```plain text
user.name
    =
userName
```

이라는 조건을 표현하고,

사용자 입력값은 쿼리 구조와 분리되어 처리된다.

### 📌 장점

- 문자열 SQL을 직접 조립하는 방식보다 안전

- 컴파일 타임 타입 체크

- 동적 쿼리 작성에 유리

- 파라미터 바인딩 활용

> 💡 단, QueryDSL을 사용한다고 무조건 안전한 것은 아니다. 개발자가 문자열을 직접 조합하는 방식으로 SQL을 구성하면 별도의 주의가 필요하다.

---

## 6️⃣ MyBatis에서는?

MyBatis는 특히 **`#{}`****와 ****`${}`****의 차이**를 알아두면 좋다.

### ✅ `#{}`

```xml
<select id="findUser">
    SELECT *
    FROM users
    WHERE id = #{userId}
</select>
```

`#{}`는 파라미터 바인딩을 사용한다.

개념적으로

```plain text
WHERE id = ?
```

형태로 처리된다.

➡️ SQL Injection 방어에 적합

---

### ⚠️ `${}`

```xml
<select id="findUser">
    SELECT *
    FROM users
    WHERE id = '${userId}'
</select>
```

`${}`는 값을 문자열에 직접 치환하는 방식이다.

즉,

```plain text
SQL + 사용자 입력
```

이 합쳐질 수 있다.

➡️ 사용자 입력을 그대로 사용하면 SQL Injection 위험

---

## 7️⃣ DB 접근 기술별 비교

| 기술 | 안전한 방식 | 주의할 방식 |
| --- | --- | --- |
| **JDBC** | `PreparedStatement` | `Statement` + 문자열 연결 |
| **JPA** | 파라미터 바인딩 | 문자열을 직접 조합한 쿼리 |
| **QueryDSL** | 조건식 + 파라미터 바인딩 | 안전하지 않은 문자열 조합 |
| **MyBatis** | `#{}` | 사용자 입력에 `${}` 직접 사용 |

---

## 8️⃣ 라이브러리가 실제로 하는 일

전체 흐름을 보면

```plain text
사용자 요청
    ↓
Controller
    ↓
Service
    ↓
Repository / DB Library
    ↓
SQL + Parameter
    ↓
Database
```

DB 라이브러리 단계에서

```plain text
SQL 구조
SELECT ...
WHERE id = ?

        +

파라미터
userInput
```

을 분리한다.

따라서 사용자가

```plain text
' OR 1=1 --
```

같은 값을 입력하더라도
일반적으로 해당 값이 SQL 구조 자체를 변경하지 않는다.

---

## 9️⃣ 그렇다면 DB 라이브러리만 사용하면 무조건 안전할까?

### ❌ 아니다.

다음과 같은 경우에는 여전히 위험하다.

### ① 문자열로 SQL을 직접 조합

```java
String sql =
    "SELECT * FROM users WHERE id = '" + userId + "'";
```

---

### ② 안전하지 않은 동적 SQL 생성

특히 테이블명, 컬럼명, 정렬 기준처럼
**파라미터 바인딩으로 처리하기 어려운 SQL 구조 자체를 사용자 입력으로 결정**하는 경우 주의해야 한다.

예:

```plain text
ORDER BY [사용자 입력]
```

이런 경우에는

```plain text
허용된 컬럼 목록(allowlist)
```

을 이용해 입력 가능한 값을 제한하는 방식 등을 고려해야 한다.

---

### ③ MyBatis `${}` 사용

```xml
WHERE id = '${userId}'
```

사용자 입력이 직접 SQL에 삽입될 수 있다.

---

## 🔟 추가적인 방어 계층

파라미터 바인딩이 가장 핵심이지만
다른 보안 대책도 함께 적용하는 것이 좋다.

### 🛡️ 입력값 검증

```plain text
전화번호 → 숫자와 하이픈만 허용
이메일 → 이메일 형식 검증
ID → 허용된 문자만 사용
```

---

### 🛡️ 최소 권한 원칙

DB 계정에

```plain text
SELECT
INSERT
UPDATE
```

등 실제 필요한 권한만 부여한다.

애플리케이션이 필요하지 않은

```plain text
DROP
CREATE
```

등의 권한까지 갖지 않도록 한다.

➡️ 공격이 성공하더라도 피해 범위를 줄일 수 있다.

---

## 📌 핵심 정리

### SQL Injection의 원인

```plain text
사용자 입력
    ↓
SQL 문자열에 직접 삽입
    ↓
SQL 코드로 해석
```

### DB 라이브러리의 기본적인 방어

```plain text
SQL 구조
    +
파라미터
    ↓
Parameter Binding
    ↓
SQL 코드와 데이터 분리
```

### Java에서 기억할 것

```plain text
JDBC
→ PreparedStatement

JPA
→ Parameter Binding

QueryDSL
→ 조건식 + Parameter Binding

MyBatis
→ #{parameter} ✅
→ ${parameter} ⚠️
```

> ⭐ **결국 핵심은 "어떤 라이브러리를 사용하느냐"보다 "사용자 입력을 SQL 구조와 분리해서 전달하느냐"이다.**
