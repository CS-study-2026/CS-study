# 12-1. DB 서버를 분산하지 않고, 트래픽을 감당할 수 있는 방법은 없을까요?

# 12-1. DB 서버를 분산하지 않고, 트래픽을 감당할 수 있는 방법은 없을까요?

## 결론

가능하다.

DB를 여러 대로 분산하지 않더라도 다음과 같은 방법을 통해 상당한 수준의 트래픽을 처리할 수 있다.

- Cache

- Query 최적화

- Connection Pool

- Scale-Up

- Partitioning

- 비동기 처리

---

## 1. DB Query 자체를 줄인다

가장 효과적인 방법 중 하나는 DB로 전달되는 Query 수 자체를 줄이는 것이다.

예를 들어 동일한 공지사항을 10만 명이 조회한다고 가정한다.

### Cache를 사용하지 않는 경우

```plain text
100,000 User
      ↓
100,000 SELECT
      ↓
Single DB
```

### Cache를 사용하는 경우

```plain text
100,000 User
      ↓
    Cache
      ↓
DB Query 최소화
```

따라서 중요한 것은 단순히 DB 서버를 더 강하게 만드는 것이 아니다.

> DB가 처리할 필요가 없는 요청은 DB까지 보내지 않는 것이 중요하다.

---

## 2. Query의 처리 비용을 줄인다

동일한 Query 수라도 각각의 Query가 얼마나 많은 자원을 사용하는지에 따라 DB 부하는 크게 달라진다.

예를 들어 모든 컬럼을 조회하는 것보다

```plain text
SELECT *
FROM users;
```

필요한 컬럼만 조회하는 것이 좋다.

```plain text
SELECT id, name
FROM users
WHERE id = ?;
```

또한 다음과 같은 방법을 사용할 수 있다.

- 필요한 컬럼만 SELECT

- 불필요한 Query 제거

- Pagination 적용

- N+1 Query 문제 제거

- 적절한 Index 사용

- 대량 데이터를 한 번에 조회하지 않도록 제한

> 적절한 Index를 포함한 Query 최적화를 통해 하나의 Query가 사용하는 비용을 줄일 수 있다.

---

## 3. Connection Pool을 통한 동시 요청 제어

DB에 요청이 많다고 모든 요청을 동시에 DB에 보내는 것이 항상 좋은 것은 아니다.

예를 들어 DB가 동시에 100개의 Query를 안정적으로 처리할 수 있다고 가정한다.

```plain text
1,000 Request
     ↓
1,000 Connection
     ↓
DB
```

보다 다음과 같은 구조가 더 안정적일 수 있다.

```plain text
1,000 Request
      ↓
Connection Pool 100개
      ↓
DB
```

Connection Pool은 DB Connection을 재사용하는 역할과 함께 DB가 감당할 수 있는 수준으로 동시 요청을 제한할 수 있다.

즉,

> Connection Pool은 DB 앞단에서 Backpressure를 제공할 수 있다.

---

## 4. Scale-Up

DB를 여러 대로 분산하지 않고 단일 서버 자체의 성능을 증가시킬 수도 있다.

```plain text
Single DB

CPU      4 Core → 32 Core
Memory   16GB   → 128GB
Disk     SSD    → NVMe
```

따라서 12-1 질문에 대한 가장 직접적인 답은 다음과 같다.

> Scale-Up을 사용하면 DB를 분산하지 않고도 DB의 처리량을 증가시킬 수 있다.

다만 Scale-Up에는 물리적이고 경제적인 한계가 존재한다.

```plain text
Scale-Up
   ↓
물리적 한계
   ↓
Scale-Out 필요
```

트래픽이 계속 증가하면 결국 Read Replica나 Sharding과 같은 Scale-Out 전략을 고려해야 할 수 있다.

---

## 5. Partitioning

Partitioning은 하나의 큰 테이블을 여러 영역으로 나누어 관리하는 방법이다.

예를 들어 로그 테이블을 날짜 기준으로 나눌 수 있다.

```plain text
logs

├─ 2026_01
├─ 2026_02
├─ 2026_03
└─ ...
```

필요한 Partition만 조회할 수 있다면 대용량 데이터 조회 비용을 줄일 수 있다.

### Partitioning과 Sharding의 차이

```plain text
Partitioning

하나의 DB 내부에서
데이터를 여러 영역으로 나눈다.
```

```plain text
Sharding

여러 DB 서버에
데이터를 나누어 저장한다.
```

따라서 Partitioning은 DB 서버를 분산하지 않고 대용량 데이터를 관리하는 하나의 방법이다.

---

## 6. 비동기 처리

모든 Write 작업을 사용자의 요청 안에서 즉시 처리해야 하는 것은 아니다.

예를 들어 로그 저장을 다음과 같이 처리할 수 있다.

### 동기 처리

```plain text
Request
   ↓
Application
   ↓
DB INSERT
   ↓
Response
```

### 비동기 처리

```plain text
Request
   ↓
Application
   ↓
Message Queue
   ↓
Response

Message Queue
   ↓
Worker
   ↓
DB
```

순간적으로 많은 요청이 발생하더라도 Queue가 이를 임시로 저장하고 Worker가 DB가 처리할 수 있는 속도로 작업을 수행할 수 있다.

```plain text
순간적인 대량 요청
        ↓
 Message Queue
████████████████
        ↓
 일정한 처리 속도
        ↓
       DB
```

이를 **Traffic Smoothing / Buffering** 관점에서 볼 수 있다.

단, 다음과 같이 즉시 데이터 반영 여부가 중요한 작업에는 주의해야 한다.

- 결제

- 재고 차감

- 좌석 예약

- 즉시 결과가 필요한 트랜잭션

---

# 예상 꼬리 질문

## Q. Scale-Up과 Scale-Out의 차이는?

### Scale-Up

하나의 DB 서버의 성능을 높이는 방식이다.

```plain text
CPU / RAM / Disk ↑
```

### Scale-Out

DB 서버의 개수를 늘려 부하를 분산하는 방식이다.

```plain text
DB 1
DB 2
DB 3
```

---

## Q. Read Replica와 Sharding의 차이는?

### Read Replica

같은 데이터를 여러 DB가 가지고 있다.

```plain text
Primary
   ↓ Replication

Replica 1
Replica 2
```

주로 Read 트래픽을 분산하기 위해 사용한다.

### Sharding

서로 다른 데이터를 여러 DB에 나누어 저장한다.

```plain text
DB 1 → User 1 ~ 1,000,000
DB 2 → User 1,000,001 ~ 2,000,000
```

Read뿐 아니라 Write 트래픽도 분산할 수 있다.

---

## Q. Cache는 무조건 사용하면 좋은가?

아니다.

Cache는 다음과 같은 데이터에 특히 효과적이다.

- 조회 빈도가 높음

- 변경 빈도가 상대적으로 낮음

- 약간의 데이터 지연을 허용할 수 있음

반대로 항상 최신 값이 필요하거나 데이터 변경이 매우 빈번하면 Cache Invalidation 관리 비용이 증가할 수 있다.

---

## Q. Connection Pool을 크게 만들면 성능이 좋아지나?

아니다.

Connection 수가 DB가 실제로 처리할 수 있는 동시 작업량보다 지나치게 많으면 오히려 다음 문제가 발생할 수 있다.

- CPU 경쟁

- 메모리 사용량 증가

- Context Switching 증가

- DB 내부 자원 경쟁 증가

따라서 DB 처리 능력에 맞게 Pool 크기를 설정해야 한다.

---

## Q. Partitioning과 Sharding은 같은 것인가?

아니다.

```plain text
Partitioning
→ 하나의 DB 내부에서 데이터를 분할

Sharding
→ 여러 DB 서버에 데이터를 분할
```

Partitioning은 대용량 테이블 관리와 특정 범위 조회 최적화에 활용할 수 있고, Sharding은 여러 DB 서버에 부하 자체를 분산하기 위한 방법이다.
