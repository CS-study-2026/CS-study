# 2-0. RDB와 NoSQL의 차이에 대해 설명해 주세요.

## RDB란?

RDB는 **Relational Database, 관계형 데이터베이스**

데이터를 다음과 같은 **행과 열로 이루어진 테이블**에 저장

### 회원 테이블

| 회원번호 | 이름 | 이메일 |
| --- | --- | --- |
| 1 | 은혜민 | hm@example.com |
| 2 | 김민수 | ms@example.com |

### 주문 테이블

| 주문번호 | 회원번호 | 상품명 |
| --- | --- | --- |
| 101 | 1 | 키보드 |
| 102 | 1 | 마우스 |

두 테이블은 `회원번호`를 통해 연결된다.

```plain text
회원.회원번호 PK
        ↑
주문.회원번호 FK
```

RDB에서는 기본키·외래키·고유성·NOT NULL 등의 제약조건으로 데이터 관계와 무결성을 관리

대표적인 RDBMS는 다음과 같다.

- Oracle

- MySQL

- PostgreSQL

- Microsoft SQL Server

- MariaDB

엄밀히 말하면 **RDB는 데이터베이스 구조**, **RDBMS는 그 데이터베이스를 관리하는 소프트웨어**

---

## NoSQL이란?

NoSQL은 관계형 테이블 구조만을 사용하지 않는 **비관계형 데이터베이스들의 통칭**

NoSQL은 하나의 특정 데이터 저장 방식이 아니라 여러 종류를 포함

| 종류 | 저장 방식 | 대표 제품 |
| --- | --- | --- |
| 문서형 | JSON과 비슷한 문서 | MongoDB |
| Key-Value형 | Key와 Value | Redis |
| Wide-Column형 | 분산된 열 중심 구조 | Cassandra |
| 그래프형 | 노드와 관계 | Neo4j |

예를 들어 MongoDB에서는 회원과 주문 정보를 하나의 문서 안에 함께 넣을 수 있다.

```plain text
{
  "memberId":1,
  "name":"은혜민",
  "email":"hm@example.com",
  "orders": [
    {
      "orderId":101,
      "product":"키보드"
    },
    {
      "orderId":102,
      "product":"마우스"
    }
  ]
}
```

MongoDB는 같은 컬렉션의 문서가 반드시 동일한 필드를 가질 필요가 없는 유연한 스키마를 지원하며,

관련 데이터를 객체나 배열로 문서 내부에 포함할 수 있다.

다만 필요하면 스키마 검증 규칙도 설정할 수 있다.

## 핵심 차이

| 구분 | RDB | NoSQL |
| --- | --- | --- |
| 데이터 구조 | 행·열 기반 테이블 | 문서, Key-Value, 그래프 등 |
| 스키마 | 비교적 명확하고 엄격함 | 비교적 유연함 |
| 관계 표현 | PK·FK와 JOIN | 문서 포함, 참조, 그래프 관계 등 |
| 질의 방식 | 주로 SQL | 제품별 질의 언어·API |
| 정규화 | 주로 정규화 | 반정규화·데이터 중복을 자주 활용 |
| 트랜잭션 | 복수 테이블 트랜잭션에 강함 | 제품과 데이터 모델에 따라 다름 |
| 확장 방식 | 전통적으로 수직 확장 중심 | 수평 확장을 고려한 제품이 많음 |
| 적합한 데이터 | 관계가 명확한 정형 데이터 | 구조가 다양하거나 빠르게 변하는 데이터 |
| 대표 용도 | 금융, 주문, 회계, 인사 | 로그, 캐시, SNS, 추천, 대규모 이벤트 |

## 스키마의 차이

### RDB

테이블을 생성할 때 컬럼과 자료형을 먼저 정의

```plain text
CREATETABLE member (
    member_id NUMBERPRIMARYKEY,
    name VARCHAR2(30)NOTNULL,
    email VARCHAR2(100)UNIQUE
);
```

이후 저장되는 회원 데이터는 기본적으로 이 구조를 따라야 한다.

```plain text
member_id → 숫자
name      → 문자열, NULL 불가
email     → 문자열, 중복 불가
```

따라서 데이터 구조가 명확하고 잘못된 값이 저장되는 것을 통제하기 좋다.

---

### NoSQL 문서형 DB

문서별로 다른 필드를 가질 수 있다.

```plain text
{
  "name":"은혜민",
  "email":"hm@example.com"
}
```

```plain text
{
  "name":"김민수",
  "phone":"010-0000-0000",
  "interests": ["여행","개발"]
}
```

새로운 필드가 필요할 때 기존 테이블 전체 구조를 변경하지 않고 추가하기 쉽다.

하지만 자유롭게 저장하기만 하면 데이터 구조가 제각각이 될 수 있으므로

**애플리케이션 검증**이나 **데이터베이스의 스키마 검증 기능**이 필요
