# 5-4. 기본키는 인덱스라고 할 수 있을까요? 그렇지 않다면, 인덱스와 기본키는 어떤 차이가 있나요?

결론부터 말하면, **기본키(PK) 자체가 인덱스인 것은 아니지만, 대부분의 DBMS는 기본키를 생성하면 인덱스를 자동으로 생성합니다.**

### 기본키(PK)와 인덱스(Index)의 차이

| 구분 | 기본키(PK) | 인덱스(Index) |
| --- | --- | --- |
| 목적 | 행을 **유일하게 식별** | 데이터를 **빠르게 조회** |
| 중복 | ❌ 불가능 | ⭕ 가능 |
| NULL | ❌ 불가능 | ⭕ 일반 인덱스는 가능 |
| 개수 | 테이블당 **1개** | 여러 개 생성 가능 |
| 역할 | 데이터 무결성 제약조건 | 조회 성능 향상을 위한 자료구조 |
| 생성 시 | 보통 인덱스 자동 생성 | 직접 생성 가능 |

예를 들어 다음과 같은 테이블이 있다고 해보겠습니다.

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50),
    email VARCHAR(100)
);
```

여기서 `id`는 **기본키**입니다.

```plain text
id(PK)
1 → 김철수
2 → 이영희
3 → 박민수
```

DB는 `id`를 이용해 각 행을 유일하게 구분해야 합니다. 그리고 대부분의 DBMS에서는 PK를 빠르게 찾고 중복 여부를 검사하기 위해 **PK에 대응하는 인덱스를 자동으로 생성**합니다.

반면 다음과 같이 만들 수도 있습니다.

```sql
CREATE INDEX idx_users_name
ON users(name);
```

`name`은 기본키가 아니지만 검색 성능을 높이기 위해 인덱스를 만들 수 있습니다.

```sql
SELECT *
FROM users
WHERE name = '김철수';
```

### 그러면 "PK = Index"라고 하면 틀린 걸까?

엄밀하게는 **틀립니다.**

> **PK는 제약조건(Constraint)이고, Index는 검색 성능을 높이기 위한 자료구조입니다.**

다만 PK의 `UNIQUE`, `NOT NULL` 성질을 효율적으로 보장하고 PK 조회를 빠르게 하기 위해 **DBMS가 PK 생성 시 인덱스를 함께 생성하는 경우가 일반적**입니다.

그리고 DBMS에 따라 구현 방식도 조금 다릅니다. 특히 **MySQL InnoDB에서는 PK가 클러스터드 인덱스(Clustered Index)가 되어 실제 데이터가 PK 순서의 B+Tree 리프 페이지에 저장**됩니다. 그래서 MySQL을 공부하다 보면 `PK = 클러스터드 인덱스`처럼 느껴질 수 있습니다.

### 한 줄 정리

**기본키는 행을 유일하게 식별하기 위한 제약조건이고, 인덱스는 검색 성능을 높이기 위한 자료구조이다. 기본키 자체가 인덱스인 것은 아니지만, 대부분의 DBMS는 기본키를 설정하면 이를 효율적으로 관리하기 위한 인덱스를 자동으로 생성한다.**

<summary>추가로 나올 수 있는 질문</summary>

- **기본키를 생성하면 왜 인덱스가 자동으로 생성되나요?**
→ PK의 유일성을 검사하고 `WHERE id = ?` 같은 조회를 빠르게 하기 위해서.

  - **기본키와 UNIQUE 제약조건의 차이는 무엇인가요?**
→ PK는 테이블당 하나이고 `NULL`이 불가능. UNIQUE는 여러 개 설정할 수 있고 `NULL` 허용 여부는 DBMS마다 차이가 있음.

  - **UNIQUE INDEX와 일반 INDEX의 차이는 무엇인가요?**
→ 일반 인덱스는 중복 값을 허용하지만, UNIQUE INDEX는 중복 값을 허용하지 않음.

  - **기본키가 없어도 인덱스를 만들 수 있나요?**
→ 가능. 조회가 자주 발생하는 컬럼에 별도의 인덱스를 생성할 수 있음.

  - **인덱스가 많으면 무조건 좋은가요?** ⭐
→ 아님. 조회는 빨라질 수 있지만 `INSERT/UPDATE/DELETE` 때 인덱스도 같이 수정해야 해서 쓰기 성능과 저장 공간에 비용이 발생함.

  - **인덱스는 어떤 자료구조로 만들어지나요?** ⭐
→ 일반적으로 **B-Tree/B+Tree 계열**을 사용. DBMS에 따라 Hash 등의 인덱스도 존재.

  - **왜 인덱스에 B+Tree를 많이 사용하나요?** ⭐
→ 탐색이 빠르고 정렬된 상태를 유지하기 때문에 **범위 검색(****`>`****, ****`<`****, ****`BETWEEN`****)과 정렬**에도 유리함.

  - **클러스터드 인덱스와 논클러스터드(Secondary) 인덱스의 차이는?** ⭐
→ 클러스터드 인덱스는 실제 데이터 저장 구조와 밀접하게 연결되고, Secondary Index는 별도의 인덱스 구조를 만들어 데이터 위치를 찾음.

  - **MySQL InnoDB에서 기본키는 어떤 인덱스가 되나요?**
→ PK가 **클러스터드 인덱스**가 됨. 따라서 PK 설계가 저장 구조와 성능에도 영향을 줌.

  - **기본키를 UUID로 설정하면 어떤 문제가 생길 수 있나요?** ⭐
→ 랜덤 UUID를 PK로 사용하면 B+Tree 중간에 데이터가 삽입되는 일이 많아져 페이지 분할, 인덱스 크기 증가 등 성능 문제가 발생할 수 있음.

  - **복합 기본키에도 인덱스가 생성되나요?**
→ 생성됨. `(user_id, group_id)`가 PK라면 두 컬럼을 이용한 복합 인덱스가 만들어짐.

  - **복합 인덱스에서 컬럼 순서가 중요한 이유는?** ⭐⭐⭐
→ **Leftmost Prefix(최좌측 접두사) 원칙** 때문. `(A, B)` 인덱스는 보통 `A`, `A+B` 검색에는 효과적이지만 `B`만 검색할 때는 제대로 활용하기 어려움.
