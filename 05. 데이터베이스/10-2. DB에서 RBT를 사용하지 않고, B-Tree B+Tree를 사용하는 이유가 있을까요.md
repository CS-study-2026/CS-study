# 10-2. DB에서 RBT를 사용하지 않고, B-Tree/B+Tree를 사용하는 이유가 있을까요?

> 

DB에서 Red-Black Tree와 같은 이진 탐색 트리보다 B-Tree나 B+Tree를 주로 사용하는 가장 큰 이유는 **디스크 I/O를 줄이기 위해서입니다.**

Red-Black Tree는 한 노드에 하나의 키를 저장하고 최대 두 개의 자식만 가지기 때문에 데이터가 많아지면 트리의 높이가 상대적으로 커집니다. 반면 B-Tree 계열은 하나의 노드에 여러 개의 키와 자식 포인터를 저장할 수 있어서 트리의 높이를 훨씬 낮게 만들 수 있습니다.

데이터베이스에서는 한 번의 디스크 접근으로 페이지 단위의 데이터를 읽기 때문에, 한 페이지에 많은 키를 저장할 수 있는 B-Tree 계열이 유리합니다. 트리의 높이가 낮아지면 검색 과정에서 필요한 디스크 I/O 횟수도 줄어듭니다.

특히 B+Tree는 실제 데이터를 리프에 모으고 리프 노드를 연결하기 때문에 **범위 검색과 정렬된 순차 접근에도 효율적**입니다.

따라서 DB에서는 단순히 CPU에서의 비교 연산을 빠르게 하는 것보다 **디스크 I/O를 줄이는 것이 중요하기 때문에 B-Tree/B+Tree가 적합합니다.**

---

## 1️⃣ RBT(Red-Black Tree)란?

**[Red-Black Tree](/p/2f54f7753cf2805ebe7ae3af8fdcfb7f)**는 균형을 유지하는
대표적인 **Balanced Binary Search Tree**이다.

각 노드에 색상(Red / Black)을 부여하고
규칙을 유지하면서 트리의 높이를 제한한다.

```plain text
        20(B)
       /    \
    10(R)   30(R)
```

따라서 탐색, 삽입, 삭제를
일반적으로 **O(log N)**에 수행할 수 있다.

---

## 2️⃣ 그렇다면 RBT도 O(log N)인데 왜 DB에서는 안 쓸까?

여기서 중요한 것은

> **시간복잡도만으로 자료구조를 선택하지 않는다는 것**

이다.

DB에서는 데이터가 주로

```plain text
CPU
 ↓
Memory
 ↓
Disk / SSD
```

에 존재한다.

특히 디스크 접근은
CPU의 메모리 접근보다 훨씬 큰 비용이 발생할 수 있다.

따라서 DB에서는

> **"몇 번 비교했는가?"**

보다

> **"몇 번 디스크 페이지에 접근했는가?"**

가 중요하다.

---

## 3️⃣ RBT의 구조적 한계

RBT는 이진 트리이기 때문에

```plain text
한 노드
 ├── Key
 ├── Left Child
 └── Right Child
```

형태를 가진다.

즉, 한 노드가 최대 2개의 자식만 가진다.

데이터가 많아질수록

```plain text
           O
          / \
         O   O
        / \
       O   O
      / \
     ...
```

트리의 높이가 증가한다.

➡️ 탐색 과정에서 더 많은 노드를 방문해야 함

➡️ DB에서는 더 많은 페이지 접근으로 이어질 수 있음

---

## 4️⃣ B-Tree 계열은 여러 키를 저장

B-Tree는 한 노드에 여러 키를 저장할 수 있다.

```plain text
              [10 | 20 | 30 | 40]
            /    |    |    |    \
          ...   ...  ...  ...   ...
```

하나의 노드가 많은 자식을 가질 수 있기 때문에

```plain text
RBT

       O
      / \
     O   O
    / \
   O   O
   ...
```

보다

```plain text
B-Tree

       [10 | 20 | 30 | 40]
      /    |    |    |    \
    ...   ...  ...  ...   ...
```

처럼 훨씬 낮은 높이를 만들 수 있다.

---

## 5️⃣ 핵심: 디스크 I/O 감소

DB는 데이터를 **페이지(Page)** 단위로 디스크에서 읽어온다.

B-Tree의 하나의 노드를
하나의 페이지에 대응시키면,

```plain text
Disk Page
┌───────────────────────────┐
│ 10 | 20 | 30 | 40 | ...  │
│ child | child | child ... │
└───────────────────────────┘
```

한 번의 디스크 I/O로
여러 키를 가져올 수 있다.

따라서

```plain text
여러 키 / 여러 자식
        ↓
트리 높이 감소
        ↓
페이지 접근 횟수 감소
        ↓
디스크 I/O 감소
```

➡️ 대규모 데이터베이스에서 큰 장점

---

## 6️⃣ RBT vs B-Tree

| 구분 | Red-Black Tree | B-Tree |
| --- | --- | --- |
| 트리 종류 | 이진 균형 트리 | 다방향 균형 트리 |
| 한 노드의 키 | 일반적으로 1개 | **여러 개** |
| 자식 수 | 최대 2개 | **여러 개** |
| 높이 | 상대적으로 높음 | **낮음** |
| 탐색 | O(log N) | O(log N) |
| 주요 장점 | 메모리 기반 탐색 | **디스크 기반 탐색** |
| DB 인덱스 | 일반적으로 사용하지 않음 | **널리 사용** |

> 💡 둘 다 O(log N)이지만, **DB에서는 상수항과 메모리/디스크 접근 비용이 매우 중요하다.**

---

## 7️⃣ B+Tree는 여기서 한 단계 더 최적화

B+Tree는

```plain text
Internal Node
→ 탐색용 Key

Leaf Node
→ 실제 Data
```

형태로 데이터를 구성한다.

그리고

```plain text
[10 | 20] → [30 | 40] → [50 | 60]
```

처럼 리프 노드를 연결한다.

따라서

### 단일 검색

```plain text
Root
 ↓
Internal
 ↓
Leaf
 ↓
Data
```

### 범위 검색

```plain text
Root
 ↓
첫 번째 값 탐색
 ↓
Leaf → Leaf → Leaf → Leaf
```

➡️ 범위 검색을 효율적으로 수행할 수 있다.

---

## 8️⃣ DB 인덱스 관점에서 정리

DB 인덱스의 목적은

> **원하는 데이터를 빠르게 찾기 위해 전체 데이터를 모두 탐색하지 않는 것**

이다.

B+Tree를 사용하면

```plain text
전체 테이블

1 2 3 4 5 6 7 8 9 ...
        ↓
      Index
        ↓
   필요한 페이지
        ↓
      Data
```

처럼 검색 범위를 빠르게 좁힐 수 있다.

특히 범위 조건에서는

```sql
WHERE id BETWEEN 100 AND 200
```

처럼 시작 지점을 찾은 후
연결된 리프를 순차적으로 탐색할 수 있다.

---

## 9️⃣ 중요한 포인트

### ❌ "RBT는 O(log N)이라 DB에서 느리다"

정확하지 않음.

### ✅ "RBT도 O(log N)이지만, DB에서는 디스크 I/O가 중요하기 때문에 다방향 트리가 유리하다"

이렇게 설명하는 것이 정확하다.

---

## 📌 핵심 정리

### RBT

```plain text
이진 트리
→ 한 노드에 적은 키
→ 트리 높이가 상대적으로 높음
→ 디스크 접근 횟수가 증가할 수 있음
```

### B-Tree / B+Tree

```plain text
다방향 트리
→ 한 노드에 여러 키
→ 트리 높이 감소
→ 한 페이지에서 많은 키 처리
→ 디스크 I/O 감소
```

### B+Tree

```plain text
+ 리프 노드 연결
+ 범위 검색 효율
+ 순차 접근 효율
```

➡️ **따라서 DB 인덱스에서는 CPU 연산 횟수보다 디스크 I/O를 줄이는 것이 중요하기 때문에 B-Tree/B+Tree 계열이 적합하다.**
