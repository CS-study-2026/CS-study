# **2-5.** Load Factor에 대해 설명하고, 본인 언어의 해시 자료구조 정책을 설명해 주세요.

# 📦 Load Factor & 해시 자료구조 정책

## 1️⃣ Load Factor 개념

### 📌 정의

- 해시 테이블이 **얼마나 채워져 있는지**를 나타내는 지표

- 충돌 발생 가능성과 성능을 예측하는 핵심 요소

### 📐 공식

**Load Factor = n / m**

| 기호 | 의미 |
| --- | --- |
| n | 저장된 데이터 개수 |
| m | 해시 테이블 버킷 수 |

👉 값이 클수록 테이블이 많이 차 있음

👉 값이 작을수록 여유 공간이 많음

---

## 2️⃣ Load Factor가 중요한 이유

### 📈 Load Factor 증가 시

- 충돌 확률 증가

- 탐사 길이 증가

- 탐색 성능 저하

➡️ 평균 O(1) → O(n)에 가까워질 수 있음

### 📉 Load Factor 감소 시

- 충돌 감소

- 성능 향상

하지만

⚠️ 메모리 낭비 발생

### 📌 Load Factor와 성능 관계

| Load Factor | 상태 | 특징 |
| --- | --- | --- |
| 낮음 (≤ 0.5) | 여유 | 빠르지만 메모리 낭비 |
| 적정 (0.5 ~ 0.75) | 균형 | 일반적인 목표 |
| 높음 (≥ 0.9) | 과밀 | 충돌 급증 |

👉 Load Factor는 **성능과 메모리 사용량 사이의 균형 지표**

---

## 3️⃣ Resize (Rehash)의 역할

Load Factor가 임계치를 넘으면

- 테이블 크기 확장

- 모든 데이터를 다시 해싱

➡️ 평균 O(1) 성능 유지

---

## 4️⃣ Java HashMap 정책

### 📌 기본 설정

- 기본 용량: **16**

- 기본 Load Factor: **0.75**

👉 임계값 = capacity × load factor

### 📌 Resize 전략

- 임계값 초과 시

➡️ 버킷 수 **2배 증가**

- 모든 요소 재해싱 수행

### 📌 충돌 처리 방식

1️⃣ 기본: Separate Chaining (Linked List)

2️⃣ 충돌이 심한 경우

➡️ 버킷 크기 ≥ 8

➡️ **Red-Black Tree로 변환**

👉 최악 시간 복잡도 O(log n) 보장

### 📌 왜 0.75인가

- 메모리 효율성과 성능의 균형점

- 충돌 증가 전 성능 유지 가능한 임계값

---

## 5️⃣ 실무에서의 의미

✔️ 대규모 데이터 처리 시 성능 튜닝 기준

✔️ 캐시, 세션 저장소 설계 핵심 요소

✔️ 초기 용량 설정으로 리사이징 비용 감소

✔️ 성능 문제 원인 분석 지표

---

## 📌 핵심 정리

- Load Factor는 **테이블 사용 밀도**로, 해시 테이블 성능을 좌우하는 핵심 지표

- 충돌 확률과 성능을 직접적으로 결정

- 일반적으로 **0.75 수준 유지**

- Java HashMap은
👉 체이닝 + 리사이징(2배 확장) + 트리화 전략으로
평균 O(1), 최악 O(log n) 보장
