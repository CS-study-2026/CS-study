# **7-4. 타 스케줄러와 비교하여, Multi-level Feedback Queue(MLFQ)는 어떤 문제점들을 해결한다고 볼 수 있을까요?**

MLFQ는 현대 운영체제(Windows, Mac OS 등)가 사용하는 **가장 완성도 높은 스케줄링 알고리즘**.

기존 알고리즘들이 가진 여러 단점을 **피드백(Feedback)**이라는 규칙을 통해 한 번에 해결.

| **분류** | **알고리즘** | **핵심 전략** | **단점 및 비고** |
| --- | --- | --- | --- |
| **비선점**
_(신사적인 방식)_
- 한번 CPU를 차지하면 스스로 내려놓기 전까지 계속 사용 | **FCFS**
(First-Come, First-Served) | 먼저 온 번호표 순서대로 처리 | **콘보이 효과(Convoy Effect) 발생**
(앞에 1시간 걸리는 손님이 있으면, 뒤에 1초면 끝날 손님도 1시간 대기) |
|   | **SJF**
(Shortest Job First) | 업무 시간이 가장 짧은 사람부터 먼저 처리 | **기아 현상(Starvation) 발생**
(짧은 손님들이 계속 들어오면, 긴 업무를 가진 손님은 평생 자기 차례가 안 옴) |
|   | **HRN**
(Highest Response-ratio Next) | SJF의 단점을 보완하여 "기다린 시간"까지 고려 | **공식:**
`(대기 시간 + 서비스 시간) / 서비스 시간` |
| **선점**
_(현대적인 방식)_
- Windows, Mac OS 등 대부분의 현대 OS가 사용 | **라운드 로빈**
(Round Robin, RR) | '시간 할당량(Time Quantum)'을 정해두고, 그 시간이 지나면 무조건 다음 사람으로 넘김 | 모든 프로세스가 공평하게 CPU를 선점.
**현대 OS의 기초** |
|   | **SRTF**
(Shortest Remaining Time First) | SJF의 선점 버전. 현재 하고 있는 일보다 **더 빨리 끝날 것 같은 손님이 오면 자리를 뺏음** | 계속해서 남은 시간을 비교하며 스케줄링 |

### 💡 기존 알고리즘들의 문제점과 MLFQ의 해결책

1. **SJF / SRTF의 문제: "미래를 알아야 한다" → 과거의 데이터로 예측**

  - **문제:** 이 알고리즘들은 `가장 빨리 끝나는 프로세스`를 미리 알아야 작동. 하지만 OS가 프로세스의 실행 시간을 미리 정확히 아는 것은 불가능.

  - **MLFQ의 해결 (과거 관찰):** 프로세스가 들어오면 일단 가장 높은 우선순위 큐(줄)에 넣음. 그리고 행동을 관찰(Feedback). 주어진 시간(Time Quantum)을 다 써버리면 **오래 걸린다고 예측**하고 우선순위를 한 단계 낮춤. (미래를 예측하는 대신 행동을 보고 강등)

1. **라운드 로빈(RR)의 문제: "응답 시간 vs 오버헤드"**

  - **문제:** 모든 프로세스에게 똑같이 짧은 시간을 주면, 빠르게 끝내야 하는 작업(키보드 입력 등)은 좋지만, 아주 무거운 계산을 하는 작업은 너무 자주 자리를 비켜줘야 해서 문맥 교환(Context Switching) 오버헤드가 커짐.

  - **MLFQ의 해결 (큐마다 다른 시간 할당):** 우선순위가 높은 큐(짧은 작업 위주)는 시간을 아주 짧게 줘서 응답 속도를 극대화. 우선순위가 낮아져 맨 밑으로 떨어진 무거운 작업들은 시간을 길게 줘서, 한 번 CPU를 잡았을 때 오랫동안 계산에 집중 가능.

1. **우선순위 스케줄링의 문제: "기아 현상(Starvation)"**

  - **문제:** 짧고 우선순위가 높은 작업만 계속 들어오면, 우선순위가 낮은 무거운 작업은 실행 못함.

  - **MLFQ의 해결 (에이징, Aging):** 밑바닥 큐에서 너무 오래 기다린 프로세스가 있다면, OS가 우선순위를 다시 가장 위로 올림. (승격 피드백)
