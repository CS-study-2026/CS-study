# 17-5. 세그멘테이션 방식을 사용하고 있다면, 가상 메모리를 사용할 수 없을까요?

# 17-5. 세그멘테이션 방식을 사용하고 있다면, 가상 메모리를 사용할 수 없을까요?

## 1. 결론부터

아니. **세그멘테이션을 사용해도 가상 메모리를 사용할 수 있어.**

둘은 서로 배타적인 개념이 아니야.

정확히 말하면:

> 가상 메모리는 프로세스에게 실제 물리 메모리보다 크고 독립적인 주소 공간을 제공하는 메모리 관리 기법이고,

세그멘테이션은 그 가상 주소 공간을 논리적인 단위인 segment로 나누는 주소 변환 방식 중 하나다.

즉, 세그멘테이션은 가상 메모리를 구현하는 방식 중 하나가 될 수 있어.

---

# 2. 가상 메모리와 세그멘테이션의 차이

## 가상 메모리

가상 메모리의 핵심은 이거야.

```plain text
프로세스는 가상 주소를 사용한다.
OS와 하드웨어가 가상 주소를 물리 주소로 변환한다.
필요한 데이터만 물리 메모리에 올릴 수 있다.
물리 메모리에 없으면 디스크에서 가져올 수 있다.
```

즉, 가상 메모리는 **추상화 개념**이야.

---

## 세그멘테이션

세그멘테이션은 주소 공간을 논리적인 단위로 나누는 방식이야.

예를 들어 프로세스의 주소 공간을 이렇게 나눌 수 있어.

```plain text
Code Segment
Data Segment
Heap Segment
Stack Segment
```

각 segment는 크기가 다를 수 있어.

세그멘테이션에서 가상 주소는 보통 이렇게 구성돼.

```plain text
| Segment Number | Offset |
```

예를 들어:

```plain text
Segment Number = 2
Offset = 100
```

이면,

```plain text
2번 segment의 시작 주소 + 100
```

으로 실제 주소를 계산한다.

---

# 3. 세그멘테이션 주소 변환

세그멘테이션에서는 segment table을 사용해.

segment table에는 보통 이런 정보가 들어간다.

| 항목 | 의미 |
| --- | --- |
| Base | 해당 segment가 물리 메모리에서 시작하는 주소 |
| Limit | segment의 크기 |
| Protection bit | 읽기/쓰기/실행 권한 |
| Present bit 또는 Valid bit | 현재 메모리에 올라와 있는지 여부 |

주소 변환은 이렇게 진행돼.

```plain text
1. CPU가 가상 주소 생성
   예: segment 번호 + offset

2. segment table에서 해당 segment entry 확인

3. offset이 limit보다 작은지 검사

4. 권한 검사

5. base + offset으로 물리 주소 계산
```

예를 들어:

```plain text
Segment 1
Base = 10000
Limit = 4000

가상 주소:
Segment = 1
Offset = 300
```

그러면 물리 주소는:

```plain text
10000 + 300 = 10300
```

이 된다.

만약 offset이 limit보다 크면?

```plain text
Offset = 5000
Limit = 4000
```

이건 segment 범위를 벗어난 접근이므로 오류가 발생한다.

---

# 4. 세그멘테이션에서도 Page Fault 같은 일이 가능한가?

가능해.

세그멘테이션에서는 페이지 단위가 아니라 **segment 단위로 메모리에 올라오거나 내려갈 수 있어.**

예를 들어 어떤 segment가 현재 물리 메모리에 없다고 하자.

```plain text
Segment 3
Present bit = 0
```

프로세스가 Segment 3에 접근하면 OS는 이 segment가 유효한 segment인지 확인하고, 유효하다면 디스크에서 물리 메모리로 가져올 수 있어.

즉, paging에서는 page fault가 발생하고, segmentation에서는 비슷하게 **segment fault** 또는 segment-not-present 예외가 발생할 수 있어.

핵심은 이거야.

> 가상 주소가 가리키는 대상이 현재 물리 메모리에 없으면, OS가 디스크에서 가져와 실행을 계속할 수 있다.

이게 가상 메모리의 핵심이기 때문에, 세그멘테이션에서도 가상 메모리 구현이 가능해.

---

# 5. 그러면 왜 현대 시스템은 주로 페이징을 쓰나?

세그멘테이션만으로도 가상 메모리를 구현할 수 있지만, 단점이 있어.

가장 큰 문제는 **외부 단편화**야.

## 세그멘테이션은 크기가 가변적이다

segment는 논리 단위라서 크기가 제각각이야.

```plain text
Code Segment: 20MB
Data Segment: 5MB
Heap Segment: 100MB
Stack Segment: 8MB
```

이런 가변 크기 블록들을 물리 메모리에 배치하면 중간중간 빈 공간이 생기기 쉽다.

```plain text
[Segment A 20MB][빈 공간 3MB][Segment B 50MB][빈 공간 5MB][Segment C 10MB]
```

전체 빈 공간은 8MB지만, 8MB짜리 segment 하나를 넣을 연속 공간이 없을 수 있어.

이게 외부 단편화야.

---

## 페이징은 고정 크기라 외부 단편화가 없다

페이징에서는 메모리를 고정 크기의 page/frame으로 나눠.

```plain text
Page size = 4KB
Frame size = 4KB
```

모든 단위가 같기 때문에 어디에 넣어도 된다.

```plain text
가상 페이지 0 → 물리 프레임 10
가상 페이지 1 → 물리 프레임 3
가상 페이지 2 → 물리 프레임 99
```

연속된 물리 메모리 공간이 필요하지 않아.

그래서 대규모 가상 메모리 관리에는 페이징이 더 적합하다.

---

# 6. 세그멘테이션과 페이징을 같이 쓸 수도 있다

중요한 포인트야.

세그멘테이션과 페이징은 같이 사용할 수도 있어.

이 방식은 대략 이렇게 동작해.

```plain text
가상 주소
= Segment Number + Page Number + Offset
```

처리 흐름은:

```plain text
1. Segment Number로 segment table을 찾는다.
2. 해당 segment 안의 page table을 찾는다.
3. Page Number로 물리 frame을 찾는다.
4. Offset을 더해 실제 물리 주소를 만든다.
```

즉:

```plain text
세그먼트로 논리적 구분
+ 페이지로 고정 크기 메모리 관리
```

를 동시에 하는 거야.

이렇게 하면 세그멘테이션의 장점인 논리적 보호/구분과, 페이징의 장점인 외부 단편화 감소를 함께 얻을 수 있어.

---

# 7. 발표에서 주의할 점

이 질문에서 가장 흔한 오답은 이거야.

> 세그멘테이션은 연속 할당 방식이니까 가상 메모리를 못 쓴다.

이건 틀렸어.

정확히는:

```plain text
순수 세그멘테이션에서는 각 segment가 물리 메모리에서 연속 공간을 차지해야 할 수 있다.
그래서 외부 단편화 문제가 있다.

하지만 segment 전체를 필요할 때 메모리에 올리고 내리는 방식으로 가상 메모리를 구현할 수 있다.
또는 segmentation + paging을 결합해서 가상 메모리를 구현할 수도 있다.
```

즉, 세그멘테이션의 단점이 있을 뿐이지, 가상 메모리 자체가 불가능한 건 아니야.

---

# 8. Page Fault와 연결해서 설명하기

17-2에서 Page Fault를 설명했다면, 여기서는 이렇게 연결하면 좋다.

페이징에서는 접근한 페이지가 물리 메모리에 없으면 Page Fault가 발생한다.

```plain text
Page table entry
Present bit = 0
→ Page Fault
```

세그멘테이션에서도 비슷하게 접근한 segment가 물리 메모리에 없으면 예외가 발생할 수 있다.

```plain text
Segment table entry
Present bit = 0
→ Segment not present
→ OS가 디스크에서 segment를 가져올 수 있음
```

둘 다 핵심은 같아.

> 가상 주소 공간의 일부가 현재 물리 메모리에 없어도, 필요할 때 디스크에서 가져와 실행을 계속할 수 있다.

---

# 세그먼트와 페이징

좋아. 세그먼트는 처음 들으면 페이지랑 섞여서 헷갈리기 쉬워.

핵심부터 잡으면 이거야.

> **세그먼트는 프로그램의 메모리를 “의미 있는 덩어리”로 나눈 것**이야.

페이지가 **고정 크기 조각**이라면, 세그먼트는 **논리적 의미를 가진 가변 크기 조각**이라고 보면 돼.

---

# 1. 프로그램의 메모리는 여러 영역으로 나뉜다

프로그램이 실행되면 메모리 안에는 여러 종류의 데이터가 들어가.

예를 들어 Java든 C든 프로그램을 실행하면 대략 이런 것들이 필요해.

```plain text
프로그램 코드
전역 변수
동적 할당 영역
함수 호출 정보
지역 변수
```

운영체제 관점에서는 이걸 논리적으로 나눠서 볼 수 있어.

```plain text
Code Segment   : 실행할 명령어들
Data Segment   : 전역 변수, static 변수
Heap Segment   : 동적으로 할당되는 메모리
Stack Segment  : 함수 호출, 지역 변수, 매개변수
```

이렇게 **의미별로 나눈 메모리 영역 하나하나가 세그먼트**야.

---

# 2. 페이지와 세그먼트의 가장 큰 차이

페이지와 세그먼트를 비교하면 바로 이해가 쉬워.

| 구분 | 페이지 | 세그먼트 |
| --- | --- | --- |
| 나누는 기준 | 고정 크기 | 논리적 의미 |
| 크기 | 보통 4KB 같은 고정 크기 | 영역마다 다름 |
| 예시 | page 0, page 1, page 2 | code, data, heap, stack |
| 장점 | 메모리 관리가 쉬움 | 프로그램 구조와 잘 맞음 |
| 단점 | 의미 없이 잘림 | 외부 단편화 발생 가능 |

페이지는 이렇게 잘라.

```plain text
[4KB][4KB][4KB][4KB][4KB]
```

반면 세그먼트는 이렇게 나눠.

```plain text
[Code 20KB][Data 8KB][Heap 100KB][Stack 16KB]
```

즉, 페이지는 **기계적으로 같은 크기로 자르는 방식**이고,

세그먼트는 **프로그램의 의미에 맞게 자르는 방식**이야.

---

# 3. 세그먼트는 왜 필요한가?

세그먼트의 장점은 프로그램을 사람이 이해하는 구조와 비슷하게 관리할 수 있다는 거야.

예를 들어 코드 영역은 읽기와 실행만 가능해야 해.

```plain text
Code Segment
- 읽기 가능
- 실행 가능
- 쓰기 불가능
```

전역 변수 영역은 읽고 쓸 수 있어야 해.

```plain text
Data Segment
- 읽기 가능
- 쓰기 가능
- 실행 불가능
```

스택 영역은 함수 호출마다 커졌다 작아졌다 해.

```plain text
Stack Segment
- 함수 호출 시 증가
- 함수 종료 시 감소
```

이런 식으로 세그먼트 단위로 권한과 역할을 나누면 관리가 직관적이야.

---

# 4. 세그멘테이션이란?

**세그멘테이션**은 메모리를 세그먼트 단위로 나누어 관리하는 메모리 관리 방식이야.

즉:

> 세그먼트 = 나눠진 논리적 메모리 덩어리

세그멘테이션 = 세그먼트 단위로 메모리를 관리하는 방식

---

# 5. 세그먼트 주소는 어떻게 생겼나?

페이징에서는 가상 주소가 보통 이렇게 나뉘어.

```plain text
| Page Number | Offset |
```

세그멘테이션에서는 주소가 이렇게 나뉘어.

```plain text
| Segment Number | Offset |
```

예를 들어 이런 주소가 있다고 해보자.

```plain text
Segment Number = 2
Offset = 300
```

이 뜻은:

> 2번 세그먼트의 시작 지점에서 300만큼 떨어진 위치

라는 뜻이야.

---

# 6. 세그먼트 테이블

CPU가 `Segment Number + Offset` 주소를 만들면, OS와 하드웨어는 **세그먼트 테이블**을 확인해.

세그먼트 테이블에는 각 세그먼트에 대한 정보가 들어 있어.

| 항목 | 의미 |
| --- | --- |
| Segment Number | 세그먼트 번호 |
| Base | 물리 메모리에서 세그먼트가 시작하는 주소 |
| Limit | 세그먼트의 크기 |
| Protection | 읽기/쓰기/실행 권한 |
| Present bit | 현재 RAM에 올라와 있는지 여부 |

예를 들어 세그먼트 테이블이 이렇게 생겼다고 하자.

| Segment | Base | Limit | 권한 |
| --- | --- | --- | --- |
| 0번 Code | 1000 | 500 | Read, Execute |
| 1번 Data | 3000 | 300 | Read, Write |
| 2번 Stack | 5000 | 700 | Read, Write |

---

# 7. 주소 변환 예시

CPU가 이런 주소에 접근한다고 해보자.

```plain text
Segment Number = 1
Offset = 100
```

그러면 세그먼트 테이블에서 1번을 찾는다.

```plain text
1번 Data Segment
Base = 3000
Limit = 300
```

먼저 offset이 limit보다 작은지 확인해.

```plain text
Offset 100 < Limit 300
```

정상 접근이야.

그러면 물리 주소는 이렇게 계산돼.

```plain text
물리 주소 = Base + Offset
        = 3000 + 100
        = 3100
```

즉, 최종적으로 RAM의 3100번 위치에 접근하는 거야.

---

# 8. 잘못된 접근은 어떻게 막나?

이번에는 이런 주소에 접근한다고 해보자.

```plain text
Segment Number = 1
Offset = 500
```

1번 세그먼트의 limit은 300이었어.

```plain text
Offset 500 > Limit 300
```

그러면 이건 세그먼트 범위를 벗어난 접근이야.

OS는 이 접근을 막아.

```plain text
잘못된 메모리 접근
→ 예외 발생
→ 프로세스 종료 가능
```

우리가 흔히 말하는 **Segmentation Fault**도 이런 잘못된 메모리 접근과 관련 있어.

다만 현대 OS의 실제 Segmentation Fault는 순수 세그멘테이션만의 오류라기보다는, 더 넓게 “잘못된 메모리 접근”을 의미하는 경우가 많아.

---

# 9. 세그먼트는 크기가 다를 수 있다

이게 페이지와 다른 핵심이야.

세그먼트는 논리적 단위라서 크기가 제각각일 수 있어.

```plain text
Code Segment  : 20MB
Data Segment  : 5MB
Heap Segment  : 200MB
Stack Segment : 8MB
```

이런 식으로 각 영역의 크기가 달라.

그래서 사람이 보기에는 직관적인데, OS가 실제 RAM에 배치할 때는 문제가 생길 수 있어.

---

# 10. 세그멘테이션의 단점: 외부 단편화

세그먼트는 크기가 제각각이니까 물리 메모리에 배치하다 보면 중간중간 빈 공간이 생겨.

예를 들어 RAM 상태가 이렇다고 해보자.

```plain text
[세그먼트 A 100MB][빈 공간 20MB][세그먼트 B 200MB][빈 공간 30MB][세그먼트 C 150MB]
```

빈 공간을 합치면 50MB야.

```plain text
20MB + 30MB = 50MB
```

그런데 50MB짜리 세그먼트를 넣을 수 있을까?

못 넣을 수 있어.

왜냐하면 세그먼트는 보통 연속된 공간이 필요하기 때문이야.

```plain text
빈 공간 20MB 따로
빈 공간 30MB 따로
→ 연속된 50MB 공간은 없음
```

이걸 **외부 단편화**라고 해.

---

# 11. 외부 단편화 vs 내부 단편화

여기서 많이 헷갈리니까 같이 정리하면 좋아.

## 외부 단편화

메모리 사이사이에 빈 공간이 흩어져서 생기는 낭비.

```plain text
[사용중][빈칸][사용중][빈칸][사용중]
```

총 빈 공간은 충분한데, 연속된 공간이 부족해서 못 쓰는 상황이야.

세그멘테이션에서 주로 문제가 돼.

---

## 내부 단편화

할당받은 공간 안에서 일부가 낭비되는 것.

예를 들어 4KB 페이지를 할당했는데 실제로는 3KB만 쓴다면:

```plain text
[사용 3KB][낭비 1KB]
```

이게 내부 단편화야.

페이징에서 주로 문제가 돼.

---

# 12. 세그멘테이션의 장점

그래도 세그멘테이션은 장점이 있어.

## 1. 프로그램 구조와 잘 맞음

코드, 데이터, 힙, 스택처럼 의미 있는 단위로 관리할 수 있어.

```plain text
Code Segment
Data Segment
Heap Segment
Stack Segment
```

---

## 2. 보호가 쉽다

세그먼트마다 권한을 다르게 줄 수 있어.

| Segment | 권한 |
| --- | --- |
| Code | Read + Execute |
| Data | Read + Write |
| Stack | Read + Write |
| 공유 라이브러리 | Read + Execute |

예를 들어 코드 영역에 쓰려고 하면 막을 수 있어.

```plain text
Code Segment에 write 시도
→ 권한 위반
→ 예외 발생
```

---

## 3. 공유가 쉽다

여러 프로세스가 같은 코드 세그먼트를 공유할 수 있어.

예를 들어 같은 프로그램을 여러 번 실행하면 코드 자체는 같을 수 있지?

```plain text
프로세스 A → Code Segment X
프로세스 B → Code Segment X
프로세스 C → Code Segment X
```

읽기 전용 코드라면 굳이 여러 번 RAM에 올릴 필요 없이 공유할 수 있어.

---

## 4. 동적 성장에 자연스럽다

Heap이나 Stack처럼 실행 중에 크기가 변하는 영역을 논리적으로 관리하기 좋다.

```plain text
Heap Segment  : 동적 할당 시 증가
Stack Segment : 함수 호출 시 증가
```

---

# 13. 세그먼트와 가상 메모리의 관계

중요한 질문이 이거였지.

> 세그멘테이션을 쓰면 가상 메모리를 못 쓰나?

아니야. 쓸 수 있어.

가상 메모리의 핵심은:

```plain text
프로세스는 가상 주소를 사용한다.
OS와 하드웨어가 물리 주소로 변환한다.
필요한 부분만 RAM에 올릴 수 있다.
```

세그멘테이션에서도 이게 가능해.

세그먼트가 현재 RAM에 없다면:

```plain text
Segment table에서 Present bit = 0
→ 세그먼트가 RAM에 없음
→ OS가 디스크에서 가져옴
→ RAM에 적재
→ 다시 실행
```

즉, 페이지 단위가 아니라 **세그먼트 단위로 필요한 부분을 가져오는 가상 메모리**를 만들 수 있어.

---

# 14. 그런데 왜 현대 OS는 페이지를 더 많이 쓰나?

이유는 단순해.

> 페이징이 메모리 관리하기 더 쉽기 때문이야.

세그먼트는 크기가 제각각이라 외부 단편화가 생겨.

반면 페이지는 전부 같은 크기야.

```plain text
Page 4KB
Page 4KB
Page 4KB
Page 4KB
```

RAM도 같은 크기의 frame으로 나눠.

```plain text
Frame 4KB
Frame 4KB
Frame 4KB
Frame 4KB
```

그래서 아무 페이지나 빈 프레임에 넣으면 돼.

```plain text
가상 페이지 0 → 물리 프레임 8
가상 페이지 1 → 물리 프레임 3
가상 페이지 2 → 물리 프레임 15
```

연속된 물리 공간이 필요 없으니까 외부 단편화 문제가 크게 줄어.

---

# 15. 세그멘테이션 + 페이징 조합

실제로는 둘을 섞어서 쓸 수도 있어.

아이디어는 이거야.

```plain text
프로그램을 먼저 논리적 세그먼트로 나눔
각 세그먼트를 다시 페이지로 나눔
```

그럼 주소는 이런 식으로 볼 수 있어.

```plain text
| Segment Number | Page Number | Offset |
```

주소 변환은 대략 이렇게 진행돼.

```plain text
1. Segment Number로 세그먼트를 찾음
2. 그 세그먼트의 페이지 테이블을 찾음
3. Page Number로 물리 프레임을 찾음
4. Offset으로 프레임 안의 위치를 찾음
```

이 방식의 장점은 둘의 장점을 섞는 거야.

```plain text
세그멘테이션 장점:
- 논리적 구분
- 보호와 공유가 쉬움

페이징 장점:
- 고정 크기 관리
- 외부 단편화 감소
```

---

# 16. 그림으로 전체 비교

## 세그멘테이션

```plain text
가상 주소 공간

[ Code Segment ][ Data Segment ][ Heap Segment ][ Stack Segment ]

각 segment 크기가 다름
```

물리 메모리 배치:

```plain text
RAM

[ Code ][ 빈 공간 ][ Stack ][ Data ][ 빈 공간 ][ Heap ]
```

---

## 페이징

```plain text
가상 주소 공간

[Page][Page][Page][Page][Page][Page]
```

물리 메모리 배치:

```plain text
RAM

[Frame][Frame][Frame][Frame][Frame][Frame]
```

각 페이지는 아무 빈 프레임에나 들어갈 수 있어.

---

# 17. 쉽게 비유하면

## 세그먼트

책을 의미 있는 장 단위로 나눈 것과 비슷해.

```plain text
1장: 개념 설명
2장: 예제
3장: 문제 풀이
4장: 정답
```

각 장은 길이가 다르지?

```plain text
1장 20쪽
2장 5쪽
3장 40쪽
4장 10쪽
```

이게 세그먼트야.

의미는 분명하지만 크기는 제각각이야.

---

## 페이지

책을 무조건 10쪽씩 자르는 것과 비슷해.

```plain text
1~10쪽
11~20쪽
21~30쪽
31~40쪽
```

의미와 상관없이 크기가 같아.

이게 페이지야.

---

# 18. 발표용 답변으로 정리

그대로 말하면 이렇게 하면 돼.

> 세그먼트는 프로그램의 주소 공간을 논리적인 의미 단위로 나눈 메모리 영역입니다. 예를 들어 코드, 데이터, 힙, 스택 같은 영역이 각각 세그먼트가 될 수 있습니다. 세그멘테이션 방식에서는 가상 주소가 세그먼트 번호와 오프셋으로 구성되고, 세그먼트 테이블의 base와 limit 정보를 이용해 실제 물리 주소로 변환됩니다.

이때 base는 해당 세그먼트가 물리 메모리에서 시작하는 주소이고, limit은 세그먼트의 크기입니다. CPU가 특정 세그먼트의 오프셋에 접근하면, 먼저 오프셋이 limit을 넘지 않는지 검사하고, 권한이 맞는지 확인한 뒤 base + offset으로 물리 주소를 계산합니다.

세그멘테이션의 장점은 프로그램 구조와 잘 맞고, 세그먼트 단위로 보호와 공유를 적용하기 쉽다는 점입니다. 예를 들어 코드 세그먼트는 읽기와 실행만 가능하게 하고, 데이터 세그먼트는 읽기와 쓰기가 가능하게 설정할 수 있습니다.

하지만 세그먼트는 크기가 가변적이기 때문에 물리 메모리에 배치할 때 외부 단편화가 발생할 수 있습니다. 전체 빈 공간은 충분하지만 연속된 공간이 부족해서 새 세그먼트를 배치하지 못하는 문제가 생길 수 있습니다.

따라서 세그멘테이션을 사용해도 가상 메모리는 사용할 수 있지만, 현대 시스템에서는 메모리 관리를 더 단순하게 하기 위해 페이징을 주로 사용하거나, 세그멘테이션과 페이징을 함께 사용하기도 합니다.

---

# 19. 진짜 핵심만 다시

```plain text
세그먼트
= 프로그램 메모리를 의미 있는 단위로 나눈 것

예시
= Code, Data, Heap, Stack

세그멘테이션 주소
= Segment Number + Offset

세그먼트 테이블
= Base, Limit, 권한 정보 등을 저장

주소 변환
= Base + Offset

장점
= 논리적 구분, 보호, 공유에 유리

단점
= 크기가 가변적이라 외부 단편화 발생 가능

가상 메모리와 관계
= 세그멘테이션을 써도 가상 메모리 사용 가능
```

헷갈리면 이렇게만 기억해도 돼.

> **페이지는 OS가 관리하기 좋게 똑같은 크기로 자른 조각이고, 세그먼트는 사람이 이해하기 좋게 의미별로 나눈 덩어리다.**
