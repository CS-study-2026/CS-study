# **12-3.** Race Condition 이 무엇인가요?

**Race Condition(경쟁 상태)**는 여러 개의 스레드나 프로세스가 **공유 자원(shared resource)**에 동시에 접근하면서, **실행 순서에 따라 결과가 달라지는 문제**를 말합니다.

### 1. 한 줄 정의

"공유 자원에 여러 프로세스/스레드가 동시에 접근할 때, 실행 순서에 따라 결과값이 달라지는 현상"을 말합니다.

### 2. 핵심 요약

- **문제의 본질**: "누가 먼저 실행되느냐"라는 운에 따라 결과가 결정됨 (비결정적 결과).

- **발생 이유**: 데이터를 **읽고 → 수정하고 → 저장하는** 과정이 한 번에(Atomic) 일어나지 않고 중간에 끊기기 때문입니다.

---

### **3. 간단한 예시 (Count 증가 문제)**


예를 들어, 하나의 변수 `count = 0`이 있고

두 개의 스레드가 동시에 `count += 1`을 수행한다고 해봅시다.

겉보기엔 결과가 `2`가 되어야 할 것 같지만 실제로는:

```plain text
Thread A: count 읽기 → 0
Thread B: count 읽기 → 0
Thread A: +1 → 1 저장
Thread B: +1 → 1 저장
```

👉 최종 결과: **1 (잘못된 결과)**

이처럼 **읽기 → 계산 → 쓰기** 과정이 원자적(atomic)이지 않기 때문에 문제가 발생합니다.

---

## ⚠️ 왜 위험한가?

- 데이터 손상 (값이 틀어짐)

- 버그 재현이 어려움 (실행할 때마다 다름)

- 멀티스레드 환경에서 매우 흔한 문제

---

## 🧠 4. Race Condition 주요 발생 상황 

### 1️⃣ 커널 작업 중 인터럽트(Interrupt) 발생

- **상황**: 커널이 공유 변수를 읽어 수정하려는 찰나, 인터럽트가 발생하여 인터럽트 핸들러가 실행됨.

- **문제**: 인터럽트 핸들러가 동일한 공유 변수를 건드려 값이 수정되면, 원래 작업으로 돌아왔을 때 이전의 데이터 상태가 오염되어 있음.

- **해결**: 커널 변수를 건드리는 동안에는 **인터럽트를 비활성화(Disable)** 시켜서 작업의 원자성을 보장함.

### 2️⃣ 시스템 콜 수행 중 문맥 교환(Context Switch) 발생

- **상황**: 프로세스 A가 커널 모드에서 공유 데이터를 조작하던 중, CPU 할당 시간이 다 되어 프로세스 B로 CPU가 넘어감(Preemption).

- **문제**: 프로세스 B도 커널 모드에서 같은 데이터를 조작할 경우, 나중에 다시 돌아온 프로세스 A는 엉뚱한 결과값을 가지게 됨.

- **해결**: 커널 모드에서 수행 중일 때는 CPU를 뺏지 않도록 하거나(**비선점형 커널**), 공유 데이터에 **Lock**을 걸어 다른 프로세스의 접근을 막음.

### 3️⃣ 멀티프로세서(Multiprocessor) 환경의 동시 접근

- **상황**: 여러 개의 CPU가 있는 환경에서, 각 CPU 내부의 프로세스들이 동시에 메인 메모리의 커널 공유 데이터에 접근함.

- **문제**: 인터럽트를 막는 것만으로는 해결 안 됨. (CPU 1의 인터럽트를 막아도 CPU 2가 접근할 수 있기 때문) 물리적으로 동시에 데이터를 수정하며 충돌 발생.

- **해결**: 하드웨어 수준에서 데이터 자체에 **Lock/Unlock**을 거는 방식(예: Spin Lock)을 사용하여 한 번에 한 CPU만 접근하게 함.

---

## 🔐 해결 방법 ⇒ 여러번 햇 져 ?ㅋ

Race Condition을 막으려면 **동시에 접근하지 못하게 제어**해야 합니다.

대표적인 방법들:

### 1. Lock (Mutex)

- 한 번에 하나의 스레드만 접근 가능

```plain text
lock.acquire()
count+=1
lock.release()
```

또는

```plain text
withlock:
count+=1
```

---

### 2. Atomic Operation

- 연산 자체를 쪼개지지 않게 보장

---

### 3. Semaphore

- 동시에 접근 가능한 스레드 수 제한

---

### 4. Thread-safe 자료구조 사용

- 내부적으로 안전하게 처리됨

## 🧠 한 줄 정리

👉 **Race Condition = “동시에 건드려서 결과가 꼬이는 상황”**

## **🔥 Deadlock vs Race Condition**

| **구분** | **Race Condition (경쟁 상태)** | **Deadlock (교착 상태)** |
| --- | --- | --- |
| **발생 원인** | 공유 자원에 대한 비원자적(Non-atomic) 접근 | 자원 순환 대기 (Circular Wait) |
| **핵심 증상** | 결과값이 실행할 때마다 다름 (**데이터 오염**) | 프로그램이 응답 없음 (**시스템 중단**) |
| **비유** | 좁은 문을 두 명이 동시에 통과하려다 부딪힘 | 서로 "네가 먼저 가"라며 길을 막고 서 있음 |
| **주요 해결책** | **상호 배제(Lock)**, 원자적 연산 | **교착 상태 4조건** 중 하나를 제거 |

| 구분 | Race Condition | Deadlock |
| --- | --- | --- |
| 결과 | 값이 틀림 | 프로그램 멈춤 |
| 특징 | 비결정적 (랜덤) | 정지 상태 |
| 원인 | 동시 접근 | 자원 점유 + 대기 |
| 문제 유형 | 데이터 무결성 | 시스템 정지 |
| 해결 | Lock으로 보호 | 대기 구조 제거 |
