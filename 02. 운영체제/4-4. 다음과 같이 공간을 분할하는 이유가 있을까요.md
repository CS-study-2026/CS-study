# **4-4.** 다음과 같이 공간을 분할하는 이유가 있을까요?

# 🧠 힙(Heap)과 스택(Stack)으로 메모리를 분할하는 이유

프로세스의 메모리를 **스택(Stack)**과 **힙(Heap)**으로 나누는 이유는

> **데이터의 성격과 사용 방식이 완전히 다르기 때문**이다.

---

## ✅ 1. 데이터의 생명주기(Lifecycle)가 다르기 때문

### 📌 Stack

- 함수 호출 시 생성되고, 함수 종료 시 자동 제거

- **짧은 생명주기 (LIFO 구조)**

```java
public void func() {
    int a = 10;   // Stack에 저장
    int b = 20;   // Stack에 저장
}
```

> 🔥 

  1. `func()` 호출

    - Stack Frame 생성

    - `a`, `b` 생성

  1. `func()` 종료

    - Stack Frame 통째로 제거

    - `a`, `b` 자동 삭제

---

  - 함수가 끝나면 자동으로 사라짐

  - 개발자가 신경 쓸 필요 없음

### 📌 Heap

- 개발자가 직접 할당/해제 (`new`, `malloc` 등)

> 🔥 

### malloc vs new

---

  - 둘 다 Heap에 동적 할당

  - 차이:

    - malloc → 수동 해제

    - new → GC 자동 해제

- **긴 생명주기 (언제 해제될지 모름)**

```java
public void func() {
    User user = new User(); // Heap에 객체 생성
}
```

> 🔥 

  1. `new User()`

    - Heap에 객체 생성

  1. `user` 변수

    - Stack에 "참조값" 저장

  1. `func()` 종료

    - Stack의 `user` 변수는 사라짐

---

BUT! Heap의 `User 객체는 바로 사라지지 않음`

  - 참조가 없어진 상태 → GC 대상

  - 언제 삭제될지는 **GC가 결정**

👉 서로 다른 생명주기를 같은 공간에서 관리하면 **메모리 관리가 매우 복잡해짐 → 분리 필요**

---

## ✅ 2. 메모리 관리 방식이 다르기 때문

### 📌 Stack

- **컴파일 타임에 크기 결정 (정적 할당)**

- push/pop으로 관리 → 매우 빠름

- OS가 자동 관리

```java
int a = 10;
int b = 20;
```

> 🔥 컴파일 시점에 이미:

  - `a`는 int → 4byte

  - `b`는 int → 4byte

> **얼마나 메모리가 필요한지 미리 알 수 있음**

### 📌 Heap

- **런타임에 크기 결정 (동적 할당)**

- 할당/해제 비용 큼 (free list, GC 등 필요)

- 개발자 또는 GC가 관리

```java
User user = new User();
```

> 🔥 이건 실행해봐야:

  - 객체가 만들어짐

  - 메모리 크기/구조가 실제로 할당됨

> **실행 전에는 정확한 메모리 상태를 알 수 없음**

👉 **관리 방식이 다르므로 한 공간에 섞으면 비효율 발생**

---

## ✅ 3. 성능 최적화를 위해서

### 📌 Stack

- 메모리 접근이 빠름 (연속된 공간, 캐시 친화적)

> 🔥 

```java
| 변수 A |
| 변수 B |
| 변수 C |  ← Stack Pointer (SP)
```

  - 메모리가 연속적으로 붙어 있음 → CPU는 연속된 메모리를 훨씬 빠르게 읽음

  - 주소 계산도 간단함

  - SP + offset을 이용 → 이미 위치를 알고 있어서 바로 접근 가능

- 단순한 구조 → 오버헤드 거의 없음

> 🔥 

### 오버헤드

---

> 원래 작업 외에 추가로 드는 비용 
**“메모리 할당/사용을 위해 추가로 필요한 연산 비용”**

### 📌 Stack

```java
int a = 10;
```

👉 과정:

  - SP 이동

  - 값 저장

  - 끝 (오버헤드 거의 없음)

---

### 📌 Heap

```java
int *p = malloc(sizeof(int));
```

👉 과정:

  1. Heap에서 빈 공간 탐색

  1. 적절한 크기 찾기

  1. 블록 분할

  1. 메타데이터 기록

👉 훨씬 많은 작업 필요

### 📌 Heap

- 유연하지만 느림 (오버헤드)

  - 런타임에 필요할 때 원하는 크기만큼 자유롭게 할당할 수 있다

- 메모리 단편화(Fragmentation) 발생 가능

> 🔥 

### 메모리 단편화

---

> 메모리가 잘게 쪼개져서 비효율적으로 쓰이는 현상

  - Stack은 항상 위에서만 넣고 빼기 때문에 메모리 단편화 발생할 일 없음

👉 자주 쓰는 지역 변수는 Stack에 → 빠르게

👉 유연한 구조는 Heap에 → 확장성 확보

---

## ✅ 4. 메모리 안정성과 보호

### 📌 Stack

- 최대 크기가 제한됨 → overflow 발생 가능

- 대신 구조가 단순해서 안전

### 📌 Heap

- 크기 유동적

  - 프로그램 실행 중에 `malloc()` 같은 걸로 계속 확장 가능 

  - 제한은 있음! 전체 RAM 크기/프로세스 메모리 제한/OS 정책

- 대신 메모리 누수(leak), dangling pointer 위험 존재

  - `why?` ”개발자가 직접 관리하는 영역이라서”

> 🔥 

### 메모리 누수 

---

> 할당한 메모리를 해제하지 않아서 계속 남아있는 상태

  - Heap 메모리 계속 점유

  - 프로그램 종료 전까지 회수 안 됨

→ 메모리가 점점 부족해지고 심하면 프로그램 죽음

> 🔥 

### Dangling Pointer

---

> 이미 해제된 메모리를 가리키는 포인터

  - 이미 OS가 회수한 메모리 접근

  - 다른 데이터 덮어쓰기 가능

👉 역할을 분리해서 위험을 관리

---

## ✅ 5. 구조적 이유 (Call Stack vs Dynamic Object)

### 📌 Stack → 함수 실행 흐름 관리

- 함수 호출 정보 (return address, 매개변수 등)

### 📌 Heap → 객체 저장

- 크기가 가변적인 데이터 구조 (List, Tree 등)

👉 **역할 자체가 다름**

---

## 🔥 핵심 요약

| 구분 | Stack | Heap |
| --- | --- | --- |
| 생명주기 | 짧음 | 김 |
| 할당 방식 | 정적 | 동적 |
| 속도 | 빠름 | 상대적으로 느림 |
| 관리 | 자동 | 개발자/GC |
| 용도 | 함수 호출, 지역 변수 | 객체, 동적 데이터 |

---

## 🎯 한 줄 정리

👉 **"빠르고 단순한 데이터(Stack)와 유연하고 동적인 데이터(Heap)를 효율적으로 관리하기 위해 분리한다."**
