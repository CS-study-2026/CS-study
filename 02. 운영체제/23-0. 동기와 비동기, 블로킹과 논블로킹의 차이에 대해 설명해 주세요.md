# 23-0. 동기와 비동기, 블로킹과 논블로킹의 차이에 대해 설명해 주세요.

# 23. 동기와 비동기, 블로킹과 논블로킹의 차이

## 1. 먼저 결론

동기/비동기와 블로킹/논블로킹은 비슷해 보이지만 서로 다른 기준의 개념이다.

간단히 나누면 다음과 같다.

```plain text
동기 / 비동기
= 작업의 완료와 결과 처리를 누가 주도하느냐

블로킹 / 논블로킹
= 호출한 스레드가 기다리느냐, 바로 제어권을 돌려받느냐
```

즉, 동기와 비동기는 **작업 완료를 다루는 방식**에 대한 개념이고,

블로킹과 논블로킹은 **함수 호출 후 스레드가 멈추는지 여부**에 대한 개념이다.

<details>
<summary>동기/비동기의 오해</summary>

```javascript
[오해]
동기 = 결과 올 때까지 기다림
비동기 = 안 기다림
--------------------------------
[사실]
동기
= 결과를 호출한 쪽이 직접 관리

비동기
= 결과를 시스템이 알려줌

---------------------------------
기다림 여부 ≠ 동기/비동기
```
</details>

---

## 2. 동기와 비동기

## 2-1. 동기란?

동기는 호출한 쪽이 작업의 완료를 직접 신경 쓰는 방식이다.

어떤 작업을 요청한 뒤, 그 작업이 끝났는지 확인하고 결과를 받아 다음 흐름을 이어간다.

```plain text
작업 요청
→ 작업 완료 여부를 호출한 쪽이 신경 씀
→ 결과를 받아 다음 작업 진행
```

예를 들어 파일을 읽는 함수가 있다고 하자.

```java
String data = readFile();
process(data);
```

이 코드는 `readFile()`의 결과가 있어야 `process(data)`를 실행할 수 있다.

즉, 흐름이 작업 완료에 맞춰져 있다.

이런 방식이 동기적 흐름이다.

중요한 점은 동기가 반드시 “스레드가 멈춘다”는 뜻은 아니라는 것이다.

동기는 **작업 완료와 결과를 호출한 쪽이 직접 맞춰간다**는 의미에 가깝다.

---

## 2-2. 비동기란?

비동기는 호출한 쪽이 작업을 요청한 뒤, 작업 완료를 직접 기다리거나 계속 확인하지 않아도 되는 방식이다.

작업이 끝나면 시스템, 런타임, 콜백, 이벤트, Future, Promise 같은 방식으로 결과를 알려준다.

```plain text
작업 요청
→ 호출한 쪽은 다른 일을 계속함
→ 작업이 끝나면 완료 알림 또는 콜백으로 결과 처리
```

예를 들어 다음과 같은 구조를 생각할 수 있다.

```javascript
fetch("/api/logs")
  .then(response => response.json())
  .then(data => process(data));

doSomethingElse();
```

요청을 보낸 뒤 바로 다음 작업을 진행하고, 응답이 오면 등록해둔 콜백이 실행된다.

이런 방식이 비동기적 흐름이다.

---

## 3. 블로킹과 논블로킹

## 3-1. 블로킹이란?

블로킹은 호출한 함수가 작업을 끝낼 때까지 호출한 스레드가 기다리는 방식이다.

예를 들어 소켓에서 데이터를 읽으려고 하는데 아직 데이터가 도착하지 않았다고 하자.

블로킹 I/O에서는 데이터가 올 때까지 `read()` 호출이 반환되지 않는다.

```plain text
read() 호출
→ 데이터가 아직 없음
→ 스레드가 대기 상태로 멈춤
→ 데이터 도착
→ read() 반환
```

즉, 블로킹의 핵심은 **호출한 스레드가 제어권을 돌려받지 못하고 기다린다**는 점이다.

---

## 3-2. 논블로킹이란?

논블로킹은 작업을 즉시 완료할 수 없더라도 함수가 바로 반환되는 방식이다.

예를 들어 소켓에서 데이터를 읽으려고 했는데 아직 데이터가 없다고 하자.

논블로킹 I/O에서는 데이터가 올 때까지 기다리지 않고 바로 반환한다.

```plain text
read() 호출
→ 데이터가 아직 없음
→ 바로 반환
→ "지금은 읽을 데이터가 없음"을 알려줌
```

운영체제나 언어에 따라 `EAGAIN`, `EWOULDBLOCK`, `null`, 빈 결과, 상태 코드 등으로 표현될 수 있다.

논블로킹의 핵심은 **작업이 아직 끝나지 않았더라도 호출한 스레드가 바로 제어권을 돌려받는다**는 점이다.

---

# 4. 네 가지 조합

동기/비동기와 블로킹/논블로킹은 서로 다른 기준이므로 네 가지 조합이 가능하다.

| 구분 | 설명 | 예시 |
| --- | --- | --- |
| 동기 + 블로킹 | 작업이 끝날 때까지 호출한 스레드가 기다림 | 일반적인 파일 read, DB 조회 |
| 동기 + 논블로킹 | 호출은 바로 반환되지만, 호출한 쪽이 완료 여부를 직접 확인함 | non-blocking read를 반복 확인 |
| 비동기 + 논블로킹 | 요청 후 바로 반환되고, 완료되면 콜백/이벤트로 알림 | 비동기 네트워크 요청, Promise, async callback |
| 비동기 + 블로킹 | 비동기 작업을 요청했지만 결과를 기다리며 막힘 | Future를 호출하자마자 get으로 기다리는 경우 |

---

# 5. 동기 + 블로킹

가장 흔하고 이해하기 쉬운 방식이다.

```plain text
작업 요청
→ 작업이 끝날 때까지 기다림
→ 결과를 받음
→ 다음 작업 진행
```

예를 들어 다음과 같은 코드는 동기 + 블로킹 방식으로 볼 수 있다.

```java
String result = callApi();
System.out.println(result);
```

`callApi()`가 끝나야 다음 줄로 넘어갈 수 있고, 그동안 호출한 스레드는 기다린다.

장점은 코드 흐름이 단순하다는 것이다.

```plain text
위에서 아래로 읽으면 됨
구현과 디버깅이 비교적 쉬움
```

단점은 작업이 오래 걸릴 경우 스레드가 놀게 된다는 것이다.

```plain text
I/O 대기 시간 동안 스레드가 다른 일을 못 함
동시 요청이 많으면 많은 스레드가 필요함
```

---

# 6. 동기 + 논블로킹

동기 + 논블로킹은 처음에는 어색해 보이지만 실제로 의미가 있다.

핵심은 다음과 같다.

```plain text
호출은 바로 반환된다.
하지만 작업 완료 여부는 호출한 쪽이 직접 계속 확인한다.
```

예를 들어 논블로킹 소켓에서 데이터를 읽는 상황을 생각할 수 있다.

```plain text
read() 호출
→ 데이터 없음
→ 바로 반환

호출한 쪽이 나중에 다시 read() 호출
→ 아직 없음
→ 바로 반환

다시 read() 호출
→ 데이터 있음
→ 읽기 성공
```

이 방식은 블로킹처럼 스레드가 잠들어 기다리지는 않는다.

하지만 작업 완료를 시스템이 알아서 알려주는 것도 아니다.

호출한 쪽이 계속 상태를 확인해야 한다.

그래서 동기 + 논블로킹이라고 할 수 있다.

다만 이 방식을 단순 반복문으로 구현하면 문제가 생긴다.

```plain text
while (true) {
    read();
}
```

이런 방식은 데이터가 없는데도 계속 CPU를 사용하게 된다.

이를 busy waiting이라고 한다.

따라서 실제 시스템에서는 무작정 반복 확인하지 않고, 이벤트 통지나 I/O 멀티플렉싱 같은 방식을 함께 사용해 효율적으로 처리한다.

이 부분은 I/O 멀티플렉싱 주제와 연결된다.

<details>
<summary>그럼 여기서 문제… 이 방식에서 **데이터를 직접 확인하는 코드가 없으면?**</summary>

답 안적어놨지롱

```javascript
Data data = null;

while(data == null){
    data = read();
}

process(data);

// 이건 내가 참고할거 ㅎㅎㅎ
```
</details>

# 7. 비동기 + 논블로킹

(난 오히려 이게 어렵더라…)

비동기 + 논블로킹은 고성능 I/O나 이벤트 기반 프로그래밍에서 자주 등장하는 형태다.

```plain text
작업 요청
→ 바로 반환
→ 호출한 쪽은 다른 작업 수행
→ 작업 완료 시 콜백, 이벤트, Future, Promise 등으로 결과 수신
```

예를 들어 네트워크 요청을 보내고 응답이 올 때까지 현재 스레드가 막히지 않는 구조다.

```javascript
fetch("/api/data")
  .then(data => {
    process(data);
  });

doSomethingElse();
```

이 방식의 장점은 I/O 대기 시간 동안 스레드를 묶어두지 않는다는 것이다.

따라서 많은 요청을 적은 수의 스레드로 처리할 수 있다.

단점은 코드 흐름이 복잡해질 수 있다는 점이다.

```plain text
콜백 중첩
에러 처리 복잡
실행 순서 추적 어려움
디버깅 난이도 증가
```

그래서 현대 언어에서는 async/await, Promise, Future, Coroutine 같은 문법이나 추상화를 제공해 비동기 코드를 동기 코드처럼 읽기 쉽게 만들기도 한다.

---

# 8. 비동기 + 블로킹

비동기 + 블로킹은 가능한 조합이지만, 일반적으로는 좋은 형태라고 보기 어렵다.

예를 들어 비동기 작업을 요청해놓고 바로 결과를 기다린다고 하자.

```java
Future<String> future = asyncCall(); // 여기까지는 비동기. 스레드 결과 대신 Future를 받음

String result = future.get(); // 여기서는 get()이 아직 안됐으니 스레드 대기(블로킹)

doSomethingElse();
```

`asyncCall()` 자체는 비동기로 시작되었지만, 바로 `future.get()`을 호출하면 현재 스레드는 결과가 올 때까지 막힌다.

```plain text
asyncCall()
↓
비동기 작업 시작
↓
Future 객체 반환 (예약표 받음)
↓
future.get()
↓
결과 나올 때까지 스레드 대기
↓
결과 반환
↓
doSomethingElse()
----------------------
비동기 작업 요청
→ 결과를 기다리며 blocking
→ 완료 후 다음 작업 진행
```

이 경우 비동기의 장점이 많이 사라진다.

다만 모든 경우에 완전히 의미가 없는 것은 아니다.

예를 들어 내부적으로는 작업을 다른 스레드나 다른 시스템에 맡겨 병렬로 수행하게 하고, 특정 시점에서 결과를 합치기 위해 기다리는 구조라면 의미가 있을 수 있다.

```plain text
여러 비동기 작업을 먼저 시작
→ 다른 작업 수행
→ 마지막에 필요한 시점에서 결과 대기
```

하지만 비동기 요청 직후 바로 blocking으로 기다린다면, 사실상 동기 + 블로킹 코드와 큰 차이가 없어질 수 있다.
