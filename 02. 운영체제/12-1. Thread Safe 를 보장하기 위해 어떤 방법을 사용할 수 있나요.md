# 12-1. Thread Safe를 보장하기 위해 어떤 방법을 사용할 수 있나요?

## 1. Thread Safe란?

**Thread Safe**란 여러 스레드가 동시에 어떤 코드나 데이터에 접근해도 **데이터의 일관성이 깨지지 않고, 예상 가능한 결과가 보장되는 상태**를 말한다.

예를 들어 여러 스레드가 동시에 하나의 `count` 값을 증가시킨다고 해보자.

```java
count++;
```

겉보기에는 한 줄짜리 단순한 코드지만, 실제로는 다음 세 단계로 나뉜다.

```plain text
1. count 값을 읽는다.
2. 1을 더한다.
3. 다시 count에 저장한다.
```

즉, 내부적으로는 이런 흐름이다.

```plain text
read → add → write
```

그래서 두 스레드가 동시에 실행되면 문제가 생길 수 있다.

```plain text
초기 count = 0

Thread A: count 읽음 → 0
Thread B: count 읽음 → 0

Thread A: 0 + 1 계산 → 1
Thread B: 0 + 1 계산 → 1

Thread A: count에 1 저장
Thread B: count에 1 저장

최종 count = 1
```

분명 두 번 증가시켰는데 결과는 `2`가 아니라 `1`이 된다.

이처럼 여러 스레드가 같은 공유 자원에 동시에 접근하면서 실행 순서에 따라 결과가 달라지는 문제가 생길 수 있다. 따라서 Thread Safe를 보장하려면 **공유 자원을 안전하게 다루는 방법**이 필요하다.

---

# 2. Thread Safe를 보장하는 대표적인 방법

Thread Safe를 보장하는 방법은 하나가 아니다.

무조건 `lock`을 거는 것이 정답도 아니다.

크게 보면 다음 순서로 생각하는 것이 좋다.

```plain text
1. 공유 상태를 없앨 수 있는가?
2. 불변 객체로 만들 수 있는가?
3. Thread-safe한 자료구조를 사용할 수 있는가?
4. 단순 연산이라면 Atomic 클래스로 해결할 수 있는가?
5. 가시성 문제라면 volatile로 충분한가?
6. 그래도 공유 자원 보호가 필요하다면 synchronized나 Lock을 사용할 것인가?
```

핵심은 **공유를 줄이고, 꼭 필요한 부분만 동기화하는 것**이다.

---

## 2-1. 공유 상태를 없애기

가장 좋은 방법은 애초에 여러 스레드가 같은 데이터를 공유하지 않도록 만드는 것이다.

Thread Safe 문제가 생기는 가장 큰 이유는 다음과 같다.

```plain text
여러 스레드가
같은 데이터를
동시에
읽고 쓰기 때문
```

그러면 가장 단순한 해결책은 이거다.

```plain text
같은 데이터를 공유하지 않으면 된다.
```

예를 들어 메서드 내부의 지역 변수는 보통 안전하다.

```java
public int calculate(int a, int b) {
    int result = a + b;
    return result;
}
```

여기서 `result`는 메서드 안에서 만들어진 지역 변수다.

각 스레드는 자기만의 스택 영역을 가지기 때문에, 서로 다른 스레드가 이 `result`를 공유하지 않는다.

반대로 객체의 필드나 `static` 변수는 조심해야 한다.

```java
class Counter {
    private int count = 0;

    public void increase() {
        count++;
    }
}
```

여기서 `count`는 여러 스레드가 같은 `Counter` 객체를 공유하면 동시에 접근될 수 있다.

따라서 이 코드는 Thread Safe하지 않을 수 있다.

특히 Spring에서는 `Controller`, `Service`, `Repository` 같은 Bean이 기본적으로 싱글톤으로 관리된다.

그래서 여러 요청이 같은 객체를 공유할 수 있다.

```java
@Service
public class OrderService {
    private int lastOrderId;

    public void order() {
        lastOrderId++;
    }
}
```

이런 식으로 Service 안에 변경 가능한 상태를 필드로 두면 여러 요청이 동시에 접근하면서 값이 꼬일 수 있다.

따라서 Spring Bean은 가능하면 상태를 가지지 않는 **stateless** 구조로 만드는 것이 좋다.

---

## 2-2. 불변 객체 사용하기

**불변 객체, Immutable Object**를 사용하는 것도 Thread Safe를 보장하는 좋은 방법이다.

불변 객체는 생성된 뒤 내부 상태가 바뀌지 않는 객체다.

대표적인 예로 Java의 `String`이 있다.

```java
String name = "hello";
```

문자열을 수정하는 것처럼 보여도 기존 문자열 객체가 바뀌는 것이 아니라 새로운 문자열 객체가 만들어진다.

불변 객체가 안전한 이유는 간단하다.

```plain text
읽기만 가능하고 수정이 불가능하면,
여러 스레드가 동시에 접근해도 데이터가 깨질 일이 적다.
```

예를 들어 다음 객체는 비교적 안전하다.

```java
public final class UserInfo {
    private final String name;
    private final int age;

    public UserInfo(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public String getName() {
        return name;
    }

    public int getAge() {
        return age;
    }
}
```

불변 객체를 만들 때는 보통 다음 조건을 지킨다.

```plain text
- 클래스를 final로 만든다.
- 필드를 private final로 만든다.
- setter를 만들지 않는다.
- 내부의 변경 가능한 객체를 그대로 노출하지 않는다.
```

다만 `final`만 붙인다고 무조건 완전한 불변이 되는 것은 아니다.

```java
public final class Team {
    private final List<String> members;

    public Team(List<String> members) {
        this.members = members;
    }

    public List<String> getMembers() {
        return members;
    }
}
```

이 코드는 위험하다.

`members` 참조 자체는 바뀌지 않지만, 리스트 내부 내용은 바꿀 수 있기 때문이다.

```java
team.getMembers().add("new member");
```

진짜 불변으로 만들려면 외부에서 받은 리스트를 복사하거나 수정 불가능한 형태로 만들어야 한다.

```java
public final class Team {
    private final List<String> members;

    public Team(List<String> members) {
        this.members = List.copyOf(members);
    }

    public List<String> getMembers() {
        return members;
    }
}
```

## 2-3. synchronized 사용하기

공유 자원을 꼭 수정해야 한다면, 해당 영역에 한 번에 하나의 스레드만 접근하게 만들 수 있다.

Java에서 가장 기본적인 방법은 `synchronized`다.

```java
class Counter {
    private int count = 0;

    public synchronized void increase() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}
```

`synchronized`가 붙은 메서드는 한 번에 하나의 스레드만 실행할 수 있다.

```plain text
Thread A가 increase() 실행 중
→ Thread B는 기다림

Thread A가 끝남
→ Thread B가 들어감
```

이렇게 여러 스레드가 동시에 접근하면 문제가 생기는 코드 영역을 **임계 영역, Critical Section**이라고 한다.

```java
synchronized (lock) {
    count++;
}
```

다만 `synchronized`를 너무 넓게 잡으면 성능이 떨어질 수 있다.

```java
public synchronized void doSomething() {
    validate();
    callExternalApi();
    updateCount();
    saveToDatabase();
}
```

이 코드는 외부 API 호출이나 DB 저장처럼 오래 걸릴 수 있는 작업까지 전부 잠가버린다.

그러면 다른 스레드들이 불필요하게 오래 기다려야 한다.

더 나은 방식은 공유 자원을 실제로 수정하는 부분만 잠그는 것이다.

```java
public void doSomething() {
    validate();
    callExternalApi();

    synchronized (lock) {
        updateCount();
    }

    saveToDatabase();
}
```

## 2-4. Lock 사용하기

`synchronized`보다 더 세밀한 제어가 필요하면 `ReentrantLock` 같은 명시적 Lock을 사용할 수 있다.

```java
import java.util.concurrent.locks.ReentrantLock;

class Counter {
    private int count = 0;
    private final ReentrantLock lock = new ReentrantLock();

    public void increase() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();
        }
    }
}
```

여기서 중요한 부분은 `finally`다.

```java
try {
    count++;
} finally {
    lock.unlock();
}
```

중간에 예외가 발생해도 반드시 lock을 해제해야 한다.

그렇지 않으면 다른 스레드들이 영원히 기다리는 문제가 생길 수 있다.

`synchronized`와 `ReentrantLock`은 다음처럼 비교할 수 있다.

| 구분 | synchronized | ReentrantLock |
| --- | --- | --- |
| 사용 방식 | 문법 차원에서 제공 | 객체로 직접 제어 |
| lock 해제 | 자동 해제 | 직접 unlock 필요 |
| 코드 복잡도 | 단순함 | 상대적으로 복잡함 |
| tryLock | 불가능 | 가능 |
| timeout | 제한적 | 가능 |
| 공정성 설정 | 어려움 | 가능 |
| 적합한 상황 | 기본적인 동기화 | 복잡한 동기화 제어 |

예를 들어 `tryLock()`을 사용하면 lock을 무한정 기다리지 않고, 얻지 못했을 때 다른 처리를 할 수 있다.

```java
if (lock.tryLock()) {
    try {
        count++;
    } finally {
        lock.unlock();
    }
} else {
    // lock을 얻지 못했을 때 다른 처리
}
```

## 2-5. Atomic 클래스 사용하기

단순한 숫자 증가처럼 하나의 값에 대한 원자적 연산이 필요하다면 `AtomicInteger` 같은 클래스를 사용할 수 있다.

```java
import java.util.concurrent.atomic.AtomicInteger;

class Counter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void increase() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}
```

`AtomicInteger`는 내부적으로 원자적 연산을 제공한다.

```plain text
원자적 연산
= 중간에 다른 스레드가 끼어들 수 없는 하나의 작업처럼 처리되는 연산
```

즉, 다음 코드는 여러 스레드가 동시에 호출해도 안전하게 증가할 수 있다.

```java
count.incrementAndGet();
```

하지만 Atomic 클래스가 항상 정답은 아니다.

단순히 값 하나를 증가시키는 정도에는 좋지만, 여러 값을 함께 변경해야 하는 경우에는 부족할 수 있다.

예를 들어 다음 로직을 보자.

```java
if (stock > 0) {
    stock--;
    soldCount++;
}
```

이 로직은 단순히 `stock`과 `soldCount`를 각각 `AtomicInteger`로 만든다고 항상 안전해지는 것은 아니다.

왜냐하면 여기서는 다음 작업 전체가 하나의 논리적 단위이기 때문이다.

```plain text
1. 재고가 있는지 확인한다.
2. 재고를 감소시킨다.
3. 판매 수량을 증가시킨다.
```

이런 경우에는 전체 로직을 하나의 임계 영역으로 묶기 위해 `synchronized`나 `Lock`이 필요할 수 있다.

## 2-6. volatile 사용하기

`volatile`은 여러 스레드가 같은 변수를 볼 때 **가시성 문제**를 해결하기 위해 사용한다.

가시성 문제란 한 스레드가 값을 변경했는데, 다른 스레드가 그 변경을 바로 보지 못하는 문제다.

예를 들어 다음 코드를 보자.

```java
class Worker {
    private boolean running = true;

    public void stop() {
        running = false;
    }

    public void work() {
        while (running) {
            // 작업 수행
        }
    }
}
```

한 스레드가 `stop()`을 호출해서 `running = false`로 바꿔도, 다른 스레드가 그 변경을 바로 보지 못하면 `while`문이 계속 돌 수 있다.

이때 `volatile`을 붙일 수 있다.

```java
class Worker {
    private volatile boolean running = true;

    public void stop() {
        running = false;
    }

    public void work() {
        while (running) {
            // 작업 수행
        }
    }
}
```

`volatile`을 붙이면 한 스레드가 변경한 값을 다른 스레드가 볼 수 있도록 보장한다.

쉽게 말하면:

```plain text
한 스레드가 바꾼 값을
다른 스레드가 오래된 값으로 계속 보지 않게 해준다.
```

하지만 `volatile`은 **가시성은 보장하지만 원자성은 보장하지 않는다.**

예를 들어 다음 코드는 안전하지 않다.

```java
private volatile int count = 0;

public void increase() {
    count++;
}
```

`volatile`이 붙었기 때문에 각 스레드는 최신 `count` 값을 볼 수 있다.

하지만 `count++`는 하나의 작업이 아니다.

```plain text
1. count 값을 읽는다.
2. 1을 더한다.
3. 다시 count에 저장한다.
```

그래서 두 스레드가 동시에 실행하면 이런 일이 생길 수 있다.

```plain text
초기 count = 0

Thread A: count 읽음 → 0
Thread B: count 읽음 → 0

Thread A: 0 + 1 계산 → 1
Thread B: 0 + 1 계산 → 1

Thread A: count = 1 저장
Thread B: count = 1 저장

최종 count = 1
```

`volatile` 덕분에 둘 다 최신 값인 `0`을 읽었다고 해도, 둘 다 같은 값을 읽고 계산하면 증가 결과가 누락될 수 있다.

정리하면 다음과 같다.

| 구분 | volatile |
| --- | --- |
| 최신 값이 보이게 하는가? | 가능 |
| 가시성을 보장하는가? | 가능 |
| `count++`를 안전하게 만드는가? | 불가능 |
| 여러 연산을 하나로 묶어주는가? | 불가능 |
| lock처럼 임계 영역을 보호하는가? | 불가능 |

따라서 `volatile`은 보통 다음과 같은 단순 상태 플래그에 적합하다.

```java
private volatile boolean running = true;
```

```plain text
- 실행 중인지 여부
- 종료 요청 여부
- 설정값 갱신 여부
- 단순 상태 표시
```

반면 다음과 같은 복합 연산에는 적합하지 않다.

```java
count++;
```

```java
if (stock > 0) {
    stock--;
}
```

이런 경우에는 `synchronized`, `Lock`, `AtomicInteger` 등을 고려해야 한다.

## 2-7. Thread-safe한 자료구조 사용하기

직접 동기화 코드를 작성하는 대신, 이미 Thread Safe하게 만들어진 자료구조를 사용할 수도 있다.

Java에서는 다음과 같은 클래스들이 제공된다.

```plain text
- ConcurrentHashMap
- CopyOnWriteArrayList
- BlockingQueue
- ConcurrentLinkedQueue
- AtomicInteger
- LongAdder
```

예를 들어 일반 `HashMap`은 멀티스레드 환경에서 안전하지 않다.

```java
Map<String, Integer> map = new HashMap<>();
```

여러 스레드가 동시에 `put`, `get`, `remove`를 수행하면 문제가 생길 수 있다.

이럴 때는 `ConcurrentHashMap`을 사용할 수 있다.

```java
Map<String, Integer> map = new ConcurrentHashMap<>();
```

작업 큐가 필요하다면 `BlockingQueue`를 사용할 수 있다.

```java
BlockingQueue<String> queue = new LinkedBlockingQueue<>();
```

이 구조는 생산자-소비자 패턴에서 자주 사용된다.

```plain text
Producer Thread → BlockingQueue → Consumer Thread
```

다만 이것은 같은 프로세스 안의 스레드 간 작업 큐에 가깝고, IPC에서 말하는 Message Queue는 프로세스 간 통신 방식이라는 차이가 있다.

## 2-8. ThreadLocal 사용하기

`ThreadLocal`은 각 스레드마다 독립적인 값을 갖게 해주는 방법이다.

```java
private static final ThreadLocal<String> userIdHolder = new ThreadLocal<>();
```

예를 들어 각 스레드는 자기만의 값을 가질 수 있다.

```plain text
Thread A → userId = "userA"
Thread B → userId = "userB"
Thread C → userId = "userC"
```

서로 값을 공유하지 않기 때문에 Race Condition을 줄이는 데 도움이 될 수 있다.

주로 다음과 같은 값을 저장할 때 사용된다.

```plain text
- 현재 로그인한 사용자 정보
- 요청 추적 ID
- 로그 MDC
- 트랜잭션 컨텍스트
```

하지만 ThreadLocal은 남발하면 위험하다.

특히 **Thread Pool 환경**에서는 더 조심해야 한다.

서버는 요청이 들어올 때마다 스레드를 새로 만들지 않고, 미리 만들어둔 스레드를 재사용한다.

```plain text
요청 A → Thread-1이 처리
요청 B → Thread-2가 처리
요청 C → Thread-1이 다시 처리
```

중요한 점은 요청이 끝나도 `Thread-1`이 사라지는 것이 아니라는 점이다.

스레드는 살아남아서 다음 요청을 또 처리한다.

예를 들어 요청 A에서 ThreadLocal에 사용자 정보를 저장했다고 하자.

```java
userIdHolder.set("userA");
```

그런데 요청 처리가 끝난 뒤 `remove()`를 하지 않았다.

```java
// userIdHolder.remove(); 안 함
```

그러면 `Thread-1` 안에 `"userA"` 값이 남아 있을 수 있다.

이후 요청 B가 우연히 같은 `Thread-1`에서 처리되면, 요청 B가 이전 요청의 사용자 정보를 읽어버릴 수 있다.

```plain text
요청 B를 처리하는데 userA 정보가 보이는 상황 발생
```

이건 데이터 오염이고, 경우에 따라 보안 문제로 이어질 수 있다.

따라서 ThreadLocal을 사용할 때는 반드시 사용 후 제거해야 한다.

```java
try {
    userIdHolder.set(userId);

    // 비즈니스 로직 수행
} finally {
    userIdHolder.remove();
}
```

정리하면 ThreadLocal 사용 시 주의할 점은 다음과 같다.

```plain text
1. Thread Pool에서는 스레드가 재사용된다.
2. remove를 하지 않으면 이전 요청의 값이 남을 수 있다.
3. 요청 간 사용자 정보가 섞이면 보안 문제가 될 수 있다.
4. 코드 흐름이 숨겨진 전역 변수처럼 변해 추적이 어려워질 수 있다.
5. 사용 후 try-finally로 반드시 정리하는 것이 좋다.
```

## 2-9. ReadWriteLock과 Semaphore 사용하기

상황에 따라 특수한 동기화 도구를 사용할 수도 있다.

### ReadWriteLock

읽기는 여러 스레드가 동시에 해도 괜찮지만, 쓰기는 한 번에 하나만 해야 하는 경우가 있다.

예를 들어 게시글 조회는 많고 수정은 적은 상황이다.

```plain text
읽기: 여러 명이 동시에 가능
쓰기: 한 명만 가능
```

이럴 때는 `ReadWriteLock`을 사용할 수 있다.

```java
private final ReadWriteLock rwLock = new ReentrantReadWriteLock();

public int read() {
    rwLock.readLock().lock();
    try {
        return value;
    } finally {
        rwLock.readLock().unlock();
    }
}

public void write(int newValue) {
    rwLock.writeLock().lock();
    try {
        value = newValue;
    } finally {
        rwLock.writeLock().unlock();
    }
}
```

읽기 작업이 많고 쓰기 작업이 적은 경우 성능상 유리할 수 있다.

### Semaphore

`Semaphore`는 동시에 접근 가능한 스레드 수를 제한할 때 사용한다.

```plain text
Mutex: 한 번에 1명
Semaphore: 한 번에 N명
```

예를 들어 동시에 최대 3개 스레드만 어떤 자원에 접근하게 하고 싶다면 다음처럼 사용할 수 있다.

```java
Semaphore semaphore = new Semaphore(3);
```

```java
semaphore.acquire();
try {
    // 제한된 자원 사용
} finally {
    semaphore.release();
}
```

예를 들어 DB 커넥션 수 제한, 외부 API 호출 수 제한, 다운로드 동시 처리 제한 등에 사용할 수 있다.

# 3. Thread Safe를 설계할 때 중요한 기준

## 3-1. 무엇이 공유 자원인지 먼저 찾아야 한다

무작정 lock을 거는 것이 아니라 먼저 다음 질문을 해야 한다.

```plain text
이 코드에서 여러 스레드가 함께 접근하는 데이터가 무엇인가?
```

대표적인 공유 자원은 다음과 같다.

```plain text
- static 변수
- 싱글톤 객체의 필드
- Spring Bean의 필드
- 공유 컬렉션
- 캐시
- 카운터
- 파일
- DB 연결 객체
```

공유 자원이 없다면 동기화 문제도 크게 줄어든다.

그래서 가장 좋은 해결책은 가능한 한 공유 상태를 줄이는 것이다.

---

## 3-2. 임계 영역을 최소화해야 한다

Thread Safe하게 만들겠다고 모든 메서드에 lock을 걸면 성능이 떨어진다.

나쁜 예시는 다음과 같다.

```java
public synchronized void process() {
    validate();
    callExternalApi();
    updateCount();
    saveToDatabase();
}
```

이렇게 하면 외부 API 호출 중에도 lock을 잡고 있게 된다.

다른 스레드들이 불필요하게 기다려야 한다.

더 나은 방식은 공유 자원을 수정하는 부분만 잠그는 것이다.

```java
public void process() {
    validate();
    callExternalApi();

    synchronized (lock) {
        updateCount();
    }

    saveToDatabase();
}
```

---

## 3-3. Lock 순서를 정해야 한다

여러 lock을 사용할 때는 순서를 정해야 한다.

나쁜 예시는 다음과 같다.

```plain text
Thread A: lock1 → lock2
Thread B: lock2 → lock1
```

이 경우 서로가 가진 lock을 기다리면서 Deadlock이 발생할 수 있다.

좋은 방식은 모든 스레드가 같은 순서로 lock을 획득하게 만드는 것이다.

```plain text
모든 스레드가 항상 lock1 → lock2 순서로 획득
```

---

## 3-4. 동시성 문제는 테스트로 잡기 어렵다

Thread Safe 문제는 항상 바로 드러나지 않는다.

```plain text
오늘은 정상
내일도 정상
시연 때도 정상
배포 후 갑자기 장애
```

이런 식으로 뒤늦게 터질 수 있다.

왜냐하면 스레드 실행 순서는 매번 달라질 수 있기 때문이다.

따라서 동시성 문제는 단순히 “실행해봤는데 괜찮다”로 판단하면 위험하다.

코드 구조상 안전한지 따져야 한다.

---

# 4. 핵심 한 문장

> Thread Safe를 보장하는 가장 좋은 방법은 먼저 공유 상태를 줄이는 것이고, 공유가 꼭 필요할 때만 `synchronized`, `Lock`, `Atomic`, `volatile`, `Concurrent Collection`, `ThreadLocal` 등을 상황에 맞게 선택하는 것이다.
