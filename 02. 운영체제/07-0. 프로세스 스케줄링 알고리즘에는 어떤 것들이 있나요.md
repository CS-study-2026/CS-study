# 7-0. 프로세스 스케줄링 알고리즘에는 어떤 것들이 있나요?

# 1. 스케줄링이 왜 필요한가

### OS의 스케줄링 = “CPU를 누구에게, 언제, 얼마나 줄지 정하는 일”

  - 단순히 순서를 정하기 X

  - 다양한 목적이 존재 → 다만 **목표간 충돌 多**

  - 스케줄링에는 **“무조건 좋은 하나의 정답” X**, **무엇을 더 중요하게 볼지**에 대한 선택

  <details>
  <summary>자세한 설명</summary>

운영체제에서 스케줄링은 “**CPU를 누구한테, 언제, 얼마나 줄지 정하는 일**”이야.

CPU는 보통 한 순간에 한 작업만 제대로 실행할 수 있으니까, 여러 프로세스나 스레드가 경쟁할 때 운영체제가 순서를 정해줘야 해.

여기서 중요한 건 그냥 “순서 정하기”가 아니라, **목적이 여러 개**라는 점이야.

예를 들면:

    - CPU를 최대한 놀리지 않고 싶다

    - 작업을 많이 처리하고 싶다

    - 사용자 입장에서 빨리 반응했으면 좋겠다

    - 너무 오래 기다리는 작업이 없었으면 좋겠다

문제는 이 목표들이 **서로 충돌할 때가 많다**는 거야.

예를 들어:

    - 짧은 작업만 계속 먼저 처리하면 평균 성능은 좋아 보일 수 있음

    - 근데 긴 작업은 계속 밀려서 공정성은 나빠짐

즉, 스케줄링은 **“무조건 좋은 하나의 정답”이 아니라, 무엇을 더 중요하게 볼지에 따른 선택**이야.
  </details>

# 2. 스케줄링을 평가하는 기준 → Trade off

### 1. CPU Utilization (CPU 이용률)

    - CPU가 얼마나 쉬지 않고 잘 사용되는지

    - 다만 사용자는 CPU의 이용률 자체보다 내 프로그램이 빨리 반응하는지를 더 신경씀

### 2. Throughput

    - 단위시간 동안 몇 개의 작업을 처리했는지

    - **배치 시스템**에서 특히 중요

### 3. Turnaround Time

    - 작업이 도착해서 **완료될 때까지 걸린 전체 시간 **(작업 요청 ~ 완료 시간)

    - 사용자 입장에서 중요한 지표

### 4. Waiting Time

    - 프로세스가 Ready Queue 에서 **CPU를 받지 못하고 기다린 시간**

### 5. Response Time

    - 요청 이후 **처음으로  CPU를 할당받아 반응하기까지 기다린 시간**

    - 사용자 입장에선 작업 전체가 빨리 끝나는 것보다 처음 반응이 오는 것이 중요할 때가 많음

### 6. Fairness (공정성)

    - 어떤 프로세스가 지나치게 차별받지 않는지의 지표

이거부터 먼저 설명해주면 뒤 내용이 훨씬 잘 이해돼.
알고리즘 이름보다 이게 더 중요해.

## 2-1. CPU Utilization

CPU 이용률.
CPU가 쉬지 않고 얼마나 잘 사용되고 있는가.

      - 높을수록 좋음

      - CPU가 놀고 있으면 자원 낭비니까

하지만 이것만 높다고 좋은 건 아냐.
사용자는 CPU 이용률 자체보다 “내 프로그램이 빨리 반응하냐”를 더 신경 쓰거든.

---

## 2-2. Throughput

단위 시간 동안 몇 개의 작업을 처리했는가.

예를 들어 1초에 10개 작업 처리 vs 1초에 3개 작업 처리.
당연히 많을수록 좋지.

이건 **배치 시스템**에서 특히 중요해.
예: 서버가 요청을 많이 처리해야 하는 경우.

---

## 2-3. Turnaround Time

작업이 **도착해서 완료될 때까지 걸린 전체 시간**.

예를 들어:

      - 10시에 작업 요청

      - 10시 8분에 끝남

그럼 turnaround time은 8분.

사용자 입장에서는 꽤 중요한 지표야.
“결국 언제 끝나냐”를 나타내니까.

---

## 2-4. Waiting Time

프로세스가 Ready Queue에서 **CPU를 받지 못하고 기다린 시간**.

실행은 금방 끝나는 작업인데, 앞에 긴 작업들 때문에 오래 기다리면 waiting time이 커져.

---

## 2-5. Response Time

프로세스가 요청된 뒤 **처음으로 CPU를 할당받아 반응하기까지 걸린 시간**.

이건 인터랙티브 시스템에서 엄청 중요해.

예를 들어:

      - 버튼 눌렀는데 3초 뒤에 화면 반응 시작

      - 이건 사용자 입장에서 느림

작업 전체가 빨리 끝나는 것보다
**처음 반응이 빨리 오는 것**이 더 중요할 때가 많아.

---

## 2-6. Fairness

공정성.
어떤 프로세스가 지나치게 차별받지 않는가.

성능만 보고 짧은 작업만 계속 먼저 처리하면 긴 작업은 영원히 밀릴 수도 있어.
그러면 평균은 좋아도 시스템은 불공정해짐.
    </details>

# 3. 선점형 / 비선점형 먼저 정리 - 안해

## 3-1. 비선점 스케줄링

한 번 CPU를 받은 프로세스가
**스스로 CPU를 반납할 때까지** 뺏지 않는 방식.

즉,

    - 끝나거나

    - I/O 하러 가거나

    - 자발적으로 양보할 때까지

계속 실행됨.

### 장점

    - 구현이 단순함

    - context switching이 적음

    - 오버헤드가 작음

### 단점

    - 한 프로세스가 오래 잡으면 다른 애들이 계속 기다려야 함

    - 응답성이 나쁨

즉, 간단하지만 사용자 입장에서는 답답해질 수 있어.

---

## 3-2. 선점 스케줄링

운영체제가 필요하다고 판단하면
**실행 중인 프로세스에게서 CPU를 뺏을 수 있는 방식**.

예를 들면:

    - 더 우선순위 높은 작업이 들어옴

    - time slice가 끝남

### 장점

    - 응답성이 좋아짐

    - 중요한 작업을 빨리 처리할 수 있음

    - 인터랙티브 환경에 적합

### 단점

    - context switching이 자주 발생할 수 있음

    - 구현이 더 복잡함

    - 오버헤드 증가
  </details>

# 4. 각 스케줄링 알고리즘 자세히 - 가볍게

---

## 4-1. FCFS (First Come First Served)

말 그대로 먼저 온 순서대로 처리.

큐에 먼저 들어온 프로세스가 먼저 CPU를 받는다.

### 특징

    - 비선점형

    - 가장 단순함

    - 공평해 보이지만 실제로는 효율이 나쁠 수 있음

### 장점

    - 구현 쉬움

    - 도착 순서가 명확해서 직관적임

### 단점

    - **Convoy Effect** 발생

### Convoy Effect가 뭔데?

앞에 긴 작업 하나가 있으면 뒤에 짧은 작업들이 줄줄이 묶여서 기다리는 현상.

예를 들어:

      - P1: 20초

      - P2: 1초

      - P3: 1초

FCFS면

      - P1 먼저 20초

      - 그다음 P2

      - 그다음 P3

짧은 작업 둘은 금방 끝날 수 있었는데 긴 작업 때문에 다 막혀버림.

### 한 줄 요약

단순하지만 평균 대기시간이 커질 수 있고, 인터랙티브 환경에는 별로다.

---

## 4-2. SJF (Shortest Job First)

실행 시간이 가장 짧은 작업부터 먼저 처리.

### 핵심 아이디어

짧은 작업을 먼저 처리하면 전체 평균 대기시간이 줄어들 수 있다.

이론적으로는 **평균 waiting time을 최소화하는 데 매우 유리**해.

### 장점

    - 평균 대기시간이 작아짐

    - 짧은 작업이 빨리 끝나서 체감 성능 좋아 보일 수 있음

### 단점 1: 실행 시간을 미리 알아야 함 ⭐

현실에서 프로세스의 CPU burst time을 정확히 미리 아는 건 어렵다.

이게 SJF의 가장 큰 현실적 한계야.

### 단점 2: Starvation ⭐

짧은 작업이 계속 들어오면 긴 작업은 계속 밀릴 수 있음.

예를 들어 긴 작업 하나 기다리고 있는데 짧은 작업들이 끝없이 새로 들어오면?
그 긴 작업은 계속 뒤로 밀림.

### 한 줄 요약

이론상 예쁘지만 현실에서는 “실행 시간을 정확히 모른다”는 치명적인 문제가 있다.

---

## 4-3. SRTF (Shortest Remaining Time First)

SJF의 선점형 버전.

현재 실행 중인 프로세스보다
**남은 실행 시간이 더 짧은 프로세스가 들어오면** CPU를 뺏어서 그쪽에 줌.

### 예시

    - P1이 10초짜리인데 4초 실행 중

    - 그때 2초짜리 P2 도착

그러면 P1 남은 시간 6초 > P2 2초니까
P2가 먼저 실행됨.

### 장점

    - 평균 대기시간 측면에서 더 유리할 수 있음

    - 짧은 작업에 매우 빠르게 대응 가능

### 단점

    - context switching 증가

    - 긴 작업 starvation 가능

    - 여전히 “남은 시간”을 알아야 한다는 문제가 있음

### 한 줄 요약

SJF보다 더 공격적으로 짧은 작업을 우대하지만 현실 제약과 기아 문제가 더 강하게 드러난다.

---

## 4-4. Priority Scheduling

우선순위가 높은 프로세스를 먼저 실행.

우선순위는

    - 숫자로 줄 수도 있고

    - 시스템/사용자/프로세스 중요도 기준으로 정할 수도 있어

선점형도 가능하고 비선점형도 가능해.

### 장점

    - 중요한 작업을 먼저 처리할 수 있음

    - 시스템 프로세스나 긴급 작업 처리에 유리

### 단점: Starvation

낮은 우선순위 작업이 계속 밀릴 수 있음.

예를 들어:

    - 우선순위 높은 작업들이 계속 들어옴

    - 낮은 우선순위 작업은 영원히 CPU 못 받을 수도 있음

### 해결책: Aging

기다린 시간이 길수록 우선순위를 조금씩 올려주는 방식.

즉,

    - 처음엔 낮은 우선순위였어도

    - 너무 오래 기다리면 점점 올라가서

    - 결국 실행 기회를 얻게 함

### 한 줄 요약

중요도 기반 제어에 좋지만, 공정성을 위해 aging 같은 보완 장치가 필요하다.

---

## 4-5. Round Robin (RR) ⭐⭐⭐

각 프로세스에 **time quantum** 또는 **time slice**라는 짧은 실행 시간을 나눠준다.

    - 일정 시간 동안 실행

    - 시간이 끝나면 CPU를 빼앗김

    - Ready Queue 맨 뒤로 감

    - 다음 프로세스 실행

### 특징

    - 선점형

    - 시분할 시스템의 대표 방식

    - 모든 프로세스가 조금씩 번갈아 CPU를 받음

### 장점

    - 응답성이 좋음

    - 특정 프로세스가 CPU를 독점하기 어려움

    - 공정성이 비교적 좋음

### 단점

    - **quantum 설정이 매우 중요함**

    - **context switching 오버헤드**가 있음

---

# 5. RR의 time slice에 따른 trade-off → 진석 띠에가 함

## 5-1. time slice가 너무 길면

사실상 FCFS처럼 됨.

왜냐면 한 프로세스가 너무 오래 CPU를 잡고 있어서
다른 프로세스 입장에서는 “돌아가면서 쓴다”는 느낌이 사라짐.

### 문제

    - response time이 나빠짐

    - 인터랙티브 시스템에서 체감이 느려짐

    - 공정성도 떨어질 수 있음

예를 들어 quantum이 1초, 5초처럼 너무 길면
버튼 눌렀는데 내 작업 차례가 늦게 와서 버벅이는 느낌이 생길 수 있음.

---

## 5-2. time slice가 너무 짧으면

이번엔 반대로 context switching이 너무 자주 발생.

### context switching 때 무슨 일이 벌어지냐

운영체제는 현재 프로세스를 멈추고 다음 프로세스를 실행시키기 위해:

    - 레지스터 값 저장

    - 다음 프로세스 레지스터 복원

    - 커널 모드 진입/복귀

    - 스케줄러 실행

    - 캐시/TLB/pipeline에 영향

즉, 이 시간 동안 **실제 사용자 작업은 거의 안 하고 전환 작업만 함**.

### 결과

    - CPU는 바쁘게 움직이는 것처럼 보이지만

    - 진짜 유용한 작업량은 줄어듦

    - throughput이 떨어질 수 있음

---

## 5-3. 결국 적절한 quantum이 중요

너무 길면 응답성 감소, 너무 짧으면 오버헤드 증가.

핵심은:

> 문맥 교환 비용보다 실제 실행 시간이 충분히 커야 한다.

# 6. MLQ (Multi-Level Queue)

Ready Queue를 여러 개의 큐로 나누는 방식.

예를 들면:

  - 시스템 프로세스 큐

  - 인터랙티브 프로세스 큐

  - 배치 작업 큐

각 큐마다 다른 알고리즘을 적용할 수 있음.

예:

  - foreground: RR

  - background: FCFS

### 핵심

큐 자체를 성격별로 분리해버리는 거야.

### 장점

  - 유형이 다른 작업을 다르게 처리 가능

  - 중요한 작업과 덜 중요한 작업을 분리 가능

### 단점

  - 큐 간 이동이 안 되면 경직됨

  - 한 번 분류되면 계속 그 큐에 갇힘

  - 낮은 레벨 큐는 계속 손해볼 수 있음

### 한 줄 요약

작업 종류가 명확히 나뉠 때 유용하지만, 유연성이 부족하다.

---

# 7. MLFQ (Multi-Level Feedback Queue) ⭐⭐⭐

그냥 “큐 여러 개”가 아니라 **피드백**이 핵심이야.

MLQ는 레벨 간 이동이 거의 없는데,
MLFQ는 **프로세스의 행동에 따라 큐를 옮긴다**.

## 왜 필요?

**현실에서는 프로세스의 실행 시간을 미리 모르기 때문.**

SJF가 좋다는 건 알겠는데,
“누가 짧은 작업인지”를 사전에 모르잖아.

그래서 MLFQ는 실행하면서 추측한다.

---

## 기본 아이디어

    - 처음에는 높은 우선순위 큐에서 시작

    - CPU를 오래 쓰면: “얘 긴 작업 같네?” → 낮은 큐로 내림

    - 빨리 끝나거나 자주 양보하면: “얘 인터랙티브/짧은 작업 같네?” → 높은 큐 유지

즉,
**실행 패턴을 보고 스케줄러가 성격을 추정하는 방식**이야.

---

## 보통의 동작 방식

예를 들어 큐가 3개 있다고 하자.

    - Q0: 가장 높은 우선순위, quantum 짧음

    - Q1: 중간 우선순위, quantum 좀 더 김

    - Q2: 낮은 우선순위, quantum 김

프로세스가 처음 오면 Q0에서 시작.

### 경우 1: quantum 다 써버림

→ CPU를 오래 쓰는 작업이라고 보고 Q1로 강등

### 경우 2: quantum 다 안 쓰고 I/O 하러 감

→ 인터랙티브 작업 같다고 보고 높은 우선순위 유지

### 경우 3: 너무 오래 기다림

→ 다시 올려주기도 함
이건 starvation 방지용

---

## MLFQ의 장점 → 영관띠

### 1) 실행 시간을 몰라도 SJF 비슷하게 흉내 낼 수 있음

짧은 작업은 높은 큐에서 빨리 끝나는 경향이 있음.

### 2) 인터랙티브 작업에 유리

자주 CPU를 조금만 쓰고 I/O 하는 작업은 높은 큐에 남기 쉬움.
그래서 사용자 입력 반응이 빨라짐.

### 3) 긴 작업도 결국 처리 가능

완전히 버려지는 건 아니고, 낮은 큐에서 돌아감.

---

## 단점 → 가 한대요

    - 설계가 복잡함

    - 큐 수, quantum 크기, 승급/강등 기준 등 정책 설정이 어렵다

    - 잘못 설계하면 여전히 starvation이나 unfairness가 생길 수 있음

---

## 한 줄 핵심

MLFQ는
**“프로세스의 실제 행동을 보면서 우선순위를 동적으로 조정하는 현실적인 스케줄링 방식”**이야.

이걸 설명하면 스터디 수준이 꽤 올라간다.

---

# 8. Context Switching 비용

이 부분은 다들 “오버헤드 있음” 정도로만 말하고 지나가는데, 사실 꽤 중요해.

## 8-1. 단순 저장/복원만 있는 게 아님

프로세스 바뀔 때 운영체제는:

    - 현재 레지스터 저장

    - 다음 프로세스 레지스터 복원

    - 프로그램 카운터 복원

    - 스택 포인터 복원

이건 기본.

---

## 8-2. 캐시 친화성이 깨질 수 있음

이게 실제 성능에서 꽤 크다.

현재 실행 중인 프로세스가 CPU 캐시에 자기 데이터를 올려놨는데,
다른 프로세스로 바뀌면 그 캐시 내용이 도움이 안 될 수 있음.

그러면 다시 메모리에서 가져와야 해서 느려짐.

즉,
문맥 교환 자체의 짧은 비용보다도
**캐시 지역성이 깨지는 간접 비용**이 더 아플 수 있어.

---

## 8-3. TLB, pipeline 등도 영향

TLB → 19번, pipe → 11번에서 함…

    - 주소 변환용 TLB

    - CPU 파이프라인
이런 것도 프로세스 전환에 따라 성능 영향이 생길 수 있음.

스터디에서는 너무 하드웨어 깊게 안 가도 되지만,
최소한 “문맥 교환은 그냥 스위치 하나 누르는 수준이 아니다”는 점은 강조하면 좋다.

# 1️⃣ TLB (Translation Lookaside Buffer)

## 먼저 문제부터 보자

프로세스는 **가상 주소**를 사용한다.

근데 실제 메모리는 **물리 주소**로 접근해야 한다.

👉 그래서 매번 이런 과정이 필요함:

```plain text
가상 주소 → (페이지 테이블 조회) → 물리 주소 → 메모리 접근
```

문제는?

👉 **페이지 테이블 조회 자체도 메모리 접근이다**

→ 느림

---

## 그래서 나온 게 TLB

> “최근에 쓴 주소 변환 결과를 캐시에 저장해두는 것”

즉:

      - 가상 주소 → 물리 주소 변환 결과를

      - CPU 내부의 작은 캐시에 저장

---

## 동작

      1. CPU가 가상 주소 접근

      1. TLB 먼저 확인

### ✔ TLB hit

      - 이미 변환 정보 있음

→ 바로 물리 주소 얻음 → 빠름

### ❌ TLB miss

      - 없음

→ 페이지 테이블까지 가야 함 → 느림

---

## 핵심 요약

> TLB는 “주소 변환 캐시”다

---

## context switching과 연결

프로세스마다 주소 공간이 다르다.

👉 A 프로세스 → TLB 내용은 A 기준

👉 B 프로세스 → 완전히 다름

그래서 context switch하면:

      - TLB 내용이 무효화되거나

      - 거의 쓸모 없어짐

👉 결과:

> 다음 메모리 접근마다 TLB miss 증가 → 느려짐

---

# 2️⃣ Pipeline (CPU 파이프라인)

이건 좀 감각적으로 이해하는 게 좋다.

---

## CPU는 이렇게 일하지 않는다

“명령어 하나 → 끝 → 다음”

❌ 이렇게 안 함

---

## 대신 이렇게 한다

> 여러 명령어를 동시에 겹쳐서 처리한다

---

## 예시 (세탁기 비유)

세탁기 하나 있다고 생각해봐:

      - 빨래

      - 헹굼

      - 건조

이걸 하나씩 하면:

```plain text
A 빨래 → 헹굼 → 건조
B 빨래 → 헹굼 → 건조
```

👉 느림

---

## 파이프라인 방식

```plain text
A: 빨래
B:      빨래
C:           빨래

A:      헹굼
B:           헹굼

A:           건조
```

👉 여러 단계가 겹쳐서 진행됨 → 훨씬 빠름

---

## CPU도 똑같다

명령어 실행을 단계로 나눔:

      - Fetch (가져오기)

      - Decode (해석)

      - Execute (실행)

      - Memory access

      - Write back

👉 여러 명령어가 동시에 각 단계에 있음

---

## 핵심 요약

> pipeline은 “명령어를 겹쳐서 동시에 처리하는 구조”

---

# 3️⃣ context switching이 pipeline에 미치는 영향

이제 연결이다.

---

## 상황

      - 프로세스 A 실행 중

      - pipeline에 A의 명령어들이 꽉 차 있음

---

## context switch 발생

      - A 중단

      - B 실행 시작

---

## 문제

pipeline 안에 있던 A의 작업들:

👉 다 버려야 함 (flush)

---

## 결과

      - pipeline 다시 채워야 함

      - 그동안 CPU 효율 떨어짐

---

# 🔥 전체 연결 (TLB + Cache + Pipeline)

context switching이 왜 비싸냐면:

---

## 1️⃣ 캐시 깨짐

      - 데이터 다시 가져와야 함

## 2️⃣ TLB 깨짐

      - 주소 변환 다시 해야 함

## 3️⃣ pipeline flush

      - CPU 내부 작업 다시 채워야 함

---

👉 한 줄 핵심

> context switching은 단순한 전환이 아니라, CPU가 쌓아둔 최적화 상태를 다 초기화하는 행동이다

---

# 👍 발표용으로 한 문장 정리

이렇게 말하면 좋다:

> context switching은 레지스터 저장/복원뿐 아니라 캐시, TLB, pipeline 상태까지 영향을 주기 때문에, 단순한 전환 이상의 성능 비용을 발생시킨다.

---

여기까지 이해했으면

👉 “왜 time slice를 무작정 줄이면 안 되는지”

👉 “왜 OS가 스케줄링을 신중하게 해야 하는지”

완전히 납득되는 상태다.

---

원하면

👉 “CFS에서 이걸 어떻게 완화하려고 하는지”까지 이어서 설명해줄게.

# 9. Starvation과 Aging

## Starvation

특정 프로세스가 계속 CPU를 못 받는 상태.

완전히 영원할 수도 있고, 사실상 매우 오래일 수도 있음.

생기는 이유:

    - 짧은 작업 우대

    - 높은 우선순위 우대

    - 낮은 큐 작업 차별

즉, 성능 최적화가 지나치면 공정성이 깨진다.

---

## Aging

기다린 시간이 길수록 우선순위를 높여주는 보정 장치.

이건 그냥 테크닉이 아니라, 운영체제가 “공정성도 중요하다”는 걸 반영한 거야.

### 핵심 메시지

    - 성능만 보면 특정 작업을 계속 뒤로 미루고 싶을 수 있음

    - 하지만 시스템은 결국 모든 작업에 기회를 줘야 함

    - 그래서 aging이 필요함

---

# 10. 실제 운영체제는 왜 이론 알고리즘 하나만 안 쓰나

교재에서는 따로따로 배우니까마치 현실 OS도 하나를 택해서 쓰는 것처럼 느껴질 수 있어.

근데 실제로는 거의 그렇지 않아. 현실 시스템은 요구사항이 너무 다양하거든.

예:

  - 사용자 입력은 빨리 반응해야 하고

  - 백그라운드 작업도 돌아야 하고

  - 시스템 프로세스는 안정적으로 유지돼야 하고

  - 너무 불공정하면 안 됨

그래서 실제 OS는 보통
**우선순위, time slice, 피드백, 공정성 보정** 같은 요소를 섞어서 사용해.

즉,

> 이론 알고리즘은 개별 재료이고, 실제 OS는 그걸 섞어서 만든 실전형 정책이다.

# 11. 추가 관점

---

## 11-1. CPU-bound / I/O-bound 프로세스 차이

### CPU-bound  - CPU를 오래 쓰는 작업

CPU를 오래 쓰는 작업.
예:

      - 대규모 계산

      - 영상 인코딩

      - 과학 계산

특징:

      - 한 번 실행되면 quantum을 꽉 채우는 경우 많음

### I/O-bound - CPU를 잠깐 쓰고 IO 입력을 기다리는 작업

CPU를 잠깐 쓰고 자주 I/O 기다리는 작업.
예:

      - 키보드 입력

      - 파일 읽기

      - 네트워크 요청

특징:

      - CPU burst가 짧음

      - 자주 block 상태로 빠짐

---

### 왜 이게 중요하냐

인터랙티브 프로그램은 대개 I/O-bound 성격이 강해.

그래서 MLFQ 같은 스케줄러는
CPU를 조금만 쓰고 자주 양보하는 프로세스를 높은 우선순위로 유지해서
사용자 체감 반응을 좋게 만들 수 있어.

이거 설명하면 “왜 어떤 알고리즘이 인터랙티브에 유리한지” 연결된다.

---

## 11-2. 배치 시스템 vs 인터랙티브 시스템 vs 실시간 시스템

### 배치 시스템

사용자 즉시 반응보다 전체 처리량 중요.

    - throughput

    - turnaround time

### 인터랙티브 시스템

사용자 입력에 빨리 반응해야 함.

    - response time 중요

### 실시간 시스템

정해진 시간 안에 반드시 처리되어야 함.

    - 단순 평균 성능이 아니라 deadline이 중요

여기서 중요한 건:
**좋은 스케줄링은 상황마다 다르다**는 것.

---

## 11-3. “평균이 좋다”와 “공정하다”는 다르다

이거 질문거리로 되게 좋다.

예를 들어 SJF는 평균 waiting time에 강하지만
긴 작업 입장에서는 매우 불리할 수 있음.

즉,

    - 평균 성능 최적화

    - 개별 사용자 만족

    - 공정성

이 셋이 항상 같은 방향은 아니다.

이 말 해주면 스터디에서 생각할 포인트가 생긴다.
