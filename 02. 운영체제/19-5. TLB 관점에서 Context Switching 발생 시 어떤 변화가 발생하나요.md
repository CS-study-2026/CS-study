# 19-5. TLB 관점에서 Context Switching 발생 시 어떤 변화가 발생하나요?

## 1. Context Switching이란?

Context Switching은 CPU가 실행 중인 프로세스나 스레드를 바꾸는 작업이야.

예를 들어:

```plain text
프로세스 A 실행 중
→ 타이머 인터럽트 발생
→ OS가 프로세스 A를 중단
→ 프로세스 B 실행
```

이때 CPU 레지스터, 프로그램 카운터, 스택 포인터 같은 실행 상태를 저장하고 복원해.

그런데 TLB 관점에서도 중요한 변화가 생겨.

---

## 2. 왜 TLB가 문제가 되나?

TLB에는 현재 실행 중이던 프로세스의 주소 변환 정보가 들어 있어.

프로세스 A가 실행 중이었다면 TLB에는 A의 변환 정보가 있을 수 있어.

```plain text
TLB:

A의 가상 페이지 1 → 물리 프레임 10
A의 가상 페이지 2 → 물리 프레임 15
A의 가상 페이지 3 → 물리 프레임 21
```

그런데 Context Switching으로 프로세스 B가 실행된다고 하자.

프로세스 B도 같은 가상 주소를 사용할 수 있어.

```plain text
프로세스 A의 가상 주소 0x1000
프로세스 B의 가상 주소 0x1000
```

둘은 숫자는 같지만 완전히 다른 메모리를 의미해.

```plain text
A의 0x1000 → A의 코드 또는 데이터
B의 0x1000 → B의 코드 또는 데이터
```

그런데 TLB에 A의 정보가 남아 있는데 B가 그걸 사용하면?

```plain text
B가 0x1000 접근
→ TLB에 A의 0x1000 변환 정보가 남아 있음
→ B가 A의 물리 메모리에 접근할 위험
```

이건 심각한 보안/정확성 문제야.

---

## 3. 그래서 Context Switching 때 무엇을 해야 하나?

크게 두 가지 방식이 있어.

```plain text
1. TLB flush
2. ASID/PCID 기반으로 주소 공간 구분
```

---

# 방식 1. TLB Flush

가장 단순한 방식은 Context Switching 때 기존 TLB 내용을 비우는 거야.

```plain text
프로세스 A → 프로세스 B 전환

기존 TLB:
A의 주소 변환 정보

전환 시:
TLB flush

전환 후:
B가 실행되면서 필요한 주소 변환을 다시 TLB에 채움
```

이렇게 하면 B가 A의 TLB 정보를 잘못 사용하는 문제를 막을 수 있어.

---

## TLB flush의 단점

문제는 성능이야.

TLB를 비우면 처음에는 B의 주소 변환 정보가 거의 없어.

그래서 B가 실행되기 시작하면 TLB miss가 많이 발생해.

```plain text
Context Switch
→ TLB flush
→ 새 프로세스 실행
→ TLB miss 증가
→ page table walk 증가
→ 메모리 접근 지연 증가
```

이걸 TLB cold start처럼 생각하면 돼.

캐시를 다 비운 뒤 프로그램을 시작하면 처음에 cache miss가 많이 나듯이, TLB도 비우면 처음에 TLB miss가 많이 발생한다.

---

## 주의: TLB miss와 Page Fault는 다르다

여기서 헷갈리면 안 돼.

```plain text
TLB miss
= 주소 변환 정보가 TLB에 없음
= page table을 보면 해결될 수 있음

Page Fault
= 필요한 페이지가 RAM에 없음
= 디스크에서 가져와야 할 수 있음
```

즉, Context Switching 후 TLB miss가 늘어난다고 해서 무조건 Page Fault가 나는 건 아니야.

TLB에만 없고 page table에는 정상 매핑되어 있으면 page table walk 후 다시 TLB에 저장하면 된다.

---

# 방식 2. ASID / PCID 사용

TLB flush 비용을 줄이기 위해 TLB 엔트리에 주소 공간 식별자를 붙일 수 있어.

```plain text
ASID = Address Space Identifier
PCID = Process Context Identifier
```

개념은 이거야.

TLB 엔트리에 단순히 이렇게 저장하는 게 아니라:

```plain text
가상 페이지 1 → 물리 프레임 10
```

어느 주소 공간의 매핑인지도 같이 저장해.

```plain text
ASID A, 가상 페이지 1 → 물리 프레임 10
ASID B, 가상 페이지 1 → 물리 프레임 50
```

그러면 같은 가상 페이지 번호라도 프로세스를 구분할 수 있어.

```plain text
프로세스 A의 0x1000
프로세스 B의 0x1000

숫자는 같아도 ASID가 다르므로 구분 가능
```

---

## ASID/PCID가 있으면 뭐가 좋은가?

Context Switching 때 TLB를 전부 비우지 않아도 돼.

```plain text
프로세스 A 실행
→ A의 TLB 엔트리 저장

프로세스 B로 전환
→ B의 ASID 사용
→ A의 TLB 엔트리는 남겨둬도 B가 사용하지 않음

다시 A로 전환
→ A의 기존 TLB 엔트리 재사용 가능
```

이렇게 하면 Context Switching 후 TLB miss를 줄일 수 있어.

---

## 그래도 언제나 flush가 필요 없는 건 아님

ASID/PCID가 있어도 page table 자체가 바뀌면 해당 주소 공간의 오래된 TLB 엔트리는 무효화해야 해.

예를 들어 A 프로세스의 특정 페이지 매핑이 바뀌었다면:

```plain text
ASID A, 가상 페이지 1 → 물리 프레임 10
```

이 엔트리는 오래된 정보가 될 수 있어.

그럼 해당 엔트리는 invalidate해야 해.

즉:

```plain text
Context Switching 비용 감소
≠ TLB 무효화가 영원히 필요 없음
```

이건 구분해야 해.

---

## 4. Context Switching 시 page table base도 바뀜

프로세스마다 page table이 다르지?

Context Switching이 발생하면 OS는 현재 프로세스의 page table을 가리키는 레지스터도 바꿔야 해.

예를 들어 x86에서는 CR3 레지스터가 page table의 기준 주소를 가리켜.

개념적으로는 이렇게 보면 돼.

```plain text
프로세스 A 실행 중:
page table base = A의 page table

프로세스 B로 전환:
page table base = B의 page table
```

이게 바뀌어야 MMU가 B의 가상 주소를 B의 page table 기준으로 변환할 수 있어.

---

## 5. 스레드 전환이면 항상 TLB flush가 필요한가?

좋은 질문 포인트야.

Context Switching에는 크게 두 경우가 있어.

```plain text
1. 같은 프로세스 안의 스레드 전환
2. 서로 다른 프로세스 간 전환
```

## 같은 프로세스 안의 스레드 전환

같은 프로세스의 스레드들은 주소 공간을 공유해.

```plain text
Thread A of Process X
Thread B of Process X
```

둘은 같은 page table을 사용해.

따라서 같은 프로세스 안의 스레드 전환이라면, 주소 공간이 바뀌지 않으므로 TLB를 크게 비울 필요가 없을 수 있어.

---

## 서로 다른 프로세스 간 전환

프로세스가 바뀌면 주소 공간도 바뀐다.

```plain text
Process A
→ Process B
```

이 경우에는 이전 프로세스의 TLB 엔트리를 그대로 사용하면 안 돼.

그래서 flush하거나 ASID/PCID로 구분해야 해.

---

## 19-5 발표용 답변

> Context Switching이 발생하면 실행 주체가 바뀌고, 특히 서로 다른 프로세스 간 전환이라면 주소 공간도 바뀝니다. TLB에는 이전 프로세스의 가상 주소와 물리 주소 변환 정보가 남아 있을 수 있는데, 새 프로세스가 이 정보를 그대로 사용하면 잘못된 물리 메모리에 접근할 수 있습니다.

그래서 전통적으로는 Context Switching 시 TLB를 flush해서 이전 주소 변환 정보를 제거합니다. 하지만 TLB를 비우면 새 프로세스가 실행될 때 TLB miss가 증가하고 page table walk가 자주 발생하므로 성능 오버헤드가 생깁니다.

이를 줄이기 위해 ASID나 PCID 같은 주소 공간 식별자를 TLB 엔트리에 붙일 수 있습니다. 이렇게 하면 같은 가상 주소라도 어느 프로세스의 주소 공간에 속한 매핑인지 구분할 수 있기 때문에, Context Switching 때 TLB를 전부 비우지 않고도 안전하게 기존 엔트리를 재사용할 수 있습니다.

---

## 한 장 요약

```plain text
TLB와 MMU 위치
- 둘 다 CPU 내부에 있음
- MMU: 가상 주소 → 물리 주소 변환
- TLB: 주소 변환 결과를 캐싱
- 보통 코어마다 독립적인 TLB를 가짐

멀티코어 TLB 동기화
- page table이 바뀌면 다른 코어 TLB에 오래된 매핑이 남을 수 있음
- OS가 IPI를 보내 해당 코어들의 TLB 엔트리를 무효화
- 이 과정을 TLB Shootdown이라고 함
- 비용이 크므로 필요한 코어/주소만 무효화하려고 함

Context Switching 시 TLB 변화
- 프로세스가 바뀌면 주소 공간도 바뀜
- 이전 프로세스의 TLB 매핑을 그대로 쓰면 위험
- 해결 1: TLB flush
- 해결 2: ASID/PCID로 주소 공간을 구분해 flush 감소
- flush 후에는 TLB miss가 증가해서 성능 오버헤드 발생
```

## 추가 질문

## Q. TLB Shootdown은 왜 필요한가요?

> page table이 변경되어도 다른 코어의 TLB에는 예전 주소 변환 정보가 남아 있을 수 있기 때문입니다. 이 오래된 정보를 사용하면 잘못된 물리 주소에 접근하거나 권한 검사가 깨질 수 있으므로, OS가 다른 코어에 인터럽트를 보내 해당 TLB 엔트리를 무효화합니다.

## Q. TLB flush와 TLB Shootdown은 같은 건가요?

완전히 같은 말은 아니야.

```plain text
TLB flush
= 현재 코어의 TLB 전체 또는 일부를 비움

TLB Shootdown
= 멀티코어에서 다른 코어들의 TLB 엔트리까지 무효화하도록 요청하는 과정
```

즉, shootdown 과정 안에서 각 코어가 flush 또는 invalidate를 수행한다고 보면 돼.

## Q. Context Switching 때 왜 TLB를 비워야 하나요?

> 프로세스마다 같은 가상 주소라도 다른 물리 주소를 의미할 수 있기 때문입니다. 이전 프로세스의 TLB 매핑을 새 프로세스가 사용하면 잘못된 메모리에 접근할 수 있으므로, 주소 공간이 바뀔 때는 TLB를 비우거나 ASID/PCID로 구분해야 합니다.

## Q. 같은 프로세스의 스레드 전환에서도 TLB를 비우나요?

보통 프로세스 간 전환보다 덜 필요해.

같은 프로세스의 스레드들은 주소 공간과 page table을 공유하기 때문이야.

```plain text
같은 프로세스 내 스레드 전환
→ 주소 공간 동일
→ TLB를 유지할 수 있음

다른 프로세스로 전환
→ 주소 공간 변경
→ TLB flush 또는 ASID/PCID 구분 필요
```

## Q. TLB miss가 나면 Page Fault인가요?

아니야. 둘은 달라.

```plain text
TLB miss
= TLB에 주소 변환 정보가 없음
= page table을 조회하면 해결될 수 있음

Page Fault
= page table을 봤는데 해당 페이지가 RAM에 없음
= 디스크에서 가져와야 할 수 있음
```

즉, TLB miss는 주소 변환 캐시 미스고, Page Fault는 필요한 페이지가 물리 메모리에 없는 상황이야.
