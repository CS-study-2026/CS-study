# 15-0. 메모리의 연속할당 방식 세 가지를 설명해주세요.

# 🧠 메모리의 연속 할당 방식 (Contiguous Allocation)

# 0️⃣ 메모리 할당 방식

운영체제는 프로세스를 메모리에 적재하기 위해

크게 두 가지 방식을 사용한다.

### 📌 연속 할당 (Contiguous Allocation)

프로세스가 하나의 연속된 공간을 차지

```javascript
메모리

┌─────┬─────┬─────┬─────┐
│ OS  │ P1  │ P2  │ P3  │
└─────┴─────┴─────┴─────┘
```

### 📌 불연속 할당 (Non-Contiguous Allocation)

프로세스가 여러 영역에 나누어 저장

대표 예

- Paging

- Segmentation

```javascript
Page0 → Frame3
Page1 → Frame8
Page2 → Frame1
```

# 1️⃣ 연속 할당 방식

연속 할당은 다시

- 고정 분할

- 가변 분할

로 나뉜다.

### 📌 고정 분할 방식 (Fixed Partition)

메모리를 미리 고정 크기로 나누는 방식

```javascript
┌─────┐
│100MB│
├─────┤
│100MB│
├─────┤
│100MB│
└─────┘
```

장점

- 구현 단순

단점

- 내부 단편화 발생

### 📌 가변 분할 방식 (Variable Partition)

프로세스 크기에 맞춰 동적으로 할당

```javascript
┌─────┬─────────┬─────┐
│ OS  │   P1    │ P2  │
└─────┴─────────┴─────┘
```

장점

- 내부 단편화 감소

단점

- 외부 단편화 발생

<details>
<summary>내부 단편화와 외부 단편화</summary>

# 📌 내부 단편화

할당받은 메모리 공간 내부에서 사용되지 않고 낭비되는 공간

즉, **프로세스에게 메모리를 너무 크게 할당해서 발생하는 낭비**

---

발생 원인:

주로 **고정 분할 방식(Fixed Partition)** 에서 발생

프로세스 크기보다 큰 파티션에 할당될 경우 남은 공간을 다른 프로세스가 사용할 수 없음

---

ex)

100MB 파티션
프로세스 크기 = 70MB

```plain text
┌───────────────┐
│ 프로세스 70MB │
├───────────────┤
│ 낭비 30MB     │
└───────────────┘
```

→ 30MB가 파티션 내부에서 낭비

---

특징:

  - 할당은 성공

  - 공간은 남아 있음

  - 하지만 다른 프로세스는 사용 불가

---

해결 방법:

  - 가변 분할 방식 사용

  - Paging 사용

---

# 📌 외부 단편화

총 빈 공간은 충분하지만 연속된 공간이 부족하여 프로세스를 적재하지 못하는 현상

즉, **빈 공간이 여기저기 흩어져 발생하는 낭비**

---

발생 원인:

주로 **가변 분할 방식(Variable Partition)** 에서 발생

프로세스 생성과 종료가 반복되면서 중간중간 Hole(빈 공간)이 생성됨

---

ex)

```plain text
┌─────┬──────┬─────┬──────┬─────┐
│ P1  │10MB  │ P2  │20MB  │ P3  │
└─────┴──────┴─────┴──────┴─────┘
          ↑           ↑
         Hole        Hole
```

총 빈 공간

```plain text
10MB + 20MB = 30MB
```

---

새로운 프로세스

```plain text
25MB 필요
```

⇒

결과: ❌ 적재 불가

이유: 연속된 25MB 공간은 없음

---

특징:

  - 총 여유 공간은 충분

  - 연속 공간 부족

  - 가변 분할에서 자주 발생

---

해결 방법:

### 1️⃣ 압축(Compaction)

프로세스를 한쪽으로 몰아서

빈 공간을 하나로 합침

```plain text
Before

P1 | Hole | P2 | Hole | P3

After

P1 | P2 | P3 | Large Hole
```

단점

  - 비용 매우 큼

---

### 2️⃣ Paging

물리 메모리를 고정 크기 Frame으로 분할

→ 연속 공간이 필요 없음

→ 외부 단편화 제거

---

## 📌 한눈에 비교

| 구분 | 내부 단편화 | 외부 단편화 |
| --- | --- | --- |
| 의미 | 할당된 공간 내부 낭비 | 빈 공간이 흩어져 발생 |
| 발생 원인 | 고정 분할 | 가변 분할 |
| 공간 상태 | 공간이 너무 큼 | 공간이 조각남 |
| 해결 방법 | 가변 분할, Paging | Compaction, Paging |
</details>

---

# 2️⃣ 연속 할당이 필요한 이유

초기 운영체제에서는

- 구현이 단순

- 주소 계산이 쉬움

- 메모리 관리 비용이 적음

따라서 연속 할당 방식을 사용하였다.

---

# 3️⃣ 연속 할당의 문제

프로세스가 종료되면

```plain text
┌─────┬─────┬─────┬─────┐
│ OS  │ P1  │빈공간│ P3 │
└─────┴─────┴─────┴─────┘
```

중간에 빈 공간(Hole)이 발생한다.

---

# 4️⃣ 연속 할당 방식 3가지 (가변 분할의 배치 알고리즘)

운영체제는 새로운 프로세스를 적재할 때

어떤 Hole에 넣을지 결정해야 한다.

---

## 1️⃣ First Fit

### 📌 방법

앞에서부터 탐색

처음 발견한 충분한 공간에 즉시 배치

---

### 예

```plain text
Hole
100KB
300KB
500KB

프로세스 = 250KB
```

→ 300KB 공간에 배치

---

### 장점

- 구현 단순

- 탐색 속도 빠름

---

### 단점

- 앞부분에 작은 Hole이 많이 생성

---

# 2️⃣ Best Fit

### 📌 방법

들어갈 수 있는 공간 중

가장 작은 Hole 선택

---

### 예

```plain text
Hole
100KB
300KB
250KB-> 내가 임의로 만들었다. 영관ㅎㅎ
500KB

프로세스 = 250KB
```

→ 250KB 공간 선택

---

### 장점

- 남는 공간 최소화

---

### 단점

- 매우 작은 Hole 다수 생성

- 전체 탐색 필요

---

# 3️⃣ Worst Fit

### 📌 방법

가장 큰 Hole에 배치

---

### 예

```plain text
Hole
100KB
300KB
500KB

프로세스 = 250KB
```

→ 500KB 공간 선택

---

### 장점

- 큰 Hole 유지 가능

- 작은 조각 생성 방지

---

### 단점

- 큰 공간이 빠르게 소진

- 실제 성능 좋지 않음

---

# 5️⃣ 세 방식 비교

| 방식 | 선택 기준 |
| --- | --- |
| First Fit | 처음 발견한 공간 |
| Best Fit | 가장 알맞은 공간 |
| Worst Fit | 가장 큰 공간 |

---

| 방식 | 속도 | 단편화 |
| --- | --- | --- |
| First Fit | 빠름 | 보통 |
| Best Fit | 느림 | 높음 |
| Worst Fit | 느림 | 높음 |

---

# 6️⃣ 현대 OS는?

현대 운영체제는

- Paging (불연속 할당 기법)

- Virtual Memory

사용

# 1. Paging (페이징)

## 왜 필요한가?

연속 할당에서는 프로세스를 메모리에 넣을 때

```plain text
100MB짜리 프로세스
→ 100MB 연속 공간 필요
```

합니다.

문제는 메모리 전체에 빈 공간이 충분해도

```plain text
50MB 빈공간
30MB 빈공간
40MB 빈공간
```

처럼 흩어져 있으면 적재할 수 없습니다.

이것이 **외부 단편화(External Fragmentation)** 입니다.

---

## Paging의 핵심 아이디어

프로세스를 잘게 쪼개자!

---

### 프로세스 분할

프로세스를 일정한 크기로 나눔

```plain text
프로세스
┌────┬────┬────┬────┐
│Page0│Page1│Page2│Page3│
└────┴────┴────┴────┘
```

이 조각을 **Page(페이지)** 라고 한다.

---

### 메모리 분할

메인 메모리도 같은 크기로 나눔

```plain text
RAM

┌────┬────┬────┬────┬────┐
│Frame0│Frame1│Frame2│Frame3│Frame4│
└────┴────┴────┴────┴────┘
```

이 조각을 **Frame(프레임)** 이라고 한다.

---

## 적재 방식

페이지를 연속으로 넣지 않아도 된다.

예)

```plain text
Page0 → Frame5
Page1 → Frame2
Page2 → Frame10
Page3 → Frame7
```

메모리 모습

```plain text
RAM

Frame0
Frame1
Frame2  ← Page1
Frame3
Frame4
Frame5  ← Page0
Frame6
Frame7  ← Page3
Frame8
Frame9
Frame10 ← Page2
```

프로세스가 메모리에 흩어져 존재할 수 있다.

---

## 주소 변환

CPU는

```plain text
논리 주소(Logical Address)
```

를 사용한다.

예)

```plain text
(Page 번호, Offset)

(2, 100)
```

의미

```plain text
Page 2의 100번째 바이트
```

---

운영체제는

### 페이지 테이블(Page Table)

을 이용한다.

예)

| Page | Frame |
| --- | --- |
| 0 | 5 |
| 1 | 2 |
| 2 | 10 |
| 3 | 7 |

---

CPU 요청

```plain text
(Page2, 100)
```

↓

페이지 테이블 조회

```plain text
Page2 → Frame10
```

↓

실제 주소

```plain text
(Frame10, 100)
```

---

## Paging의 장점

### ① 외부 단편화 제거

연속 공간이 필요 없음

---

### ② 메모리 활용도 증가

빈 프레임만 있으면 적재 가능

---

### ③ 가상 메모리 구현 가능

Virtual Memory의 기반 기술

---

## Paging의 단점

### 내부 단편화(Internal Fragmentation)

페이지 크기가 4KB라고 가정

프로세스 마지막 페이지

```plain text
3000B 사용
4096B 확보
```

남는 공간

```plain text
1096B 낭비
```

---

즉

Paging은

  - 외부 단편화 제거

  - 대신 내부 단편화 발생

---

# 2. Virtual Memory (가상 메모리)

---

## 왜 필요한가?

예전 방식

```plain text
프로세스 전체
↓
RAM 적재
↓
실행
```

---

문제

RAM = 8GB

프로세스 = 20GB

```plain text
실행 불가
```

---

또는

프로그램 대부분은 실제로 사용되지 않는다.

예)

```plain text
크롬
↓
설정창 코드
↓
인쇄 기능
↓
확장 프로그램
```

실행 순간에는 일부만 사용

---

그래서 나온 개념

## "필요한 부분만 RAM에 올리자"

---

# Virtual Memory 개념

CPU는

```plain text
큰 메모리가 있다고 착각
```

한다.

예)

```plain text
실제 RAM
8GB
```

하지만

```plain text
가상 주소 공간
128TB
```

처럼 사용할 수 있다.

(64비트 OS 기준)

---

## 구조

```plain text
CPU
 ↓
가상 주소
 ↓
페이지 테이블
 ↓
RAM
 ↓
디스크(SSD/HDD)
```

---

## 필요한 페이지만 RAM에 적재

예)

프로세스

```plain text
Page0
Page1
Page2
Page3
Page4
Page5
Page6
Page7
```

---

RAM

```plain text
Page0
Page1
Page3
```

만 존재

---

나머지

```plain text
Page2
Page4
Page5
Page6
Page7
```

은 SSD에 저장

---

# Demand Paging (요구 페이징)

현대 OS가 사용하는 방식

---

### 처음 실행

RAM

```plain text
Page0
Page1
```

만 적재

---

CPU가

```plain text
Page5 사용
```

요청

↓

RAM에 없음

↓

Page Fault 발생

↓

OS 개입

↓

SSD에서 Page5 읽음

↓

RAM 적재

↓

실행 재개

---

# Page Fault

정의

> 필요한 페이지가 메모리에 없어서 운영체제가 디스크에서 가져오는 현상

---

과정

```plain text
CPU 접근
 ↓
페이지 없음
 ↓
Page Fault
 ↓
OS 호출
 ↓
디스크 접근
 ↓
RAM 적재
 ↓
실행 재개
```

---

## 페이지 교체(Page Replacement)

RAM이 꽉 찼다면?

```plain text
새 페이지
들어와야 함
```

↓

기존 페이지 하나 제거

---

대표 알고리즘

### FIFO

먼저 들어온 페이지 제거

---

### LRU

가장 오래 사용되지 않은 페이지 제거

실제 OS에서 많이 사용

---

### Optimal

앞으로 가장 늦게 사용될 페이지 제거

이론적 최적

---

# Virtual Memory의 장점

### ① RAM보다 큰 프로그램 실행 가능

```plain text
RAM = 8GB
프로그램 = 20GB
```

실행 가능

---

### ② 멀티프로그램 효율 증가

더 많은 프로세스 동시 실행

---

### ③ 메모리 사용량 감소

필요한 부분만 적재

---

### ④ 프로세스 격리

프로세스마다 독립적인 가상 주소 공간 제공

보안성 향상

---

# Paging과 Virtual Memory의 관계

많이 헷갈리는 부분입니다.

### Paging

> 메모리를 페이지 단위로 관리하는 기술

---

### Virtual Memory

> Paging을 이용해서 실제 메모리보다 큰 메모리를 사용하는 개념

---

즉

```plain text
Paging
   ↓
기반 기술
   ↓
Virtual Memory
```

관계입니다.

---

# 한눈에 정리

```plain text
연속 할당
 └─ 외부 단편화 발생

Paging
 ├─ Page / Frame 사용
 ├─ 비연속 적재 가능
 ├─ 외부 단편화 제거
 └─ 내부 단편화 발생

Virtual Memory
 ├─ Paging 기반
 ├─ 필요한 Page만 RAM 적재
 ├─ 나머지는 SSD/HDD 저장
 ├─ Page Fault 발생 가능
 └─ RAM보다 큰 프로그램 실행 가능
```

운영체제 시험에서는 특히 **"Page → Frame 매핑", "Page Fault 발생 과정", "Paging과 Virtual Memory의 차이"** 세 가지가 가장 자주 출제됩니다.
</details>

따라서 순수 연속 할당은 거의 사용하지 않는다.

---

# 📌 핵심 정리

- 연속 할당은 프로세스를 하나의 연속된 공간에 적재하는 방식

- 외부 단편화 문제가 발생

- 대표 알고리즘은 First Fit, Best Fit, Worst Fit

- 현대 OS는 대부분 Paging 사용
