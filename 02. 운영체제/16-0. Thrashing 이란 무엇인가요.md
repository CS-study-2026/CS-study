# 16-0. Thrashing 이란 무엇인가요?

# 16. Thrashing이란 무엇인가요?

## 1. 한 줄 정의

**Thrashing은 프로세스들이 실제 연산보다 페이지를 메모리에 올리고 내리는 작업에 대부분의 시간을 쓰게 되어, 시스템 성능이 급격히 떨어지는 현상**이야.

조금 더 정확히 말하면:

> 실행 중인 프로세스들이 필요한 페이지를 충분히 물리 메모리에 유지하지 못해서 Page Fault가 과도하게 발생하고, CPU는 계산을 거의 못 한 채 디스크 I/O와 페이지 교체 작업에 시간을 빼앗기는 상태

---

## 2. Thrashing은 왜 발생하나요?

가상 메모리에서는 프로그램 전체를 한 번에 메모리에 올리지 않고, 필요한 페이지만 물리 메모리에 올려서 실행해.

문제는 이때 프로세스가 자주 사용하는 페이지 집합, 즉 **Working Set**이 물리 메모리에 충분히 올라와 있어야 한다는 거야.

예를 들어 어떤 프로세스가 당장 원활히 실행되려면 다음 페이지들이 필요하다고 해보자.

```plain text
프로세스 A의 현재 작업 집합: P1, P2, P3, P4, P5
```

그런데 이 프로세스에 할당된 물리 프레임이 3개뿐이면?

```plain text
메모리에 올라올 수 있는 페이지: P1, P2, P3
필요하지만 없는 페이지: P4, P5
```

그러면 P4가 필요할 때 Page Fault가 발생해.

P4를 올리려면 기존 페이지 하나를 내보내야 해.

그런데 내보낸 페이지가 곧 다시 필요하면 또 Page Fault가 발생해.

이 과정이 반복되면 시스템은 이런 상태가 돼.

```plain text
페이지 필요
 → Page Fault 발생
 → 디스크에서 페이지 읽기
 → 기존 페이지 내보내기
 → 다시 실행
 → 또 Page Fault 발생
 → 또 디스크 I/O
 → 반복
```

결국 CPU는 실제 프로그램 명령을 처리하기보다, 페이지를 교체하느라 시간을 낭비하게 돼.

---

## 3. Thrashing의 핵심 원인

### 1. 물리 메모리보다 활성 작업 집합이 너무 큼

프로세스 하나만 봐도 문제지만, 보통은 여러 프로세스가 동시에 실행될 때 더 심해져.

```plain text
프로세스 A의 Working Set: 200MB
프로세스 B의 Working Set: 300MB
프로세스 C의 Working Set: 400MB

필요한 총 메모리: 900MB
실제 사용 가능한 물리 메모리: 600MB
```

이러면 모든 프로세스가 자신에게 필요한 페이지를 안정적으로 유지하지 못해.

결과적으로 서로 페이지를 밀어내면서 Page Fault가 폭증한다.

---

### 2. 다중 프로그래밍 정도가 너무 높음

OS는 CPU 활용률을 높이기 위해 여러 프로세스를 동시에 메모리에 올려두고 실행해.

그런데 너무 많은 프로세스를 메모리에 올리면 각 프로세스가 사용할 수 있는 프레임 수가 줄어들어.

```plain text
프로세스 수 증가
 → 각 프로세스에 할당되는 프레임 감소
 → Page Fault 증가
 → 디스크 I/O 증가
 → CPU 대기 증가
 → CPU 사용률 감소
```

여기서 중요한 함정이 있어.

CPU 사용률이 낮아졌다고 해서 OS가 단순히 “프로세스를 더 올리자”고 판단하면 상황이 더 나빠질 수 있어.

```plain text
CPU 사용률 낮음
 → 더 많은 프로세스 투입
 → 메모리 부족 심화
 → Page Fault 더 증가
 → CPU 사용률 더 감소
```

이 악순환이 Thrashing의 전형적인 흐름이야.

---

### 3. Page Replacement가 계속 실패함

페이지 교체 알고리즘이 어떤 페이지를 내보낼지 결정하는데, Thrashing 상황에서는 내보낸 페이지가 곧 다시 필요해지는 일이 많아.

예를 들어:

```plain text
1. A 페이지가 필요함
2. A를 올리기 위해 B를 내보냄
3. 곧바로 B가 필요함
4. B를 올리기 위해 C를 내보냄
5. 곧바로 C가 필요함
```

이런 식이면 교체 알고리즘이 어떤 걸 선택하든 큰 효과가 없어져.

문제의 본질은 교체 알고리즘 하나가 아니라 **프로세스가 필요로 하는 페이지 수에 비해 물리 메모리가 부족하다**는 데 있어.

---

## 4. Thrashing이 발생했을 때의 증상

Thrashing이 발생하면 보통 다음 증상이 나타나.

| 증상 | 설명 |
| --- | --- |
| Page Fault 비율 증가 | 필요한 페이지가 메모리에 없어 계속 Fault 발생 |
| 디스크 I/O 급증 | 페이지를 swap 영역이나 디스크에서 계속 읽고 씀 |
| CPU 사용률 감소 | CPU가 계산하지 못하고 I/O 대기 상태에 빠짐 |
| 응답 시간 증가 | 프로그램이 멈춘 것처럼 느려짐 |
| 처리량 감소 | 단위 시간당 완료되는 작업 수가 줄어듦 |

중요한 건 **CPU가 바빠서 느린 게 아니라, CPU가 일을 못 해서 느린 상태**라는 점이야.

---

## 5. Cache Miss와 Thrashing의 차이

발표 때 헷갈릴 수 있어서 짚고 가면 좋아.

| 구분 | Cache Miss | Page Fault / Thrashing |
| --- | --- | --- |
| 대상 | CPU Cache ↔ RAM | RAM ↔ Disk |
| 비용 | 비교적 작음 | 매우 큼 |
| 원인 | 캐시에 데이터가 없음 | 물리 메모리에 페이지가 없음 |
| 결과 | RAM에서 캐시로 가져옴 | 디스크에서 RAM으로 가져옴 |
| 심각도 | 성능 저하 | 시스템 전체 성능 붕괴 가능 |

즉, Thrashing은 단순히 “캐시가 안 맞아서 느린 현상”이 아니야.

**RAM보다 훨씬 느린 디스크 I/O가 계속 발생하는 문제**라서 훨씬 심각해.

# RAM 크기에 따른 로그 정렬 알고리즘 선택 정리 → pt 문제였음

## 0. 문제 상황

어떤 프로그램이 로그를 저장하고 있는데, 로그가 날짜순으로 저장되어 있지 않고 무작위 순서로 저장되어 있다고 하자.

```plain text
원본 로그

2026-05-03 log A
2026-01-11 log B
2026-04-20 log C
2025-12-30 log D
2026-02-14 log E
...
```

요구사항은 보통 다음과 같이 해석할 수 있어.

> 무작위로 저장된 대량의 로그를 날짜 기준으로 정렬하거나, 날짜순으로 처리해야 한다.

이때 핵심 질문은 이거야.

> RAM 크기가 다르면 어떤 정렬 알고리즘을 선택해야 하는가?

---

# 1. 핵심 결론

전체 결론부터 말하면 이거야.

| RAM 크기 | 선택할 방식 | 핵심 아이디어 |
| --- | --- | --- |
| RAM 무제한 | In-memory Sort | 전체 로그를 RAM에 올려 정렬 |
| RAM 중간 크기 | External Merge Sort | chunk 단위로 정렬 후 병합 |
| RAM 매우 작음 | Priority Queue 기반 External Sort + Polyphase Merge Sort | 작은 메모리로 긴 run을 만들고 효율적으로 병합 |

한 줄로 정리하면:

> RAM에 다 올라가면 내부 정렬, RAM에 다 안 올라가면 외부 정렬, RAM이 아주 작으면 우선순위 큐 기반 run 생성과 Polyphase Merge로 병합한다.

---

# 2. RAM이 무제한일 때

## 선택 알고리즘

```plain text
In-memory Sort
```

RAM이 충분하다면 가장 단순하게 전체 로그를 메모리에 올려서 정렬하면 돼.

```plain text
1. 전체 로그를 RAM에 적재
2. 날짜를 기준으로 정렬
3. 정렬된 결과를 파일에 저장
```

---

## 예시

```plain text
입력:
[5일, 1일, 4일, 2일, 3일]

RAM에 전부 올림:
[5일, 1일, 4일, 2일, 3일]

정렬:
[1일, 2일, 3일, 4일, 5일]
```

---

## 장점

  - 구현이 가장 단순함

  - 디스크 I/O가 적음

  - 전체 데이터를 메모리에서 정렬하므로 빠름

---

## 단점

  - 전체 로그가 RAM보다 작을 때만 가능

  - 실제 로그 데이터는 매우 커질 수 있어서 항상 가능한 방식은 아님

---

## 발표용 답변

> RAM이 무제한이라면 전체 로그를 메모리에 적재한 뒤 날짜를 key로 내부 정렬을 수행하겠습니다. 이 경우 일반적인 `O(N log N)` 정렬 알고리즘을 사용할 수 있고, 디스크 I/O는 입력과 출력 정도로 제한됩니다.

---

# 3. RAM이 4096MB처럼 중간 크기일 때

## 선택 알고리즘

```plain text
External Merge Sort
```

RAM이 4GB라고 해도 전체 로그가 수십 GB, 수백 GB라면 한 번에 메모리에 올릴 수 없어.

이때는 **외부 정렬**을 사용해야 해.

---

## External Merge Sort 흐름

```plain text
1. 로그 파일을 RAM에 들어갈 수 있는 chunk 단위로 나눈다.
2. 각 chunk를 RAM에 올린다.
3. chunk 내부를 날짜순으로 정렬한다.
4. 정렬된 chunk를 임시 파일, 즉 sorted run으로 저장한다.
5. 여러 sorted run을 병합한다.
6. 최종 날짜순 로그 파일을 만든다.
```

---

## 그림으로 보면

```plain text
원본 로그 파일
[무작위 로그 100GB]

RAM 4GB

↓ chunk 단위로 읽기

chunk1 → 정렬 → run1
chunk2 → 정렬 → run2
chunk3 → 정렬 → run3
chunk4 → 정렬 → run4
...

↓ 병합

run1 + run2 + run3 + run4 + ...
→ 최종 정렬 파일
```

---

## 왜 chunk를 RAM 크기만큼 꽉 채우면 안 되나?

RAM이 4096MB라고 해서 chunk를 4096MB로 잡으면 위험해.

실제로는 다음 메모리도 필요해.

```plain text
- 정렬할 로그 데이터
- 정렬 알고리즘의 추가 메모리
- 입력 버퍼
- 출력 버퍼
- 객체 오버헤드
- 프로그램 실행 메모리
- OS가 사용하는 메모리
```

그래서 보통은 여유를 둬야 해.

```plain text
RAM 4096MB
→ chunk 1GB ~ 2GB 정도로 설정
```

이런 식으로 잡는 게 안전해.

---

# 4. External Merge Sort의 병합 단계

정렬된 run들이 여러 개 생겼다고 하자.

```plain text
run1: 1일, 4일, 7일
run2: 2일, 5일, 8일
run3: 3일, 6일, 9일
```

이걸 날짜순으로 합치려면 각 run의 맨 앞 원소만 비교하면 돼.

초기 상태:

```plain text
run1의 현재 값: 1일
run2의 현재 값: 2일
run3의 현재 값: 3일
```

가장 작은 `1일`을 출력하고, run1에서 다음 값인 `4일`을 가져와.

```plain text
출력: 1일

현재 후보:
run1: 4일
run2: 2일
run3: 3일
```

이걸 반복하면 최종 정렬 결과가 만들어져.

---

## 여기서 Priority Queue를 사용할 수 있음

여러 run의 현재 후보 중 가장 작은 날짜를 빠르게 찾기 위해 **Priority Queue**, 정확히는 **min-heap**을 사용할 수 있어.

```plain text
PQ:
1일 from run1
2일 from run2
3일 from run3
```

가장 작은 값을 꺼낸 뒤, 해당 run에서 다음 값을 다시 PQ에 넣는다.

```plain text
1일 꺼냄
→ run1에서 4일 읽음
→ PQ에 4일 삽입
```

즉, External Merge Sort의 병합 단계에서 Priority Queue를 쓰는 건 자연스러운 방식이야.

---

## 발표용 답변

> RAM이 4096MB처럼 제한되어 있고 전체 로그가 메모리에 다 올라가지 않는다면 External Merge Sort를 사용하겠습니다. 로그를 메모리에 들어갈 수 있는 chunk 단위로 읽고, 각 chunk를 날짜순으로 정렬해 sorted run으로 저장합니다. 이후 여러 run의 현재 후보를 Priority Queue에 넣고, 가장 빠른 날짜의 로그를 하나씩 꺼내는 방식으로 k-way merge를 수행합니다.

---

# 5. RAM이 512MB처럼 매우 작을 때

여기서부터가 이 문제의 핵심이야.

RAM이 아주 작으면 단순 External Merge Sort도 동작은 하지만, 문제가 생길 수 있어.

---

## 문제 1. chunk 크기가 작아진다

RAM이 작으면 한 번에 정렬할 수 있는 chunk 크기도 작아져.

예를 들어 원본 로그가 100GB라고 하자.

```plain text
RAM 4GB
→ chunk 1GB
→ run 약 100개

RAM 512MB
→ chunk 128MB
→ run 약 800개
```

run이 많아지면 병합해야 할 파일이 많아지고, 병합 횟수도 늘어나.

---

## 문제 2. 한 번에 병합할 수 있는 run 수가 제한된다

k-way merge를 하려면 각 run마다 입력 버퍼가 필요해.

```plain text
100개 run을 한 번에 병합
→ 입력 버퍼 100개 필요
→ 파일 핸들 100개 필요
→ PQ 원소 100개 필요
```

RAM이 아주 작으면 한 번에 너무 많은 run을 병합하기 어렵다.

그래서 이때는 다음 전략이 필요해.

```plain text
1. Priority Queue 기반 External Sort로 긴 sorted run 생성
2. Polyphase Merge Sort로 run 병합
```

---

# 6. Priority Queue 기반 External Sort

여기서 말하는 Priority Queue 기반 External Sort는 단순히 전체 로그를 PQ에 넣는다는 뜻이 아니야.

그건 틀린 방식이야.

```plain text
전체 로그 100GB
RAM 512MB

전체 로그를 PQ에 넣음
→ RAM 초과
→ swap 발생
→ Page Fault 폭증
→ Thrashing 위험
```

정확한 의미는 이거야.

> RAM에 들어가는 일부 로그만 Priority Queue에 유지하면서, 정렬된 run을 생성한다.

이때 대표적으로 사용하는 방식이 **Replacement Selection**이야.

---

# 7. Replacement Selection

## 목적

Replacement Selection의 목적은 이거야.

> 작은 RAM으로도 가능한 한 긴 sorted run을 만드는 것

일반 chunk sort는 RAM 크기만큼만 run을 만들 수 있어.

```plain text
RAM에 5개 로그 저장 가능

chunk sort:
run1 길이 5
run2 길이 5
run3 길이 5
...
```

그런데 Replacement Selection을 쓰면 평균적으로 RAM 크기보다 긴 run을 만들 수 있어.

---

## 동작 방식

```plain text
1. RAM에 들어갈 만큼 로그를 min-heap에 넣는다.
2. heap에서 가장 날짜가 빠른 로그를 꺼내 현재 run에 출력한다.
3. 입력 파일에서 새 로그를 하나 읽는다.
4. 새 로그가 방금 출력한 로그보다 날짜가 같거나 뒤라면 현재 run에 넣는다.
5. 새 로그가 방금 출력한 로그보다 앞선 날짜라면 현재 run에는 넣지 않고 다음 run으로 넘긴다.
6. 현재 run에 넣을 수 있는 로그가 없어질 때까지 반복한다.
```

---

## 예시

입력 로그가 이렇게 들어온다고 하자.

```plain text
입력:
5, 1, 9, 3, 8, 2, 7, 4, 6
```

RAM에는 3개만 들어간다고 하자.

초기 heap:

```plain text
heap: 1, 5, 9
```

가장 작은 1을 출력한다.

```plain text
출력: 1
다음 입력: 3
```

3은 1보다 크니까 현재 run에 들어갈 수 있어.

```plain text
heap: 3, 5, 9
```

다음 3을 출력한다.

```plain text
출력: 1, 3
다음 입력: 8
```

8도 3보다 크니까 현재 run에 들어갈 수 있어.

```plain text
heap: 5, 8, 9
```

이런 식으로 진행하면 RAM에는 3개밖에 못 올려도 run 길이가 3보다 길어질 수 있어.

---

## 핵심 장점

```plain text
작은 RAM
→ 더 긴 sorted run 생성 가능
→ run 개수 감소
→ merge pass 감소
→ 디스크 I/O 감소
```

RAM이 아주 작을 때 유리한 이유가 여기 있어.

---

# 8. Polyphase Merge Sort

## Polyphase Merge Sort란?

Polyphase Merge Sort는 외부 정렬에서 여러 sorted run을 병합하는 방식 중 하나야.

특히 다음 상황에서 의미가 있어.

```plain text
- RAM이 작다
- 입력/출력 버퍼가 제한적이다
- 사용할 수 있는 작업 파일 수가 제한적이다
- run 개수가 많다
```

---

## 일반적인 Balanced Merge

일반적인 병합은 run을 여러 파일에 균등하게 나누고 병합해.

예를 들어 작업 파일이 3개 있다고 하자.

```plain text
A: run 1, run 2, run 3
B: run 4, run 5, run 6
C: 비어 있음
```

A와 B를 병합해서 C에 쓰는 식으로 진행할 수 있어.

문제는 어떤 단계에서는 파일이 비거나, 불필요한 복사 작업이 많이 생길 수 있다는 거야.

---

## Polyphase Merge의 아이디어

Polyphase Merge는 run을 일부러 균등하게 나누지 않아.

예를 들어:

```plain text
A: run 5개
B: run 3개
C: 비어 있음
```

이 상태에서 A와 B를 병합해서 C에 쓴다.

```plain text
A + B → C
```

어느 한 파일이 비면 역할을 바꾼다.

```plain text
B가 비었음

다음 단계:
A + C → B
```

다시 어느 파일이 비면 또 역할을 바꾼다.

```plain text
A가 비었음

다음 단계:
B + C → A
```

이렇게 입력 파일과 출력 파일의 역할을 계속 바꿔가면서 병합한다.

---

## 왜 Polyphase가 도움이 되나?

핵심은 이거야.

> 제한된 파일 수와 버퍼 수로도 run들을 효율적으로 병합하기 위한 방식

특히 작업 파일이 적을 때, 불필요한 복사나 빈 파일 낭비를 줄이는 데 도움이 돼.

다만 현실적으로는 요즘 시스템에서는 단순 multi-way merge도 많이 사용해.

그래서 발표할 때는 이렇게 말하는 게 안전해.

> 현대 시스템에서는 balanced multi-way merge도 많이 사용되지만, RAM과 작업 파일 수가 제한된 조건에서는 Polyphase Merge Sort가 외부 정렬의 병합 전략으로 사용될 수 있습니다.

이렇게 말하면 과장 없이 정확해.

---

# 9. 세 가지 상황 최종 비교


```plain text
In-memory Sort
```

```plain text
전체 로그 읽기

```








# 10. Thrashing과 연결하기

이 문제는 네가 맡은 **Thrashing** 주제랑도 잘 연결돼.

RAM이 작은데 전체 로그를 억지로 메모리에 올리려고 하면 어떻게 될까?

```plain text
전체 로그 적재 시도
→ RAM 부족
→ OS가 swap 사용
→ Page Fault 증가
→ 디스크 I/O 폭증
→ Thrashing 발생 가능
```

이러면 정렬이 느려지는 정도가 아니라, 시스템 전체가 멈춘 것처럼 느려질 수 있어.

그래서 작은 RAM 환경에서는 OS에게 맡기면 안 되고, 애플리케이션이 직접 메모리 사용량을 제어해야 해.

```plain text
나쁜 방식:
전체 데이터를 메모리에 올리고 OS swap에 의존

좋은 방식:
chunk, buffer, run 개수를 직접 제어하는 External Sort
```

발표에서 이렇게 연결하면 좋아.

> RAM이 부족한 상황에서 전체 로그를 메모리에 올리려 하면 Page Fault가 과도하게 발생하고 Thrashing으로 이어질 수 있습니다. 따라서 대용량 로그 정렬에서는 메모리에 올라가는 데이터 양을 명시적으로 제한하는 External Sort가 필요합니다.

---

# 11. 이 문제의 진짜 평가 포인트

이 문제는 단순히 정렬 알고리즘 이름을 묻는 게 아니야.

아마 면접관이 보고 싶었던 건 이거야.

## 1. 데이터 크기와 RAM 크기를 비교할 수 있는가?

```plain text
데이터가 RAM보다 작다
→ 내부 정렬

데이터가 RAM보다 크다
→ 외부 정렬
```

---

## 2. 디스크 I/O 비용을 고려하는가?

대용량 로그는 RAM 안에서만 처리할 수 없으니까 디스크 I/O가 중요해.

```plain text
랜덤 I/O 많이 발생
→ 느림

순차 I/O 중심 처리
→ 상대적으로 효율적
```

External Sort는 가능하면 순차 읽기/쓰기를 중심으로 동작하게 만들 수 있어.

---

## 3. RAM이 작을 때 swap에 의존하지 않는가?

작은 RAM에서 전체 데이터를 억지로 올리는 건 위험해.

```plain text
swap 의존
→ Page Fault 증가
→ Thrashing 위험
```

---

## 4. 우선순위 큐를 정확히 이해하고 있는가?

중요한 오해는 이거야.

```plain text
틀린 이해:
전체 로그를 Priority Queue에 넣는다.

정확한 이해:
제한된 RAM 안에서 일부 후보만 Priority Queue에 넣는다.
```

Priority Queue는 전체 데이터를 담는 저장소가 아니라, **현재 후보 중 가장 빠른 날짜를 고르는 도구**야.

---

## 5. Polyphase Merge를 병합 전략으로 이해하는가?

Polyphase Merge는 run을 만드는 알고리즘이라기보다는, 만들어진 sorted run들을 효율적으로 병합하는 전략이야.

---

# 12. 발표용 최종 스크립트

그대로 읽어도 되는 버전으로 정리하면 이래.

> 이 문제는 무작위 순서로 저장된 로그를 날짜순으로 정렬해야 할 때, RAM 크기에 따라 어떤 알고리즘을 선택할 것인지 묻는 문제로 볼 수 있습니다.

먼저 RAM이 무제한이라면 가장 단순하게 전체 로그를 메모리에 올리고 날짜 기준으로 내부 정렬을 수행하면 됩니다. 이 경우 일반적인 `O(N log N)` 정렬을 사용하면 되고, 디스크 I/O는 입력과 출력 정도로 제한됩니다.

하지만 RAM이 4096MB처럼 제한되어 있고 전체 로그가 메모리에 다 올라가지 않는다면 External Merge Sort를 사용해야 합니다. 로그를 메모리에 들어갈 수 있는 chunk 단위로 읽고, 각 chunk를 날짜순으로 정렬한 뒤 sorted run으로 저장합니다. 이후 여러 run을 병합해서 최종 정렬 파일을 만듭니다. 병합 단계에서는 각 run의 현재 후보를 Priority Queue에 넣고, 가장 날짜가 빠른 로그를 하나씩 꺼내는 k-way merge를 사용할 수 있습니다.

RAM이 512MB처럼 매우 작다면 단순 chunk sort만으로는 run 개수가 너무 많아질 수 있습니다. 이때는 Priority Queue 기반 External Sort, 구체적으로 Replacement Selection을 사용해 작은 메모리로 가능한 긴 sorted run을 생성할 수 있습니다. 이후 생성된 run들은 Polyphase Merge Sort 방식으로 병합할 수 있습니다. Polyphase Merge는 작업 파일이나 버퍼 수가 제한된 상황에서 run들을 효율적으로 병합하기 위한 외부 정렬 전략입니다.

중요한 점은 Priority Queue에 전체 로그를 넣는 것이 아니라는 점입니다. 전체 데이터를 넣으면 RAM을 초과하고 OS swap에 의존하게 되며, Page Fault가 폭증해 Thrashing이 발생할 수 있습니다. 따라서 작은 RAM 환경에서는 애플리케이션이 chunk 크기, buffer 크기, run 개수, merge fan-in을 직접 제어하는 외부 정렬 방식을 사용해야 합니다.

---

# 13. 예상 질문과 답변

## Q1. RAM이 작으면 왜 그냥 Priority Queue에 다 넣으면 안 되나요?

Priority Queue도 메모리 자료구조라서 전체 로그를 넣으면 RAM을 초과해.

그러면 OS swap을 쓰게 되고 Page Fault가 급증해서 Thrashing이 발생할 수 있어.

정확한 방식은 전체 로그가 아니라 **현재 처리 가능한 일부 로그만 PQ에 유지**하는 거야.

---

## Q2. External Merge Sort와 Priority Queue 기반 External Sort는 다른 건가요?

완전히 다른 개념이라기보다는 External Sort 안에서 Priority Queue를 활용하는 방식이라고 보면 돼.

Priority Queue는 보통 두 곳에서 쓰일 수 있어.

| 위치 | 역할 |
| --- | --- |
| run 생성 단계 | Replacement Selection으로 긴 run 생성 |
| run 병합 단계 | k-way merge에서 가장 작은 현재 후보 선택 |

---

## Q3. Replacement Selection은 왜 쓰나요?

작은 RAM으로도 더 긴 sorted run을 만들기 위해서야.

run이 길어지면 run 개수가 줄고, 병합 횟수도 줄어서 디스크 I/O 비용을 줄일 수 있어.

---

## Q4. Polyphase Merge Sort는 왜 쓰나요?

작업 파일 수나 버퍼 수가 제한된 환경에서 여러 sorted run을 효율적으로 병합하기 위해 사용해.

특히 RAM이 작고 run이 많을 때 병합 전략으로 고려할 수 있어.

---

## Q5. 요즘도 꼭 Polyphase Merge를 써야 하나요?

꼭 그런 건 아니야.

요즘 시스템에서는 디스크, SSD, 파일 핸들, 버퍼 관리 방식이 예전과 달라서 balanced multi-way merge도 많이 사용해.

다만 면접 문제에서 RAM이 매우 작고 “Priority Queue 기반 External Sort / Polyphase Merge Sort”가 답으로 나왔다면, 의도는 **작은 메모리에서 run 생성과 병합 전략을 분리해서 설명할 수 있는지**였다고 보면 돼.

---


# 제일 중요한 문장

발표에서 이것만 제대로 말해도 좋아.

> RAM이 충분하면 내부 정렬을 사용하고, RAM보다 데이터가 크면 External Merge Sort를 사용합니다. RAM이 매우 작으면 단순 chunk sort로는 run이 너무 많아지므로 Priority Queue 기반 Replacement Selection으로 긴 sorted run을 만들고, Polyphase Merge Sort로 제한된 파일과 버퍼 안에서 병합합니다. 이 방식은 전체 데이터를 메모리에 올리지 않기 때문에 Page Fault 폭증과 Thrashing을 피할 수 있습니다.
