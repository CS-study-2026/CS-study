# 16-1. Thrashing 발생 시, 어떻게 완화할 수 있을까요?

# 16-1. Thrashing 발생 시 어떻게 완화할 수 있나요?

## 1. 핵심 방향

Thrashing을 완화하는 방법은 결국 하나로 정리할 수 있어.

> 각 프로세스가 현재 실행에 필요한 페이지 집합을 물리 메모리에 유지할 수 있도록 만들어야 한다.

방법은 크게 네 가지야.

1. 동시에 실행되는 프로세스 수를 줄인다.

1. 프로세스에 더 많은 프레임을 할당한다.

1. Working Set을 기준으로 메모리를 관리한다.

1. 프로그램 자체의 메모리 접근 지역성을 개선한다.

---

## 2. 다중 프로그래밍 정도 줄이기

가장 직접적인 방법이야.

현재 물리 메모리로 감당할 수 있는 수준보다 많은 프로세스가 올라와 있다면, 일부 프로세스를 잠시 중단하거나 swap out해서 메모리에서 빼야 해.

```plain text
너무 많은 프로세스 실행
 → 각 프로세스의 프레임 부족
 → Thrashing 발생

해결:
일부 프로세스 중단 또는 swap out
 → 남은 프로세스에 더 많은 프레임 제공
 → Page Fault 감소
 → CPU가 다시 실제 연산 수행
```

즉, 무조건 많은 프로세스를 동시에 돌리는 게 좋은 게 아니야.

**메모리가 감당할 수 있는 수준까지만 실행해야 전체 처리량이 좋아진다.**

---

## 3. Working Set Model 사용

Working Set은 어떤 프로세스가 최근 일정 시간 동안 사용한 페이지들의 집합이야.

예를 들어 최근 10,000번의 메모리 접근 동안 사용한 페이지가 다음과 같다면:

```plain text
P1, P2, P3, P4, P5
```

이 프로세스의 Working Set은 대략 `{P1, P2, P3, P4, P5}`라고 볼 수 있어.

OS는 이 Working Set 크기를 보고 판단할 수 있어.

```plain text
모든 프로세스의 Working Set 총합 <= 사용 가능한 물리 프레임
```

이면 정상적으로 실행 가능해.

반대로,

```plain text
모든 프로세스의 Working Set 총합 > 사용 가능한 물리 프레임
```

이면 Thrashing 위험이 커져.

이 경우 OS는 일부 프로세스를 중단하거나 swap out해서 전체 Working Set 크기를 줄여야 해.

---

## 4. Page Fault Frequency 방식

Page Fault Frequency, 줄여서 PFF 방식은 프로세스별 Page Fault 발생 빈도를 보고 조절하는 방법이야.

아이디어는 단순해.

```plain text
Page Fault가 너무 자주 발생한다
 → 이 프로세스에 할당된 프레임이 부족하다
 → 프레임을 더 준다

Page Fault가 너무 적다
 → 이 프로세스에 프레임이 과하게 할당되었을 수 있다
 → 일부 프레임을 회수할 수 있다
```

하지만 모든 프로세스가 동시에 “프레임 더 주세요” 상태라면?

그때는 물리 메모리가 부족한 거니까 일부 프로세스를 중단해야 해.

```plain text
프레임을 더 줄 수 있음
 → 해당 프로세스에 프레임 추가

프레임을 더 줄 수 없음
 → 일부 프로세스 swap out
 → 남은 프로세스에 프레임 확보
```

---

## 5. Local Replacement 정책 사용

페이지 교체에는 크게 두 가지 관점이 있어.

| 방식 | 설명 |
| --- | --- |
| Global Replacement | 모든 프로세스의 프레임 중에서 희생 페이지 선택 |
| Local Replacement | 자기 프로세스에 할당된 프레임 안에서만 희생 페이지 선택 |

Global Replacement는 유연하지만, 한 프로세스가 다른 프로세스의 프레임을 빼앗으면서 Thrashing을 악화시킬 수 있어.

반면 Local Replacement는 프로세스 간 간섭을 줄일 수 있어.

다만 Local Replacement만 쓴다고 무조건 해결되는 건 아니야.

애초에 각 프로세스에 할당된 프레임 수가 너무 적으면, 자기 안에서 아무리 교체해도 계속 Page Fault가 날 수 있어.

그래서 보통은 **프레임 할당 정책 + 교체 정책 + Working Set 관리**를 함께 봐야 해.

---

## 6. 물리 메모리 증설

현실적인 해결책으로는 RAM을 늘리는 방법도 있어.

Thrashing은 결국 현재 실행 중인 작업 집합에 비해 물리 메모리가 부족해서 생기는 문제니까, 물리 메모리를 늘리면 완화될 수 있어.

하지만 이것도 근본적으로는 다음 조건이 맞아야 해.

```plain text
활성 프로세스들의 Working Set 총합 <= 물리 메모리
```

RAM을 늘려도 프로그램이 더 많은 메모리를 계속 요구하면 Thrashing은 다시 발생할 수 있어.

---

## 7. 프로그램의 지역성 개선

이건 OS 관점은 아니고 개발자 관점에서의 완화 방법이야.

프로그램이 메모리를 여기저기 무작위로 접근하면 Working Set이 커지고 Page Fault가 늘어날 수 있어.

반대로 한 번 가져온 데이터를 최대한 가까운 시간 안에 다시 쓰고, 인접한 데이터를 순차적으로 접근하면 지역성이 좋아져.

예를 들어 이차원 배열을 탐색할 때도 메모리 배치 순서에 맞게 접근하면 캐시 효율이 좋아지고, 큰 데이터에서는 페이지 단위 접근 효율도 좋아질 수 있어.

다만 이 부분은 14번 발표와 겹칠 수 있으니, 너는 깊게 들어가지 말고 이렇게만 연결하면 돼.

> Thrashing 완화의 개발자 관점에서는 프로그램의 메모리 접근 지역성을 높여 Working Set을 불필요하게 키우지 않는 것도 중요합니다.

---

## 8. 발표용 요약

Thrashing은 메모리가 부족해서 Page Fault가 과도하게 발생하고, CPU가 실제 연산보다 페이지 교체와 디스크 I/O 대기에 시간을 쓰는 현상입니다. 이를 완화하려면 동시에 실행되는 프로세스 수를 줄이거나, 각 프로세스에 충분한 프레임을 할당해야 합니다. 대표적으로 Working Set Model은 프로세스가 최근에 사용한 페이지 집합을 기준으로 필요한 프레임 수를 추정하고, Page Fault Frequency 방식은 Page Fault 빈도에 따라 프레임 할당량을 조절합니다. 핵심은 현재 실행 중인 프로세스들의 Working Set 총합이 물리 메모리가 감당할 수 있는 범위 안에 있도록 제어하는 것입니다.
