# **7-1.** RR을 사용할 때, Time Slice에 따른 trade-off를 설명해 주세요.

Round Robin 스케줄링에서 **Time Slice**(또는 Time Quantum)는 시스템의 성능과 사용자 경험을 결정하는 가장 핵심적인 변수입니다. 이 값이 너무 크거나 작을 때 발생하는 상충 관계(Trade-off)를 정리하면 다음과 같습니다.

---

# 1. Time Slice가 너무 큰 경우 (Large Time Slice)

- Time Slice가 무한대에 가까워지면 RR은 **FCFS(First-Come, First-Served)** 방식과 유사하게 동작합니다.

- **장점 (Efficiency):**

  - **Context Switch 오버헤드 감소:** 프로세스 교체가 자주 일어나지 않으므로, CPU가 실제 작업을 수행하는 유효 시간 비율이 높아집니다.

  - **처리량(Throughput) 향상:** 오버헤드가 줄어들어 전체적인 작업 처리 속도가 빨라질 수 있습니다.

- **단점 (Responsiveness):**

  - **응답 시간(Response Time) 악화:** 대화형 시스템에서 특정 프로세스가 CPU를 오래 점유하면 다른 프로세스들이 오래 대기해야 하므로 사용자 경험이 저하됩니다.

  - **대기 시간 증가:** 짧은 작업들이 긴 작업 뒤에서 한참을 기다려야 하는 Convoy Effect가 발생할 수 있습니다.

---

# 2. Time Slice가 너무 작은 경우 (Small Time Slice)

- Time Slice를 매우 작게 설정하면 모든 프로세스가 동시에 실행되는 것 같은 **Processor Sharing** 효과를 줍니다.

- **장점 (Responsiveness):**

  - **응답 시간 최적화:** 각 프로세스가 CPU를 아주 자주 할당받으므로, 사용자 입장에서는 시스템이 매우 기민하게 반응한다고 느낍니다.

  - **공정성(Fairness):** 모든 프로세스가 거의 동일한 속도로 진행됩니다.

- **단점 (Efficiency):**

  - **Context Switch 오버헤드 급증:** 프로세스 상태를 저장하고 복원하는 오버헤드가 실제 연산 시간보다 커질 수 있습니다.

  - **배다보다**** 배꼽이 더 큰 상황:** CPU가 일을 하는 시간보다 스케줄링을 관리하는 데 더 많은 자원을 소모하게 되어 전체 시스템 성능이 곤두박질칩니다.

# 3. 요약 및 최적의 선택

| **특성** | **Time Slice ↑ (Large)** | **Time Slice ↓ (Small)** |
| --- | --- | --- |
| **알고리즘 성격** | FCFS에 가까워짐 | Processor Sharing에 가까워짐 |
| **Context Switch 빈도** | 낮음 | 높음 |
| **오버헤드** | 적음 | 많음 |
| **응답성 (Interactive)** | 나쁨 | 좋음 |
| **CPU 효율성** | 높음 | 낮음 |
