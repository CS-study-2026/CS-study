# 4-3. Stack과 Heap 공간에 대해, 접근 속도가 더 빠른 공간은 어디일까요?

# 4-3. Stack vs Heap 속도

👉 그냥 결론부터

👉 **Stack이 더 빠름**

---

## 이유 제대로 이해해야 된다

### Stack 빠른 이유

- 구조가 단순함 (LIFO)

- 포인터 하나만 이동하면 끝

- OS 관여 없음

---

### Heap 느린 이유

- 메모리 찾고 할당해야 함

- 관리 로직 있음

- 단편화 문제 있음

---

👉 느낌으로 보면

- Stack = 바로 꺼내 쓰는 서랍

- Heap = 창고 가서 찾는 느낌

---

# 🔥 핵심 요약 (이건 꼭 기억해라)

- 프로세스 주소공간 = 프로그램 전용 메모리 구조

- BSS = 초기화 안된 변수 (자동 0)

- Stack = 빠름, 작음, 자동 관리

- Heap = 느림, 큼(상대적으로), 수동 관리

- Stack은 시작할 때 크기 고정, Heap은 실행 중 증가

---

# 📌 1. Stack vs Heap의 본질적인 차이

## Stack

```plain text
그냥 포인터 한 칸 올리고/내리고 끝
```

## Heap

```plain text
빈 공간 찾아야 함 → 할당 → 관리 정보 기록
```

👉 이미 여기서 게임 끝이다.

Stack은 **계산 1번**, Heap은 **작업 여러 개**

---

# 📌 2. Heap이 느린 이유 (진짜 핵심 4개)

---

## 1️⃣ “빈 공간 탐색”이 필요함

Stack은 그냥 쌓기만 하면 되는데

Heap은 이런 상황임:

```plain text
[사용][빈][사용][빈][빈][사용]
```

👉 여기서 "크기 맞는 빈 공간" 찾아야 한다

- first-fit

- best-fit

- next-fit

이런 알고리즘 돌림

👉 즉, **탐색 비용 발생**

---

## 2️⃣ 메타데이터 관리 비용

Heap은 그냥 메모리만 있는 게 아니라

**관리 정보도 같이 저장함**

예를 들면:

```plain text
[크기][사용 여부][실제 데이터]
```

👉 할당할 때:

- 메타데이터 기록

👉 해제할 때:

- 다시 연결 (free list 관리)

👉 이게 다 오버헤드

---

## 3️⃣ 단편화 (Fragmentation)

이게 진짜 핵심이다.

```plain text
[사용][빈][사용][빈][사용]
```

👉 빈 공간 많아 보이는데

👉 연속된 공간이 없음

그래서:

- 쓸 수 있는 메모리인데 못 씀

- 또는 재정리 필요

👉 이 과정 자체가 비용

---

## 4️⃣ OS 개입 가능성

Heap은 부족하면:

```plain text
"OS야 메모리 좀 더 줘"
```

👉 system call 발생

- context switch

- 커널 모드 진입

👉 이건 Stack에서는 절대 없음

---

# 📌 3. 속도 차이 한 줄 정리

👉 Stack

- 단순 구조

- CPU 레벨에서 처리 가능

👉 Heap

- 탐색 + 관리 + OS 개입 가능

---

# 📌 4. 감각적으로 이해하기

이 비유가 제일 정확하다

---

## Stack

👉 책상 위에 쌓기

- 그냥 올림

- 그냥 뺌

- 끝

---

## Heap

👉 창고에서 물건 찾기

- 빈 자리 찾기

- 넣기

- 나중에 다시 정리해야 함

---

# 📌 5. 근데 중요한 반전 하나

여기서 대부분 착각하는데

👉 “Heap은 무조건 느리다” ❌

---

## 실제로는

- 한 번 할당한 객체는

👉 Stack이랑 접근 속도 거의 동일

---

👉 느린 건 “할당/해제” 과정이지

👉 “사용(access)”은 거의 차이 없음

---

# 📌 6. 그래서 실무에서는 이렇게 함

- 작은, 짧은 데이터 → Stack

- 크거나 오래 쓰는 데이터 → Heap

---

# 🔥 핵심 요약

- Heap이 느린 이유는 단순히 "동적이라서"가 아니라

  - 빈 공간 탐색

  - 메타데이터 관리

  - 단편화

  - OS 개입 가능성

- 실제 느린 건 **할당/해제**, 접근 자체는 거의 동일

---

## 👉 “그럼 왜 모든 걸 Stack에 안 넣을까?”

👉 **Stack은 “빠른 대신 제약이 너무 많아서” 모든 걸 못 넣는다**

그 제약을 하나씩 까보자.

---

### 📌 1. Stack은 크기가 너무 작다

- 보통 몇 MB 수준 (예: 1~8MB)

- 프로그램 시작할 때 고정됨

👉 만약 다 Stack에 넣는다?

```plain text
큰 배열 / 객체 → 바로 터짐 (Stack overflow)
```

👉 그래서 큰 데이터는 무조건 Heap

---

### 📌 2. Stack은 “함수 수명”에 묶여 있다

Stack의 본질:

👉 **함수 호출이 끝나면 같이 사라짐**

```c
int* func() {
    int a = 10;
    return &a;  // 위험
}
```

👉 함수 끝나면 a는 사라짐

👉 주소 반환하면 **쓰레기 참조**

---

## 그래서 문제가 뭐냐?

👉 프로그램에서 필요한 데이터 중 상당수는

- 함수 끝나도 살아야 함

- 여러 곳에서 공유해야 함

👉 Stack으로는 절대 못 함

---

### 📌 3. Stack은 구조가 너무 단순함 (LIFO)

Stack은:

👉 **Last In First Out (후입선출)**

```plain text
A → B → C (쌓임)
C → B → A (빠짐)
```

---

## 문제

👉 “중간에 있는 데이터만 지우기” 불가능

👉 “순서 무시하고 관리” 불가능

---

## Heap은?

👉 원하는 타이밍에 생성 / 삭제 가능

👉 그래서 유연함

---

### 📌 4. Stack은 크기 변경이 안 된다

- 실행 중에 Stack 크기 늘리는 거 거의 불가능

👉 근데 프로그램은:

- 데이터 크기 예측 못함

- 사용자 입력에 따라 달라짐

---

👉 예:

```plain text
유저가 파일 업로드 → 크기 몇 MB인지 모름
```

👉 Stack으로 처리? 바로 망함

---

### 📌 5. 멀티 스레드 문제

- Stack은 **스레드마다 따로 있음**

- Heap은 **모든 스레드가 공유**

---

## 의미

👉 공유 데이터는 Stack에 못 둔다

---

### 📌 6. 핵심 비교 한 방에 정리

| 항목 | Stack | Heap |
| --- | --- | --- |
| 크기 | 작고 고정 | 크고 유동적 |
| 생명주기 | 함수 기준 | 자유 |
| 구조 | LIFO (제한적) | 자유 |
| 공유 | 불가능 | 가능 |
| 용도 | 임시 데이터 | 장기 데이터 |

---

## 🔥 결론

👉 Stack은

**“빠른 대신, 짧게 쓰는 임시 공간”**

👉 Heap은

**“느리지만, 오래 쓰고 자유롭게 쓰는 공간”**

---

## 💣 한 줄 핵심

👉 **“Stack은 속도를 위해 자유를 포기했고, Heap은 자유를 위해 비용을 낸다”**

---

### 마지막으로 하나 더 찔러볼게

👉 “그럼 지역 변수는 왜 Stack에 두는 게 맞을까?”

이거까지 자연스럽게 설명되면

이 주제는 거의 끝낸 거다.

필요하면 JVM 기준으로 이어서 더 깊게 간다.
