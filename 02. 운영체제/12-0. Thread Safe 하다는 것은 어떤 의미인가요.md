# 12-0. Thread Safe 하다는 것은 어떤 의미인가요?

### 0. 멀티스레드 프로그래밍이란?

하나의 프로세스에서 여러 개의 스레드를 만들어 자원 생성과 관리 중복을 최소화하는 것

장점

- 멀티 프로세스에 비해 메모리 자원소모가 줄어듦

- Heap 영역을 통해 스레드 간 통신이 가능해, 프로세스 간 통신이 간단해짐

- 컨텍스트 스위칭 속도 : 스레드 < 프로세스 ⇒ 스레드가 더 빠름!

  <details>
  <summary>컨텍스트 스위칭 리마인드</summary>

→ **프로세스는 주소 공간 교체(TLB flush 포함)**

→ **스레드는 같은 주소 공간 사용 ⇒ 훨씬 가벼움**
  </details>

단점

- 힙 영역에 있는 자원을 사용할 때 동기화 필요

- 동기화를 위해 과도한 락 사용 시 성능 저하 가능

- 한 스레드가 비정상적으로 동작하면 다른 스레드도 영향받아 종료될 수 O

### 1. 스레드 안전(Thread-Safety)이란?

멀티스레딩 환경에서 여러 스레드가 동시에 같은 코드 영역에 접근하거나 데이터를 공유할 때, 올바른 실행 결과를 보장하는 코드의 속성을 의미. 즉, 코드가 여러 스레드로부터 동시에 호출되더라도 각 스레드의 실행 경로가 서로를 방해하지 않도록 안전하게 설계되어 있다는 것

thread-safe하다의 의미 : 두 개 이상의 스레드가 race-condition에 들어가거나 같은 객체에 동시 접근해도 연산 결과의 정합성이 보장될 수 있게 메모리 가시성이 확보된 상태

- 정합성 : 여러 스레드가 동시에 접근해도 **데이터가 깨지지 않고 올바른 값 유지**

```python
count++ → 1000개 스레드 → 결과 1000 유지
```

- 메모리 가시성 : 한 스레드가 변경한 값이 **다른 스레드에서도 즉시 보이는가**

```java
boolean flag = false;

Thread A: flag = true;
Thread B: while(!flag) {}
```

→ 캐시 때문에 B가 계속 false로 볼 수 있음( 해결 : `volatiile`, `synchronized`, `lock`)

### 3. 스레드 안전을 지키기 위한 전략

아래 전략들은 서로 상호 보완적으로 사용될 수 있으며, 특정 상황이나 요구사항에 맞게 선택해 적용해야 한다!

1. 상호 배제 (Mutual Exclusion)

- **목적**: 한 시점에 하나의 스레드만이 특정한 코드 영역에 접근할 수 있도록 보장

- **방법**: synchronized 블록(자바), Mutex (Go, C++), 또는 다른 잠금 메커니즘을 사용하여 공유 데이터에 대한 접근을 제어

- **예시**: 자바에서는 synchronized 키워드를 메서드나 코드 블록에 적용 가능

**synchronized**는 단순 lock이 아닌 `monitor lock` + `memory barrier` 역할까지 포함하여 가시성까지 같이 해결됨 !

→ 메모리 장벽 : 메모리 장벽 명령어가 실행될 때, 시스템은 후속 적재 또는 저장 연산이 수행되기 전에 모든 적재 및 저장이 완료되도록 하여, 다른 프로세서에서 실행중인 스레드에 메모리 변경 사항이 보이는 것을 보장함

→ 모니터 락 : OS 에서 Monitor 는 Lock 보다 더 높은 수준의 추상화로 critical section에 한 번에 하나의 쓰레드만 들어가도록** 프로그래밍 언어에서 제공하는 동기화 기법으로, **자바의 모든 객체는 **모니터를 가지며, 객체의 락을 활용하여 스레드 동기화를 제공**함 
모든 객체가 갖고 있으니 고유 락(intrinsic lock), 모니터처럼 동작한다고 하여 모니터 락(monitor lock) 또는 모니터(monitor)라고도 부르기도 한다.

2. 불변성 (Immutability) 🌟🌟

- **목적**: 데이터가 생성 후 변경되지 않도록 하여 공유 데이터에 대한 동시 접근 문제 해결

- **방법**: 객체를 불변으로 만들어 생성 시점에만 데이터를 할당하고 이후에는 변경할 수 없게 

- **예시**: 자바의 String 클래스, Go의 상수 사용

⇒ 데이터 변경 자체를 막으므로, 사실상 최고의 해결책임.

락도 필요없고 / 레이스컨디션도 없고 / 성능도 좋음 ! ⇒ 최우선 고려하기

3. 스레드 로컬 저장소 (Thread-Local Storage)

- **목적**: 각 스레드가 데이터의 자신만의 복사본을 가지고 있도록 하여 공유 데이터 문제 회피

- **방법**: ThreadLocal 클래스(자바) 사용, 각 스레드에서 고유한 인스턴스를 생성하고 사용

- **예시**: 자바에서 ThreadLocal 변수를 사용하여 각 스레드에 고유한 데이터 인스턴스 제

- **단점**: 메모리 누수 위험(특히 Thread Pool 환경), `remove()` 안하면 값이 유지

4. 원자적 연산 (Atomic Operations)

- **목적**: 데이터에 대한 연산을 분할 불가능한 단일 단위로 만들어, 동시성 문제 없이 실행 O

- **방법**: AtomicInteger 같은 원자적 클래스 사용 또는 **C**ompare**A**nd**S**wap 같은 원자적 하드웨어 지원 연산 활용

- **예시**: 자바의 `java.util.concurrent.atomic` 패키지 내 클래스

```java
count++
읽기 - 증가 - 쓰기 3단계라서 깨짐
```

5. 락-프리 프로그래밍 (Lock-Free Programming)

- **목적**: **락을 사용하지 않고 **동시성 문제를 해결하여 데드락(deadlock)이나 락 경쟁(lock contention)으로 인한 성능 저하 방지

- **방법**: 원자적 연산을 활용하여 공유 데이터 구조를 업데이트하거나, 데이터 구조 자체를 락-프리(lock-free) 또는 웨이트-프리(wait-free)로 설계

- **예시**: 락-프리 큐, 카운터 등

- **단점**: 구현 난이도가 높으며, ABA 문제가 발생할 수 있음

**ABA문제란?**

  - 스레드 1이 변수의 값을 A라고 확인 후 나중에 그 값이 여전히 A라서 안전하다고 착각해 연산 진행

  - 사실은 그 사이에** 스레드 2가 A → B → A로 바꿔치기**한 경우 발생하는 문제

  - 즉, 값은 다시 A라서 “겉보기엔 변화 없음”처럼 보이지만, 실제로는 상태가 바뀌었고 의도하지 않은 결과가 생김

### 3. Holder 방식 (BEST)

```java
class Singleton {
private static class Holder {
static final Singleton INSTANCE= new Singleton();
    }
public static Singleton getInstance() {
	return Holder.INSTANCE;
    }
}
```

👉 이유:

    - 클래스 로딩 시점 → thread-safe

    - lazy loading

    - 성능 좋음
  </details>

1. 동기화(Syncronized) 키워드 사용하기

```java
public class SafeCounter {
    private int count = 0;

    // 스레드 세이프한 카운터 증가 메서드
    public synchronized void increment() {
        count++;
    }

    // 스레드 세이프한 현재 카운터 값 반환 메서드
    public synchronized int getCount() {
        return count;
    }

    public static void main(String[] args) throws InterruptedException {
        SafeCounter sc = new SafeCounter();

        // 1000개의 스레드를 생성하여 카운터를 증가시키는 작업
        Thread[] threads = new Thread[1000];
        for (int i = 0; i < threads.length; i++) {
            threads[i] = new Thread(() -> {
                sc.increment();
            });
            threads[i].start();
        }

        // 모든 스레드의 작업이 끝나기를 기다림
        for (Thread t : threads) {
            t.join();
        }

        // 최종 카운터 값 출력
        System.out.println("Final count: " + sc.getCount()); // 1000 출력
    }
}
```

→ 만약 increment 메서드에 synchronized 키워드가 없었다면, 여러 스레드가 동시에 count++ 연산을 수행하면서 race condition이 발생하여 잘못된 결과가 나올 수 있습니다.

애플리케이션의 **안정성**과 **신뢰성** 유지에, 스레드 세이프한 코드를 작성하는 것은 매우 중요함. 특히, 공유 자원에 대한 접근을 동기화하는 것은 멀티스레드 환경에서 발생할 수 있는 여러 문제를 예방하는 핵심적인 방법

# 5. 추가로 반드시 알아야 하는 개념

## ✔ Happens-Before 관계

자바 메모리 모델(Java Memory Model, JMM)에서

**“A 작업이 B 작업보다 먼저 일어났음을 메모리 차원에서 보장하는 관계”**를 말한다.

즉, A happens-before B라면 → A의 메모리 변경 결과는 B에서 **반드시 보인다**.

단순한 코드 순서가 아니라, **메모리 가시성(visibility)**과 관련된 개념 !

👉 Java 메모리 모델 핵심

```java
예:
- synchronized unlock → lock
- volatile write → read
```

👉 이 관계가 있어야 **가시성이 보장됨**
