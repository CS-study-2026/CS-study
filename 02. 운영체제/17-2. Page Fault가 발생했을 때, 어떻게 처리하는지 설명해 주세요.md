# 17-2. Page Fault가 발생했을 때, 어떻게 처리하는지 설명해 주세요.

# 17-2. Page Fault가 발생했을 때 어떻게 처리하나요?

여기서는 가상 메모리 전체 설명보다는 **Page Fault 처리 과정**에 집중하면 돼.

---

## 1. Page Fault란?

Page Fault는 CPU가 어떤 가상 주소에 접근했는데, 해당 페이지가 현재 물리 메모리에 없을 때 발생하는 예외야.

예를 들어 프로세스가 다음 주소에 접근했다고 해보자.

```plain text
가상 주소: 0x1234
```

MMU는 이 가상 주소가 어느 가상 페이지에 속하는지 확인하고, 페이지 테이블을 통해 물리 프레임을 찾으려고 해.

그런데 페이지 테이블 항목에 이런 식으로 표시되어 있다면?

```plain text
Present bit = 0
```

즉, 이 페이지가 현재 물리 메모리에 없다는 뜻이야.

이때 Page Fault가 발생한다.

---

## 2. Page Fault는 무조건 오류인가요?

아니야.

Page Fault는 두 종류로 나눠서 봐야 해.

| 종류 | 설명 | 처리 |
| --- | --- | --- |
| 정상적인 Page Fault | 유효한 페이지지만 아직 메모리에 올라오지 않음 | 디스크에서 가져와 실행 계속 |
| 잘못된 접근 | 존재하지 않는 주소 또는 권한 없는 접근 | 프로세스 종료 또는 예외 처리 |

예를 들어 프로그램이 아직 사용하지 않은 코드나 데이터를 처음 접근할 때 Page Fault가 날 수 있어.

이건 Demand Paging에서는 자연스러운 동작이야.

반면 다음 경우는 잘못된 접근이야.

```plain text
NULL 포인터 접근
배열 범위 밖 접근
권한 없는 메모리 접근
읽기 전용 페이지에 쓰기 시도
```

이런 경우에는 OS가 페이지를 가져와 주는 게 아니라, 보통 프로세스를 종료시키거나 예외를 전달해.

---

## 3. Page Fault 처리 흐름

전체 흐름은 이렇게 볼 수 있어.

```plain text
1. CPU가 가상 주소 접근
2. MMU가 페이지 테이블 확인
3. 페이지가 물리 메모리에 없음
4. Page Fault trap 발생
5. OS의 Page Fault Handler 실행
6. 접근이 유효한지 검사
7. 유효하지 않으면 프로세스 종료
8. 유효하면 필요한 페이지 위치 확인
9. 빈 프레임 확보
10. 빈 프레임이 없으면 희생 페이지 선택
11. 필요하면 희생 페이지를 디스크에 기록
12. 필요한 페이지를 디스크에서 메모리로 적재
13. 페이지 테이블 갱신
14. TLB 갱신 또는 무효화
15. 중단됐던 명령어 재실행
```

이제 하나씩 풀어서 설명하면 돼.

---

## 4. 1단계: CPU가 가상 주소에 접근

프로세스는 실제 물리 주소를 직접 다루지 않아.

항상 가상 주소를 사용해.

```plain text
프로세스: "주소 0x1234에 있는 값을 읽어야지"
```

CPU는 이 가상 주소를 MMU에 전달하고, MMU는 가상 주소를 물리 주소로 변환하려고 해.

---

## 5. 2단계: MMU가 페이지 테이블 확인

MMU는 먼저 TLB를 확인할 수 있어.

```plain text
TLB hit
 → 바로 물리 주소 얻음

TLB miss
 → 페이지 테이블 확인
```

페이지 테이블에는 대략 이런 정보가 있어.

```plain text
가상 페이지 번호
물리 프레임 번호
Present bit
Protection bit
Dirty bit
Reference bit
```

이 중 Page Fault와 가장 직접적으로 관련 있는 것은 **Present bit**야.

```plain text
Present bit = 1
 → 물리 메모리에 있음

Present bit = 0
 → 물리 메모리에 없음
 → Page Fault 발생
```

---

## 6. 3단계: Page Fault trap 발생

페이지가 물리 메모리에 없으면 하드웨어는 OS에게 제어권을 넘겨.

이걸 trap 또는 exception이라고 볼 수 있어.

이때 OS는 현재 실행 중이던 프로세스의 상태를 저장하고, 커널 모드에서 Page Fault Handler를 실행해.

```plain text
사용자 프로세스 실행 중
 → Page Fault 발생
 → 커널 모드 전환
 → Page Fault Handler 실행
```

---

## 7. 4단계: OS가 접근이 유효한지 검사

OS가 가장 먼저 해야 하는 일은 이 접근이 정상적인 접근인지 확인하는 거야.

예를 들어 다음을 확인해.

```plain text
이 주소가 프로세스의 유효한 가상 주소 공간 안에 있는가?
이 페이지에 접근할 권한이 있는가?
읽기 전용 페이지에 쓰려고 한 것은 아닌가?
커널 영역을 사용자 프로세스가 접근하려 한 것은 아닌가?
```

유효하지 않은 접근이면 OS는 페이지를 가져오지 않아.

대신 프로세스에 예외를 전달하거나 종료시켜.

```plain text
잘못된 접근
 → Segmentation Fault 등 발생
 → 프로세스 종료 가능
```

유효한 접근이면 다음 단계로 넘어가.

---

## 8. 5단계: 필요한 페이지가 어디에 있는지 찾음

유효한 접근이라면 OS는 해당 페이지를 어디서 가져와야 하는지 확인해.

페이지의 종류에 따라 가져오는 위치가 다를 수 있어.

| 페이지 종류 | 가져오는 위치 |
| --- | --- |
| 실행 파일의 코드 페이지 | 실행 파일 |
| 초기화된 데이터 페이지 | 실행 파일 |
| swap out된 페이지 | swap 영역 |
| 아직 한 번도 쓰지 않은 빈 페이지 | 0으로 초기화된 새 페이지 |
| Copy-on-Write 페이지 | 복사해서 새 프레임 할당 |

발표에서는 너무 깊게 안 들어가도 되지만, Page Fault가 항상 swap에서만 가져오는 건 아니라는 정도는 말하면 좋아.

---

## 9. 6단계: 빈 물리 프레임 확보

필요한 페이지를 메모리에 올리려면 물리 프레임이 필요해.

먼저 OS는 빈 프레임이 있는지 확인해.

```plain text
빈 프레임 있음
 → 그 프레임에 페이지 적재

빈 프레임 없음
 → 기존 페이지 중 하나를 내보내야 함
```

빈 프레임이 있으면 간단해.

그 프레임에 필요한 페이지를 읽어오면 돼.

---

## 10. 7단계: 빈 프레임이 없으면 희생 페이지 선택

빈 프레임이 없으면 OS는 기존에 메모리에 올라와 있는 페이지 중 하나를 골라 내보내야 해.

이때 사용하는 것이 Page Replacement Algorithm이야.

대표적으로는 다음과 같은 방식들이 있어.

```plain text
FIFO
LRU
Clock
Optimal
```

다만 네 발표에서는 교체 알고리즘을 깊게 설명할 필요는 없어.

다른 주제와 겹칠 수 있으니 이렇게만 말하면 충분해.

> 빈 프레임이 없으면 OS는 페이지 교체 알고리즘을 사용해 희생 페이지를 선택합니다. 이때 어떤 페이지를 내보내느냐에 따라 이후 Page Fault 빈도가 달라질 수 있습니다.

---

## 11. 8단계: 희생 페이지가 dirty인지 확인

희생 페이지를 골랐다고 바로 버릴 수 있는 건 아니야.

페이지가 수정되었는지 확인해야 해.

이때 보는 것이 **Dirty bit**야.

```plain text
Dirty bit = 0
 → 메모리에 올라온 뒤 수정되지 않음
 → 그냥 버려도 됨

Dirty bit = 1
 → 메모리에서 수정됨
 → 디스크에 반영해야 함
```

예를 들어 코드 페이지처럼 읽기만 한 페이지라면 그냥 버려도 돼.

나중에 필요하면 실행 파일에서 다시 읽어오면 되니까.

하지만 데이터 페이지가 수정되었다면, 그냥 버리면 변경 내용이 사라져.

그래서 디스크나 swap 영역에 먼저 기록해야 해.

```plain text
희생 페이지가 clean
 → 바로 제거 가능

희생 페이지가 dirty
 → 디스크에 write-back 후 제거
```

Dirty page를 내보내는 경우에는 디스크 쓰기까지 필요하므로 Page Fault 처리 비용이 더 커진다.

---

## 12. 9단계: 필요한 페이지를 디스크에서 메모리로 읽어옴

프레임이 확보되면 OS는 필요한 페이지를 디스크나 실행 파일, swap 영역 등에서 읽어와 물리 메모리에 적재해.

이 작업은 디스크 I/O가 포함될 수 있기 때문에 매우 느려.

그래서 Page Fault는 일반적인 메모리 접근이나 캐시 미스보다 훨씬 비용이 크다.

```plain text
필요한 페이지 위치 확인
 → 디스크 I/O 요청
 → 해당 프로세스는 대기 상태
 → I/O 완료 후 다시 실행 가능 상태
```

이동안 CPU는 다른 프로세스를 실행할 수도 있어.

---

## 13. 10단계: 페이지 테이블 갱신

페이지가 물리 메모리에 올라왔으면 페이지 테이블을 갱신해야 해.

예를 들어 기존에는 이렇게 되어 있었다고 하자.

```plain text
가상 페이지 5번
Present bit = 0
Frame number = 없음
```

페이지를 물리 프레임 12번에 올렸다면 이렇게 바뀐다.

```plain text
가상 페이지 5번
Present bit = 1
Frame number = 12
Protection = read/write
Dirty bit = 0
Reference bit = 0 또는 1
```

이제 MMU는 이 페이지에 접근할 때 물리 주소로 변환할 수 있어.

---

## 14. 11단계: TLB 갱신 또는 무효화

TLB는 페이지 테이블 정보를 캐싱하는 장치야.

페이지 테이블이 바뀌었으므로 TLB도 함께 신경 써야 해.

상황에 따라 OS는 해당 가상 페이지의 TLB 엔트리를 무효화하거나 새 매핑으로 갱신해.

```plain text
페이지 테이블 변경
 → 기존 TLB 정보가 오래되었을 수 있음
 → TLB invalidate 또는 update
```

이 과정을 제대로 하지 않으면 CPU가 예전 주소 변환 정보를 사용해서 잘못된 물리 주소에 접근할 수 있어.

---

## 15. 12단계: 중단된 명령어 재실행

마지막으로 Page Fault를 일으켰던 명령어를 다시 실행해.

중요한 점은 **다음 명령어를 실행하는 게 아니라, 실패했던 명령어를 다시 실행한다**는 거야.

처음에는 페이지가 없어서 실패했지만, 이제 페이지가 메모리에 올라와 있고 페이지 테이블도 갱신됐으니 정상적으로 실행될 수 있어.

```plain text
처음 실행:
LOAD R1, [가상주소 X]
 → Page Fault 발생

처리 후:
LOAD R1, [가상주소 X]
 → 정상 실행
```
