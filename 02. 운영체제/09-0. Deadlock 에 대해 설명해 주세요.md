# 9-0. Deadlock 에 대해 설명해 주세요.

# 🙋🏻 아니 그래서 Lock이 뭔데요? Synchronized는요?

## **✅ 1. Lock이란?**

> **여러 실행 흐름(스레드/프로세스)이 동시에 같은 자원에 접근하지 못하게 막는 장치**

> “공유 자원에 대한 접근을 제어하기 위한 ‘동기화 메커니즘(도구/상태)”

---

### **🔹 왜 필요하냐?**

멀티스레드 환경에서는:

  - 여러 스레드가 동시에 같은 데이터 접근 → Race Condition 발생

👉 그래서:

> **“한 번에 하나만 접근하게 하자”**

---

### **🔹 핵심 개념**

  - Lock 획득 (acquire)

  - 작업 수행

  - Lock 해제 (release)

---

### **🔹 예시 (개념)**

```plain text
Thread1 → Lock 획득 → 작업 → 해제
Thread2 → 대기 → Lock 획득 → 작업
```

---

### **🔥 한 줄 정의**

👉 **Lock = 공유 자원에 대한 동시 접근을 제어하는 메커니즘**

---

## **✅ 2. DB Row Lock**

👉 **데이터베이스에서 “특정 행(row)”에 대해 동시 접근을 막는 락**

---

### **🔹 왜 필요하냐?**

예: 계좌 잔액

  - A: 출금

  - B: 출금

👉 동시에 실행되면 값 꼬임 (Race Condition)

---

### **🔹 동작 방식**

```plain text
SELECT * FROM account WHERE id=1 FOR UPDATE;
```

👉 결과:

  - 해당 row에 lock 걸림

  - 다른 트랜잭션은 대기

---

### **🔹 특징**

  - **데이터 단위 (row, table 등)**

  - 트랜잭션과 함께 동작

  - commit/rollback 시 해제

---

### **🔥 핵심**

👉 **“DB 데이터 보호를 위한 Lock”**

---

## **✅ 3. synchronized (Java)**

👉 **Java에서 스레드 간 동시 실행을 막기 위한 키워드**

---

### **🔹 사용 예시**

```plain text
synchronized(lock) {
    // 한 번에 하나의 스레드만 실행
}
```

---

### **🔹 동작 방식**

  1. 특정 객체의 lock 획득

  1. 블록 실행

  1. 종료 시 자동 해제

---

### **🔹 특징**

  - JVM 레벨 락

  - 자동으로 lock 관리

  - Mutual Exclusion 보장

---

### **🔥 핵심**

👉 **“코드 블록을 보호하는 스레드 락”**

---

## **✅ 4. 세 개 비교**

| **구분** | **Lock (일반)** | **DB Row Lock** | **synchronized** |
| --- | --- | --- | --- |
| 개념 | 추상 개념 | DB 구현 | Java 구현 |
| 대상 | 모든 공유 자원 | DB 데이터 | Java 객체 |
| 범위 | OS/언어 전반 | DB 시스템 | JVM |
| 단위 | 자유 | row/table | 코드 블록 |
| 목적 | 동시성 제어 | 데이터 정합성 | 스레드 안전성 |

---

## **✅ 5. 한 번에 이해하는 구조**

👉 관계는 이렇게 보면 된다:

```plain text
Lock (개념)
 ├─ synchronized (Java)
 ├─ DB Row Lock (DB)
 └─ mutex / semaphore (OS)
```

---

# **🎯 최종 한 줄 정리**

👉 **Lock은 동시성 제어를 위한 일반 개념이고, DB row lock은 데이터베이스에서 행 단위로 적용되는 락이며, synchronized는 Java에서 코드 블록을 보호하기 위한 스레드 락이다.**

---

# ✅ 1. Deadlock이란?

👉 **여러 스레드(또는 프로세스)가 서로가 가진 자원을 기다리면서, 아무도 더 이상 진행하지 못하는 상태**

---

## 🔹 핵심 키워드

- 서로 기다림

- 자원 점유 상태

- 무한 대기

---

## 🔥 한 줄 정의

👉 **“서로 자원을 잡고 놓지 않은 채, 상대가 가진 자원을 기다리며 영원히 멈추는 상태”**

---

# ✅ 2. 가장 쉬운 예시 (직관)

## 📌 상황

자원 A, B가 있음

---

## 🔹 Thread 1

1. A 획득

1. B 기다림

---

## 🔹 Thread 2

1. B 획득

1. A 기다림

---

## 🔥 결과

- Thread 1 → B 기다림

- Thread 2 → A 기다림

👉 서로 기다림 → **아무도 못 끝냄**

> 이것이 **Deadlock**

---

# ✅ 3. Deadlock 발생 조건 (중요 ⭐)

Deadlock은 아래 4가지 조건이 모두 만족될 때 발생 가능

## 1️⃣ Mutual Exclusion (상호 배제)

> 한 번에 하나의 스레드만 사용할 수 있는 자원이 존재하는 것

- 프린터

- DB row lock

- synchronized 블록

### 🔹 왜 필요한가?

👉 여러 스레드가 동시에 접근하면 데이터가 깨질 수 있음

그래서:

> **“한 번에 하나만 쓰자” → 락(lock)**

### 🔥 Deadlock과의 관계

👉 자원이 공유 가능(동시 사용 가능)하다면 Deadlock 자체가 성립 안 됨

### 🔹 이 조건 깨는 방법

👉 공유 자원을 없애거나, 동시에 접근 가능하게 설계

- lock-free 구조

- read/write lock 분리

(완전히 제거는 현실적으로 어려움)

---

## 2️⃣ Hold and Wait (점유 대기)

> 이미 자원을 하나 가진 상태에서 다른 자원을 추가로 기다리는 것

```java
lock(A);   // 이미 A 잡음
lock(B);   // B 기다림
```

### 🔥 Deadlock과의 관계

> Deadlock은 대부분 여기서 시작됨

- 하나 잡고

- 또 하나 기다림

- 서로 꼬임

### 🔹 이 조건 깨는 방법

👉 **“필요한 자원을 한 번에 다 요청”**

```java
lock(A, B); // 한 번에
```

또는

- 하나라도 못 얻으면 다 놓고 다시 시도

---

## 3️⃣ No Preemption (비선점)

> 이미 할당된 자원을 강제로 빼앗을 수 없는 것

```java
lock(A); // 잡으면 끝
// OS나 다른 스레드가 강제로 뺏지 못함
```

### 🔹 직관

> “한 번 잡은 자원은 자발적으로 놓기 전까지 계속 가지고 있음”

### 🔥 Deadlock과의 관계

👉 만약 강제로 뺏을 수 있다면:

- Deadlock 상황에서 강제로 회수 가능

👉 그런데 못 뺏으니까 → **무한 대기**

### 🔹 이 조건 깨는 방법

- timeout 설정

- lock 획득 실패 시 rollback

```java
tryLock(timeout)
```

---

## 4️⃣ Circular Wait (순환 대기)

> 스레드 혹은 프로세스들이 원형 구조로 서로의 자원을 기다리는 것

```plain text
Thread1 → Thread2 → Thread3 → Thread1

Thread1 → A 잡고 B 기다림
Thread2 → B 잡고 C 기다림
Thread3 → C 잡고 A 기다림
```

### 🔹 이 조건 깨는 방법 (가장 많이 사용)

👉 **Lock 순서 통일**

```plain text
항상 A → B 순서로lock
```

👉 그러면:

- A → B만 가능

- B → A 같은 역순 발생 안 함

---

## 🔥 핵심

👉 이 4개가 동시에 만족하면 Deadlock 발생 가능

---

# ✅ 4. Deadlock vs Race Condition (헷갈리는 부분)

> 🔥 

### Race Condition

## Race Condition이란?

> **여러 스레드가 공유 자원에 동시에 접근하면서, 실행 순서에 따라 결과가 달라지는 문제**다.

핵심은

👉 **공유 자원**

👉 **동시 접근**

👉 **순서에 따라 결과가 달라짐**

이 세 가지다.

### 예시

은행 계좌 잔액이 100원이라고 하자.

    - Thread A: 잔액을 읽고 50원 출금

    - Thread B: 잔액을 읽고 30원 출금

원래라면 최종 잔액은 20원이 되어야 한다.

그런데 실제 실행이 이렇게 꼬일 수 있다.

    1. Thread A가 잔액 100 읽음

    1. Thread B가 잔액 100 읽음

    1. Thread A가 50원 출금 후 50 저장

    1. Thread B가 30원 출금 후 70 저장

최종 결과: **70원**

원래 기대값은 20원인데, 잘못된 결과가 나왔다.

이게 Race Condition이다.

### 왜 발생하나?

출금 연산이 겉보기엔 한 줄처럼 보여도 실제로는 보통 여러 단계다.

    1. 값 읽기

    1. 계산하기

    1. 결과 저장하기

이 세 단계 사이에 다른 스레드가 끼어들 수 있다.

즉, **하나의 작업처럼 보여도 실제론 원자적(atomic)이지 않기 때문**이다.

### 특징

    - 실행할 때마다 결과가 다를 수 있음

    - 재현이 어려운 경우가 많음

    - 테스트에서는 잘 안 보이는데 실서비스에서 터지기도 함

### 해결 방법

    - mutex, synchronized 같은 **상호 배제**

    - atomic 연산

    - semaphore

    - lock-free 자료구조

    - 공유 자원 자체를 줄이는 설계

| 구분 | Deadlock | Race Condition |
| --- | --- | --- |
| 문제 | 멈춤 | 값이 꼬임 |
| 상태 | 무한 대기 | 실행됨 (잘못된 결과) |
| 원인 | 락 대기 | 동시 접근 |

- Deadlock → **아예 실행이 멈춤**

- Race Condition → **실행은 되는데 결과가 틀림**

---

# ✅ 5. 해결 방법

## 🔹 1) 예방 (Prevention)

> Deadlock 조건 중 하나를 깨기

---

### ✔️ 방법

- Lock 순서 통일 → Circular Wait 제거

```java
[문제 상황]
// Thread 1
synchronized(A) {
    synchronized(B) {
    }
}

// Thread 2
synchronized(B) {
    synchronized(A) {
    }
}


[해결]
// 모든 스레드가 동일한 순서
synchronized(A) {
    synchronized(B) {
    }
}
```

- Lock 최소화

  - 한 번에 모든 lock 획득

```java
lock(A, B); // 한 번에
```

  - 필요할 때만 lock

  - 범위 줄이기

- timeout 사용

```java
tryLock(시간) // 무한 대기 방지
```

  - tryLock + timeout 사용 (무한 대기 대신 포기 전략)

```java
Lock lockA = new ReentrantLock();
Lock lockB = new ReentrantLock();

if (lockA.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lockB.tryLock(1, TimeUnit.SECONDS)) {
            try {
                // 작업 수행
            } finally {
                lockB.unlock();
            }
        }
    } finally {
        lockA.unlock();
    }
}
```

- 중첩 lock 최소화

```java
synchronized(A) {
    synchronized(B) { // 최대한 피하기
```

- (근본적/구조적으로) 공유 자원 줄이기

  - immutable 객체 사용

> 🍌 **한 번 만들어지면 내부 상태를 바꿀 수 없는 객체 (e.g. Java의 String)**

      - Deadlock은 여러 스레드가 같은 데이터를 “수정” 하려고 할 때 주로 발생

      - immutable 객체는 생성 후 값이 바뀌지 않으므로 여러 스레드가 공유해도 비교적 안전하다

  - ThreadLocal 사용

> 🍌 **공유하지 말고, 스레드마다 자기 전용 값을 따로 갖게 하자**

      - 공유 자원이 없으면 lock도 필요 없고

      - Race condition도 줄어들고 Deadlock 가능성도 줄어듦

      - `주의` 스레드풀 환경에서는 값을 지우지 않으면 문제 발생 가능

```java
try {
    currentUser.set("userA");
    // 작업
} finally {
    currentUser.remove();
}
```

이렇게 정리해주는 게 안전하다.

  - lock-free 자료구조

> 🍌 **락을 사용하지 않거나 최소화하면서도 여러 스레드가 안전하게 접근할 수 있도록 만든 자료구조**

      - 예시

        - `ConcurrentLinkedQueue`

        - `AtomicInteger`

        - `AtomicReference`

      - 어떻게 가능?

        - 보통 CPU가 제공하는 **원자적 연산(atomic operation)**을 사용한다.

        - 대표적으로 **CAS(Compare-And-Set)**가 있다.

> “현재 값이 내가 예상한 값과 같으면 새 값으로 바꿔라. 아니면 실패하라.”

이걸 이용하면 lock 없이도 안전하게 값을 바꾸는 구조를 만들 수 있다.

---

## 🔹 2) 회피 (Avoidance)

> **안전한 상태인지 검사 후 실행**

- 대표: Banker’s Algorithm (은행가 알고리즘)

<details>
<summary>_Banker’s Algorithm_</summary>

# **✅ 1. 왜 필요한가?**

Deadlock은 보통:

  - 자원을 나눠주다가

  - 어느 순간 서로 기다리는 구조가 만들어지면서 발생

👉 그래서 아이디어는:

> **“애초에 위험해질 요청은 거절하자”**

---

# **✅ 2. 핵심 개념**

## **🔹 Safe State (안전 상태)**

👉 어떤 순서로든 모든 프로세스가 **자원을 받아서 끝낼 수 있는 상태**

---

## **🔹 Unsafe State (불안전 상태)**

👉 당장은 문제 없어 보여도

→ **Deadlock으로 이어질 가능성이 있는 상태**

(※ Unsafe = Deadlock은 아님, “위험한 상태”라는 의미)

---

# **✅ 3. 기본 아이디어**

👉 자원 요청이 들어오면:

  1. **일단 준다고 가정**

  1. 그 상태에서

  1. 모든 프로세스가 끝날 수 있는지 시뮬레이션

  1. 가능하면 승인, 아니면 거절

---

# **✅ 4. 필요한 데이터 구조**

프로세스 n개, 자원 m종류라고 할 때:

  - **Available**: 현재 사용 가능한 자원

  - **Max**: 각 프로세스가 최대 필요로 하는 자원

  - **Allocation**: 현재 할당된 자원

  - **Need = Max - Allocation**

---

# **✅ 5. 동작 과정 (핵심 알고리즘)**

## **🔹 Step 1. 요청이 들어옴**

```plain text
P1 → 자원 요청
```

---

## **🔹 Step 2. 조건 체크**

  - 요청 ≤ Need ?

  - 요청 ≤ Available ?

👉 둘 다 만족해야 진행 가능

---

## **🔹 Step 3. “가상 할당”**

👉 실제로 주기 전에:

```plain text
Available -= 요청
Allocation += 요청
Need -= 요청
```

---

## **🔹 Step 4. 안전성 검사 (핵심 ⭐)**

👉 모든 프로세스를 순서대로 검사:

  - Need ≤ Available 이면 실행 가능

  - 실행되면 자원 반환

👉 이 과정을 반복해서

👉 **모든 프로세스가 끝나면 → 안전 상태**

👉 하나라도 못 끝나면 → 위험 상태

---

# **✅ 6. 예시 (간단)**

## **📌 상황**

Available = 3

| **Process** | **Need** |
| --- | --- |
| P1 | 2 |
| P2 | 1 |

---

## **🔹 실행**

  - P2 (Need 1 ≤ 3) → 실행 → 자원 반환 → Available = 4

  - P1 (Need 2 ≤ 4) → 실행

👉 **모든 프로세스 완료 → Safe**

---

# **❗ 위험 상황 예시**

Available = 1

| **Process** | **Need** |
| --- | --- |
| P1 | 2 |
| P2 | 2 |

👉 누구도 실행 못함

👉 → Unsafe → 요청 거절

---

# **✅ 7. 핵심 특징**

## **🔹 장점**

  - Deadlock을 **사전에 방지**

  - 안전한 상태만 유지

---

## **🔹 단점**

  - 모든 프로세스의 최대 요구량을 미리 알아야 함

  - 계산 비용 큼

  - 현실 시스템에서는 거의 안 씀

(→ “확실함”: 실제 OS에서는 거의 사용 안 함)

# **✅ 8. Deadlock 방지 vs 회피 vs 탐지**

| **방식** | **설명** |
| --- | --- |
| 예방 | 조건 자체를 깨버림 |
| 회피 | 위험 상태를 피함 (Banker) |
| 탐지 | 발생 후 처리 |

---

👉 Banker’s Algorithm은 **회피(Avoidance)** 방법

# ✅ 7. Deadlock vs Starvation

## 🔹 Deadlock

- 서로 기다림

- 👉 **영원히 진행 안 됨**

## 🔹 Starvation (기아 상태)

👉 어떤 스레드가:

- 계속 실행 기회를 못 얻음

예:

- 높은 우선순위 스레드만 계속 실행

## 🔥 핵심 차이

| 구분 | Deadlock | Starvation |
| --- | --- | --- |
| 원인 | 자원 대기 | 스케줄링 |
| 상태 | 서로 멈춤 | 일부만 못 실행 |
| 특징 | 완전 정지 | 불공정 |

---

# ✅ 8. Livelock

## 🔹 정의

👉 서로 **양보**만 하다가 아무 작업도 못 하는 상태

---

## 📌 예시

- Thread1: “너 먼저 해”

- Thread2: “아니 너 먼저 해”

👉 둘 다 계속 양보 → 아무도 작업 안 함

---

## 🔥 차이

| 구분 | Deadlock | Livelock |
| --- | --- | --- |
| 상태 | 멈춤 | 계속 움직이지만 진행 없음 |
| 특징 | 대기 | 반복 |

---

# ✅ 9. 직관적인 비유

👉 두 사람이 좁은 길에서 마주침

- A: “너 먼저 지나가”

- B: “아니 너 먼저”

👉 둘 다 안 움직임 → **Deadlock**

# 🎯 최종 한 줄 정리

👉 **Deadlock은 여러 스레드가 서로가 가진 자원을 기다리면서 무한히 대기하는 상태로, 프로그램이 더 이상 진행되지 않는 문제이다.**
