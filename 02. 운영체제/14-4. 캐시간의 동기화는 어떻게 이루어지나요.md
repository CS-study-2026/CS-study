# 14-4. 캐시간의 동기화는 어떻게 이루어지나요?

> 💡 이 질문은 요즘처럼 코어가 여러 개인 **멀티코어(Multi-Core) 환경**에서 아주 중요. ⇒ 캐시 일관성

### 1️⃣ 문제 상황: 캐시 불일치 (Cache Incoherence)

CPU 안에 일꾼(코어)이 4명이라고 가정해 봅시다.

- **Write-Back 방식이라 가정한 <지우의 6월 싸급> 상황극 예시**

  - `1번 코어`가 한 일

    - 메인 메모리 **“1,000,000원”**

    - 어제 결석 이슈로, 메인 메모리에서 캐시로 **“1,000,000원”** 가져와서 **“940,000원”**으로 수정

  - 이후 `2번 코어`가 한 일 

    - 메인 메모리에서 가져오기 → **“1,000,000원”**

_“지우의 싸급은 940,000원으로 줄었는데, 2번 코어가 캐시가 아닌 메인 메모리에서 가져와서 __**데이터 정합성**__이 깨졌다!” 쌰갈@!@!!@!@!@!!@_

### 2️⃣ 해결책: 스누핑 프로토콜 (Snooping Protocol)

문제 해결을 위해 현대 CPU는 '스누핑(Snooping, 기웃거리다/엿듣다)' 방식 사용.

- **개념:** 코어들이 공용 버스(통신망)를 통해 다른 코어들이 캐시에 무슨 짓을 하는지 **항상 엿듣고(Snooping) 있는 것**.

- **동작 방식:**

  1. 1번 코어가 자기 캐시의 데이터를 수정.

  1. 1번 코어는 버스에 대고 "동네 사람들! 나 A 통장 잔고 바꿨다!!"라고 방송(Broadcast).

  1. 방송을 엿듣고 있던 2번 코어는 자기 메모장에 있던 A 통장 잔고 서류에 **'무효(Invalid)'** 도장을 찍어서 파기.

  1. 나중에 2번 코어가 A 통장 잔고가 필요해지면, 무효화되었기 때문에 1번 코어 쪽에서 최신 데이터를 가져옴.

(참고: 이 스누핑 방식을 구현한 가장 대표적인 상태 관리 모델이 **MESI 프로토콜**입니다.)

### MESI 프로토콜의 등장 (면접 단골 키워드)

아까 잠깐 언급했던 멀티코어 환경에서는 이 상태 비트를 조금 더 세밀하게 4가지 상태로 나눕니다. 이것이 바로 유명한 **MESI 프로토콜**입니다.

  - **M (Modified):** 나만 가지고 있고, 내가 수정했어. (메인 메모리와 다름)

  - **E (Exclusive):** 나만 가지고 있고, 아주 깨끗해. (메인 메모리와 같음)

  - **S (Shared):** 다른 애들도 가지고 있고, 다 같이 깨끗해.

  - **I (Invalid): 무효화됨. 쓰레기 데이터야. ⬅️ 무효화는 바로 이 상태**
</details>

> 

멀티코어 환경에서는 각자의 개인 메모장(캐시)을 쓰기 때문에 필연적으로 오해가 생깁니다. 이를 해결하는 방법이 '스누핑(Snooping)'입니다. 단어 뜻 그대로 다른 코어들이 뭘 하는지 '엿듣는' 겁니다. 내가 가진 데이터가 다른 코어에 의해 수정되었다는 소문을 들으면, 재빨리 내 캐시에 있는 구형 데이터를 '무효화(폐기)'시킴으로써 항상 최신 상태(정합성)를 유지하는 것이 핵심입니다!"

# 🚨 주의: "어떤 캐시"를 묻는 질문인가요?

  1. 14-3, 14-4에서 다루었던 캐시는 'CPU 안에 있는 하드웨어 캐시(L1, L2, L3)'

  1. 웹 서비스 백엔드에서 사용하는 소프트웨어 분산 캐시(Redis, Memcached 등).

면접관이 질문할 때 이 두 가지를 구분해서 대답하지 않으면 "어? 이 지원자는 OS의 CPU 캐시를 물어봤는데 왜 웹 서버의 Redis 이야기를 하지?" 하고 오해할 수 있습니다.

두 세계의 차이를 명확히 구분해 드릴게요!

### 1️⃣ 하드웨어 레벨 (OS, 컴퓨터 구조 과목)

  - **대상:** CPU 코어들 사이의 캐시 (L1, L2)

  - **동기화 방식:** **스누핑(Snooping), MESI 프로토콜** (메인보드의 전기적 버스(Bus)를 통해 엿듣기)

  - **특징:** 개발자가 직접 코딩하는 게 아니라 하드웨어가 알아서 0.000001초 단위로 처리함.

### 2️⃣ 소프트웨어 레벨 (백엔드, 시스템 아키텍처 과목) ⬅️ 영관님이 가져오신 내용

  - **대상:** 여러 대의 웹 서버(스프링)와 DB(MySQL) 사이에 두는 캐시 서버 (Redis)

  - **동기화 방식:** **Pub/Sub, DB 트리거, 메시지 큐** (네트워크 통신을 통해 알림 보내기)

  - **특징:** 백엔드 개발자가 직접 구조를 짜고 코딩해서 맞춰줘야 함.

# 💡 질문에 대한 답변: Redis에도 똑같이 적용되나요?

네, **원리(철학)는 완벽하게 똑같이 적용됩니다!** 이것이 컴퓨터 공학의 가장 아름다운 점이기도 합니다.

규모만 커졌을 뿐, 우리가 CPU에서 배운 **Write-Through, Write-Back, 무효화(Invalidation)** 개념이 웹 서비스와 Redis 같은 In-Memory DB(캐시)에서도 이름만 조금씩 바뀌어 똑같이 쓰입니다.

| **개념** | **CPU 하드웨어 캐시** | **백엔드 분산 캐시 (Redis 등)** |
| --- | --- | --- |
| **목적** | 코어 간 데이터 불일치 방지 | 웹 서버 간 데이터 불일치 방지 |
| **Write-Through** | L1 캐시에 쓸 때 메인 메모리(RAM)도 씀 | Redis에 쓸 때 원본 DB(MySQL)도 동시에 씀 |
| **Write-Back** | L1 캐시에만 쓰고 나중에 RAM에 반영 | Redis에만 쓰고 나중에 배치로 DB에 반영 |
| **동기화(알림) 방법** | **스누핑 (Snooping)**
(버스 선을 통해 엿듣기) | **Pub/Sub (발행/구독)**
(네트워크로 이벤트 쏴주기) |
| **데이터 무효화** | 상태 비트를 **'Invalid'**로 변경 | Redis에서 해당 Key를 **'Evict(삭제/만료)'** 시킴 |

> 

14-4번, 캐시 간의 동기화

이 동기화는 관점에 따라 'CPU 하드웨어 캐시'와 **'백엔드의 분산 캐시(Redis)'** 두 가지로 나누어 볼 수 있는데요, 놀랍게도 원리는 똑같습니다!

우선 **CPU 입장**에서는 멀티코어 환경에서 데이터가 꼬이는 것을 막기 위해 하드웨어적으로 **'스누핑(Snooping)'** 기법을 씁니다. 통신망(버스)을 엿듣다가 남이 데이터를 수정하면 내 데이터를 무효화(Invalid)하는 MESI 프로토콜을 사용하죠.

반면 이걸 백엔드 아키텍처로 확장해서 **서버와 Redis 캐시 입장**으로 보면 어떨까요? 방식만 소프트웨어로 바뀌었을 뿐입니다. 스누핑 대신 **'Pub/Sub(발행/구독)' 패턴**이나 'DB 트리거'를 사용해서, 원본 데이터가 변경되면 메시지를 쏴서 로컬 캐시를 무효화(Evict)시킵니다.

결론적으로 캐시 동기화는 하드웨어든 소프트웨어든 '데이터의 무효화 알림을 어떻게 빠르게 전파할 것인가?'의 문제이며, 이에 따라 시스템의 오버헤드와 동시성 문제가 결정됩니다.

[영관님이 직접 조사하신 내용(Pub/Sub, Race Condition, 네트워크 오버헤드)](/p/3724f7753cf280939c7be258aad5816d)은 **백엔드 개발자로서 성장하는 데 있어 OS 지식보다 훨씬 더 많이 쓰일 실무적인 내용**입니다. 아주 방향을 잘 잡고 계십니다!

# 🔄 캐시 동기화 (Cache Synchronization) 개요

캐시 동기화란 시스템 성능 향상을 위해 임시 저장한 데이터(캐시)가 원본 데이터와 일치하지 않는 데이터 불일치(Inconsistency) 문제를 해결하는 기술입니다. 주로 여러 서버가 캐시를 공유하거나, 분산된 캐시 구조를 사용할 때 발생합니다. [1, 2, 3, 4]

## 💡 왜 동기화가 필요한가요?

    - 데이터 불일치 방지: 원본 데이터가 수정되었는데 캐시가 갱신되지 않으면, 사용자가 오래된 데이터를 보게 되는 문제가 발생합니다. [1, 2]

    - 독립적 캐시의 한계: 여러 서버가 개별적인 로컬 캐시를 가지면 특정 서버에서 데이터를 변경해도 다른 서버는 알 수 없습니다. [1, 2]

## 🔄 주요 캐시 동기화 방식 및 기술

### 1. Pub/Sub (발행/구독) 패턴

    - 원리: 데이터 변경 시 중앙 메시지 브로커(예: Redis)가 변경 이벤트를 발행(Publish)하고, 이를 구독(Subscribe) 중인 서버들이 자신의 로컬 캐시를 무효화(Evict)하거나 갱신합니다.

    - 활용: Redis와 클라이언트 캐시 간 데이터 동기화 기술을 참고하여 분산 시스템에서 캐시를 효과적으로 관리할 수 있습니다. [1, 2, 3, 4]

### 2. 데이터베이스 트리거 및 종속성

    - 원리: 데이터베이스 자체의 변경(Insert, Update, Delete) 이벤트를 감지하여 캐시를 무효화하거나 업데이트합니다. [1]

### 3. 캐싱 전략 패턴

    - Write-Through: 데이터를 캐시와 원본 저장소(DB)에 동시에 기록하여 항상 일치 상태를 유지합니다.

    - Write-Back: 모든 데이터를 캐시에 먼저 저장하고 일정 주기마다 원본 저장소에 반영합니다. [1, 2]

## ⚠️ 동기화 시 고려할 점

    - 네트워크 오버헤드: 동기화를 위해 메시지를 주고받는 과정이 잦아지면 시스템 성능(Latency)이 저하될 수 있습니다. [1, 2]

    - 동시성 문제(Race Condition): 여러 서버에서 동시에 캐시를 갱신하려고 할 때 데이터 충돌이 발생할 수 있습니다. [1]

    - 관련 자료: 캐시 동기화 구현 시 Redis 캐시 동기화 문제와 해결 전략을 통해 Race Condition 등의 이슈를 예방할 수 있습니다. [1]
