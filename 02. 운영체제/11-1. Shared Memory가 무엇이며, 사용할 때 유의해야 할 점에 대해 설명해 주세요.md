# **11-1.** Shared Memory가 무엇이며, 사용할 때 유의해야 할 점에 대해 설명해 주세요.

```plain text
IPC, Inter-Process Communication
= 서로 다른 프로세스끼리 데이터를 주고받거나 상태를 공유하는 방법

대표 방식
1. Pipe
2. Named Pipe
3. Message Queue
4. Shared Memory
5. Socket
6. Signal
7. Semaphore
```

여기서 네 발표 주제는 크게 보면 이거야.

```plain text
Shared Memory → 가장 빠르지만 가장 위험할 수 있는 IPC

Message Queue → 느릴 수 있지만 구조가 명확한 IPC

```

# 11-1. Shared Memory가 무엇이며, 사용할 때 유의해야 할 점

## 1. Shared Memory란?

**Shared Memory, 공유 메모리**는 말 그대로 **두 개 이상의 프로세스가 같은 메모리 영역을 함께 사용하는 IPC 방식**이야.

일반적으로 프로세스는 서로 메모리 공간이 분리되어 있어.

```plain text
프로세스 A 메모리
[ code | data | heap | stack ]

프로세스 B 메모리
[ code | data | heap | stack ]
```

프로세스 A가 가진 변수는 프로세스 B가 직접 볼 수 없어.
왜냐하면 운영체제가 프로세스마다 독립된 주소 공간을 제공하기 때문이야.

그런데 Shared Memory를 사용하면 운영체제가 특정 메모리 영역을 만들고, 여러 프로세스가 그 영역을 자기 주소 공간에 연결해서 사용할 수 있게 해줘.

```plain text
프로세스 A 주소 공간          실제 물리 메모리          프로세스 B 주소 공간

[ 일반 메모리 ]              [ Shared Memory ]          [ 일반 메모리 ]
[ 공유 메모리 매핑 ]  ---->   [   같은 영역   ]   <----  [ 공유 메모리 매핑 ]
```

즉, 프로세스 A가 공유 메모리에 값을 쓰면, 프로세스 B도 같은 메모리 영역을 보고 있기 때문에 그 값을 읽을 수 있어.

---

## 2. Shared Memory가 빠른 이유

Shared Memory는 IPC 방식 중에서도 **가장 빠른 편**이야.

왜냐하면 데이터 전달 과정에서 커널을 계속 거쳐서 복사하지 않아도 되기 때문이야.

예를 들어 Message Queue나 Pipe는 보통 이런 흐름이야.

```plain text
프로세스 A
  ↓ 데이터 복사
커널 공간
  ↓ 데이터 복사
프로세스 B
```

즉, 데이터를 한 번 보내기 위해 커널 영역을 거치고 복사 비용이 발생해.

반면 Shared Memory는 처음에 공유 메모리 영역을 만들고 연결하는 과정에서는 커널의 도움이 필요하지만, 연결된 뒤에는 보통 이런 식이야.

```plain text
프로세스 A  →  공유 메모리에 직접 쓰기
프로세스 B  →  공유 메모리에서 직접 읽기
```

그래서 대용량 데이터를 자주 주고받아야 할 때 유리해.

예를 들어:

```plain text
- 영상 처리
- 게임 서버 내부 상태 공유
- DB나 캐시 시스템
- 실시간 데이터 처리
- 고성능 서버 프로그램
```

같은 곳에서 고려될 수 있어.

---

## 3. 하지만 Shared Memory는 위험하다

Shared Memory의 핵심 문제는 이거야.

> 메모리는 공유되지만, 접근 순서는 자동으로 관리되지 않는다.

즉, 운영체제가 “누가 먼저 읽고, 누가 먼저 쓰고, 동시에 접근하면 어떻게 할지”를 알아서 다 해결해주지 않아.

예를 들어 공유 메모리에 이런 값이 있다고 해보자.

```plain text
sharedCounter = 10
```

프로세스 A와 프로세스 B가 동시에 이 값을 1 증가시키려고 해.

겉보기에는 이렇게 기대할 수 있어.

```plain text
A가 +1
B가 +1

결과: 12
```

그런데 실제로는 이렇게 될 수 있어.

```plain text
초기값: 10

프로세스 A: sharedCounter 읽음 → 10
프로세스 B: sharedCounter 읽음 → 10

프로세스 A: 10 + 1 계산 → 11
프로세스 B: 10 + 1 계산 → 11

프로세스 A: sharedCounter에 11 저장
프로세스 B: sharedCounter에 11 저장

최종 결과: 11
```

분명 두 번 증가시켰는데 결과는 12가 아니라 11이 됐어.

이런 문제가 바로 **Race Condition, 경쟁 상태**야.

---

# Shared Memory 사용 시 유의할 점

## 1. 동기화가 반드시 필요하다

Shared Memory 자체는 그냥 “공유 공간”만 제공해.
그래서 여러 프로세스가 동시에 접근할 때는 별도의 동기화 장치가 필요해.

대표적으로는:

```plain text
- Mutex
- Semaphore
- Spin Lock
- Read-Write Lock
- File Lock
- Condition Variable
```

같은 걸 사용할 수 있어.

공유 메모리를 사용할 때는 보통 이렇게 생각해야 해.

```plain text
Shared Memory
= 데이터를 공유하는 공간

Semaphore / Mutex
= 그 공간에 들어가는 순서를 통제하는 장치
```

비유하면 Shared Memory는 **공용 화이트보드**고, Semaphore나 Mutex는 **화이트보드 앞에 한 명씩 서게 만드는 줄 관리 규칙**이야.

---

## 2. 읽기와 쓰기의 순서를 조심해야 한다

공유 메모리에서는 누군가 데이터를 쓰는 중에 다른 프로세스가 읽어버릴 수 있어.

예를 들어 공유 메모리에 사용자 정보를 저장한다고 해보자.

```plain text
name = "Kim"
age = 25
status = "READY"
```

프로세스 A가 이 값을 수정하고 있어.

```plain text
name = "Park"
age = 26
status = "READY"
```

그런데 수정 도중 프로세스 B가 읽으면 이런 이상한 상태를 볼 수도 있어.

```plain text
name = "Park"
age = 25
status = "READY"
```

이건 이전 데이터와 새 데이터가 섞인 상태야.
이런 걸 막으려면 “쓰기 작업이 완전히 끝난 뒤에 읽게 하는 방식”이 필요해.

그래서 공유 메모리를 쓸 때는 보통 이런 흐름을 만든다.

```plain text
쓰기 프로세스:
1. lock 획득
2. 공유 메모리에 데이터 쓰기
3. 쓰기 완료 표시
4. lock 해제

읽기 프로세스:
1. lock 획득
2. 공유 메모리에서 데이터 읽기
3. lock 해제
```

---

## 3. Deadlock을 조심해야 한다

동기화를 위해 lock을 쓰다 보면 **Deadlock, 교착 상태**가 생길 수 있어.

예를 들어 프로세스 A와 B가 각각 다른 lock을 잡고 서로 기다리는 상황이야.

```plain text
프로세스 A:
lock1 획득
lock2 기다림

프로세스 B:
lock2 획득
lock1 기다림
```

결과적으로 둘 다 영원히 기다려.

```plain text
A: 너 lock2 내놔
B: 너 lock1 내놔
A: 먼저 내놔
B: 네가 먼저 내놔
```

이게 Deadlock이야.

그래서 공유 메모리와 lock을 함께 사용할 때는:

```plain text
- lock 획득 순서를 정해두기
- lock을 오래 잡고 있지 않기
- 예외가 발생해도 반드시 lock 해제하기
- timeout을 둘 수 있으면 두기
```

이런 규칙이 필요해.

---

## 4. 공유 메모리 안에 포인터를 저장하면 위험할 수 있다

이건 발표에서 말하면 꽤 괜찮은 포인트야.

공유 메모리는 여러 프로세스가 같은 물리 메모리를 바라보지만, 각 프로세스의 **가상 주소 값은 다를 수 있어**.

예를 들어 프로세스 A에서는 공유 메모리가 이런 주소에 붙어 있을 수 있어.

```plain text
프로세스 A 기준 주소: 0x1000
```

그런데 프로세스 B에서는 같은 공유 메모리가 다른 주소에 붙을 수 있어.

```plain text
프로세스 B 기준 주소: 0x5000
```

그러면 프로세스 A가 공유 메모리 안에 포인터 값을 저장하면 문제가 생길 수 있어.

```plain text
공유 메모리 안에 저장된 포인터: 0x1234
```

이 주소가 프로세스 A에서는 의미가 있을 수 있지만, 프로세스 B에서도 같은 대상을 가리킨다는 보장은 없어.

그래서 공유 메모리에서는 일반 포인터보다 **offset, 즉 기준 위치로부터의 거리**를 저장하는 방식이 더 안전해.

```plain text
나쁜 방식:
pointer = 0x1234

더 안전한 방식:
offset = sharedMemoryStart + 128
```

이건 학생 입장에서는 어려울 수 있는데, 핵심만 말하면 돼.

> 공유 메모리에서는 “주소값”을 그대로 공유하면 위험하다. 프로세스마다 같은 주소값이 같은 의미를 갖는다고 보장할 수 없기 때문이다.

---

## 5. 데이터 구조를 단순하게 유지하는 것이 좋다

공유 메모리에는 복잡한 객체 구조를 그대로 넣기 어렵다.

예를 들어 Java 객체, C++ 객체, 포인터가 많은 연결 리스트 같은 구조는 공유 메모리에 그대로 넣기 까다로워.

왜냐하면 객체 내부에 참조, 포인터, 런타임 메타데이터 같은 게 들어갈 수 있기 때문이야.

공유 메모리에는 보통 이런 식의 단순한 데이터가 어울려.

```plain text
- 숫자
- 고정 길이 문자열
- 배열
- 구조체
- 상태 코드
- 플래그
```

예를 들면 이런 구조가 좋아.

```plain text
struct SharedData {
    int status;
    int count;
    char message[256];
};
```

반면 이런 건 조심해야 해.

```plain text
struct SharedData {
    char* message;
};
```

왜냐하면 `char*`는 실제 문자열이 아니라 문자열이 있는 주소를 저장하기 때문이야.

---

## 6. 메모리 크기와 생명주기 관리가 필요하다

공유 메모리는 생성하고, 연결하고, 사용하고, 해제하는 과정이 필요해.

대략 이런 흐름이야.

```plain text
1. 공유 메모리 생성
2. 프로세스들이 공유 메모리에 attach / map
3. 데이터 읽기/쓰기
4. 사용이 끝나면 detach / unmap
5. 공유 메모리 객체 제거
```

문제는 프로세스가 비정상 종료되면 공유 메모리나 세마포어 같은 리소스가 남아있을 수 있다는 거야.

그래서:

```plain text
- 누가 공유 메모리를 생성하는지
- 누가 삭제하는지
- 프로세스가 죽었을 때 어떻게 정리할지
- 이미 존재하는 공유 메모리를 재사용할지
```

이런 정책이 필요해.

---

## 7. 권한과 보안 문제도 있다

Shared Memory는 여러 프로세스가 접근할 수 있는 자원이야.
그래서 권한 설정을 잘못하면 의도하지 않은 프로세스가 접근할 수 있어.

주의할 점은:

```plain text
- 읽기 권한
- 쓰기 권한
- 생성 권한
- 접근 가능한 사용자/그룹
- 민감한 데이터 저장 여부
```

예를 들어 공유 메모리에 인증 토큰, 비밀번호, 개인정보 같은 걸 넣는 건 매우 조심해야 해.

---

## 8. 데이터가 언제 준비되었는지 알려주는 장치가 필요하다

공유 메모리는 그냥 메모리 공간이야.

프로세스 A가 데이터를 썼다고 해서 프로세스 B가 자동으로 “아, 데이터가 왔구나!” 하고 알 수 있는 건 아니야.

그래서 보통 이런 신호가 필요해.

```plain text
- Semaphore
- Condition Variable
- Event
- Signal
- 상태 플래그
```

예를 들어:

```plain text
status = EMPTY
status = WRITING
status = READY
```

이런 식으로 상태를 두고 관리할 수 있어.

```plain text
Writer:
1. status를 WRITING으로 변경
2. 데이터 작성
3. status를 READY로 변경

Reader:
1. status가 READY인지 확인
2. 데이터 읽기
3. status를 EMPTY로 변경
```

하지만 이 status 값 자체도 동시에 접근하면 문제가 생길 수 있으므로, 결국 동기화가 필요해.

---

## Shared Memory 한 줄 요약

> Shared Memory는 여러 프로세스가 같은 메모리 영역을 직접 공유하는 IPC 방식이다. 매우 빠르지만, 동기화가 자동으로 보장되지 않기 때문에 Race Condition, Deadlock, 데이터 불일치, 권한 문제 등을 반드시 주의해야 한다.
