# 7-7.유저 스레드와 커널 스레드의 스케줄링 알고리즘은 똑같을까

### 1. 커널 레벨 스레드의 개념 및 특징

커널 레벨 스레드는 운영체제 커널이 직접 관리하는 스레드로, 각 스레드의 상태 정보는 TCB라는 구조체에 저장

⇒ 커널이 직접 스케줄링을 담당

특징

- 스레드 생성 및 관리 : 응용 프로그램이 시스템 호출을 통해 커널 레벨 스레드 생성

- 스케줄링 : 멀티코어 환경에서 여러 스레드가 실제로 동시에 실행될 수 있고

- 블로킹 처리 : 한 스레드가 블로킹될 경우, 타 스레드는 영향 받지 X

장점

- 병렬성 지원 : 멀티코어 CPU에서 높은 병렬성 제공, 여러 CPU 코어에서 스레드들이 병렬로 실행될 수 O

- 블로킹 처리의 유연성 : 블로킹된 스레드만 중단, 타 스레드는 계속 실행됨

단점

- 성능 오버헤드 : 커널이 직접 스레드 관리

→ 항상 커널을 거쳐야 함

→ 컨텍스트 스위칭 or 스레드 생성/소멸 시 오버헤드 발생

- 이식성 문제 : 운영체제마다 스레드를 관리하는 방식이 달라 코드 이식성이 낮음

⇒ OS 커널 스케줄러가 관리하며, 보통 **우선순위 기반 + 선점형 스케줄링 (MLFQ 등)**

### 2. 사용자 레벨 스레드의 개념 및 특징

→ **우리가 흔히 프로그래밍 과정에서 스레드를 코드에 적는 것!!**

스레드 라이브러리나 런타임에서 관리되는 스레드로,

스레드 정보는 U-TCB(User-level Thread Control Block)라는 구조체에 저장되어 사용자 공간에서 관리됨

특징

- 스레드 생성 및 관리 : 스레드 라이브러리 함수 호출을 통해 스레드 생성, 해당 정보는 사용자 공간에 저장

- 스케줄링 : 스레드 라이브러리가 직접 스케줄링 담당, 커널 개입없이 사용자 모드에서 실행됨

- 블로킹 처리 : 한 스레드가 블로킹 되면 해당 프로세스의 모든 사용자 레벨 스레드가 중단될 수 O

장점

- 높은 이식성 : 운영체제에 관계없이 동일한 코드로 구현 가능해 이식성 높음

- 빠른 컨텍스트 스위칭 : 사용자 공간에서 스레드 전환이 일어남(→ 커널 레벨 스레드에 비해 매우 빠름)

- 낮은 커널 부담 : 스레드 라이브러리가 모든 스레드를 관리하므로 커널에 부담 X

단점

- 병렬성 제한 : 멀티코어 CPU에서 병렬처리 불가능, 스레드 간의 진정한 병렬성이 제공되지 X

  - **1:1 모델 (Java, pthread)** → 병렬성 가능

  - **N:1 모델 (옛날 유저 스레드)** → 병렬성 불가능

  - **M:N 모델 (Go 등)** → 병렬성 가능

⇒ 즉 유저 스레드 자체가 병렬성이 없는 게 아니라, 커널 스레드와 매핑 구조에 따라 달라진다.

(N:1 구조에서는 병렬성이 없고, 1:1이나 M:N 구조에서는 병렬 실행이 가능)

- 블로킹 문제 : 한 스레드가 블로킹될 경우, 프로세스 전체 스레드가 중단될 수 있음

⇒ 사용자 라이브러리가 관리 → 구현마다 다름 (**라운드 로빈, cooperative 등 자유롭게 구현 가능**)

**“즉, 커널은 OS 정책, 유저 스레드는 라이브러리 정책을 따른다”**

### 3. 스레드별 스케줄링 알고리즘

1) 커널 레벨 스레드 (OS)

대표 알고리즘:

- Multilevel Feedback Queue (MLFQ)

여러 개의 큐(우선순위별)를 이용,

  - CPU 많이 쓰는 스레드 : 낮은 순위로 강등

  - I/O 위주 스레드 : 높은 순위 유지

⇒ 목적 : 인터렉티브 프로그램 응답성 보장

- CFS (Linux Completely Fair Scheduler)

“모든 스레드가 공평하게 CPU를 쓰게 하자” 가상 실행 시간(Virtual Runtime) 기반

  - 실행 많이 한 스레드 : vruntime 증가

  - 가장 덜 실행된 스레드 선택

⇒ 핵심 : **공정성**

- Priority-based scheduling

우선순위 높은 스레드 먼저 실행, starvation 방지 위해 aging 적용

특징:

- 선점형 (preemptive) : 타이머 인터럽트로 강제 교체 → 특정 스레드가 CPU 독점 못함

- 타이머 인터럽트 기반 : 커널이 강제로 컨텍스트 스위칭

- 공정성 / 응답성 고려 :CPU 코어마다 run quene 존재, load balancing 수행

⇒ 커널 스케줄러는 공정성 + 응답성 + 시스템 전체 효율을 기준으로 동작함!

2) 유저 레벨 스레드 (라이브러리)

대표 알고리즘:

- Cooperative (yield 기반)

스레드가 스스로 CPU 양보, 강제 preemption 없음

→ 한 놈이 안 내놓으면 끝남(starvation)

- Round Robin

간단 큐 기반, 일정 시간씩 번갈아 실행

→ 구현 쉽고 공정하지만 비효율적일 수 있음

- Work stealing (Go, ForkJoin)

각 스레드가 자신의 작업 큐를 보유, 놀고 있는 스레드가 다른 큐에서 작업 훔침

ex) Go runtime, Java ForkJoinPool

→ 멀티코어에서 효율 매우 높음

- Event loop 기반 (Node.js 스타일)

하나의 스레드 + 비동기 처리, 콜백/Promise 기반(Node.js)

→ 스레드 수 최소화, I/O-heavy 작업에 최적

특징:

- 보통 **비선점형 (cooperative)** 많음

- 컨텍스트 스위칭 매우 빠름(레지스터 + 스택만 바꿈)

- 커널 개입 없음(syscall 없음 → 빠름)

⇒ 유저 스레드는 성능 최적화와 유연성 중심으로 설계됨

### 4. 최근 경향과 결론

1) N:1 (유저 스레드 N개 → 커널 1개)

- 빠름

- 병렬성 없음

- 하나 블로킹 → 전체 멈춤(커널은 스레드 1개짜리 프로세스로 인식)

2) 1:1 (요즘 표준, Java, Linux pthread)

“유저 스레드 = 커널 스레드라서 단순하지만 비용이 크다”

- 유저 스레드 1개 = 커널 스레드 1

- 병렬성 O

- 대신 오버헤드 큼

3) M:N (Go, 일부 런타임)

“유저 스케줄러가 스레드 관리, 커널은 N개만 관리”

- 유저 스레드 M개 ↔ 커널 스레드 N개

- 유연 + 병렬성 둘 다 확보

- 구현 복잡

### 5. TMI(Go 언어)

Go Lang

- Go 언어는 **경량 스레드(goroutine) + M:N 스케줄러**를 제공하는 언어

- 구글 infra strucure에서는 굉장히 많은 서버가 있었고, 원래 C++을 사용

→ 너무 불편하고 컴파일이 오래 걸려서 Go 언어를 만듦

- Go는 쓰레드에 최적화되어 있어서 goroutine을** 사용해서 내부에서 user-level thread를 지원**

---

### 6. 결론

실제로 CPU는 사용자 스레드를 직접 실행하지 않고, 항상 커널 스레드를 실행

즉, 커널이 먼저 스레드를 스케줄링하고, 그 위에서 사용자 스레드가 실행되는 구

커널 스레드 :

-  안정성과 병렬성에 강점

사용자 스레드 :

- 성능과 유연성에 강점

스케줄링 또한 커널은 OS 정책을, 사용자 스레드는 라이브러리 정책을 따른다 !
