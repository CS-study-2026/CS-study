# 20-1. volatile 키워드는 어떤 의미가 있나요?

## volatile이란?

`volatile`은 Java에서 **변수의 가시성(Visibility)을 보장하기 위한 키워드**이다.

멀티스레드 환경에서 일반 변수는 CPU 캐시나 레지스터에 저장되어 사용될 수 있기 때문에, 한 스레드가 값을 변경하더라도 다른 스레드가 변경된 값을 즉시 확인하지 못할 수 있다.

`volatile`로 선언된 변수는 한 스레드의 변경 사항이 다른 스레드에게 즉시 보이도록 보장한다.

```java
private volatile boolean running = true;
```

---

## 왜 필요한가?

멀티코어 환경에서는 각 스레드가 변수 값을 캐시에 저장하여 사용할 수 있다.

```plain text
Main Memory
     ↑
  CPU Cache (Thread1)

Main Memory
     ↑
  CPU Cache (Thread2)
```

예를 들어 Thread1이 값을 변경하더라도 Thread2는 자신의 캐시에 저장된 이전 값을 계속 사용할 수 있다.

이러한 문제를 **가시성(Visibility) 문제**라고 한다.

`volatile`은 이러한 캐시 불일치 문제를 해결하여 모든 스레드가 최신 값을 볼 수 있도록 한다.

---

## volatile이 보장하는 것

### 1. 가시성(Visibility)

한 스레드가 volatile 변수에 기록한 값은 다른 스레드가 즉시 확인할 수 있다.

```java
volatile boolean stop = false;
```

Thread A

```java
while(!stop) {
}
```

Thread B

```java
stop = true;
```

volatile이 없다면 Thread A는 계속 `false`를 읽을 수 있지만, volatile이 있으면 변경된 값을 즉시 확인한다.

---

### 2. Happens-Before 관계 보장

Java 5부터 도입된 규정으로 volatile 변수에 대한 쓰기(write)는 이후의 읽기(read)에 대해 Happens-Before 관계를 형성한다.

```java
data = "Hello";
ready = true;   // volatile
```

다른 스레드가

```java
if (ready) {
    System.out.println(data);
}
```

를 실행한다면, `ready == true`를 관측한 순간 `data = "Hello"`도 반드시 보이게 된다.

즉, volatile은 단순히 변수 하나만 보장하는 것이 아니라 이전 메모리 작업의 가시성도 함께 보장한다.

---

### 3. 명령어 재정렬(Reordering) 방지

JVM과 CPU는 성능 향상을 위해 명령어 순서를 변경할 수 있다.

```java
a = 1;
flag = true;
```

하지만 `flag`가 volatile이라면 관련 명령어의 재정렬이 제한된다.

volatile 변수에 대한 읽기/쓰기를 기준으로 Memory Barrier가 삽입되어 특정 재정렬이 금지된다.

이를 통해 멀티스레드 환경에서 예기치 않은 동작을 방지한다.

## 명령어 재정렬(Instruction Reordering)이란?

CPU와 컴파일러는 **성능 향상**을 위해 명령어 순서를 바꿔 실행할 수 있다.

예를 들어 코드가

```java
a = 1;
b = 2;
```

라고 작성되어 있어도

CPU 입장에서는

```java
b = 2;
a = 1;
```

로 실행해도 결과가 같다면 순서를 바꿀 수 있다.

---

## 왜 바꿀까?

CPU는 최대한 쉬지 않고 일하려고 함.

예를 들어

```plain text
1. 메모리 읽기 (100ns)
2. 계산 (1ns)
```

이면 메모리 읽는 동안 CPU가 놀게 됨.

그래서 CPU는

```plain text
다른 명령어 먼저 실행
↓
메모리 응답 오면 나중에 처리
```

를 함.

이걸 Out-of-Order Execution이라고 함.

---

## 싱글 스레드에서는 문제 없음

```java
a = 1;
b = 2;
```

를

```java
b = 2;
a = 1;
```

로 실행해도

최종 결과는

```plain text
a = 1
b = 2
```

라서 상관없음.

---

## 멀티스레드에서는 문제 발생

예를 들어

### Thread1

```java
data = 100;
ready = true;
```

### Thread2

```java
if (ready) {
    System.out.println(data);
}
```

우리는

```plain text
ready == true
↓
그러면 data는 100이겠지
```

라고 생각함.

---

하지만 CPU가 재정렬하면

실제로는

```java
ready = true;
data = 100;
```

순서로 실행될 수 있음.

---

그러면

### Thread1

```plain text
ready = true
```

먼저 수행

---

### Thread2

```java
if (ready)
```

↓

```plain text
true 발견
```

↓

```java
System.out.println(data);
```

↓

```plain text
0 출력
```

(아직 data=100 안 됨)

---

즉

```plain text
ready=true
인데
data=0
```

라는 이상한 상황이 발생함.

---

## 그래서 Memory Barrier 사용

```java
data = 100;
ready = true; // volatile
```

volatile 변수 앞뒤에는 Memory Barrier가 삽입됨.

개념적으로

```plain text
data = 100
↓
Memory Barrier
↓
ready = true
```

가 됨.

---

Barrier는

```plain text
앞의 명령 다 끝내고
뒤의 명령 실행해라
```

라는 의미.

따라서

```plain text
ready=true를 보면
반드시 data=100도 보인다
```

가 보장됨.

---

## 면접용 한 줄

> 명령어 재정렬은 CPU나 컴파일러가 성능 향상을 위해 명령어 실행 순서를 변경하는 최적화 기법입니다. 싱글 스레드에서는 문제가 없지만 멀티스레드 환경에서는 예상치 못한 결과를 초래할 수 있어, Memory Barrier나 volatile을 통해 재정렬을 제한합니다.

---

한마디로:

```plain text
캐시 문제
= 최신 값이 안 보임 (가시성 문제)

명령어 재정렬 문제
= 순서가 꼬임 (순서 보장 문제)
```

이 둘을 해결하려고 `volatile`과 `Memory Barrier`가 존재한다고 이해하면 됨.

## volatile이 보장하지 않는 것

### 원자성(Atomicity)

volatile은 가시성만 보장할 뿐 연산 자체를 원자적으로 수행하지는 않는다.

```java
volatile int count = 0;

count++;
```

`count++`는 실제로

```plain text
1. count 읽기
2. 값 증가
3. count 저장
```

의 세 단계로 수행된다.

두 스레드가 동시에 실행하면 Race Condition이 발생할 수 있다.

따라서 여러 스레드가 동시에 값을 수정하는 경우에는

- synchronized

- Lock

- AtomicInteger

등을 사용해야 한다.

---

## 언제 사용하는가?

volatile은 다음과 같은 경우에 적합하다.

- 하나의 스레드가 값을 변경하고 여러 스레드가 읽는 경우

- 상태 플래그(flag)

- 종료 신호(stop flag)

- 설정값(Configuration) 공유

**적합한 케이스**: **"1명의 작업자(Write)와 N명의 관찰자(Read)"** 구조일 때 가장 효율적

---

## 한 줄 정리

> volatile은 멀티스레드 환경에서 변수의 가시성을 보장하고 명령어 재정렬을 방지하지만, 원자성은 보장하지 않는 Java 키워드이다.

- Main Memory 접근은 CPU Cache 접근보다 비용이 훨씬 큽니다. 따라서 **꼭 필요한 가시성 보장 상황에서만 제한적으로 사용**해야 성능 저하를 막을 수 있습니다

## 나올수있는Q&A

### Q1. `volatile`과 `synchronized`의 가장 결정적인 차이는 무엇인가요?

  - **A.** **`volatile`****은 '가시성'만 보장**하고, **`synchronized`****는 '가시성'과 '원자성(상호 배제)'을 모두 보장**합니다. `volatile`은 락(Lock)을 걸지 않기 때문에 성능 소모가 덜하지만 동시 Write를 막지 못하고, `synchronized`는 락을 걸어 안전하지만 그만큼 비용이 큽니다.

### Q2. `volatile` 변수를 사용할 때 Java 컴파일러의 'Instruction Reordering(명령어 재정렬)'은 어떻게 되나요?

  - **A.** Java는 성능 최적화를 위해 컴파일러나 CPU가 명령어 순서를 바꿀 수 있습니다. 하지만 `volatile` 변수를 사용하면 **Happens-Before 관계**가 성립되어, `volatile` 변수 기점으로 앞뒤 명령어의 재정렬이 금지됩니다(Memory Barrier 작동).

### Q3. 여러 스레드가 Write하는 상황에서 `synchronized` 말고 다른 대안은 없나요?

  - **A.** `java.util.concurrent.atomic` 패키지의 **`AtomicInteger`**, `AtomicBoolean` 등을 사용할 수 있습니다. 이는 락(Lock)을 걸지 않고 CPU 수준의 **CAS(Compare-And-Swap) 알고리즘**을 사용하기 때문에, `synchronized`보다 성능상 우위에 있으면서도 원자성을 보장합니다.

### Q4. 실무나 오픈소스에서 `volatile`이 실제로 활용되는 대표적인 예시가 있나요?

  - **A.** 멀티스레드 환경에서 안전한 싱글톤(Singleton) 패턴을 구현할 때 사용하는 **DCL(Double-Checked Locking)** 구조에서 인스턴스 변수에 `volatile`을 사용합니다. 인스턴스가 완전히 생성되기 전에 다른 스레드가 참조하는 메모리 가시성 오류를 막기 위함입니다.

| 언어 | volatile 의미 |
| --- | --- |
| Java | 가시성 보장 + 재정렬 방지 |
| C | 컴파일러 최적화 방지 |
| C++ | C와 동일, 동기화는 atomic 사용 |
| C# | Java와 유사 |
| Go | volatile 없음 |
| Rust | volatile 없음 |
