# 10-0. 프로그램이 컴파일 되어, 실행되는 과정을 간략하게 설명해 주세요.

# 1. 컴파일(Compile)

1. 컴파일이란?

  - C, Java 등 인간이 이해하기 쉬운 고급 프로그래밍 언어로 작성된 소스 코드를 컴퓨터의 CPU가 직접 이해할 수 있는 0과 1로 된 기계어(저급 언어)로 한꺼번에 변환하는 과정.

  - 즉, 소스 코드가 실행 가능한 바이너리 파일로 변환되는 과정.

  - 이 작업을 수행하는 소프트웨어는 컴파일러라고 함.

1. 컴파일의 종류

  - AOT(Ahead-of-Time)

  - 인터프리터(Interpreter)

  - JIT(Just-In-Time)

---

# 2. AOT(Ahead-of-Time)

1. **방식:** 프로그램을 실행하기 전(Ahead-of-Time)에 소스 코드를 타겟 시스템의 기계어로 미리 다 번역해 놓습니다.

1. **시점:** 빌드 타임(컴파일 단계)에 모든 작업이 완료됩니다.

1. **특징:** 실행 시점에 이미 기계어로 되어 있어 실행 속도가 가장 빠릅니다. 하지만 하드웨어에 종속적이라 CPU나 OS가 바뀌면 새로 컴파일해야 합니다.

1. **대표 언어:** C, C++, Rust, Go.

1. **진행 방식 : **주로 C, C++, Rust 등에서 사용하며, 실행 전 모든 단계를 완료합니다.

  - **전처리(Pre-processing):** 소스 코드의 매크로와 헤더를 병합하여 `.i` 파일을 생성합니다.

  - **컴파일(Compilation):** 소스 코드를 최적화하여 CPU가 이해할 수 있는 어셈블리어(`.s`)로 변환합니다. 이 단계에서 문법 검사를 철저히 합니다.

  - **어셈블(Assembly):** 어셈블러를 통해 어셈블리어를 기계어 형태인 오브젝트 파일(`.o`)로 바꿉니다.

  - **링킹(Linking):** 여러 오브젝트와 라이브러리를 하나로 묶어 최종 실행 파일(.exe, .out)을 생성합니다.

> **면접 포인트:** 실행 시점에는 이미 모든 번역이 끝난 상태라 로더(Loader)가 메모리에 올리기만 하면 즉시 실행됩니다.

---

# 3. 인터프리터(Interpreter)

1. **방식:** 코드를 한 줄씩 읽어서 즉시 실행합니다.

1. **시점:** 런타임(프로그램 실행 중)에 실시간으로 번역합니다.

1. **특징:** 별도의 빌드 과정이 없어 가볍지만, 매번 실행할 때마다 번역을 반복하므로 속도가 느립니다.

1. **대표 언어:** 초기 Python, JavaScript, Ruby 등.

1. **진행 방식 : **별도의 명시적인 빌드 단계가 없거나 매우 간소화되어 있습니다.

  - **전처리:** 실행 직전 최소한의 환경 설정이나 모듈 로딩을 수행합니다.

  - **컴파일 & 어셈블:** 이 단계들이 독립적인 파일 생성 없이 메모리 상에서 실시간으로 일어납니다. 소스 코드를 한 줄씩 읽으면서 즉시 기계어 명령으로 해석하여 실행합니다.

  - **링킹:** 실행 중에 필요한 라이브러리나 모듈을 동적으로 연결합니다.

> **면접 포인트:** 별도의 실행 파일을 생성하지 않고 소스 코드를 직접 실행하며, 컴파일러의 최적화 단계를 생략하는 경우가 많아 실행 속도는 상대적으로 느립니다.

---

# 4. JIT(Just-In-Time)

1. **방식:** 인터프리터 방식의 '느린 속도'와 AOT의 '미리 번역'하는 장점을 합친 하이브리드 방식입니다.

1. **시점:** 런타임(실행 중)에 바이트코드를 기계어로 번역합니다.

1. **특징:** 처음에는 인터프리터처럼 한 줄씩 실행하다가, 반복되는 코드(Hot Spot)를 발견하면 이를 기계어로 번역해서 캐싱해 둡니다. 다음에 같은 코드가 나오면 번역 없이 캐싱된 기계어를 바로 써서 속도를 높입니다.

1. **대표 언어:** Java(JVM), C#(.NET), 최신 JavaScript 엔진(V8).

1. **진행 방식 : **Java는 컴파일과 실행 시점이 나뉘어 진행됩니다.

  - **빌드 타임 (AOT와 유사한 컴파일)**

    - **전처리 ~ 컴파일:** 자바 컴파일러(`javac`)가 소스 코드를 바이트코드(`.class`)로 변환합니다. (완전한 기계어가 아닌 중간 단계입니다.)

  - **런타임 (JVM 실행 중)**

    - **링킹 & 로딩:** JVM 내부에서 클래스들을 로드하고 연결합니다.

    - **JIT 컴파일:** 실행 중 빈번하게 호출되는 바이트코드를 실시간으로 **어셈블 및 기계어 변환** 과정을 거쳐 기계어로 바꾼 뒤 캐싱합니다.

> **면접 포인트:** 모든 코드를 미리 기계어로 만드는 것이 아니라, 실행 중에 필요한 부분만 즉석(Just-In-Time)에서 기계어로 바꾼다는 점이 핵심입니다.

---

# 5. 그럼 왜 속도가 빠른 AOT를 사용하지 않는걸까? 

1. 속도 vs 유연성 & 생산성

  - 속도가 느림에도 불구하고 인터프리터나 JIT 방식을 사용하는 이유는 **유연성(Flexibility)과 생산성(Productivity)** 때문입니다. 모든 상황에서 속도가 최우선은 아니기 때문이죠.

1. 속도와 맞바꾼 플랫폼 독립성

  - AOT의 가장 큰 단점은 특정 CPU와 OS에 맞춰 기계어를 미리 만들어버린다는 것입니다.

  - **AOT (C/C++):** 윈도우용으로 빌드한 실행 파일은 맥이나 리눅스에서 절대 안 돌아갑니다. 각 환경마다 새로 빌드(컴파일)해야 하죠.

  - **인터프리터/JIT (Java, Python):** 소스 코드나 바이트코드만 던져주면, 그 환경에 설치된 인터프리터(또는 VM)가 알아서 그 OS에 맞는 기계어로 바꿔줍니다. 개발자는 **한 번만 짜면 어디서든 돌아가는(Cross-platform)** 프로그램을 만들 수 있습니다.

1. 개발 및 수정 속도 (생산성)

  - 개발 과정에서는 코드를 고치고 결과를 확인하는 과정이 수만 번 반복됩니다.

  - **AOT:** 단 한 줄만 고쳐도 다시 [전처리-컴파일-어셈블-링킹] 과정을 거쳐 실행 파일을 새로 만들어야 합니다. 프로젝트가 커지면 이 빌드 시간만 몇 분, 몇 시간이 걸리기도 합니다.

  - **인터프리터:** 빌드 과정이 없으므로 고치자마자 바로 실행해서 결과를 볼 수 있습니다. "수정 -> 확인" 사이클이 압도적으로 빠릅니다.

1. 동적 타이핑 및 유연성

  - 인터프리터 언어들은 프로그램이 실행되는 도중에 변수의 타입을 바꾸거나, 새로운 코드를 불러와 실행하는 등의 **동적인 작업**이 훨씬 쉽습니다. AOT는 실행 전에 모든 것을 확정 지어야 하므로 이런 유연한 구조를 구현하기가 매우 까다롭고 복잡해집니다.

1. 상황별 컴파일러 선정

  - **AOT를 쓰는 경우:**

    - 하드웨어 자원이 극히 제한적인 경우 (임베디드) → OS 변경 X

    - 초 단위의 실행 속도가 생명인 경우 (게임 엔진, 운영체제 커널, 고성능 서버) → 속도

  - **인터프리터/JIT를 쓰는 경우:**

    - 빠른 배포와 잦은 수정이 필요한 경우 (웹 서비스 백엔드) → 유연성

    - 다양한 OS 환경을 지원해야 하는 경우 (일반 업무용 소프트웨어) → OS 변경 O

    - 데이터 분석이나 AI 모델링처럼 코드를 실행하며 바로바로 결과를 확인해야 하는 경우 (Python) → 생산성

# 6. 프로그램의 실행 (Runtime Process)

1. 실행 파일이 메모리에 로드되어 CPU에 의해 처리되는 과정입니다.

  1. 로더(Loader)의 동작: 사용자가 실행 파일을 실행하면 로더가 하드디스크에 있는 프로그램을 읽어 메인 메모리(RAM)에 할당합니다.

  1. 프로세스 생성: 운영체제는 프로그램을 실행하기 위해 프로세스를 생성하고, 코드(Code), 데이터(Data), 힙(Heap), 스택(Stack) 영역으로 메모리를 구획합니다.

  1. CPU의 명령 처리: CPU 내의 제어 장치가 메모리에 있는 명령어를 하나씩 가져와(Fetch) 해석하고(Decode) 실행(Execute)합니다.

# 7. 면접 대비

### SW 면접 대비 핵심 포인트

- 정적 링킹(Static Linking) vs 동적 링킹(Dynamic Linking):

  - 정적 링킹은 실행 파일 내에 라이브러리 코드를 모두 포함하는 방식입니다. 속도는 빠르지만 파일 크기가 커집니다.

  - 동적 링킹(DLL, Shared Library)은 실행 시점에 라이브러리를 참조하는 방식입니다. 메모리 효율이 좋지만 실행 시 라이브러리가 존재해야 합니다.

### 1. AOT 방식 (주로 정적 링킹 선호)

AOT(C, C++, Rust 등)는 실행 속도를 극대화하기 위해 실행 전에 모든 준비를 마치는 것을 좋아합니다.

    - **정적 링킹 (Static Linking):** 컴파일 타임에 라이브러리 코드를 실행 파일(` .exe`) 안에 통째로 집어넣습니다. 실행 시점에 주소를 찾을 필요가 없어 속도가 가장 빠릅니다.

    - **동적 링킹 (Dynamic Linking):** 윈도우의 `.dll`이나 리눅스의 `.so` 파일을 사용하는 방식입니다. 실행 파일 크기를 줄이기 위해 사용하며, 로더가 프로그램을 메모리에 올릴 때 라이브러리 주소를 연결합니다.

### 2. 인터프리터 방식 (완전한 동적 링킹)

파이썬(Python)이나 자바스크립트 같은 인터프리터 언어는 미리 연결해둘 '파일' 자체가 모호하기 때문에 동적 링킹만 존재한다고 봐도 무방합니다.

    - **동적 링킹 (Dynamic Linking):** 코드를 한 줄씩 읽다가 `import`나 `require` 문을 만나는 순간, 해당 모듈이 어디 있는지 찾아서 연결합니다. 런타임에 모든 링킹이 결정됩니다.

### 3. JIT 방식 (무조건 동적 링킹 중심)

자바(Java) 같은 JIT 방식은 구조적으로 **동적 링킹**이 핵심입니다.

    - **동적 링킹 (Dynamic Linking):** 자바는 빌드 타임에 링킹을 하지 않습니다. 실행 중(런타임)에 클래스 로더가 `.class` 파일을 메모리에 올릴 때마다 실시간으로 주소를 매핑합니다.

    - **정적 링킹 (Static Linking):** 자바 세계에서는 거의 쓰이지 않습니다. 굳이 찾자면 최근 `GraalVM` 같은 기술을 이용해 자바 코드를 AOT 방식으로 컴파일하여 하나의 실행 파일로 만들 때만 정적 링킹과 유사한 방식을 사용합니다.
  </details>

- 컴파일 언어 vs 인터프리터 언어:

  - C/Java(JIT)처럼 미리 변환해두는 언어와, Python처럼 한 줄씩 해석하며 실행하는 언어의 속도 및 배포 차이를 이해해야 합니다.

- 자바(Java)의 특수성:

  - 자바는 소스 코드를 바로 기계어로 바꾸지 않고 바이트코드(.class)로 컴파일한 뒤, JVM(자바 가상 머신) 위에서 인터프리터와 JIT 컴파일러를 통해 실행됩니다. 이는 운영체제 독립성(Write Once, Run Anywhere)을 확보하기 위함입니다.

- 메모리 구조 (Heap vs Stack):

  - 스택은 컴파일 타임에 크기가 결정되는 지역 변수 등이 저장되고, 힙은 런타임에 동적으로 할당되는 데이터가 저장된다는 차이점을 명확히 설명하는 것이 중요합니다.
