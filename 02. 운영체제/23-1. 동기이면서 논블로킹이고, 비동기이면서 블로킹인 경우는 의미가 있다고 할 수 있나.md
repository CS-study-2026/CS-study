# 23-1. 동기이면서 논블로킹이고, 비동기이면서 블로킹인 경우는 의미가 있다고 할 수 있나요?

## 1. 동기이면서 논블로킹인 경우

의미가 있다.

동기 + 논블로킹은 호출한 스레드가 멈추지는 않지만, 작업 완료 여부는 호출한 쪽이 직접 확인하는 방식이다.

예를 들어 논블로킹 I/O에서 `read()`를 호출했는데 데이터가 없으면 바로 반환된다.

호출한 쪽은 나중에 다시 확인한다.

```plain text
read()
→ 아직 데이터 없음
→ 바로 반환

나중에 다시 read()
→ 데이터 있음
→ 처리
```

이 방식은 스레드를 블로킹하지 않는다는 장점이 있다.

하지만 완료 여부를 계속 확인해야 하므로 잘못 구현하면 busy waiting으로 CPU를 낭비할 수 있다.

따라서 동기 + 논블로킹은 의미는 있지만, 단독으로 사용하면 비효율적일 수 있다.

실제로는 이벤트 통지나 I/O 멀티플렉싱과 함께 사용되는 경우가 많다.

---

## 2. 비동기이면서 블로킹인 경우

비동기 + 블로킹도 가능한 조합이다.

다만 일반적으로는 비동기의 장점이 줄어들기 때문에 좋은 설계라고 보기는 어렵다.

대표적인 예시는 비동기 작업을 시작한 뒤 바로 결과를 기다리는 경우다.

```java
Future<String> future = asyncCall();
String result = future.get();
```

이 경우 작업 시작은 비동기적으로 했지만, 현재 스레드는 `get()`에서 결과가 올 때까지 막힌다.

그래서 실제 효과는 동기 + 블로킹과 비슷해질 수 있다.

하지만 여러 작업을 동시에 시작해놓고, 나중에 결과가 필요한 시점에만 기다리는 구조라면 의미가 있다.

```plain text
비동기 작업 A 시작
비동기 작업 B 시작
비동기 작업 C 시작

다른 작업 수행

마지막에 A, B, C 결과 수집
```

이 경우에는 작업들이 병렬로 진행될 수 있으므로 비동기를 사용하는 의미가 있다.

즉, 비동기 + 블로킹은 “언제 블로킹하느냐”가 중요하다.

비동기 호출 직후 바로 기다리면 장점이 거의 없고, 여러 작업을 먼저 진행시킨 뒤 필요한 시점에만 기다린다면 의미가 있다.

# 9. I/O 멀티플렉싱 파트와의 경계

이 발표에서는 다음 정도까지만 다루면 충분하다.

```plain text
논블로킹 I/O는 호출이 바로 반환된다.
하지만 결과가 준비되었는지는 별도로 확인해야 한다.
무작정 반복 확인하면 busy waiting 문제가 생긴다.
이 문제를 효율적으로 다루는 방식 중 하나가 I/O 멀티플렉싱이다.
```

`select`, `poll`, `epoll`, `kqueue` 같은 구체적인 방식은 I/O 멀티플렉싱 발표에서 다루는 것이 자연스럽다.

따라서 여기서는 I/O 멀티플렉싱을 깊게 설명하지 않고, 다음 발표로 연결만 하면 된다.

# 10. 최종 요약

동기/비동기와 블로킹/논블로킹은 서로 다른 기준의 개념이다.

```plain text
동기/비동기
= 작업 완료와 결과 처리를 누가 주도하는가

블로킹/논블로킹
= 호출한 스레드가 기다리는가, 바로 반환되는가
```

동기 + 블로킹은 가장 일반적인 방식으로, 작업이 끝날 때까지 기다린 뒤 다음 작업을 진행한다.

동기 + 논블로킹은 호출은 바로 반환되지만, 호출한 쪽이 완료 여부를 직접 확인한다. 의미 있는 방식이지만 busy waiting 문제가 생길 수 있다.

비동기 + 논블로킹은 요청 후 바로 반환되고, 완료되면 콜백이나 이벤트로 결과를 받는다. 많은 I/O 요청을 효율적으로 처리할 수 있지만 코드 흐름이 복잡해질 수 있다.

비동기 + 블로킹은 비동기 작업을 시작했지만 특정 시점에서 결과를 기다리는 방식이다. 호출 직후 바로 기다리면 비동기의 장점이 줄어들지만, 여러 작업을 먼저 시작해두고 나중에 결과를 모으는 구조라면 의미가 있다.
