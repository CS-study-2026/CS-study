# 19-4. 코어가 여러개라면, TLB는 어떻게 동기화 할 수 있을까요?

# 19-4. 코어가 여러 개라면, TLB는 어떻게 동기화할 수 있을까요?

이게 제일 중요한 부분이야.

## 1. 멀티코어에서 왜 문제가 생기나?

각 코어가 자기 TLB를 따로 가지고 있다고 했지?

```plain text
Core 0 → TLB 0
Core 1 → TLB 1
Core 2 → TLB 2
Core 3 → TLB 3
```

문제는 **페이지 테이블은 공유될 수 있는데, TLB는 코어마다 따로 캐싱되어 있다는 것**이야.

예를 들어 어떤 프로세스가 Core 0과 Core 1에서 실행된 적이 있다고 하자.

그러면 두 코어의 TLB에 같은 프로세스의 주소 변환 정보가 남아 있을 수 있어.

```plain text
Core 0 TLB:
가상 페이지 A → 물리 프레임 10

Core 1 TLB:
가상 페이지 A → 물리 프레임 10
```

그런데 OS가 page table을 바꿔서 이 매핑을 변경했다고 하자.

```plain text
변경 전:
가상 페이지 A → 물리 프레임 10

변경 후:
가상 페이지 A → 물리 프레임 99
```

이때 Core 0은 page table을 변경했으니 새 정보를 알 수 있어.

하지만 Core 1의 TLB에는 아직 예전 정보가 남아 있을 수 있어.

```plain text
Core 1 TLB:
가상 페이지 A → 물리 프레임 10  // 오래된 정보
```

이 상태에서 Core 1이 이 TLB 정보를 그대로 사용하면 잘못된 물리 메모리에 접근할 수 있어.

---

## 2. TLB는 캐시처럼 자동으로 동기화되나요?

이 부분이 중요해.

**일반적인 데이터 캐시는 하드웨어 캐시 일관성 프로토콜로 동기화될 수 있어.**

예를 들어 MESI 같은 캐시 일관성 프로토콜이 있어.

하지만 **TLB는 일반 데이터 캐시와 다르게 자동으로 항상 동기화된다고 보면 안 돼.**

TLB는 주소 변환 정보를 담고 있고, page table이 변경되면 OS가 관련 TLB 엔트리를 명시적으로 무효화해야 해.

즉, 멀티코어 환경에서 TLB 동기화의 핵심은:

> page table이 바뀌었을 때, 다른 코어의 오래된 TLB 엔트리를 무효화하는 것

이야.

---

## 3. TLB Shootdown이란?

멀티코어에서 page table 변경 후 다른 코어들의 TLB를 무효화하는 과정을 **TLB Shootdown**이라고 해.

흐름은 대략 이렇다.

```plain text
1. Core 0에서 OS가 page table을 변경한다.
2. 이 변경으로 인해 다른 코어의 TLB 엔트리가 오래된 정보가 될 수 있다.
3. OS는 해당 주소 공간을 사용 중이거나 사용했던 다른 코어들에게 인터럽트를 보낸다.
4. 인터럽트를 받은 코어들은 자기 TLB에서 해당 엔트리를 무효화한다.
5. 각 코어가 무효화 완료를 알린다.
6. 이후 새 주소 변환이 필요하면 page table을 다시 보고 TLB를 갱신한다.
```

이때 다른 코어들에게 보내는 인터럽트를 보통 **IPI**라고 해.

```plain text
IPI = Inter-Processor Interrupt
```

즉, 코어끼리 보내는 인터럽트야.

---

## 4. 그림으로 보면

```plain text
Core 0
- page table 변경
- "이 주소 변환 정보 이제 무효야"라고 판단
- 다른 코어들에게 IPI 전송

        IPI
Core 0 ─────→ Core 1
Core 0 ─────→ Core 2
Core 0 ─────→ Core 3

Core 1, 2, 3
- 자기 TLB에서 해당 엔트리 invalidate
- 완료 응답
```

그다음 해당 주소에 다시 접근하면 TLB miss가 발생하고, page table을 다시 읽어서 새 매핑을 가져온다.

---

## 5. 언제 TLB Shootdown이 필요한가?

대표적으로 page table의 매핑이 바뀔 때 필요해.

예를 들면:

```plain text
1. 어떤 페이지를 unmap할 때
2. 어떤 페이지의 권한을 변경할 때
3. 가상 페이지가 가리키는 물리 프레임이 바뀔 때
4. Copy-on-Write 처리로 쓰기 권한이나 매핑이 바뀔 때
5. mmap/munmap 같은 메모리 매핑 변경이 발생할 때
```

예를 들어 어떤 페이지를 더 이상 접근하지 못하게 `unmap`했는데, 다른 코어 TLB에 예전 매핑이 남아 있으면 문제가 생겨.

```plain text
OS: 이 페이지는 이제 접근하면 안 됨
Core 1 TLB: 예전 매핑을 가지고 있음
Core 1: 예전 TLB를 믿고 접근
```

이러면 메모리 보호가 깨질 수 있어.

그래서 반드시 오래된 TLB 정보를 무효화해야 해.

---

## 6. 전체 TLB를 다 비우나요, 일부만 비우나요?

상황에 따라 달라.

## 일부 엔트리만 무효화

특정 페이지만 바뀌었다면, 해당 가상 주소에 대한 TLB 엔트리만 무효화할 수 있어.

```plain text
특정 가상 페이지 A만 invalidate
```

이 방식은 비용이 작아.

---

## 전체 TLB flush

주소 공간 전체가 바뀌거나, 세밀하게 무효화하기 어렵다면 전체 TLB를 비울 수도 있어.

```plain text
TLB 전체 flush
```

하지만 이건 비용이 커.

왜냐하면 이후 메모리 접근에서 TLB miss가 많이 발생하기 때문이야.

---

## 7. TLB Shootdown은 왜 비싼가?

TLB Shootdown은 꽤 무거운 작업이야.

이유는 다음과 같아.

```plain text
1. 다른 코어에 IPI를 보내야 함
2. 다른 코어가 하던 일을 잠깐 멈추고 커널 코드를 실행해야 함
3. TLB 엔트리를 무효화해야 함
4. 완료 응답을 기다려야 할 수 있음
5. 이후 TLB miss가 증가함
```

특히 코어 수가 많을수록 비용이 커질 수 있어.

```plain text
4코어 시스템
→ 몇 개 코어만 무효화하면 됨

64코어 시스템
→ 많은 코어에 IPI를 보내야 할 수 있음
→ 동기화 비용 증가
```

그래서 OS는 불필요한 TLB Shootdown을 줄이려고 해.

---

## 8. TLB Shootdown을 줄이는 방법

너무 깊게 들어갈 필요는 없지만, 심화 질문 대비로 알아두면 좋아.

## 1. 필요한 코어에만 shootdown

모든 코어에 보내는 게 아니라, 해당 주소 공간을 실제로 사용한 코어에게만 보낸다.

```plain text
이 프로세스를 실행한 적 없는 코어
→ 해당 프로세스의 TLB 엔트리가 없을 가능성이 큼
→ shootdown 불필요
```

---

## 2. 여러 변경을 모아서 한 번에 처리

page table 변경이 여러 번 발생할 때마다 shootdown하면 비용이 크다.

그래서 가능한 경우 변경을 모아서 한 번에 invalidate할 수 있다.

```plain text
페이지 A 변경 → 바로 shootdown
페이지 B 변경 → 바로 shootdown
페이지 C 변경 → 바로 shootdown

이렇게 하지 않고

페이지 A/B/C 변경
→ 한 번에 shootdown
```

---

## 3. ASID / PCID 사용

이건 19-5 Context Switching에서도 중요해.

TLB 엔트리에 “어느 프로세스의 주소 공간인지”를 나타내는 태그를 붙일 수 있어.

```plain text
ASID = Address Space Identifier
PCID = Process Context Identifier
```

이런 태그가 있으면 다른 프로세스의 TLB 엔트리와 구분할 수 있어서 전체 flush를 줄일 수 있어.

---

## 19-4 발표용 답변

> 멀티코어 환경에서는 각 코어가 독립적인 TLB를 가질 수 있습니다. 문제는 page table이 변경되었을 때, 다른 코어의 TLB에는 예전 주소 변환 정보가 남아 있을 수 있다는 점입니다. 이 상태에서 다른 코어가 오래된 TLB 엔트리를 사용하면 잘못된 물리 주소에 접근하거나 메모리 보호가 깨질 수 있습니다.

이를 해결하기 위해 OS는 TLB Shootdown을 수행합니다. 한 코어에서 page table을 변경하면, 해당 주소 공간을 사용 중인 다른 코어들에게 IPI, 즉 Inter-Processor Interrupt를 보내고, 각 코어는 자기 TLB에서 해당 주소의 엔트리를 무효화합니다. 이후 다시 해당 주소에 접근하면 TLB miss가 발생하고, page table을 기준으로 새로운 변환 정보를 가져오게 됩니다.

TLB Shootdown은 다른 코어를 멈추게 하고 인터럽트 처리와 TLB miss를 유발하므로 비용이 큽니다. 그래서 OS는 필요한 코어에만 shootdown을 보내거나, 여러 변경을 모아서 처리하거나, ASID/PCID 같은 태그를 활용해 불필요한 flush를 줄이려고 합니다.
